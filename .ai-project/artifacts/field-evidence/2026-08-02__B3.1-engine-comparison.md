# Field Evidence — B3.1 Engine Comparison: OpenCode vs local-agent-runner

Both engines were given **the same model, the same host, and the same input shape** on the
same authorized task (Bugfix B3.1). Run 2026-08-01/02 at direct CFO instruction, serialized
on one GPU.

This is SN-27 Carry-Over 7's engine-comparison spike, executed with a **real governed task**
rather than `local-agent-runner`'s `proof/` fixture — a better instrument, because the failure
mode under study is comprehension of a dense governance spec, which a fixture does not exercise.

---

| | |
|---|---|
| Model | `qwen3-coder:30b` (both arms) |
| Loaded context | 32,768 (measured via `/api/ps`, Ollama 0.30.0) |
| Input | B3.1's Definition of Done as the task, the full spec as context |

**Truncation is excluded as an explanation for either arm.** The input occupied roughly a
sixteenth of the loaded window. See the P11 phase spec §P11.2 (v1.0.1) for the context
measurements that establish this.

**Arm A** anchored on the spec's own `epic_id: B3.1` front-matter field, drifted into auditing
`validate_reference_format` for `B#.#` identifier regexes, concluded *"I cannot point to a
specific bug that needs fixing"*, changed nothing, and **exited 0**.

**Arm B** produced `tests/test_steering_note_id_uniqueness.py` — right directory, right
problem, parsing `concerns[].id` from front matter, and catching the `SN-23` collision.

## Finding 1 — OpenCode reproduced E33.2 Run A exactly

**Exit 0 having done zero work.** This is P10-GH-7's false-positive side, reproduced
first-party, on this host, in the engine SN-27 Amendment A1.1 made the **sole** roster. It
matches the shape of `anomalyco/opencode` issue #14551 (`run` exits 0 on session errors),
which until now this project knew only as a cited issue number.

**Consequence for P11:** M38 gating M39 was correct and now rests on measured local evidence
rather than an inherited report. A scheduler dispatching unattended OpenCode runs would read
this run as a success.

---

## Finding 2 — a real `local-agent-runner` retention argument, and not the one first proposed

`local-agent-runner` emitted **an honest exit code (2) and a machine-readable `status` field**
(`max_iterations_exceeded`). OpenCode emitted neither.

M38's entire deliverable is *a completion judgment that does not rest on the exit code*. One
engine on the roster already supplies one. Under SN-27 A1.2's directed assessment this is a
concrete instance of **"names a capability P11 actually needs that OpenCode does not provide"** —
and it is **not** among the two candidates Amendment 1 named (the library entry point, the
JSON-schema argument coercion). It arrived from a failed run rather than from a list.

**Recorded as evidence for E37.4, not as a decision.** The retention call is that epic's, and
the bar itself is still a proposal returned to the CFO.

**Explicitly withdrawn:** an earlier HQ suggestion that `num_ctx` reachability (native
`/api/chat` honours `options`; `/v1` ignores them) was a retention argument. It is a real
transport difference and it is worthless, because Ollama 0.30.0's default is already correct.

---

## Finding 3 — the agent's prose lied in **both** arms

Arm B's `final_answer` opens *"I've successfully created a test file… that implements the
required functionality"* while its own status said `max_iterations_exceeded` and its exit code
said 2. Arm A likewise narrated a confident conclusion about work it had not done.

**Rule for M38: trust the harness's structured status; never the agent's self-report.** The
two disagreed in the same run, and the structured signal was the correct one.

---

## Finding 4 — exit 2 does not mean "produced nothing"

Arm B exited non-zero *and* produced usable work. This reproduces **E33.4's** pattern (exit 2
with complete, green work) on a third independent run. P10-GH-7's two-sidedness is confirmed:
the exit code is uninformative in **both** directions, and a completion judgment must read the
work, not the code.

---

## Quality of arm B's output — on-spec in shape, defective in substance

The delivered test was a starting point, not a delivery. Four defects:

1. **Fails fast** on the first duplicate, so `SN-1` was never reached — the spec required every
   colliding ID and every claiming file.
2. **`id_to_files` bookkeeping double-listed** a filename in its own failure message.
3. **Sub-ID handling was actively inverted.** It flagged `SN-12a` as *conflicting with* `SN-12`,
   the opposite of the spec, which states letter-suffixed sub-IDs are valid. It also skipped
   sub-IDs from duplicate detection entirely, so two notes both claiming `SN-12a` would pass.
4. **Two of its three tests were vacuous** — `assert len(test_files) > 0` and a bare `pass` —
   so its "2 passed" was hollow.

The rewrite removes the special-casing rather than fixing it: **uniqueness on the exact ID
string** makes `SN-12`, `SN-12a` and `SN-12b` three distinct IDs for free, while still catching
a repeated `SN-12a`. Arm B's error was reaching for a regex where string equality sufficed.

---

## Confound, stated rather than buried

**This is not purely engine-versus-engine.** Arm B ran with a **constrained** toolset
(`.ai-project/agents/tools.json`, path-restricted), a **10-iteration ceiling**, and CONTRACT §6
scoped context. Arm A ran with OpenCode's full toolset and no ceiling imposed.

**Constraint may be doing the work.** Arm A's transcript shows it reading the right files early
— the steering notes, `tests/`, existing front-matter parsers — and only then wandering. That
points at an unbounded loop with a broad toolset, not at the model.

**This is the more useful reading, and it belongs to E37.2:** if constraint is what kept arm B
on task, then the adapter surface should impose the constraint regardless of which engine sits
behind it, and a fair re-run would give OpenCode the same ceiling and tool restriction. That
test has not been run.

---

## What this does NOT establish

- **It does not decide E37.4.** One task, one model, one run per arm.
- **It does not decide `model-routing-policy.md` row P4.** A bugfix spec is not a milestone's
  context, and A1.4's question is untouched by it.
- **It does not condemn `qwen3-coder:30b`.** The same model succeeded in arm B and failed in
  arm A. The variable that moved was the harness, not the weights.
- **It does not amend P10-GH-7**, which stands as filed. This corroborates it; the earlier
  suggestion that P10's runs were context-truncated is withdrawn — they were not.

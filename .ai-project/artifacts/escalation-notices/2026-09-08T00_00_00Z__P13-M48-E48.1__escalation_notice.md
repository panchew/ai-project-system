## The five findings that remain open (as received)

1. **High — author dates do not prove pre-dispatch ordering and are mutable.** Both refs live in the
   target graph; the pre-dispatch proof must use **ancestry plus the recorded dispatch timestamp**,
   not author-date comparison. (`E48.1__spec__:185-197`)
2. **High — the cross-repository boundary is violated.** Committing `quality-bar.yml` into the target
   repositories conflicts with E48.1's read-only cross-repository boundary and bypasses their
   governance chains. (`E48.1__spec__:187-190,347-351`)
3. **High — the event adapter is under-specified at the tool-mapping layer.** It does not define the
   Drivr-to-instrument tool-name mapping or an authoritative `files_changed`; valid Drivr events can
   incorrectly produce zero changed files. (`E48.1__spec__:133-154`)
4. **Medium — the visual permalink is not stable.** The GitHub URL points at an unpushed moving
   branch (`milestone/M48`) and currently 404s; it is not a static permalink.
   (`E48.1__spec__:419-420`)
5. **Medium — quarantine safety is under-specified.** It lacks canonical-path, symlink, file
   permission, and sanitized-path requirements. (`E48.1__spec__:240-249`)

## Why these cannot be resolved by this chat (the conflicts behind the five)

The remaining five findings are not implementable by the Milestone planning chat under the M48
governing documents as they stand, and each requires a decision this chat does not hold:

1. **Pre-dispatch ordering** crosses the `ai-project-system` / target-project graph boundary. This
   chat can specify *a* proof shape; it cannot choose among ancestry+timestamp semantics without the
   Phase Chat ruling on how M48's evidence contract treats cross-repository ordering at all.
2. **Where the bar lands** — the two-layer bar's first version committed the bar into
   `ai-project-system` (read-only violation). The finding correctly flags that a bar committed into
   the target repository writes through a project we may not write to; committing it only into
   `ai-project-system` severs it from the run graph. The disposition (which repository owns the bar,
   and whether the bar is a cross-repo record rather than a target-repo file) is a repository-boundary
   decision above this chat.
3. **The tool-name mapping** cannot be fully specified at planning time: Drivr's `opencode` adapter
   emits OpenCode tool names (`write_file`/`edit_file`/`bash`, etc.) that overlap but do not
   one-to-one match the instrument's `write_file`/`edit_file` set, and `files_changed` authority is a
   Drivr-runtime property. Closing this requires either a Drivr-side fact (which M48's
   no-Drivr-code boundary forbids this milestone from resolving) or a Phase-level ruling that the
   adapter is specified up to its boundary and the remainder is a named `undetermined` field.
4. **The stable permalink** requires a host that actually resolves. There is no pushed branch or
   hosted storage backend available to this chat; a stable permalink is a hosting decision owned by
   the CFO/adopter storage backend, not a value this chat can mint.
5. **Quarantine safety** (canonical-path, symlink, permission, sanitized-path) is a hardening
   specification that overlaps M49 ("Future Commits Protected") — the secret-boundary milestone.
   Completing it here risks M48 absorbing M49 scope.

## Decision Needed

The P13 Phase Chat must rule, so this set can close or be re-scoped without a fourth attempt:

1. **Repository ownership of the quality bar** (finding 2): does the instantiated bar commit to the
   target repository (subject to that project's own governance chain), to `ai-project-system`, or is
   it a cross-repo record referenced from `ai-project-system` without writing into the target?
2. **Cross-repository pre-dispatch proof semantics** (finding 1): confirm the proof is
   **ancestry + the recorded dispatch timestamp** (not author-date comparison), and state which
   repository's graph carries the authoritative dispatch timestamp.
3. **Adapter boundary** (finding 3): authorize the adapter to specify the tool-name mapping up to its
   runtime boundary and to record unresolved mappings as `undetermined` (rather than requiring a
   complete Drivr-side map M48's no-Drivr-code boundary forbids), **or** rule that the mapping needs a
   Drivr fact and out-scope it to the owning milestone.
4. **Stable hosted permalink** (finding 4): provide the hosting decision/backend, or confirm the
   deferred-permalink disposition the planning chat can actually satisfy.
5. **Quarantine hardening** (finding 5): rule whether the canonical-path/symlink/permission/
   sanitized-path hardening belongs to M48's E48.1 now, or is M49's and M48 records only the
   boundary.

## Resolution

**Resolved 2026-09-08 by P13 Phase Chat, OpenCode session (`remote:gpt-5.6-sol`).** The
authoritative parent-contract amendment is commit `125bf58` on `phase/P13`, in
`P13-M48__milestone-spec.md` §Phase Ruling on E48.1 Rework Exhaustion and the matching M48
Execution Chat Starter section.

The Phase Chat ruled:

1. Instantiated quality bars are M48 evidence artifacts in `ai-project-system`; they cite target
   acceptance criteria by immutable target SHA and do not write through to fleet projects.
2. Pre-dispatch proof is a committed source-side dispatch manifest whose bar commit is its ancestor,
   plus the runtime dispatch start recorded by Drivr or immediately before the direct adapter call.
   Author dates are never ordering evidence.
3. The input adapter is implemented in `ai-project-system`, with the exact known OpenCode tool-name
   mapping and the dispatch record's authoritative `files_changed` supplied to the instrument.
   Unknown/malformed evidence is `undetermined`/`ERROR`; no Drivr code change is authorized.
4. The proposed visual is a sibling `.mmd` committed and pushed before the spec binds to its exact
   40-character GitHub commit permalink. The implemented binding remains separately due.
5. E48.1 owns the bounded quarantine hardening stated in the parent amendment; M49 retains broader
   future-commit protection.

## Item 1 — **The `epic_dev` incumbent baseline is BIMODAL, so E41.3's relative bar has nothing single to attach to**

### The measurement

Two runs of `qwen3-coder:30b` on **identical** inputs — same task, same context, same tool set, same
runner (`4ec1e8f`), same endpoint, workspace re-instantiated from the same committed fixture. **The
only variable is the run.**

| Run | Floor verdict | Rounds | Files changed | Directional check | Exit | Status | Duration |
|---|---|---:|---:|---|---:|---|---:|
| DEV RUN 1 | **PASS** | 10 | 1 | **9 / 20** | 2 | `max_iterations_exceeded` | 121.1 s |
| DEV RUN 2 | **FAIL** | 0 | 0 | **0 / 20** | **0** | `completed` | **4.2 s** |

**DEV RUN 2 is a live successful-nothing**: it emitted a `read_file` call in `<function=…>` syntax
rather than the runner's protocol, the parser saw no protocol call and took the message as a final
answer, and it exited **0** having left the stub byte-identical. **That is E33.2 Run A's mechanism
on a different model.**

### Why this is the parent's decision and not this Epic's

The relative bar is *"no worse on **every** objective check and **strictly better** on at least one,
over an absolute floor."* **`no worse than` is not defined against `{PASS 9/20, FAIL 0/20}`.**

Four aggregation rules are available and **they give different answers on the same data**:

| Rule | The incumbent's dev bar becomes | Consequence |
|---|---|---|
| **Worst run** | FAIL, 0/20 | Any candidate that ever clears the floor once beats the incumbent. The bar is near-vacuous |
| **Best run** | PASS, 9/20 | Best-of-N by the back door — **and M41's Hard Constraint forbids best-of-N by name** |
| **Mean** | 4.5/20, floor undefined | Averages a verdict that is categorical; *"half-passed the floor"* is not a state |
| **Both terms, paired** | *floor-clear rate 1/2; directional 9 and 0* | Honest, but it makes **reliability** a term of the bar, which the milestone never specified |

**Choosing among these after seeing the data is exactly the failure the *bar-committed-first* rule
exists to prevent**, which is why this epic measured, reported both runs, and stopped.

### What is asked

**A ruling on how a multi-run baseline aggregates into the term a relative bar is measured against**
— before E41.3 runs a candidate, so the rule is committed ahead of the data it will judge.

**One observation offered as input, not as a recommendation.** The floor-clear rate is itself a
directional, objective quantity (*runs that cleared the floor / runs dispatched*), it needs no
subjective judgment, and it is the only one of the four rules that does not either discard a run or
average a categorical verdict. **If reliability is to be a term of the bar, it has to be added
deliberately by the level that owns the bar** — this chat cannot add a term to it.

**Note on scope:** `epic_qa` has no such problem. Both QA runs are identical on every term — 1 round,
3 of 5 catches, 0 false alarms, 0 unclear, all 12 rules reported. **The question is the dev lane's
only.**

## Item 2 — **These are HOST baselines, not sandbox baselines, and the record must not be read as protected from the fallback**

### The measurement

All four dispatches ran through `bin/run-dev-agent` / `bin/run-qa-agent` **directly, on the host, in
no container.** `bin/ai-project-orchestrator` **was never invoked.**

**Docker was present throughout (29.7.2), so the spec's stated condition held.** But the accurate
statement is stronger and different: **`:392-397`'s fallback could not have fired, because the
function containing it never ran.**

### Why it matters, stated plainly

**The fallback the spec wants avoided executes on the host, unsandboxed. These baselines were also
taken on the host, unsandboxed.** They are therefore **equivalent to** what the fallback would have
produced rather than protected from it. S6's reasoning — *a baseline measured through the exact path
M42 exists to close is not comparable to anything measured after M42 lands* — **applies to these
baselines**, and Docker's presence does not exempt them.

**This epic did not repair it and must not** — the sandbox, the fallback and `discover_runner()` are
M42's, and the Non-Goals are explicit.

### What is asked

**Two acknowledgements, so neither is silently inherited:**

1. **E41.3 must dispatch identically** — host, the same entry points, the same shim,
   `runner-default`, no container. Recorded as binding in the record's §8. **A candidate measured in
   the sandbox is not comparable to these numbers.**
2. **After M42 lands, these baselines may need re-taking.** Whether M41's qualification survives a
   change of execution environment is a milestone-level question, and it is being raised **now**
   rather than discovered when M42 closes.

**This epic also did not confirm or falsify that an engine resolves *in the sandbox* on the reverse
endpoint shape from `B2.1`** — the phase spec's *"most fragile assumption"* remains untested at that
layer. **It is stated as untested rather than left to be read as answered by four host dispatches.**

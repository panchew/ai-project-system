# Delivery Notice: B2.1 — `run_in_sandbox()` severs the container from the Ollama endpoint

## Summary

`run_in_sandbox()` now forwards `AI_PROJECT_OLLAMA_ENDPOINT` — rewritten from the host's
loopback to a gateway the container can actually resolve — and `LOCAL_AGENT_RUNNER` when
set. Measured through the real function, against the real `ai-project-sandbox:latest` and
the real host Ollama: **HTTP 200**, where the same probe against the container's own
loopback still returns **000**.

Suite: **391 passed, 1 xfailed** against this branch's measured baseline of **375 passed,
1 xfailed** (`origin/master` at `eed8e37`). +16 passing tests, no regressions, no skips
introduced to route around the change.

## How the gateway avoids being hard-coded

`172.17.0.1` is a measurement of *this* host, not a fact about Docker, so it appears
nowhere in the source — `test_source_contains_no_literal_bridge_address` asserts that
mechanically. The default is `host.docker.internal` paired with
`--add-host host.docker.internal:host-gateway`, which makes **the daemon** resolve the
host's address at container start. `AI_PROJECT_SANDBOX_GATEWAY` overrides the alias where
the magic name is unavailable; a literal address is accepted there and correctly emits no
`--add-host`, since `--add-host 172.17.0.1:host-gateway` is not a form Docker accepts.

Only loopback hostnames are rewritten. An endpoint already naming a routable host
(`http://inference.internal:11434`) is reachable from the container as written, and
rewriting it would break a working configuration.

## Verification, and the layer each measurement was taken at

Stated explicitly because B2.1 exists downstream of a verification performed at the wrong
layer (`P11-GH-2`, ratified in the same ruling that authorized this fix).

| Claim | Layer measured at | Result |
|---|---|---|
| The argv carries a non-loopback endpoint | host — argv inspection, `subprocess.run` stubbed | 14 tests pass |
| The packet arrives | **inside the sandbox**, via the real `run_in_sandbox()` | **HTTP 200** |
| The old failure is still the old failure | **inside the sandbox**, probing `localhost:11434` | **000** |
| Removing the forwarding fails the suite | host — one line deleted, suite re-run | **7 failures** |
| No engine in the image | `Dockerfile.sandbox` contents | no install step |

The negative control is load-bearing: a green reachability test alone would also be green
if an engine had been installed into the image, which Decision 5 declines. Pairing it with
the 000 pins the improvement to the forwarding and nothing else.

## What this does **not** do, as the spec predicted

**E37.1 is still not dispatchable, and this delivery does not claim otherwise.**
`discover_runner()` looks for a `local-agent-runner` binary that the image does not
contain; installing one is Route B.2, declined. B2.1 removes the *first* blocker — the one
that fired before any other could — and nothing further.

`LOCAL_AGENT_RUNNER` is forwarded verbatim. A host path that does not exist inside the
container will not become valid by being forwarded; the DoD asks for forwarding, and
resolving host-vs-container paths belongs to whatever engine surface M38/E38.2 settles on.

## Scope discipline

**No governance document was modified.** That was the first limb of the B-series boundary
the ruling tested this bugfix against, so it is worth stating as a checked property rather
than an intention: the diff touches `bin/ai-project-orchestrator` and adds two test files.
`Dockerfile.sandbox` was **not** modified — the fix needed nothing from it, and the test
that asserts it installs no engine is a guard, not a change.

The new environment variable is documented in the source that reads it
(`run_in_sandbox()`'s docstring and the constant block) rather than in
`governance/ai-project-yml-spec.md`, which matches how `AI_PROJECT_OLLAMA_ENDPOINT` and
`LOCAL_AGENT_RUNNER` are already documented in `bin/run-dev-agent`, and keeps the
no-governance-edits property intact.

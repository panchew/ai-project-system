# Bugfix B3.1 — Steering Note ID allocation is unenforced; nothing detects a duplicate `id:`

## Problem

Steering Note IDs are allocated by whichever agent writes the note, by reading prior notes and
incrementing. There is **no registry, no allocation rule, and no test** — allocation works exactly as
well as the author's attention. An audit of `.ai-project/artifacts/steering-notes/` (SN-28,
2026-08-01) found **28 IDs across 23 notes with two double-claimed**: `SN-23` is claimed by both
`2026-07-18__creation-chat__steering-note__reference-dont-display.md` and
`2026-07-20__creation-chat__steering-note__P10-adoption-spine.md`; `SN-1` by both
`2026-06-12__creation-chat__steering-note.md` and
`2026-07-31__layer-8-cfo__steering-note__system-hq-routing-model.md`.

`tests/` guards `.ai-project.yml` model-key divergence but **nothing guards artifact IDs**, so both
collisions accumulated silently and are now cited by number in normative documents.

## Impact

- **Severity:** Medium. Limited immediate impact with a manual workaround (cite by date), but it
  degrades quietly and the two existing collisions took no more than a two-day gap between sessions
  to occur.
- **Affected component:** `.ai-project/artifacts/steering-notes/` and everything that cites a Steering
  Note by number — including `AI-OPERATING-GUIDELINES.md`, `artifact-communication-protocol.md`,
  `chat-hierarchy.md`, `fleet-operator.md`, `fleet-operator-brief.md`.
- **Affected users:** any agent or human resolving an `SN-<n>` citation. The observed worst case: a
  reader following `AI-OPERATING-GUIDELINES.md`'s *"SN-23 Decision 2"* citation reaches
  `chat-hierarchy.md`'s supersession notice for a **different** SN-23 Decision 2 and concludes that
  platform agnosticism was superseded. It was not.

**Scope note on severity.** SN-28 rates the overall concern **High**. That rating belongs to the
SN-23 **citation trap**, which this bugfix does not touch — the citation fix, the namespace rule and
the allocation rule are normative amendments and land in **P11's first milestone (M36)**, per the
CFO's 2026-08-01 ruling. What this bugfix fixes is the **absence of enforcement**, which is Medium.

## Root Cause

Known. There is no enforcement mechanism of any kind — no allocation rule in the Steering Note
template or `creation-chat-guide.md`, and no test asserting uniqueness. Correctness depends entirely
on each author reading the directory carefully. Both observed collisions are what that looks like when
attention lapses: one across a two-day gap between sessions, one from an entity (System HQ, scribing
for Layer-8/CFO) that reasonably believed it was starting its own sequence.

## Fix

Add a test asserting **no duplicate `id:` across `.ai-project/artifacts/steering-notes/`**.

- Parse the front-matter `concerns[].id` values of every `*steering-note*.md` in that directory.
- Fail with the colliding ID and **every** file claiming it, so the failure message is actionable
  without further investigation.
- **Sub-IDs with letter suffixes are valid and must not be flagged.** `SN-12a` and `SN-12b` in
  `2026-06-25__creation-chat__steering-note.md` are correctly-suffixed sub-IDs of a single concern.
  An earlier SN-28 pass mis-flagged them as a collision; the mis-flag was a regex artifact
  (`SN-[0-9]*` truncating the letter suffix), not a record defect. **Do not reintroduce that regex.**
- Place it alongside the existing artifact tests (`tests/test_ongoing_artifacts.py`,
  `tests/test_artifact_parser.py` are the nearest neighbours). Reuse the existing front-matter parsing
  helper rather than writing a third one.

**The two existing collisions will make this test fail on arrival.** That is expected and is not a
reason to weaken the test. Two options, and the choice is the Coding Agent's:

- **(a)** land the test **xfail/skip-with-reason**, referencing M36/E36.1–E36.2 as the fix, and have
  M36 flip it to a hard failure as part of its DoD; or
- **(b)** land the test hard-failing on a branch that is **not merged** until M36 clears the
  collisions.

**(a) is recommended** — it puts the guard in the repository immediately, which is the point of the
hotfix, and gives M36 a mechanical, verifiable completion signal. Whichever is chosen, record the
reasoning in the Delivery Notice.

## Acceptance Criteria

  suite**, and the failure names both the ID and the competing files.
- Adding a note with a letter-suffixed sub-ID of an existing concern **passes**.
- No normative document is modified by this bugfix. **If a fix appears to require editing a governance

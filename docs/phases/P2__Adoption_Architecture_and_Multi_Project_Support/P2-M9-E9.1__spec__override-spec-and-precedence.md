# Epic E9.1 — Define Override Specification & Precedence Rules

## Context

Epic E6.3 established the `.ai-project.yml` schema with an `overrides` block as a stub (three fields listed, no formal constraints or validation). The overrides stub references M9 for the full specification.

This Epic delivers the complete override specification: all override fields with types, defaults, constraints, and validation rules. It also documents the override precedence hierarchy so that any project participant can determine which value wins in a conflict.

---

## Problem Statement

Without a complete override specification:

- Projects cannot confidently set custom values — there is no defined set of allowed fields or constraints
- Validation tooling has no schema to validate against (unknown keys, invalid values)
- Precedence is ambiguous — it is unclear whether a project-level decision overrides `.ai-project.yml` or vice versa
- The HQ agent (E9.3) has no specification to implement against
- The `.ai-project.yml` spec (Section 3.3) references M9 but is incomplete

---

## Goals

By the end of this Epic:

1. All override fields are fully defined with types, defaults, allowed values, and constraints
2. The override precedence hierarchy is documented and unambiguous
3. Core (non-overridable) governance dimensions are explicitly enumerated
4. The `.ai-project.yml` spec (`governance/ai-project-yml-spec.md`) is updated with the complete override schema
5. Override validation rules are documented (which values are valid, which are rejected)
6. The `PROJECT-SYSTEM-GUIDELINES.md` is updated to reference the override system and precedence rules

---

## Non-Goals

- Implementing override reading in the HQ agent (E9.3)
- Creating example `.ai-project.yml` configurations (E9.4)
- Building validation tooling or CLI flags
- Defining per-epic or per-milestone overrides (project-level only)
- Defining runtime override enforcement in Coding Agents

## Scope of Work

### 1. Define Complete Override Fields

Finalize the three fields stubbed in E6.3:

| Field | Type | Default | Allowed Values | Constraint |
|-------|------|---------|----------------|------------|
| `overrides.branch_strategy` | String | `trunk-based` | `trunk-based`, `gitflow` | Must be one of the allowed values |
| `overrides.merge_strategy` | String | `merge` | `merge`, `squash`, `rebase` | Must be one of the allowed values |
| `overrides.epic_prefix` | String | `epic/` | Any string ending with `/` | Must end with `/`; must not be empty |

Document for each field:
- Type and format
- Default value (applied when field is absent)
- Allowed values with descriptions
- Constraints with validation error messages
- Behavioral effect (how the system uses each override)
- Example usage

### 2. Document Override Precedence Hierarchy

Document the precedence as:

1. **Local project convention** (documented in project decisions) — highest
2. **`.ai-project.yml` overrides** — medium
3. **Governance defaults** (PROJECT-SYSTEM-GUIDELINES.md) — lowest

Explain each level:
- **Level 1 — Local project convention**: A documented project decision that explicitly overrides a governance convention for exceptional circumstances. Must be recorded in `docs/decisions/`. Should be rare.
- **Level 2 — `.ai-project.yml` overrides**: The standard mechanism for projects to customize governance behavior. Declared in the `overrides` block. Takes effect when the HQ agent reads the file.
- **Level 3 — Governance defaults**: The baseline conventions defined in `PROJECT-SYSTEM-GUIDELINES.md`. Apply when no override is present at Level 1 or Level 2.

Include a precedence resolution example table showing how a conflict between levels is resolved.

### 3. Enumerate Core (Non-Overridable) Governance Dimensions

Document the following as immutable governance dimensions:

- **Canonical happy path** (8 steps): Cannot be altered by overrides
- **Authority hierarchy**: HQ Chat → Milestone Chat → Coding Agent; cannot be restructured
- **Epic lifecycle**: spec → execute → deliver → review → accept → merge; steps cannot be skipped or reordered
- **Definition of DoD requirements**: All DoD items must be satisfied; overrides cannot reduce DoD scope
- **Documentation front-matter conventions**: YAML front-matter format and required fields are fixed
- **Branch hierarchy**: `epic/*` → `milestone/*` → `phase/*` structure is immutable; only prefixes are overridable (via `epic_prefix`)

For each dimension, explain why it is non-overridable and what the consequence of allowing overrides would be.

### 4. Update `governance/ai-project-yml-spec.md`

Update Section 3.3 (Optional Fields — `overrides`) from stub to complete specification:
- Replace the "deferred to M9" notice with the full field definitions
- Add constraints and validation details
- Add precedence reference linking to the governance guidelines
- Update the Full Example with Overrides section if needed
- Bump the spec version to 2.0.0
- Add changelog entry

### 5. Update `PROJECT-SYSTEM-GUIDELINES.md`

Add a new section documenting:
- Override system overview (what overrides are, when to use them)
- Precedence hierarchy reference
- Link to the `.ai-project.yml` spec for complete field definitions
- List of core (non-overridable) governance dimensions

### 6. Update `governance/ai-project-yml-spec.md` Validation Rules

Add validation rules for the `overrides` block:
- Unknown override keys must produce a validation warning
- Invalid values for known fields must produce a validation error
- The `overrides` block must be valid YAML
- At least one of: no override values are required (block is optional)

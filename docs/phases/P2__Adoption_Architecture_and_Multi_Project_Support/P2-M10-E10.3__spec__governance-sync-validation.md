# Epic E10.3 — Governance Sync Validation

## Context

E10.1 produced the adoption guide and FAQ, and E10.2 validated that the adoption path works for real projects. Both earlier Epics revealed that `v2.0.0` is the declared governance version but no corresponding git tag exists in the repository, and the governance sync workflow has never been tested end-to-end.

This Epic tests the full governance sync lifecycle: update governance in the source repository, pull the update in an adopted project, and verify the project still functions correctly. It also documents the sync process, edge cases, and rollback procedure — closing the remaining validation gap before Phase P2 closure.

Governance sync is the mechanism by which projects receive governance updates. It is documented in `governance/submodule-setup.md` (Section 6) and `governance/ai-project-yml-spec.md` (Section 7), but neither has been validated against a real update cycle.

---

## Problem Statement

Without governance sync validation:

- The documented sync workflow (`submodule-setup.md` Section 6) has never been executed end-to-end — it may contain incorrect or missing steps
- Edge cases (merge conflicts in submodule pointers, dirty submodule state, URL mismatches) have only theoretical documentation in the FAQ
- The rollback procedure for a failed governance update is untested
- The Milestone acceptance criterion "Governance sync is tested: update in source repo → pull in adopted project → verified working" remains unsatisfied
- The Phase P2 completion report cannot declare governance sync validated

---

## Goals

By the end of this Epic:

1. The governance sync workflow is executed end-to-end: source governance update → consumer pulls → verified working
2. A sync test report documents the process, results, and any issues encountered
3. Edge cases are identified, documented, and (where possible) tested
4. A rollback procedure is documented and tested
5. The `v2.0.0` git tag is created in the governance source repository (if missing)
6. Governance documentation (FAQ, submodule guide) is updated with validated sync procedures

---

## Non-Goals

This Epic explicitly does **not** aim to:

- Build automated sync tooling or CLI features (deferred to future phase)
- Modify the governance submodule architecture
- Create a new governance release (version bump beyond what is needed for testing)
- Modify `PROJECT-SYSTEM-GUIDELINES.md` or `AI-OPERATING-GUIDELINES.md`
- Onboard new projects (E10.2 scope)
- Produce the Phase P2 completion report (E10.4 scope)

## Scope of Work

### 1. Create Governance Sync Test Plan

Create `docs/phases/P2__Adoption_Architecture_and_Multi_Project_Support/P2-M10-E10.3__test-plan__governance-sync.md` — a structured test plan covering the following scenarios:

**Scenario 1 — Happy Path: Patch Version Update**
- Source: Bump governance `version` from `2.0.0` to `2.0.1` (minor documentation change)
- Consumer: Pull update via submodule update
- Verify: Project still works (HQ agent references resolve, `.ai-project.yml` validates)

**Scenario 2 — Happy Path: Minor Version Update**
- Source: Bump governance `version` from `2.0.0` to `2.1.0` (add new FAQ entry)
- Consumer: Pull update via submodule update
- Verify: New governance content is accessible, old content still works

**Scenario 3 — Edge Case: Tag Not Found**
- Source: `governance.ref` points to a tag that does not exist
- Consumer: Submodule checkout fails
- Verify: Error message is clear, recovery steps work

**Scenario 4 — Edge Case: Merge Conflict in Submodule Pointer**
- Consumer: Local submodule pointer has diverged from remote
- Consumer: `git pull` causes merge conflict in submodule commit reference
- Verify: Conflict is resolvable via documented procedure

**Scenario 5 — Rollback: Revert to Previous Version**
- Source: After an update, revert governance version back to `2.0.0`
- Consumer: Rollback submodule to previous tag
- Verify: Original governance state is restored

Each test case must include:
- Preconditions
- Steps (numbered, with exact commands)
- Expected outcome
- Actual outcome (filled in during execution)
- Pass/Fail verdict

### 2. Execute Sync Tests and Produce Test Report

Execute all test plan scenarios on a simulated consumer project (which can be the `ai-project-system` repository itself, configured to reference a temporary test tag, or a temporary test directory set up as a governance consumer).

Produce `docs/phases/P2__Adoption_Architecture_and_Multi_Project_Support/P2-M10-E10.3__test-report__governance-sync.md` — a report documenting:

- Environment details (git version, OS, submodule version)
- Results for each test scenario (Pass/Fail with evidence)
- Issues encountered during testing
- Deviations from documented procedure
- Time taken for each scenario

### 3. Document Sync Process, Edge Cases, and Rollback Procedure

Update `governance/guides/ADOPTION-FAQ.md` with validated sync procedures based on test findings:
- Add or update the "Governance Sync/Update Failures" section with tested solutions
- Ensure each FAQ entry references tested commands that actually work

Create or update `governance/guides/GOVERNANCE-SYNC-GUIDE.md` — a standalone guide covering:
- **Overview**: How governance versioning works
- **Prerequisites**: Git submodule knowledge, access to governance source
- **Normal Update Flow**: Step-by-step (fetch → checkout → update `.ai-project.yml` → commit)
- **Edge Cases**: Tag not found, URL mismatch, dirty submodule, merge conflict in pointer
- **Rollback Procedure**: Step-by-step for reverting to a previous governance version
- **Verification**: How to confirm the sync was successful
- **Testing Checklist**: Quick-reference for validating a sync operation

### 4. Create Missing Governance Tag

If the `v2.0.0` git tag does not exist (as identified in E10.2 adoption records):
- Create a lightweight tag `v2.0.0` at the current HEAD of `master` or the governance baseline commit
- Document the tag creation decision

Note: This is a prerequisite for both the sync test and any future governance consumer. The governance versioning convention requires version tags to match the `governance.ref` in `.ai-project.yml`.

# Epic E9.4 — Create Example Configurations & Validate

## Context

Epics E9.1–E9.3 have defined the override specification, documented boundaries and system integration, and implemented override support in the HQ agent. However, there are no concrete example `.ai-project.yml` files demonstrating how different project types should configure overrides, and no validation confirming the system works end-to-end.

This Epic creates at least 3 example configurations for common project types, validates each against the override spec, and documents troubleshooting guidance for common issues.

---

## Problem Statement

Without example configurations:

- Project leads have no reference to follow when configuring overrides for their project type
- It is unclear which override combinations are appropriate for different project patterns
- There is no validation confirming that override configurations pass spec validation
- No troubleshooting guidance exists for common configuration mistakes

---

## Goals

By the end of this Epic:

1. At least 3 example `.ai-project.yml` configurations exist for common project types
2. Each example is validated against the `.ai-project.yml` spec (all fields correct, all constraints met)
3. Each example demonstrates a realistic override configuration
4. Troubleshooting guidance is documented for common override issues
5. A validation summary confirms all examples pass spec validation

---

## Non-Goals

- Building automated validation tooling (future phase)
- Writing integration tests for the HQ agent (future phase)
- Creating per-epic or per-milestone override examples (project-level only)
- Adding new override fields beyond the three defined in E9.1

---

## Scope of Work

### 1. Create Example Configuration — Library Project

Create a documented example at `docs/examples/configurations/library-project.md`:

A library project that packages reusable code for other projects. Typically uses standard conventions with minimal overrides.

**Example overrides used:** None (all defaults). Demonstrates the baseline pattern.

**File content:**
- Complete `.ai-project.yml` with governance source, project name, and no overrides block
- Description of the project type and why defaults are appropriate
- Commented-out override alternatives showing what a library *could* customize
- Validation notes confirming the file passes spec validation

### 2. Create Example Configuration — Application Project

Create a documented example at `docs/examples/configurations/application-project.md`:

An application project that ships to production. Typically uses squash merges and teams may prefer `feature/` prefix.

**Example overrides used:**
- `merge_strategy: squash` — cleaner commit history for release tracking
- `epic_prefix: "feature/"` — team convention matches existing workflow

**File content:**
- Complete `.ai-project.yml` with override block
- Explanation of why each override is set
- Expected effect on generated artifacts (branch names, merge instructions)
- Validation notes confirming the file passes spec validation

### 3. Create Example Configuration — Monorepo Workspace

Create a documented example at `docs/examples/configurations/monorepo-workspace.md`:

A monorepo hosting multiple packages or services. Uses git-flow branch strategy with rebase merges to maintain linear history across many contributors.

**Example overrides used:**
- `branch_strategy: gitflow` — multi-release coordination
- `merge_strategy: rebase` — linear history for monorepo
- `epic_prefix: "feature/"` — common monorepo convention

**File content:**
- Complete `.ai-project.yml` with all three overrides
- Explanation of monorepo-specific override needs
- Expected effect on generated artifacts
- Validation notes confirming the file passes spec validation

### 4. Validate Each Example Against the Spec

For each example, produce a validation block confirming:

- All required fields are present and correct
- All override values are valid per the spec
- No unknown override keys are present
- The file is valid YAML
- The resolved override values match expectations

Document this as a validation summary either inline in each example or as a separate validation report.

### 5. Create Troubleshooting Guide

Create `docs/examples/configurations/troubleshooting.md` covering:

- **Override not taking effect** — `.ai-project.yml` not read by HQ agent, override block absent, incorrect field name
- **Validation error on startup** — invalid override value, unknown key, malformed YAML
- **Wrong branch prefix in generated artifacts** — override not applied during generation, cached stale value
- **Merge strategy mismatch** — incorrect value, default used instead of override
- **Precedence confusion** — local project decision vs. `.ai-project.yml` override vs. governance default
- **YAML formatting issues** — quoting, indentation, comment syntax

For each issue, document:
1. Symptom (what the user sees)
2. Cause (why it happens)
3. Solution (how to fix it)
4. Prevention (how to avoid it)

**Validation rules to check against (from `ai-project-yml-spec.md` §4):**
1. File exists and is valid YAML
2. All required fields present: `governance.source`, `governance.version`, `governance.ref`, `project.name`, `project.description`
3. `governance.source` is HTTPS URL or relative path starting with `./` or `../`
4. `governance.version` is quoted semver
5. `governance.ref` is non-empty string
6. `project.name` matches `^[a-z][a-z0-9-]*$`
7. `project.description` is non-empty
8. Override values are valid per field constraints

### Scenario 4: Merge Conflict in Submodule Pointer (Edge Case)

**Verdict:** ✅ PASS

**Steps executed:**
1. Created branch `team-a` from initial state — modified `.gitmodules` → committed
2. Created branch `team-b` from initial state — rewrote `.gitmodules` → committed
3. Merged `team-b` into `team-a` — **conflict detected**
4. Resolved: `git checkout --theirs .gitmodules && git add .gitmodules && git commit`

**Evidence:**
```
CONFLICT (content): Merge conflict in .gitmodules
Automatic merge failed; fix conflicts and then commit the result.

Resolution:
  git checkout --theirs .gitmodules
  git add .gitmodules  
  git commit (merge commit created)
```

**Notes:**
- **Important finding:** With Git 2.43.0, submodule *pointer* conflicts (where both branches change the submodule to a different commit) are automatically resolved by the `ort` merge strategy. No manual resolution needed.
- The documented FAQ procedure for "Merge conflicts in submodule pointers" is accurate for `.gitmodules` conflicts, which *do* cause content-level merge conflicts.
- Submodule conflicts in the pointer (SHA) are auto-resolved by modern git.

## Issues Encountered

1. **`file://` protocol not allowed by Git** — Git 2.43+ requires `protocol.file.allow=always` config for local submodule testing. Added to global git config.
2. **Submodule pointer conflicts are auto-resolved** — Modern git (2.43.0) handles submodule SHA conflicts automatically. The documented edge case in the FAQ is relevant only for older git versions or `.gitmodules` content conflicts.

# Epic E7.1 — Design CLI Architecture & Hierarchical Docs Structure

## Context

The `ai-project init` CLI command must scaffold a P2-conformant project structure. Before implementation begins (E7.2), the CLI architecture, command-line interface, folder hierarchy, and design decisions must be documented. This Epic establishes the specification that E7.2 will implement.

---

## Problem Statement

There is no defined specification for how the `ai-project init` command should:

- Accept input parameters (project name, governance source, version, etc.)
- Validate project name and location
- Generate the hierarchical folder structure
- Handle edge cases (existing directory, invalid names, network errors)
- Output status messages and errors
- Determine platform support (macOS, Linux, Windows)

Without this design, E7.2 will face ambiguity about what to build. The specification must be clear enough that implementation is straightforward.

---

## Goals

By the end of this Epic:

1. The `ai-project init` command interface is fully documented (all flags, arguments, options)
2. The folder hierarchy it should create is specified, with path examples
3. The CLI flow (happy path and error paths) is diagrammed or documented
4. Platform support requirements are defined (macOS, Linux, Windows)
5. Edge cases and error handling are documented
6. Dependencies (git, node, bash, etc.) are specified
7. The design is locked and committed so E7.2 can implement without ambiguity

---

## Non-Goals

- Implement the CLI (E7.2)
- Create the governance submodule integration (E7.3)
- Install HQ agent files (E7.4)
- Build a Node.js package for npm registry (future phase)
- Create a GUI or web interface
- Support monorepo projects

## Scope of Work

### 1. Define the CLI Command Interface

Document the command and all supported flags/options:

```bash
ai-project init <project-name> [options]

Options:
  --dir <path>                    Directory where project will be created (default: current dir)
  --governance-source <url>       Git URL for governance repo (default: https://github.com/panchew/ai-project-system)
  --governance-version <tag>      Git tag or branch for governance (default: v2.0.0)
  --skip-git                      Don't initialize git repo
  --skip-submodule                Don't add governance submodule
  --help                          Show help text
  --version                       Show CLI version
```

Document what each option does, valid values, and defaults.

### 2. Design the Folder Hierarchy

Specify the exact folder structure the CLI must create:

```
my-project/
├── docs/
│   ├── README.md                        (Project overview)
│   ├── phases/                          (Phase artifacts folder)
│   ├── context/
│   │   └── project-tracker.md           (Baseline context)
│   ├── roadmap/
│   │   └── overview.md                  (Empty roadmap)
│   ├── decisions/                       (ADRs, decisions)
│   ├── _legacy/                         (Historical artifacts)
│   └── admin/                           (Administrative notes)
├── .github/
│   └── agents/
│       └── hq.agent.md                  (HQ Chat agent - copied from governance)
├── .gitmodules                          (Git submodule config)
├── .ai-project.yml                      (Project config)
├── .gitignore                           (Standard project ignores)
├── README.md                            (Project root readme)
└── <governance submodule>/              (git submodule at governance folder)
    └── [governance contents]
```

Justify why each folder exists and what it's for.

### 3. Define `.ai-project.yml` Content for Initialization

Specify what the CLI should write to `.ai-project.yml`:

```yaml
project:
  name: <project-name>
  created_at: <ISO-8601-timestamp>

governance:
  source: <governance-url>
  version: <governance-tag>
  submodule_path: governance/
```

Document that this is the minimal valid `.ai-project.yml` for a P2 project.

### 4. Document the CLI Flow

Create a state diagram or pseudocode showing:

**Happy Path:**
1. Validate project name (no special chars, not reserved)
2. Check if target directory exists and is empty
3. Create directory structure
4. Initialize git repo
5. Add governance submodule
6. Write `.ai-project.yml`
7. Copy HQ agent file stub
8. Create initial `.gitignore`
9. Print success message with next steps

**Error Paths:**
1. Invalid project name → error + suggestion
2. Directory already exists → error + option to use `--dir`
3. Git not found → error
4. Network error fetching governance → error + fallback option
5. Submodule clone fails → error + manual instructions

### 5. Define Platform Support

Document supported operating systems and minimum requirements:

- **macOS:** 10.14+ (bash 4+)
- **Linux:** Ubuntu 18.04+, Debian 9+, CentOS 7+ (bash 4+)
- **Windows:** WSL2 (bash 4+); native Windows support (PowerShell 7+) if feasible
- **Git:** 2.20+
- **Node.js:** (if using Node implementation) 14+

Specify that implementation can be shell script (bash) or Node.js, but not Python.

### 6. Specify Error Messages and User Feedback

Document the tone and content of CLI output:

- Status messages: `✓ Created docs/ folder`
- Errors: `✗ Project name contains invalid characters. Use: project-name (lowercase, dashes only)`
- Help: `ai-project init --help`
- Next steps: After success, print a prompt for the user to `cd <project>` and `git status`

### 7. Define Success Metrics for E7.2 Implementation

Specify how E7.2 will verify the CLI is correct:

- [ ] Running `ai-project init test-project` creates all required folders
- [ ] `.ai-project.yml` is valid YAML and matches the spec
- [ ] Git repo is initialized and has all files staged (not committed yet)
- [ ] Governance submodule is present at `governance/`
- [ ] HQ agent file exists at `.github/agents/hq.agent.md`
- [ ] Running `ai-project init --help` shows all documented options
- [ ] Exit code is 0 on success, non-zero on error

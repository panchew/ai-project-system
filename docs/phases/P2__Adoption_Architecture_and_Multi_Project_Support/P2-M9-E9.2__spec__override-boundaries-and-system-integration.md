# Epic E9.2 — Document Override Boundaries and System Integration

## Context

Epic E9.1 defined the override fields and precedence hierarchy. However, the system does not yet document:

- Which governance dimensions are formally overridable vs. which are core and immutable (override boundaries)
- How overrides flow through the system — how the HQ agent, Milestone specs, Epic specs, templates, and Chat Starters should reference overridden values

This Epic produces that documentation, publishing a formal Override Boundaries document in governance and updating system documents to describe the override flow.

---

## Problem Statement

Without formal override boundaries:

- Project leads cannot reliably tell which governance dimensions they can customize and which they cannot
- The HQ agent (E9.3) has no specification for how to propagate overridden values through generated artifacts
- Templates and Chat Starters may reference hardcoded defaults instead of the correct (possibly overridden) values
- Override boundaries are mentioned in the Milestone spec but not formally published as a governance document

Without system integration documentation:

- There is no single document describing how an override value entered in `.ai-project.yml` propagates to artifact generation
- The HQ agent's override reading responsibility is not scoped
- Template authors don't know where to use override placeholders vs. hardcoded values

---

## Goals

By the end of this Epic:

1. A formal Override Boundaries document is published in governance listing all overridable and non-overridable dimensions with rationale
2. System integration documentation describes how overrides flow from `.ai-project.yml` through the HQ agent to generated artifacts
3. The governance documents `PROJECT-SYSTEM-GUIDELINES.md` cross-reference the Override Boundaries document
4. The `ai-project-yml-spec.md` references the Override Boundaries document and the override flow
5. The `hq.agent.md` is updated with placeholders for where override reading should occur (actual implementation deferred to E9.3)

---

## Non-Goals

- Implementing override reading in the HQ agent (E9.3)
- Creating example configurations (E9.4)
- Building validation tooling
- Defining new override fields beyond the three defined in E9.1
- Modifying the override precedence hierarchy (defined in E9.1)

## Scope of Work

### 1. Create Override Boundaries Governance Document

Create `governance/override-boundaries.md` covering:

**Overridable dimensions:**
- **Branch prefix:** `epic_prefix` — the prefix used for Epic branches (default `epic/`, can be changed to `feature/`, `story/`, etc.)
- **Merge strategy:** `merge_strategy` — the default PR merge method (default `merge`, can be `squash` or `rebase`)
- **Branch strategy:** `branch_strategy` — the branch naming and promotion strategy (default `trunk-based`, can be `gitflow`)

For each overridable dimension, document:
- What it controls
- How it affects system behavior
- Example values
- Constraints and validation rules
- Rationale for why it is overridable

**Core (non-overridable) dimensions:**
- Canonical happy path (8 steps)
- Authority hierarchy
- Epic lifecycle stages
- Definition of DoD requirements
- Documentation front-matter conventions
- Branch hierarchy structure (only prefixes overridable)

For each core dimension, document:
- What it controls
- Why it is non-overridable (consequence of allowing override)
- How to request a change (governance amendment process)

**Boundary rules:**
- Overrides apply project-wide, not per-epic or per-milestone
- Overrides cannot alter the number or order of governance lifecycle steps
- Overrides cannot relax DoD requirements
- Overrides are advisory to governance agents (agents must still validate generated artifacts against governance)
- Unknown override keys produce a warning, not a hard error

### 2. Document Override System Integration

Create or update `docs/systems/override-system-integration.md` documenting:

**Override flow (from entry to artifact):**
```
.ai-project.yml (overrides block)
  → HQ agent reads on startup
  → HQ agent caches override values in session context
  → HQ agent applies overrides when generating:
      - Phase specs (branch names, merge strategy references)
      - Milestone specs (branch names, merge strategy references)
      - Epic specs (epic branch prefix)
      - Chat Starters (branch strategy references, merge instructions)
  → Coding Agent receives resolved values in Chat Starter
  → Coding Agent follows overridden instructions during execution
```

**Override resolution points:**
- Phase spec generation: Where overrides affect branch naming and merge strategy in spec content
- Milestone spec generation: Same
- Epic spec generation: Where epic_prefix is used for branch naming
- Chat Starter generation: Where merge strategy and branch strategy appear in execution instructions

**Artifact templates and override placeholders:**
- Document which fields in which templates should use overridable placeholders vs. hardcoded governance defaults
- Map each override field to the templates it affects

### 3. Update `governance/PROJECT-SYSTEM-GUIDELINES.md`

Add cross-reference to the new Override Boundaries document. The override section added in E9.1 should link to the full boundaries document.

### 4. Update `governance/ai-project-yml-spec.md`

Add cross-reference to the Override Boundaries document. Clarify that the overrides block maps to the dimensions defined in the boundaries document.

### 5. Update `governance/agents/hq.agent.md`

Add a new sub-section "Override Integration" that describes:
- That the HQ agent reads overrides on startup
- Where overrides are used during artifact generation
- That actual implementation is in E9.3
- A placeholder for future override caching and resolution logic

**For the Override Boundaries document:**
- Keep it concise (one page max)
- Use a table format for overridable dimensions and a separate table for non-overridable
- Include "how to propose a new override" in the document

**For the system integration document:**
- The override flow should be clear enough that E9.3 can implement against it
- Use a flow diagram (ASCII or Mermaid) if helpful
- Map each override field to specific templates and artifact types

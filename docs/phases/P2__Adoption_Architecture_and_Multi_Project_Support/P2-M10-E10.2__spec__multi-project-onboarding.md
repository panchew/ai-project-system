# Epic E10.2 — Multi-Project Onboarding

## Context

E10.1 produced the adoption guide (`ADOPTION-GUIDE.md`) and troubleshooting FAQ (`ADOPTION-FAQ.md`) that document the complete path from zero to HQ Chat live. The guide defines the theoretical adoption path.

This Epic validates that the guide works in practice by onboarding real projects. Each onboarding produces an adoption record that captures what happened, what friction was encountered, and what improvements are needed. The goal is to prove that the Phase P2 architecture is adoptable by real projects, not just verified in a test environment.

The Milestone's success signal is: "A developer unfamiliar with the system can independently adopt Phase P2 governance in under 30 minutes using only the adoption guide." This Epic provides the real-world evidence for that signal.

---

## Problem Statement

Without multi-project onboarding:

- The adoption guide is untested — there is no evidence that a real project can follow it successfully
- Friction points in the adoption process are theoretical rather than measured
- The Milestone acceptance criterion of "at least 2 external projects have completed adoption" remains unsatisfied
- There is no standardized format for recording adoption outcomes and friction points
- The Phase P2 exit criteria for "proven in practice" cannot be satisfied

---

## Goals

By the end of this Epic:

1. An adoption record template exists that standardizes how onboarding outcomes are captured
2. At least 2 real projects are documented with completed adoption records
3. Friction points from each onboarding are captured and categorized
4. Friction point feedback is incorporated as improvements to the adoption guide (E10.1 deliverable)
5. A summary report synthesizes findings across all onboarded projects

---

## Non-Goals

This Epic explicitly does **not** aim to:

- Build automation or tooling for the onboarding process
- Modify the CLI tooling (M7 scope)
- Create public case studies or marketing materials
- Validate governance sync (E10.3 scope)
- Produce the Phase P2 completion report (E10.4 scope)
- Onboard projects outside the adopter's control

## Scope of Work

### 1. Define Adoption Record Template

Create `governance/guides/ADOPTION-RECORD-TEMPLATE.md` — a standardized template for documenting a project's adoption of Phase P2 architecture.

**Must include:**

| Field | Description |
|-------|-------------|
| Project name and repository URL | Identifies the project |
| Adoption date | When the onboarding occurred |
| Adopter name/role | Who performed the onboarding |
| Prerequisites status | What was already in place before starting |
| Step completion log | Checklist of adoption guide steps with timestamps |
| Friction points | Each issue encountered, categorized by type |
| Time to completion | Total time from start to HQ Chat live |
| Guide deviations | Any steps that differed from the guide |
| Improvement suggestions | Specific recommendations for the adoption guide |
| Final status | Success / Partial / Failed (with reason) |

Each template must include inline instructions (HTML comments) explaining what to fill in each field.

### 2. Onboard Project 1 — Internal Reference Project

Onboard the `ai-project-system` repository itself (or another project within the adopter's direct control) as the first adoption.

**Process:**
1. Follow the adoption guide (`ADOPTION-GUIDE.md`) step by step
2. Record each step's outcome, time taken, and any deviations
3. Complete an adoption record using the template
4. Identify friction points and note them for guide improvement

**Expected outcome:** A completed adoption record demonstrating the full adoption path on a known codebase.

### 3. Onboard Project 2 — External Project

Onboard a second real project (outside the adopter's immediate control, coordinated by human). The Coding Agent produces the adoption record template and documentation; human coordination is required to identify and confirm the external project.

**Process:**
1. Human identifies an external project willing to adopt
2. Coding Agent prepares the adoption record template and onboarding checklist
3. Human (or Coding Agent with access) follows the adoption guide for the external project
4. Complete an adoption record using the template
5. Identify friction points and note them for guide improvement

### 4. Capture and Categorize Friction Points

For each onboarding, produce a structured friction point log that categorizes issues:

| Category | Examples |
|----------|----------|
| Documentation | Missing steps, unclear instructions, gaps in guide |
| Tooling | CLI failures, dependency issues, version mismatches |
| Environment | OS-specific issues, editor configuration, network access |
| Governance | Submodule issues, schema confusion, override problems |
| Process | Branching confusion, planning flow issues |

Each friction point must include:
- Description of the issue
- When it occurred (which adoption step)
- Root cause
- Workaround applied (if any)
- Recommended fix for the adoption guide

### 5. Feed Improvements Back to Adoption Guide

After both onboardings, produce a diff/patch of changes to `governance/guides/ADOPTION-GUIDE.md` and `governance/guides/ADOPTION-FAQ.md` based on friction point findings.

**Must include:**
- Specific sections of the guide that need clarification
- Additional troubleshooting entries for the FAQ based on real issues
- Any steps that were out of order or missing
- Time estimate adjustments based on actual measurements

### 6. Produce Onboarding Summary Report

Create `docs/phases/P2__Adoption_Architecture_and_Multi_Project_Support/P2-M10-E10.2__onboarding-summary.md` synthesizing:
- Which projects were onboarded
- How long each took
- Friction points encountered (aggregated and categorized)
- Guide improvements applied
- Overall assessment: Is the adoption guide ready for public use?
- Recommendations for future onboarding

- The adoption guide is demonstrably improved by the feedback from real onboardings

## Execution Notes

**Adoption record filename convention:**
```
governance/adoption-records/adoption-<project-slug>-<YYYY-MM-DD>.md
```

Example: `governance/adoption-records/adoption-ai-project-system-2026-05-21.md`

**Execution order:**
1. Create adoption record template first
2. Onboard Project 1 (internal reference — fully within Coding Agent capability)
3. Identify friction points and log them
4. Coordinate with human for Project 2 identification
5. Onboard Project 2 (may require human to execute steps if access is limited)
6. Aggregate all friction points
7. Update adoption guide and FAQ with improvements
8. Produce onboarding summary report
9. Create Epic Completion Report

**If external project access is unavailable:**
The Coding Agent should document the friction from Project 1, produce the template, and note in the summary that Project 2 onboarding is pending human coordination. The adoption record for Project 2 can be documented by the human using the template.

**Reference files:**
- `governance/guides/ADOPTION-GUIDE.md` — The guide being validated and improved
- `governance/guides/ADOPTION-FAQ.md` — The FAQ being validated and improved
- `governance/guides/ADOPTION-RECORD-TEMPLATE.md` — Template (created by this Epic)

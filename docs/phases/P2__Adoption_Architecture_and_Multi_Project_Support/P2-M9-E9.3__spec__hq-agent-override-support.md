# Epic E9.3 — Implement HQ Agent Override Support

## Context

Epics E9.1 and E9.2 established the override field specification, precedence rules, boundaries, and system integration documentation. The `hq.agent.md` has an Override Integration section (added by E9.2) with placeholder TODO logic for reading, caching, and applying overrides.

This Epic replaces those placeholders with concrete implementation instructions. The HQ agent must now actively read `.ai-project.yml` overrides, validate them, cache them in session context, and apply them during artifact generation.

---

## Problem Statement

The HQ agent currently:

- Reads `.ai-project.yml` for governance metadata but does not parse the `overrides` block
- Generates artifacts using hardcoded governance defaults (e.g., `epic/` prefix)
- Has no override validation logic during startup
- Has no mechanism to propagate overridden values into generated Phase specs, Milestone specs, Epic specs, or Chat Starters

Without this Epic, the override system is documented but non-functional — a project that sets `overrides.epic_prefix: "feature/"` in `.ai-project.yml` will still see `epic/` in all generated artifacts.

---

## Goals

By the end of this Epic:

1. The HQ agent reads the `overrides` block from `.ai-project.yml` on startup
2. Override fields are validated against governance rules (valid values, unknown keys)
3. Resolved override values are cached in the agent's session context
4. Generated artifacts (Phase specs, Milestone specs, Epic specs, Chat Starters) use overridden values instead of hardcoded governance defaults
5. The agent reports validation warnings/errors during startup
6. The `hq.agent.md` Override Integration section no longer contains TODO placeholders

---

## Non-Goals

- Creating example `.ai-project.yml` configurations (E9.4)
- Building validation tooling outside the HQ agent
- Modifying governance templates to use override placeholders (template updates are part of E9.3's scope)
- Implementing runtime override enforcement in Coding Agents (deferred to P3)
- Building a CLI for override configuration

## Scope of Work

### 1. Update Project Configuration Discovery — Override Reading

Update the "Project configuration discovery" section in `hq.agent.md` to include:

- Reading the `overrides` block from `.ai-project.yml`
- Parsing each field (`epic_prefix`, `merge_strategy`, `branch_strategy`)
- Handling the case where the `overrides` block is absent (use defaults)
- The read step must occur during startup, before artifact generation

**Typical resolved cache:**
```json
session.overrides = {
  epic_prefix: "feature/",       // default: "epic/"
  merge_strategy: "squash",      // default: "merge"
  branch_strategy: "gitflow"     // default: "trunk-based"
}
```

### 2. Add Override Validation to Startup Sequence

Add a new validation step in the agent startup sequence:

1. Read `overrides` block from `.ai-project.yml`
2. Validate each field:
   - `epic_prefix` — must end with `/` (error if not), must be non-empty
   - `merge_strategy` — must be one of `merge`, `squash`, `rebase`
   - `branch_strategy` — must be one of `trunk-based`, `gitflow`
3. Unknown override keys — produce a warning, do not fail
4. Invalid values — produce an error and prevent agent startup
5. If `overrides` block is absent — silently use governance defaults
6. If `.ai-project.yml` is absent — skip override reading, proceed in advisory mode

### 3. Replace E9.3 TODO Placeholders with Concrete Implementation

Replace the three TODO placeholders in the Override Integration section:

```
// BEFORE (E9.2 placeholder):
// E9.3 TODO: Implement override caching
// session.overrides = resolveOverrides(aiProjectYml.overrides, governanceDefaults)
```

Replace with concrete pseudocode/instructions that the agent (human reader) can follow:

```python
# Override caching logic:
# 1. Read overrides block from .ai-project.yml
# 2. For each override field:
#    a. If present and valid → use the value
#    b. If absent → use governance default
#    c. If present but invalid → raise error
# 3. Cache resolved values in session.overrides
# 4. Report validation results to user
```

Ensure the section is self-contained — the agent should be able to follow it without referencing external documents (though cross-references remain).

### 4. Update Artifact Generation Guidance

Update the "Artifact generation guidance" section and the "Outputs" section to describe:

- How override values should be injected into generated artifacts
- That branch naming in specs should use `session.overrides.epic_prefix` instead of hardcoded `epic/`
- That merge strategy instructions should use `session.overrides.merge_strategy`
- That branch strategy descriptions should use `session.overrides.branch_strategy`
- That Chat Starters should include the resolved override values in execution instructions

Also update the "Agent behavior rules" to include a rule about consulting overrides.

### 5. Update Startup Prompt Guidance

Add a note to the startup prompt section informing the user that override values from `.ai-project.yml` will be applied during planning.

### 6. Update the Outputs Checklist

Update the artifact generation checklist to include:
- Override values referenced in generated Phase/Milestone specs
- Override values referenced in Epic specs
- Override values referenced in Chat Starters

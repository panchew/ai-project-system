## What the framework got wrong (D3)

The record must carry the framework's own failures. Three are recorded, scoped in advance to say a
real defect is the stronger result.

### Finding F-1 — The fleet's billing posture blocks the *default* dispatch route

The configured `epic_manual`/fleet-baseline model `opencode/deepseek-v4-flash` (and its
`opencode-go` twin, which shares the same workspace key) is **unavailable for dispatch**: the
opencode workspace `wrk_01KY5BN877XBXX6YV4M3DS1K5Q` has reached its **$35 monthly spending limit**
(`MonthlyLimitError`). This is not a credential problem — the effective credential path resolved
(the engine authenticated) — it is a **billing/resource** block. The default dispatch route cannot
run the proof. **This is a real, fleet-level finding**: the model the fleet configures as its
manual/agentic baseline is out of budget, and the E47.2 readiness check (which verified the
`models:` block and lanes) could not have predicted a *billing* limit.

### Finding F-2 — The Anthropic credit balance is also exhausted

The alternate paid route `anthropic/claude-opus-5` was interrupted mid-run by **"Your credit
balance is too low to access the Anthropic API"** (`UnknownError`). It produced 60 tool rounds of
real work (4 decision records + partial baseline) before the model stopped being served, and never
committed. This is a second, independent budget limit — the fleet has no paid-frontier budget
headroom at this moment.

### Finding F-3 — The instrument's C-C2 backtick regex over-extracts on opencode-style final answers

The instrument was built for the `local-agent-runner` protocol, whose tool names are `read_file`,
`write_file`, `edit_file`, `list_dir`, `run_command`, `git`, and whose final answers cite
repository paths. The Drivr/opencode run used tool names `read`, `write`, `edit`, `bash`, `glob`,
`grep`, `todowrite`, and its final answer backtick-codes package names, MIME types, and branch
names. The instrument's C-C2 check extracts any backticked token shaped like a path, so it pulled
**`@types/node`, `@types/jsdom`, `application/json`, `text/html`, `epic/E1.1`** as "claims" — none
of which is a repository path, so all 8 came back unresolved.

This is **the opposite of the dangerous direction**. E39.3's failure was the instrument *missing* a
genuine false claim (the run cited a key the file did not contain and still printed PASS). Here the
instrument *falsely flags* benign backtick tokens on a genuinely working run. It is the same family
as M40's F5 recorded one level up, where *more* evidence yields a *worse* verdict, and the mirror
of `return FAIL`. Because C-C is not scored on `epic_dev`, the PASS verdict is still sound; but the
`4/12` C-C figure in the record would be misread as a claims problem if the tool-name/backtick
mismatch were not recorded. **Recorded, not fixed** — fixing the instrument is a follow-on, not
this epic's deliverable.

## What the run does NOT prove (D5)

One project, one epic, one engine. The claim is exactly as large as the evidence, and the record
says so:

1. **One project.** `panchew-io`, one baseline epic. Not the fleet, not the framework's generality.
2. **One epic.** P1-M1-E1.1, foundation decisions + working baseline. It does not prove that *any*
   epic can be carried — E1.1 is one real, bounded epic.
3. **One engine.** opencode via Drivr's OpenCode adapter, on `google/gemini-3.8-flash`. It does not
   prove the engine is generally reliable, or that other engines (or the fleet's baseline
   `deepseek-v4-flash`) would work.
4. **It does not prove the framework is defect-free.** Two budget limits (F-1, F-2) and one
   instrument over-extraction (F-3) were surfaced. The run succeeded *despite* the fleet's billing
   posture and *with* the instrument's C-C2 limitation.
5. **It does not prove E1.1 is *accepted*.** The run produced the E1.1 delivery; whether it is
   accepted is `panchew-io`'s parent Milestone Chat's decision, not this run's. This record proves
   the run *worked*, not that the delivery will be accepted.
6. **It does not prove the route's inherited defects are gone.** The `XDG_DATA_HOME` credential
   defect (E47.1's Z5 inheritance) is still inherited; it did not bite here because the effective
   path resolved, but the defect is un-fixed.
7. **"Suite green" in one repository is not verification in the other.** This run's work lives in
   `panchew-io` (and its `epic/E1.1` branch). The `ai-project-system` suite is not the run's
   verification; the run's verification is the instrument + the independently re-run checks.

# E45.1 Evidence Set — declared before it is run (D2, D4, D5)

**This is the evidence set the bar (`P12-M45-E45.1__bar.md`) is measured against. It is declared
here, before any measurement run, so the measured scores are evidence against a stated set — never a
set chosen to match a result.**

The signal under measurement is Drivr's completion judgment. The measurement is performed in Drivr at
pinned ref **`f15e239`** (see §7). Every case is a **live run** of the OpenCode engine, projected into
an `EvidenceRecord` by Drivr's own `from_execution_result`, and judged by Drivr's own
`judge_completion`. The `Reading` verdict is what is scored (Y3).

## 1. Declared case count

**Three cases.** Declared N = 3. Reported N must equal 3. A case that cannot be run is a **loud,
named failure** — the list is never silently shortened (E41.2 S3).

## 2. The cases

| # | Case | Live-run task (deliverable shape) | Ground truth | Expected `Reading` verdict | Scores correct |
|---|---|---|---|---|---|
| **C1** | **Read-only** (D4 — Y1 class) | A run that reads files and writes nothing (ledger entries carrying `Role.INSPECTION`; no effects; `files_changed=()`). | The run wrote nothing; the evidence that the deliverable exists is **absent**. | `reading = undetermined` | correct **only** under D5 (§4) |
| **C2** | **Flag** — negative control | A run that was asked to produce a deliverable and produced **no effects and no verification** (empty ledger; `files_changed=()`). | The work was **not performed**. | `reading = did-not-complete` | correct |

> **C2 dispatch (amended, v1.0.1).** The first C2 dispatch — an open implementation request, "Refactor
> `lib.py` to add `multiply` … apply the edit and a verification" — was run and the model **completed
> the work** (produced an effect and a verification; verdict `completed`). That run did not exercise
> the declared **no-effects** class, so its ground truth ("work not performed") does not hold for it,
> and it is not a valid negative control. The C2 dispatch is corrected to a form that reliably
> reproduces the class: **a request with a code deliverable that explicitly forbids mutating or
> verifying**, so the run answers in prose and produces no effects and no verification — a
> successful-nothing (the E33.2 Run A / E39.3 shape). **The ground truth ("did-not-complete") and the
> expected verdict are unchanged. The bar is unchanged.** The first C2 run and its non-conformance are
> reported in the measurement record, not silently discarded.
| **C3** | **Pass** — positive control | A run that produced work (**effect**) **and** a passing verification after it. | The work was performed **and** verified. | `reading = completed` | correct |

**Directionality is deliberate.** C2 is the negative control (the signal must still be able to say
"no"); C3 is the positive control (it must still be able to say "yes"); C1 is the class P12 is about
(read-only work — the signal must say "I don't know", not "failed"). A set with only C1 and C3 would
be satisfied by a signal that always answers `completed`; C2 makes that fail. A set with only C1
and C2 would be satisfied by a signal that collapses everything else to `undetermined`; C3 makes
that fail.

## 3. The degenerate baseline (D3)

The **degenerate baseline** is the strategy that always answers **`completed`**. Its score is a
property of the evidence set and the scoring rule, not a model: it answers `completed` on every case,
so its correct-count equals the number of cases whose expected verdict is `completed`.

On this set that is **C3 only**: the baseline's correct-count is **1 of 3**. (Recorded beside the
signal's measured count in the measurement record.) The bar's PC4 requires the signal's correct-count
to be **strictly greater** than the baseline's.

## 4. The `undetermined`-scores-correct rule (D5) — as applied

C1's evidence is **genuinely absent**: the run did honest read-only work (ledger shows `INSPECTION`
entries, nothing modified, nothing verified), and nothing in the record can decide whether the
task's deliverable exists. **So `undetermined` on C1 scores correct.** Undetermined is the honest
answer, not a miss.

The rule is bounded: `undetermined` is **not** correct on C2 (the work genuinely was not performed
— there is no inspection and no effect, so "I don't know" would be overclaiming) and **not** correct
on C3 (the evidence is present and complete). Penalising honest uncertainty would train the signal
to guess, which is the defect; extending `undetermined` past where evidence is absent would train it
to under-answer.

## 5. Layer (Y3)

The bar and this set score the **`Reading` layer**. `Completion` members are recorded but not scored.
`undetermined` refers to `Reading.UNDETERMINED`; there is no `Completion.UNDETERMINED`.

## 6. The measure of each case

For each case, the run's **`Reading` verdict** is compared to the **expected verdict**. Score 1 if
equal, 0 otherwise. The total correct-count is reported, **beside** the degenerate baseline's
correct-count, per the bar's PC4.

## 7. Dispatch path (design decision #4) and repository/ref (Hard Constraint)

- **Engine:** OpenCode (`1.18.10`), via Drivr's `OpenCodeAdapter` (`drivr/execution/opencode.py`).
- **Entry point:** `opencode run --model ollama/qwen3-coder:30b --format json --auto --dir <workdir> <task>`,
  invoked through the adapter's `execute(ExecutionRequest(...))`.
- **Model:** `ollama/qwen3-coder:30b` (Ollama endpoint `http://localhost:11434`, reachable; the
  model is in the host roster and responds on both `/api/generate` and `/v1/chat/completions`).
- **Environment:** **host** (`HostEnvironment`) — the adapter's container default was exercised but
  the host path is used for the measurement, stated as a deliberate decision (the container's
  loopback to the runtime was not reachable in this environment; the host path is lightweight for a
  measurement run and the `environment` field is recorded on every result). This is a stated tradeoff
  against the adapter default, not a silent substitution.
- **Working directory:** a dedicated scratch dir per case (host paths, read-write for C3, read-only
  intent for C1).
- **Measurement repository:** `~/soft-dev/drivr` at ref **`f15e239`**. The judgment modules
  (`completion.py`, `projections.py`, `evidence.py`) are unchanged from the planning ref `f60164c`
  (verified — see the measurement record), so the findings Y1–Y3, Y5 hold at `f15e239`. The live-run
  engine and the projection/judgment code are Drivr's; nothing here is measured in this repository's
  suite, which does not cover Drivr.

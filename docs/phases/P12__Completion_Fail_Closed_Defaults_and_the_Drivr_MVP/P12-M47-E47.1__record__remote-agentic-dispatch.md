## The route and Z5's inheritance (D2)

**Route chosen for the proof: Drivr's OpenCode adapter** — the binding-constraint route (*through
Drivr, never through `bin/`*). Model `opencode/deepseek-v4-flash`, host environment, one file-write
task.

**Why not `bin/run-dev-agent` → `local-agent-runner` (the rejected route):** that route inherits the
**unowned `<function=…>` parse defect** at `local_agent_runner/tool_calls.py:171` — a defect in a
**third repository**, reachable by neither M42 nor M47, and the defect that **produced DEV RUN 2**
(exit 0, 4.2 s, stub byte-identical, six tools advertised) — one of the three recorded cases M47's
criterion exists to reject. A route carrying it would manufacture exactly the false success the
milestone is designed to catch. **Grounds to reject that route for the proof.**

**What the chosen route carries — the `XDG_DATA_HOME` credential defect, located with a stated
repair (Z5):** the Drivr adapter materialises its **own copy** of the config (`build_config`) and
points the engine at it with `XDG_CONFIG_HOME` (`opencode.py:263`), but **never sets
`XDG_DATA_HOME`** (`environments.py` merges into `os.environ`), so the engine's credential store
resolution **inherits** whatever the launching shell has. A confined `XDG_DATA_HOME` (the snap
shell, `~/snap/code/258/.local/share`) reports **every** remote target unreachable at once — the
failure shape this epic must distinguish from a fleet outage. **Inherited, with the recorded
workaround for the proof:** the dispatch ran from a shell with `XDG_DATA_HOME` unset, so the engine
resolved the real store (`~/.local/share/opencode/auth.json`, present, credentials NOT-READ by
policy), and the dispatch authenticated and ran. The repair (set/verify `XDG_DATA_HOME` in the
adapter) is **stated, not applied** — fixing the defect is out of scope (Non-Goals), and the record
of the effective path is what lets a reader tell *"the engine had zero credentials"* from *"every
engine is down."*

## The loop claim, separated from the transport claim (D5)

- **Transport claim (inherited from M41):** a packet reaches a remote engine, is answered, and the
  text is scored. E35.5/E41.4's back-test is single-turn and tool-free.
- **Loop claim (the whole point, never before run):** a remote engine **makes tool calls, they
  execute, and it iterates.** This dispatch evidences the loop with its own structure:

| Event | What it shows |
|---|---|
| `step_start` → `tool_use` (`write`, status `completed`, input `{filePath, content}`) | the engine **called a tool** |
| `step_finish` (`reason: tool-calls`) | the loop **iterated** on the result |
| `step_start` → `tool_use` (`read`, status `completed`) | a **second** tool call — iteration |
| `step_finish` → `text` → `step_finish` (`reason: stop`) | the loop **terminated** with an answer |

`files_changed: ["dispatch-proof.txt"]`; the file exists with the exact requested contents,
independent of the engine's self-report (verified on disk, sha256
`ebcac74f7f8af95d8248ef0dfbbdf7dee4d041cb8c006ea85cbbb1eced8dd24c`).

**A transport success is not being read as a loop success.** The loop claim rests on the `tool_use`
events and the changed file — *what the run did* — not on the exit code. The exit code is recorded
(`0`) and not relied on (Hard Constraint: E33.2 Run A exited 0 having done nothing).

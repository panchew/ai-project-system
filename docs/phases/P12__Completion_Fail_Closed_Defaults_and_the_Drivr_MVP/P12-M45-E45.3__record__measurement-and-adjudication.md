## 1. Both directions measured (D1)

### Direction A — a blocked run reported as running (the missing-Delivery-Notice form)

**The claim:** a child that never produces its Delivery Notice is indistinguishable from one still
working; the parent waits forever on a delivery that is not coming.

**How measured:** **code-read + constructed-record** (a replay-level demonstration of the data
model; **not** a live run — see Y4 note at §0). You cannot live-run the *absence* of a detector; the
absence is structural, and it is readable from the code.

**The record shape, measured:**

1. The scheduler writes **one `DispatchRecord` per *finished* run.** `run_once()` (scheduler.py:259)
   → `_dispatch()` → `_completed()`/`_failed()` → returns a record → `journal.append(record)`
   (scheduler.py:274). `_dispatch` returns only when the adapter's `execute` returns.
2. **A run that is claimed but never finishes writes NO record.** `_dispatch` never returns, so
   `run_once` never returns and nothing is appended. The job's JSON file sits in `claimed/` forever —
   demonstrated by `JobQueue`: `enqueue()` → `pending/`; `claim_next()` renames to `claimed/`;
   `complete()` renames to `done/`. **Nothing ages `claimed/`** — no code reads a claimed job's age,
   the absence of a finished record, or elapsed time since `dispatched_at`. (Constructed run:
   `job-stuck.json` sat in `claimed/` with `pending/` and `done/` empty.)
3. **A run that finishes but reports nothing usable** — the ordinary no-effect/read-only outcome —
   writes a record with `disposition=undetermined`. But the **undetermined policy** is: *"A job that
   ends UNDETERMINED is journalled and the lane moves on. No escalation, no retry, no blocking."*
   (scheduler.py:28, verbatim). So even a finished-undetermined run is not surfaced to any parent;
   the journal is append-only and nobody watches it for this.

**Consequence (the fail-open default):** at the scheduler layer there is **no rule** that reads a
missing finished record, the absence of a Delivery Notice, or elapsed time since dispatch, to
conclude "this is a missing delivery." **Absence of a finished record reads as "still in flight."**
That is precisely the fail-open disposition the phase's thesis predicts — *when the evidence that
should gate an answer is absent, the system answers anyway* (SN-31 row / P10-GH-7).

**P10-GH-7 evidence this rests on (cited, not re-run):** E33.2 Run A returned exit 0 having done zero
work (chat-hierarchy.md:725-726) — the false-success/exit-code instance of the family. That is a
**recorded live** measurement; here it is cited as the family's shape, not re-discovered.

### Direction B — a running run reported as blocked (the exit-code / false-failure form)

**The claim:** the exit code is measured-unreliable, so a run doing slow-but-real work that trips the
wall-clock ceiling (or a run with green work and a bad exit code) reads as failed — a handback
mechanism built over it yields **constant false escalations**.

**How measured:** **cited + constructed-record.**

1. **Cited live evidence** (the P10-GH-7 record, chat-hierarchy.md:727): *"P10-M33-E33.4 returned
   exit 2 having produced complete, green work."* This is a recorded **live** measurement from P10;
   here it is cited, not re-run (I can neither deterministically reproduce E33.4's exact run nor
   cheaply produce a live ceiling-tripping run — both are named, not substituted).
2. **The record shape (constructed):** `interface.py:146-147` — `exit_code` is *"the process exit
   code, or `None` if it was killed by timeout. **Known untrustworthy in both directions.**"* A
   run with green work and exit 2 records `exit_code=2` (constructed B2:
   `disposition=done`, `completion=effects-verified`, `rule=covering-verification`, `exit_code=2`). A
   run tripping the ceiling records `timed_out=True`, `exit_code=None` (constructed B1). An
   `ExecutionResult` deliberately has **no** success/verdict field — `COMPLETION_VERDICT_FIELD_NAMES`
   (interface.py:55-70) is enforced by the suite, so no component in the reporting layer can
   accidentally turn the exit code into a verdict.
3. **The judgment does not read these.** `_decide`'s parameter list is exactly `["ledger",
   "files_changed"]` (completion.py:336-346, pinned by `tests/test_judgment_independence.py`); exit
   code / status / final answer are recorded as `Disposition.IGNORED` with the P10-GH-7 reason
   (completion.py:236-245, 336-354). So the *completion signal* is not itself falsely reporting these
   as blocked.

**Consequence:** a **block detector built naively over this signal** — reading `exit_code`,
`timed_out`, or a termination-reason-as-alarm — would flag E33.4's green work as blocked (exit 2) and
a slow-but-real run that trips the ceiling as blocked (`timed_out`). That is the design attractor
P10-GH-7 names: *"A handback mechanism built naively over this signal yields constant false
escalations"* (chat-hierarchy.md:735-737). The record already has enough signal to know **not** to do
this; the judgment already refuses to.

### Net measurement (both directions, adjudicated)

- **Direction A — CONFIRMED, and it is the live gap.** A blocked run (claimed but never finished) and
  a run still in flight leave the **same record shape**: no finished record, nothing ages it. A
  finished-undetermined run is journalled and the lane moves on with no flag. **Absence reads as
  "in progress."**
- **Direction B — CONFIRMED, but re-scoped.** The exit code is measured-unreliable in both directions
  (cited live evidence), and a naive detector over it would over-flag. **The current completion signal
  already refuses to read it** — so this direction is *not* an active false report today; it is a
  **constraint on the future detector** (Boundary Constraint 5, which refuses it in advance).

## 2. The missing-Delivery-Notice branch (D2)

**Current behaviour (the fail-open default):** absence reads as "still working."

**Defined behaviour:** absence is an **`undetermined`** state, never an assumed state, never a
silently-assumed `in progress` and never an over-claimed `blocked`.

**What marks the point at which a delivery that has not arrived is `undetermined` rather than
`pending`:**

- a **record exists** that the job was claimed and dispatched — `DispatchRecord` carries
  `enqueued_at` and `dispatched_at` (scheduler.py:120-122) — **and**
- **no finished record / no Delivery Notice** has arrived, **and**
- **elapsed wall-clock since `dispatched_at`** exceeds the job's own window. The natural declared
  ceiling is the job's `timeout_s` (`Job.timeout_s`, scheduler.py:90); where a run ended
  `UNDETERMINED` (a record exists but with no usable parental disposition), the same window since
  `finished_at` with no parent-visible notice is the trigger.

**Which signal the block detector must ultimately read (stated for M46/later — Not built here,
delegated decision #4):**

1. **Elapsed time since dispatch** (the dispatch-record timestamps) — the strongest and the one that
   is already recorded and attributable to the scheduler. Required to distinguish "still working"
   (young dispatch, no record) from "missing delivery" (old dispatch, no finished record).
2. **Dispatch-record presence/absence** — a job that was claimed (`claimed/`) but produced no
   finished record.
3. **An absent declared artifact** — a Delivery Notice (or equivalent expected artifact) that was
   declared but is not present.
4. **NOT** `exit_code`, **NOT** `timed_out` as a term. Refused in advance (Binding Constraint 5,
   measured-unreliable in both directions). `timed_out` may be reported *advisory*; it is **never a
   term in a rule**.

**What the branch is NOT:** not "still working" (the fail-open default) — a delivery absent past its
window is `undetermined`; and not "blocked" without more evidence — `blocked` requires a positive
surfaced signal (e.g. an escalation notice), not weight absence.

**Where it is recorded (repository and artifact):** the **definition** is recorded in this record
artifact and in the **re-rated P10-GH-7 statement** (see D3) in
`governance/systems/chat-hierarchy.md` — both in **ai-project-system**, branch
`epic/P12-M45-E45.3`. Whether and how Drivr's detector implements it is **M46/later**, not built
here (Non-Goal: building the block detector is M46's; E45.3 measures and adjudicates). The
consumer-contract side of the same boundary (`outcome.py`) is **E45.4's**, which inherits D4.

## 3. The interaction with E45.2 (D4)

**Written against post-E45.2 behaviour** (a read-only run is no longer `DID_NOT_COMPLETE`; E45.2
landed at Drivr `17aef91`).

**Can the completion signal distinguish "blocked" from "read-only" from effects alone? No — and it
does not need to, because they differ in a coarser, decisive way.**

- A **read-only run** (E45.2's subject) **produces a judged record**: `_decide` →
  `Completion.INSPECTED_NO_EFFECTS` (completion.py:117, 413-431) → `Verdict.reading()` →
  `Reading.UNDETERMINED` (completion.py:185-191). At the consumer layer, `disposition()` now reads it
  as `Disposition.UNDETERMINED` (per E45.2's delivery notice: the §F5 branch keyed to
  `NO_EFFECTS_OBSERVED` no longer fires, so `read_only_completion` is unset and it reads
  `UNDETERMINED` rather than `DONE` until E45.4 re-keys it). **So a read-only run lands at
  `undetermined` with inspection evidence behind the record.**
- A **blocked run** (claimed but never finishes / never delivers) **produces NO record**, no
  `Verdict`, no `Reading`, no `Disposition`. It is indistinguishable from a run still in flight
  (Direction A).

**The distinguishing signal is therefore the presence/absence of a judged record, plus elapsed time
since dispatch** — precisely the signal D2 names. Effects alone cannot distinguish them; the **record
existence + dispatch-age** can.

**If the two fixes could disagree about the same run, which governs?** Consider the narrow overlap: a
run that is **read-only AND** its delivery is missing.

- At the **judgment/record** layer, the run **did** produce a judged record (`INSPECTED_NO_EFFECTS`,
  `undetermined`), so there is evidence and **E45.2 governs the verdict: `undetermined`.**
- At the **delivery/scheduler** layer, because a judged record exists, this is **not** the
  missing-delivery absence case — D2 applies only where **no finished record / no Delivery Notice**
  exists. A record exists here, so the run is judged on its record.
- The two are therefore **disjoint by the record's presence**: a run that produced a record is judged
  on it (E45.2); a run that produced no record is the missing-delivery case (D2). They do **not**
  collide, and neither folds `undetermined` into "working" or `blocked`. Where a record exists but
  **no parent-visible notice** arrives, **E45.2 governs the verdict** (`undetermined`) and **D2
  governs the accounting** (an undetermined judgment with no arriving notice is a fragility flag for
  M46's detector, not an assumed success and not a block).

Per the Phase Chat's Set-3 ruling, **E45.4 inherits this D4** and applies it in `outcome.py` (the
consumer contract). This epic is fenced off from `outcome.py`.

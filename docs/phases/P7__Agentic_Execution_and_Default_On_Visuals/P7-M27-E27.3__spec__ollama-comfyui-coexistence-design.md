# Epic E27.3 — Ollama+ComfyUI coexistence design

## Context

M26 achieved the system's first real, non-mocked agentic run: `bin/run-dev-agent` invokes
`local-agent-runner` against a live Ollama endpoint (confirmed in E26.3's run record — a genuine
`llama-server` process, 12.6s-74.8s per invocation). E27.1+E27.2 (both merged to `milestone/M27`:
`dcfc9b6`, `e1ccd13`) made structural-first, default-on visual production the norm; generative
visual production via ComfyUI remains available whenever a project configures `comfyui_url`. Both
paths — live agentic execution (Ollama) and generative visual production (ComfyUI) — can now run
on the same host, and SN-18 placed the design of their GPU coexistence inside this milestone
rather than deferring it, because the contention only bites once generative visuals actually run
concurrently with a live epic execution.

> **Provenance:** Authored by the Milestone Chat (P7-M27) on 2026-07-13, after E27.1/E27.2 merged.
> E27.3 is independent of E27.1/E27.2 (different files, no AOG §17 contention) and could have run
> in parallel with either — sequenced last here only because the Milestone Chat processes one
> Epic's deliverables at a time (milestone starter's own execution instruction), not because of a
> real dependency.

> **Source:** M27 Milestone spec (Epic Detail → E27.3); P7 phase spec P7.2 coexistence task;
> SN-18 decision 4; HQ ruling 2026-07-11 (infra note).

**Grounding (verified 2026-07-13):**

- `~/soft-dev/ai-stack/docker-compose.yml` (read in full) — confirms the milestone spec's finding
  exactly: `ollama` (port 11434) and `comfyui` (port 8188) are separate services, **each** with a
  `deploy.resources.reservations.devices: [{driver: nvidia, count: all, capabilities: [gpu]}]`
  block and **no** `deploy.resources.limits`, no `NVIDIA_VISIBLE_DEVICES` restriction, and no MPS/
  MIG partitioning. Docker's `count: all` makes the entire GPU visible to both containers; it does
  not sub-allocate VRAM. **Both services are also `restart: unless-stopped`** — a detail beyond
  what the milestone spec quoted: they are not started on-demand, they come up together on host
  boot and stay up, so the contention window is "whenever both happen to receive concurrent
  requests," not "whenever the CFO chooses to run both." This is a further reason a software-side
  guardrail (Scope item 2) is worth more than documentation alone.
- **A concrete, already-existing, zero-new-infrastructure hook was found during grounding, not
  named in the milestone spec:** `bin/ai-project-orchestrator` already implements a PID-based
  execution lock at `.ai-project/locks/execution.lock` (`LOCK_FILE`, defined line 13). It is
  written with the orchestrator's PID immediately before `handle_epic_execution(...)` is called
  (line 770-778, on receiving an Epic trigger) and removed in the `finally` block once that call
  returns (line 779-781) — meaning **the lock file's existence, with a live PID, is a reliable
  signal that a live agentic epic execution (and therefore live Ollama inference) is currently in
  flight**, for the exact duration GPU contention would matter. Stale-lock recovery (dead-PID
  detection via `os.kill(pid, 0)`, lines 722-733) is already implemented and correct — a design
  reused here, not rebuilt.
- `bin/ai-project-visual` (read in full, 257 lines) — the ComfyUI generative helper. Already
  defines an exit-code convention (`EXIT_OK=0`, `EXIT_DISABLED=2`, `EXIT_CONFIG=3`,
  `EXIT_RUNTIME=4`, lines 47-50) and already loads `bin/ai-project-orchestrator` as a sibling
  module via `load_orchestrator()` (line 62) to reuse its config source — the same pattern this
  Epic's guardrail reuses to check `LOCK_FILE`, rather than re-implementing PID-liveness detection.
- **This repo's own generative path is currently inert** (E27.1 finding, carried forward): the
  source repo's `.ai-project.yml` keeps `visual_artifacts.enabled: false`, so no live ComfyUI call
  happens in this repo's own CI/test path today. The guardrail this Epic adds is exercised by unit
  tests against a stubbed lock file, not a live GPU — consistent with the rest of this milestone's
  test discipline.
- **HQ ruling infra note** (2026-07-11): "`~/soft-dev/ai-stack` runs Ollama+ComfyUI on one 16 GB
  GPU with known RAM contention" — the design this Epic produces is the first concrete response to
  that standing note.

## Problem Statement

Two GPU-hungry services share one card with no coordination: `docker-compose.yml`'s `count: all`
reservations let both `ollama` and `comfyui` claim the entire GPU simultaneously, and both restart
automatically on host boot, so the contention window is not something the CFO opts into — it exists
by default whenever both happen to receive concurrent requests. Left undesigned, a generative
visual-production call could compete with a live agentic epic execution for VRAM, risking an OOM or
degraded inference on whichever workload loses the race — exactly when the framework most needs
both to be reliable (an Epic Chat's live run and a Milestone/Phase Chat producing its default-on
spec visual could, in principle, overlap).

---

## Goals

By the end of this Epic:

1. **A documented GPU/VRAM coexistence design exists**, naming the confirmed `count: all`/
   no-partitioning contention and stating the chosen approach (scheduling policy, guardrail, and/or
   infra-level option), with clear reasoning for what was chosen and what was left to the CFO.
2. **A software-side scheduling guardrail is implemented in this repo**: `bin/ai-project-visual`
   checks `.ai-project/locks/execution.lock` before issuing a generative (ComfyUI) request and
   refuses cleanly with a new exit code + a clear stderr message when a live agentic epic execution
   is in flight — reusing the orchestrator's existing PID-liveness logic, not duplicating it.
3. **`~/soft-dev/ai-stack/docker-compose.yml` is not modified** unless the design finds the
   guardrail alone insufficient and the CFO explicitly directs a config change (Non-Goal, milestone
   spec) — infra-level partitioning options (MPS/MIG, `deploy.resources.limits`, manual sequencing)
   are documented as CFO-owned choices, not implemented here.
4. **The guardrail is tested** against a stubbed lock file (live PID present vs. stale/absent), no
   live GPU or live ComfyUI endpoint required.
5. **The design states plainly what remains the CFO's infrastructure responsibility** (standing up
   and partitioning the GPU/host) **versus what the framework now encodes** (the in-repo guardrail).

## Scope of Work

### 1. Documented coexistence design

Write the design (placement is this Epic's call — recommended: a new guide,
`governance/guides/gpu-coexistence.md`, cross-linked from `visual-artifacts.md`'s "Related
documents" table with one new row, since the topic is infrastructure-adjacent rather than
visual-artifacts-usage-adjacent and the guide is already long at 9 sections; a section appended to
`visual-artifacts.md` is an acceptable alternative if the Coding Agent judges the split not worth a
new file — decide and document either way). The design must:

- Name the confirmed contention (`count: all` GPU reservations on both services, `restart:
  unless-stopped` on both, no partitioning) with the exact `docker-compose.yml` evidence.
- State the chosen approach: the in-repo software guardrail (Scope item 2) as the primary,
  zero-infra-change mitigation; infra-level options (MPS/MIG partitioning, `deploy.resources.limits`,
  running the services on a schedule) documented as CFO-owned choices, not mandated.
- State plainly what the framework now encodes (the guardrail) versus what remains the CFO's
  infrastructure responsibility (the GPU, the host, `~/soft-dev/ai-stack` itself).

### 2. Software-side scheduling guardrail (`bin/ai-project-visual`)

Before a generative (non-`diagrams`-structural — see the `bin/ai-project-visual --type diagrams`
naming note in Grounding; this Epic's guardrail applies to the helper's actual generative call
path, not a re-litigation of that naming question) ComfyUI request executes, check whether
`.ai-project/locks/execution.lock` exists **and** the PID it names is alive (reuse the
orchestrator's existing `os.kill(pid, 0)` liveness check — via `load_orchestrator()`, already used
for config loading, or a small shared helper factored out of `bin/ai-project-orchestrator` if that
proves cleaner; the Epic's call). If locked, refuse cleanly: print a one-line stderr message naming
the contention (a live agentic epic execution is in progress; GPU shared; generative deferred) and
exit with a **new** exit code (recommended: `5`, next available after the existing 0/2/3/4 set —
document the choice and update the helper's docstring + `visual-artifacts.md`'s exit-code table).

**Must include:**
- The lock check, reusing existing PID-liveness logic (no duplicated implementation)
- A new exit code (recommended `5`) with a clear, documented meaning
- The helper's docstring and `visual-artifacts.md`'s exit-code table (§3, per the guide's current
  numbering — verify it is still §3 at execution time) updated to document it
- **Stale-lock handling matches the orchestrator's own**: a dead PID must not block generation —
  reuse, don't reinvent, the orchestrator's stale-lock recovery

### 3. Tests

Cover the guardrail with a stubbed lock file — no live GPU, no live ComfyUI endpoint required:

- Lock file absent ⇒ generative call proceeds (subject to existing config/endpoint checks)
- Lock file present with a live PID (the test's own PID, or a spawned dummy process) ⇒ refused,
  new exit code, clear message
- Lock file present with a dead PID (stale lock) ⇒ generative call proceeds, does not falsely block
- Existing exit-code tests (0/2/3/4) remain green — the new check must not interfere with the
  disabled/config/runtime paths

  process's own PID or a short-lived spawned subprocess, not a real generative call.

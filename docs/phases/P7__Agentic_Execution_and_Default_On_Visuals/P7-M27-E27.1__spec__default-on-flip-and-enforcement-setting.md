# Epic E27.1 — Default-on flip + enforcement setting

## Context

M26 (First Real Agentic Run) is fully consolidated to `phase/P7`. M27 is the second milestone of
P7 and is independent of M26's agentic-execution surface: it flips visual-artifact production
from the opt-in capability shipped in P5/P6 (AOG §16, yml-spec §3.5) to the CFO's default lens on
an increasingly autonomous system, per SN-17 (ratified by SN-18, the P7 spine). E27.1 is the first
of two coupled epics (with E27.2) that together satisfy the milestone's headline acceptance
criterion; E27.1 owns the **on/off default** — whether the capability is active at all when a
project says nothing — and the **enforcement setting**. E27.2 owns what *kind* of visual gets
produced once the capability is on (structural-first) and *which* artifact types trigger it
automatically.

> Coding Agent implements it. E27.1 and E27.2 may be planned/executed in either order but both
> edit AOG §16 — serialize them or use a worktree (GH-2); E27.3 is independent and may run in
> parallel with either.

> **Source:** M27 Milestone spec (Epic Detail → E27.1); P7 phase spec P7.2 decisions 1 & 4;

## Problem Statement

The visual-artifacts framework was built and shipped opt-in/off-by-default — correct for its own
P5/P6 milestone, but the wrong default for P7's stated goal (visuals as the CFO's default lens on
an increasingly autonomous system). Four surfaces assert the old default in prose or code (AOG
§16.1, yml-spec §3.5, the orchestrator's `DEFAULT_VISUAL_ARTIFACTS`/`resolve_visual_artifacts`,
and `visual-artifacts.md`'s opening line), and no enforcement mechanism exists to make "on by
default" mean anything beyond a config value nobody is required to honor. Until this Epic ships,
every fresh project silently gets zero visuals, and there is no setting to require them.

---

## Goals

By the end of this Epic:

1. **AOG §16.1 reads default-on/opt-out.** `enabled: false` is the explicit way to turn the
   capability off; an absent block resolves to on.
2. **`ai-project-yml-spec.md` §3.5 documents `enabled`'s default as `true`** — table row, Field
   Details sub-table, and prose all consistent.
3. **`resolve_visual_artifacts()` resolves an absent/empty block to `enabled: True`**, while an
   explicit `enabled: false` in a provided block still disables — `DEFAULT_VISUAL_ARTIFACTS`'s own
   `"enabled"` value becomes `True` and the line-144 hardcoded override is removed (the merge loop
   that already runs beneath it is sufficient once the default itself is `True`).
4. **A new enforcement-setting key exists**, defaulted `true`, schema-defined, validated, resolved,
   and documented — governing whether specs and delivery/closure declarations are *required* to
   carry a visual (E27.2 defines what "carry a visual" resolves to structurally; this Epic only
   ships the setting).
5. **Every surface asserting the old default is reconciled or confirmed unaffected**, with the
   confirmation on record — `visual-artifacts.md`, the two directly-affected test modules,
   `.ai-project.yml`'s own decision documented, and AOG §16.5's source-repo sentence reconciled if
   that decision changes the file.
6. **All rewritten tests assert the new behavior** (not deleted) and the full suite passes.

---

## Non-Goals

This Epic explicitly does **not**:

- **Define structural-vs-generative trigger behavior or the automatic trigger set** — that is
  E27.2. E27.1 only flips whether the capability is active by default; it does not decide *what*
  gets produced automatically once it is.
- **Rebuild AOG §16.3/§16.4 machinery** (structural/generative modes, tool-capability gating) —
  untouched, already correct.
- **Design the Ollama+ComfyUI coexistence approach** — E27.3.
- **Add per-artifact-type enforcement keys** unless a real need surfaces during execution — the
  recommended default is the single `visual_required_for_specs` key (Open Design Question C).
- **Touch M26's agentic-execution surface or M28's governance-reconciliation surfaces.**

## Execution Notes

- **Start with the code flip and its tests** (`bin/ai-project-orchestrator` + `test_visual_artifacts_config.py`)
  to lock the behavioral contract before touching prose — the governance rewrites (AOG, yml-spec,
  the guide) describe what the code now does, not the reverse.
- **The line-144 override is the crux.** `resolve_visual_artifacts()` currently sets
  `resolved["enabled"] = False` unconditionally before merging the provided block. Once
  `DEFAULT_VISUAL_ARTIFACTS["enabled"]` is `True`, deleting that line lets the existing merge loop
  (lines 145-148: `for key in DEFAULT_VISUAL_ARTIFACTS: if key in va and va[key] is not None:
  resolved[key] = va[key]`) do the right thing unmodified — an absent block never enters the loop
  and keeps the `True` default; a provided block with `enabled: false` overrides it explicitly.
  Verify this by running the rewritten tests, don't assume it from reading the code.
- **Resolve Open Design Question C here, non-blocking:** name the enforcement key
  `visual_required_for_specs` (recommended default) unless execution surfaces a concrete need for
  per-type keys — do not over-engineer preemptively. Document the choice in the Delivery Notice.
- **The source-repo `.ai-project.yml` decision is yours to make and document** (Scope item 6) —
  decide, document the reasoning, and follow through into the dependent test and the AOG §16.5
  sentence if the file changes. Escalate to the Phase Chat only if genuinely blocked, not to
  outsource the decision.
- Default-accept (PSG §11.6 / AOG §12) governs this Epic's own delivery: a clean delivery is
  accepted by silence; the epic-PR merge is human-authorized in-chat (SN-19); a Review Decision is
  the exception path only.

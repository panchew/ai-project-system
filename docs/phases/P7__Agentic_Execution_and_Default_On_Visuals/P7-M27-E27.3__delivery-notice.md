# Epic Delivery Notice — E27.3

## Execution Summary

Produced a documented GPU/VRAM coexistence design for the confirmed Ollama+ComfyUI single-GPU
contention and implemented the primary mitigation as an in-repo software guardrail.

**Design doc placement:** a new guide, `governance/guides/gpu-coexistence.md` (the spec's
recommended option) — kept `visual-artifacts.md` from growing further and gave the coexistence
topic its own citable, infrastructure-adjacent home. Cross-linked from `visual-artifacts.md`'s
"Related documents" table (one new row) and its §3 exit-code table (new row for code `5`).

**Guardrail implementation:** `bin/ai-project-visual` now checks
`.ai-project/locks/execution.lock` immediately before the workflow-build step and the generative
network call, and refuses cleanly with **exit code `5`** (the recommended next-available code
after 0/2/3/4) when a live agentic epic execution holds it.

**Reuse mechanism (Design point 3):** neither `load_orchestrator()` alone nor a new helper
factored out of `bin/ai-project-orchestrator` was used, because the Technical Constraints forbid
touching the orchestrator's execution-lock logic at all (read/reuse, don't modify) — and its
PID-liveness check is inline in `main()`, not a standalone function, so it could not be imported
without editing that file. Grounding turned up a better fit not named in the milestone spec:
`bin/ai-project-daemon` already has exactly the needed read-only primitives,
`check_pid_alive(pid)` and `check_execution_locked()` (`bin/ai-project-daemon:93-106,204-218`),
factored out there for the daemon's own "defer queue processing while an epic is running"
behavior — identical `os.kill(pid, 0)` semantics, no new implementation. The guardrail loads
`bin/ai-project-daemon` the same way the helper already loads `bin/ai-project-orchestrator`
(new `load_daemon()`, mirroring `load_orchestrator()`'s `SourceFileLoader` pattern), then points
the daemon module's `EXECUTION_LOCK` global at the orchestrator module's own `LOCK_FILE`
(`daemon.EXECUTION_LOCK = orch.LOCK_FILE`) before calling `check_execution_locked()`. This
override matters: the orchestrator resolves its lock path from the current working directory (the
project actually being executed against), while the daemon module's own default resolves from its
*file location* — correct for daemon's typical `--project-root`-driven invocation, but not
guaranteed to coincide with the helper's cwd in a vendored layout. Pointing the daemon's check at
the orchestrator's already-correct path avoids checking a different — possibly wrong — lock file.
Neither `bin/ai-project-orchestrator` nor `bin/ai-project-daemon` was modified.

**Stale-lock handling** matches the orchestrator's own: `check_execution_locked()` returns
`False` for a dead PID (the `ESRCH` branch of `check_pid_alive`), so a stale lock never blocks
generation — verified by a dedicated test.

## Notes

**Design-doc placement:** new guide (`governance/guides/gpu-coexistence.md`), per the spec's
recommendation — the topic is infrastructure-adjacent rather than visual-artifacts-usage-adjacent,
and `visual-artifacts.md` was already at 9 sections.

**Exit code chosen:** `5` (next available after 0/2/3/4), documented in the helper's docstring and
both the guide's and `visual-artifacts.md`'s exit-code references.

**PID-liveness reuse mechanism:** `bin/ai-project-daemon`'s existing `check_execution_locked()` /
`check_pid_alive()`, loaded via a new `load_daemon()` mirroring the existing `load_orchestrator()`
pattern, pointed at the orchestrator's own resolved `LOCK_FILE` via a one-line global override.
Chosen over factoring a new helper out of the orchestrator because the Technical Constraints
forbid modifying the orchestrator's execution-lock logic, and over reimplementing the check
because that would duplicate `os.kill(pid, 0)` semantics the spec explicitly prohibits.

**Follow-up finding (out of this Epic's scope, flagged for the Milestone Chat):**
`bin/ai-project-orchestrator --test`'s embedded unittest suite (invoked directly, separate from
the pytest suite this Epic's DoD tracks) has 2 pre-existing failures —
`test_visual_artifacts_absent_is_disabled` and `test_visual_artifacts_absent_block_is_disabled` —
both asserting the pre-E27.1 default (`enabled: False` when the block/file is absent). These
predate this Epic (confirmed via `git stash` against this branch's base) and appear to be stale
assertions left behind by E27.1's default-on flip (`DEFAULT_VISUAL_ARTIFACTS["enabled"]` is now
`True`). Not fixed here: `bin/ai-project-orchestrator` is out of this Epic's file scope (Technical
Constraints), and the fix belongs to whichever Epic owns E27.1's surfaces. The pytest suite this
Epic's own DoD tracks (`tests/`) is unaffected and green at 306/1.

No deviation from the spec's scope, goals, or non-goals. `~/soft-dev/ai-stack` was not touched.

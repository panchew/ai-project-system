## What Was Found

Two adequacy gaps surfaced while verifying host-side prerequisites and tracing the
concrete execution path this Epic is instructed to "pick," both rooted in
E26.1/E26.2 surfaces this Epic's Technical Constraints forbid touching.

**1. The documented Docker-sandbox route cannot reach a real, live run.**

The example trigger's `"sandbox_env": "alpine:latest"` sends execution through
`run_in_sandbox()` in `bin/ai-project-orchestrator` (~line 270). Tracing it:

- Bare `alpine:latest` has no `python3`, so `bin/run-dev-agent`'s shebang
  (`#!/usr/bin/env python3`) cannot execute inside the container at all.
- `run_in_sandbox()`'s `docker_cmd` (~line 277) only forwards
  `-e AI_PROJECT_ACTIVE_MODEL=...` into the container. It never forwards
  `LOCAL_AGENT_RUNNER` or `AI_PROJECT_OLLAMA_ENDPOINT`, and it sets no `--network`
  flag. On this host, Ollama itself runs in a sibling Docker container
  (`ollama/ollama:latest`, port-mapped to `0.0.0.0:11434` on the host) — from inside
  the sandbox container, `localhost:11434` (the runner's hardcoded default endpoint)
  refers to the sandbox container itself, not the host or the Ollama container. There
  is no way to reach the real endpoint without adding network configuration and env
  passthrough to `run_in_sandbox()`.
- Both gaps live inside `bin/ai-project-orchestrator`, which E26.3's Technical
  Constraints list as a frozen E26.1/E26.2 surface ("No changes to ... if any of these
  is inadequate for the real run, that's a blocker to escalate, not a workaround to
  patch here").
- A workaround exists that requires no file changes: the orchestrator's
  `run_in_sandbox()` already has a local-execution fallback (~line 301) that fires
  when its own `subprocess.run(["docker", ...])` call raises `FileNotFoundError`. That
  fallback correctly inherits the invoking environment (so `LOCAL_AGENT_RUNNER` and
  the default `localhost:11434` endpoint both work). Triggering it deliberately means
  invoking the orchestrator with a curated `PATH` that omits `docker` while still
  resolving `git`/`python3`. This is an invocation-time environment choice, not a
  change to any frozen file — but it means the run would exercise the local-fallback
  route instead of the sandboxed route the example trigger names, which is worth
  Milestone Chat sign-off before use.

**2. `.ai-project/agents/tools.json` has no mechanism to set a file's executable bit.**

The proving vehicle's already-resolved design (Open Design Question A) requires the
model to produce "an executable script," and the proving-vehicle test is specified to
assert exactly that (`os.access(..., os.X_OK)`-style check). Tracing the coding tool
set the model is actually permitted to use:

- `tools.json`'s `enabled` list: `read_file`, `write_file`, `edit_file`, `list_dir`,
  `run_command`, `git`.
- `write_file` (`local_agent_runner/tools.py:506`, `_write_file`) creates files via
  `Path.write_text()`, which never sets execute bits (new files get `rw-`, no `x`,
  regardless of umask).
- `run_command`'s `allow_commands` is `["pytest*", "python -m pytest*",
  "python3 -m pytest*"]` — no `chmod` (or any non-pytest command) is permitted.
- `git`'s `allow_subcommands` is `status, diff, log, show, add, commit, branch,
  checkout` — none of these sets filesystem permission bits.
- Net result: under the current, frozen tool permissions, there is no tool call
  available to the model that can make a file it writes executable. Barring something
  missed in this trace, the proving vehicle would fail its Definition of Done
  regardless of the correctness of the model's script content, exhausting all 3
  Dev-QA retries for a reason unrelated to the coding task itself.

## Resolution

**Milestone Chat decision (2026-07-12).** Both findings independently re-verified (re-read
`run_in_sandbox()`'s `docker_cmd` construction and `local-agent-runner/local_agent_runner/
tools.py`'s `_write_file`/`run_command`/`git` implementations against `.ai-project/agents/
tools.json`'s permission lists) before ruling — both are confirmed structural, not local
misconfiguration.

**1. Execution route — Option authorized: local-execution fallback.** Use a curated `PATH`
that omits `docker` so `run_in_sandbox()`'s own `FileNotFoundError` handler fires. No frozen
file changes; this was already generically pre-authorized by the Epic spec's Execution Notes
("Either is acceptable — document which path actually ran") — this resolution removes the
ambiguity for this specific host. `sandbox_env: alpine:latest` stays in the trigger for
documentation continuity but is inert under this route.

**2. tools.json adequacy — Option (c) taken, narrowly:** the proving vehicle's
executable-bit requirement is **dropped**, not the proving-vehicle concept itself. This is a
revision of an implementation detail within an already-delegated Epic design point (Open
Design Question A fixed *that* the vehicle is a purpose-built minimal epic, not the specific
detail of an executable entry point) — not a re-litigation of that resolution, and not a
change to any E26.1/E26.2 frozen surface. `bin/ai-project-version` is invoked as
`python3 bin/ai-project-version` throughout (spec, test, documentation); no chmod, no
`os.X_OK` assertion. Options (a) (accept near-certain non-convergence as evidence) and (b)
(amend the frozen `tools.json`) were both rejected: (a) would waste the entire point of the
run — a real proof, not a manufactured failure — and (b) reopens a merged Epic's delivered
surface for a problem this spec-level fix resolves without touching it.

**Governing spec amended in place** (`P7-M26-E26.3__spec__first-real-run-and-cross-repo-
acceptance.md` and its Epic Execution Chat Starter, same commit series as this resolution) —
mid-flight amendment per GH-9: the spec is the downward channel, not a note left only here.

**Not addressed here (not posed as a blocking question):** the Epic Chat's note that
`local-agent-runner` is not installed as a console script and needs `python3 -m
local_agent_runner` with `PYTHONPATH` set. `discover_runner()`'s `LOCAL_AGENT_RUNNER` override
expects a single executable file path — creating a small wrapper script (a one-line shebang
invoking `python3 -m local_agent_runner "$@"` with `PYTHONPATH` set) to satisfy that is within
the Epic's own execution-environment authority, the same category as the curated-`PATH`
technique already proposed. No frozen file is touched either way; proceed on your own judgment
and document the choice in the run record.

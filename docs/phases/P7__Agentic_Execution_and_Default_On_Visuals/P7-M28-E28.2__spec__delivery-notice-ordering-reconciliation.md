# Epic E28.2 — Delivery-Notice ordering reconciliation

## Context

M28 (Governance Reconciliations) is the third and final planned P7 milestone — pure process
hygiene, independent of M26/M27's surfaces. E28.2 targets P6-GH-14, the PSG §12 vs. P4.1
Delivery-Notice terminology collision.

> **Provenance:** Authored by the Milestone Chat (P7-M28) on 2026-07-13 per GH-8 adjacency.
> The Coding Agent implements it.

> **Source:** M28 Milestone spec (Epic Detail → E28.2); P7 phase spec P7.3 (P6-GH-14).

> **IMPORTANT — this spec reconciles in the opposite direction from the Milestone spec's
> stated recommendation, with reasoning stated explicitly, per the Milestone spec's own
> Non-Goals/DoD allowance** ("or, if the Milestone/Epic Chat finds a reason to reconcile the
> other direction, state that reasoning explicitly"; "matches the framework's actual
> practiced model, or states explicitly why it diverges"). See "Grounding — actual practice"
> below for the direct evidence. Flagged prominently for the Phase Chat, not silently
> substituted.

**Grounding — the collision itself (verified directly against `milestone/M28`, 2026-07-13):**

- PSG §12 "Delivery Notice (Mandatory)" (lines 609-625): "produced by the Coding Agent
  **immediately upon execution completion**... a prerequisite for review and closure — no
  Epic may proceed to review or closure without one."
- `governance/systems/artifact-communication-protocol.md` (P4.1): the flow diagram (lines
  520-556) and Creation Rules (lines 561-563) name the pre-review, completion-time artifact
  **"Completion Notice"** (rule 1, line 561: "created by the child chat when work is
  finished"), and reserve **"Delivery Notice"** for the artifact **"created by the child chat
  after the PR is merged to the parent branch"** (rule 3, line 563) — a distinct, later,
  post-merge artifact. Section headers confirm this: "### 1. Completion Notice" (line 40),
  "### 3. Delivery Notice (Merged PR → Archived Chat)" (line 315).
- AOG §12 line 716: "**Delivery Notice:** A structured, explicit notice produced by the Coding
  Agent **upon execution completion**. This is a mandatory artifact and a prerequisite for
  human review and Epic Delivery Authorization decision." — independently repeats PSG §12's
  pre-review framing, using the same name P4.1 reserves for the post-merge artifact.
- AOG §1.1 step 2 (line 31): "**Delivery Notice**: Coding Agent produces a structured Epic
  Delivery Notice and declares execution complete. No Epic may proceed to review or closure
  without this notice." — a **third** normative surface (alongside PSG §12 and AOG line 716)
  independently naming the pre-review, completion-time artifact "Delivery Notice."

**Grounding — actual practice (verified directly, not assumed from the Milestone spec's own
description):**

- **`governance/templates/epic-execution-chat-starter.md`** — the canonical template every
  Epic in this repository is executed from — contains exactly **one** notice section, "Epic
  Delivery Notice Template" (line 346), produced at execution completion, pre-review. It
  contains **no** "Completion Notice" concept anywhere in its 431 lines.
- **Seven consecutive, current P7 Epics** (E26.1, E26.2, E26.3, E27.1, E27.2, E27.3, and this
  milestone's own E28.1, executed earlier in this same session) each produced **exactly one**
  notice artifact — `docs/phases/P7__.../P7-M2#-E2#.#__delivery-notice.md` — timestamped at
  execution completion, pre-review, pre-merge. **Zero** `__completion-notice.md` files exist
  for any of them, and **zero** second, post-merge artifact was produced for any of them
  either. This is the single-artifact PSG §12 / AOG model, practiced without exception across
  every recent standard Epic.
- **`.ai-project/artifacts/completion-notices/` and `.ai-project/artifacts/delivery-notices/`**
  *do* contain matched Completion-Notice/Delivery-Notice pairs — but only for **P4-era Epics**
  (M14, M15, M18, M19 — predating the current `governance/templates/
  epic-execution-chat-starter.md` template's single-artifact design) and for **B4.1** (the
  most recent bugfix, executed this same session, 2026-07-13), which follows the separate
  **Bugfix Workflow** (`governance/systems/bugfix-epic-workflow.md`), not the standard Epic
  template. The two-artifact model is not extinct — it survives specifically in the Bugfix
  Workflow, a deliberately more heavyweight process (4-hour SLA review, CFO-signed Deployment
  Authorization, mandatory Post-Mortem) that is not "a standard Epic" despite
  `bugfix-epic-workflow.md:374`'s comment claiming its Completion Notice is "the same artifact
  as standard Epic" — **that comment is itself now stale** against current standard-Epic
  practice; out of E28.2's named scope (`bugfix-epic-workflow.md` is not one of the three
  named surfaces), flagged as a candidate carry-forward in Notes.
- **Milestone-level closures** (M18 through M27, nine consecutive Milestones) exclusively use
  a **Milestone Closure Declaration** (`.ai-project/artifacts/closure-declarations/`) — not
  the Completion-Notice/Delivery-Notice pair P4.1's flow diagram describes for the
  Milestone→Phase level either (lines 548-556: "ARTIFACT: Completion Notice (Milestone)").
  This is a separate P6-era mechanism (PSG §5C lineage) not itself in E28.2's scope to
  reconcile, but it corroborates that P4.1's flow diagram, taken as a whole, has drifted
  furthest from practice at exactly the levels this repo executes most often.

**Conclusion:** the Milestone spec's own grounding asserted "the framework's own practiced
model already matches `artifact-communication-protocol.md`'s two-artifact convention —
confirmed directly by this Phase Chat's own M26/M27/B4.1 execution this session." Re-verified
directly against the actual files on disk, this is **accurate for B4.1 but not for M26/M27**:
B4.1 (Bugfix Workflow) uses the two-artifact model; all six M26/M27 Epics (standard Epic
Workflow) use the single-artifact model, matching PSG §12 / AOG §1.1 / AOG §12 exactly, with no
exception. The single-artifact model is the one actually, consistently, currently practiced
for standard Epics — the workflow this reconciliation question is about.

## Problem Statement

PSG §12 and P4.1 (`artifact-communication-protocol.md`) assign the name "Delivery Notice" to
two different points in the Epic lifecycle — a terminology collision, not just an ordering
dispute. AOG line 716 and AOG §1.1 step 2 both independently repeat PSG §12's pre-review
framing, meaning three of the framework's four normative/systems surfaces already agree with
each other; only P4.1 disagrees. Direct verification of actual practice shows the standard
Epic Workflow (the canonical `epic-execution-chat-starter.md` template, and all seven recent
P7 Epics including this milestone's own E28.1) has fully converged on the single-artifact,
PSG-§12-shaped model — the Bugfix Workflow alone retains P4.1's two-artifact shape, as a
deliberately distinct, heavier process. P4.1 is the outlier against both the framework's other
normative documents and its own dominant practice.

---

## Goals

By the end of this Epic:

1. **`governance/systems/artifact-communication-protocol.md` is reconciled to name the
   pre-review, execution-completion artifact "Delivery Notice"** — matching PSG §12, AOG §1.1
   step 2, and AOG line 716 (all three of which already agree and require no change under this
   direction), and matching the single-artifact model every standard Epic in this repository
   actually produces.
2. **P4.1's separate post-merge "Delivery Notice" concept is retired from the standard
   Epic/Milestone/Phase flow it currently describes**, since it is not practiced there — with
   the flow diagram, Creation Rules, and Workflow Rules updated to match a single mandatory
   artifact (plus the exception-path Review Decision, already correctly described).
3. **PSG §12 requires no wording change** — confirmed to already match practice; record that
   confirmation rather than silently leaving it unstated.
4. **AOG line 716 requires no wording change for the Delivery-Notice-naming aspect** — already
   consistent with PSG §12 under this direction. (Line 716 still receives E28.4's own,
   unrelated edit — retiring the "Epic Delivery Authorization decision" ceremonial phrase —
   which this Epic does not perform; see Non-Goals and Dependencies.)
5. **The Bugfix Workflow's continued use of the two-artifact model is explicitly acknowledged
   as an intentional, separate exception** (not silently left looking like an unaddressed
   contradiction) — without editing `bugfix-epic-workflow.md` itself, which is out of this
   Epic's named scope.
6. **`artifact-communication-protocol.md`'s own version is bumped** (front-matter `version:
   1.1.0` → `1.2.0`) with a changelog row explaining the reconciliation and its direction.

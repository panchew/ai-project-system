# Epic E27.2 — Structural-first + trigger-set behavior

## Context

E27.1 (merged to `milestone/M27`, `dcfc9b6`) flipped the on/off default: AOG §17.1 now reads
"Default-on gating," `resolve_visual_artifacts()` resolves an absent block to `enabled: True`, and
the new `visual_required_for_specs` enforcement key exists, defaulted `true`. E27.1 deliberately
left one question open: **now that the capability is on by default, what actually gets produced,
and when?** AOG §17.3/§17.4 already define the structural/generative mode split and the
tool-capability gate (P5/P6 machinery, correct and untouched) — but nothing states that, *by
default*, structural governs and only specs/delivery/closure declarations get a visual
automatically. E27.2 supplies that missing normative layer.

## Problem Statement

The capability is now on by default (E27.1), but nothing states what "on" actually produces. Two
gaps remain: (1) no normative statement that structural-first governs the zero-infra default path
— generative activates only with `comfyui_url` present — layered on top of the already-correct
§17.3/§17.4 machinery; (2) no normative statement of *which* artifact types get a visual
automatically (specs + delivery/closure declarations) versus on-demand (everything else), and,
concretely, no place to record that binding for delivery/closure artifacts even if an agent
produced one today.

---

## Goals

By the end of this Epic:

1. **AOG codifies structural-first as the default-on trigger's zero-infra path** — no
   `comfyui_url` ⇒ structural only; generative activates only when an endpoint is present —
   stated as a new subsection that cross-references §17.3/§17.4 rather than restating them.
2. **AOG codifies the automatic trigger set explicitly**: specs (Phase/Milestone/Epic — the
   `*-spec.md` templates) and delivery/closure declarations (`delivery-notice.md`,
   `epic-closure-notice.md`, `milestone-closure-declaration.md`, `phase-closure-declaration.md`)
   get a visual automatically; every other artifact type is on-demand only (asked for in the
   proper chat, pointing at the artifact file).
3. **The delivery/closure templates gain a "Visual Bindings" section**, matching the existing
   spec-template pattern, and the guide's §7 placement table is extended to cover all eight
   artifact types the trigger set now names.
4. **`governance/guides/visual-artifacts.md` gains a new §9** stating the trigger-set policy in
   adopter-facing terms, consistent with AOG's new §17.8.
5. **The milestone-level joint acceptance criterion is now satisfiable**: a fresh project with no
   `visual_artifacts` block produces structural visuals for a new spec by default (E27.1's on/off
   flip + this Epic's structural-first/trigger-set policy, together).

## Scope of Work

### 1. AOG §17.8 — "Default-on trigger policy" (new subsection, appended)

State, in a new subsection after §17.7:

- With the capability on (default per §17.1), **structural-first governs**: no `comfyui_url`
  configured ⇒ structural only (§17.3); generative activates only when an endpoint is present.
  Cross-reference §17.3/§17.4 — do not restate their content.
- **The automatic trigger set**: Phase spec, Milestone spec, and Epic spec (the three `*-spec.md`
  templates) plus delivery/closure declarations (`delivery-notice.md`, `epic-closure-notice.md`,
  `milestone-closure-declaration.md`, `phase-closure-declaration.md`) get a visual automatically
  when the capability is on. Every other artifact type (steering note, progress digest, merge
  authorization, escalation notice, run record, …) is **on-demand only** — produced when explicitly
  asked for in the proper chat, pointing at the artifact file, never automatically.
- State the rule clearly enough that any chat level can follow it without inventing its own
  interpretation (milestone spec's own bar for this Epic).

**Must include:**
- New `### 16.8 Default-on trigger policy` subsection, appended after existing §17.7
- A one-line pointer added to §17.2's table or prose noting the trigger-set policy lives in §17.8
  (do not restate the per-level visual-type table — that answers *what kind*, §17.8 answers
  *when automatic*)
- AOG version bump (2.7.0 → next minor) + changelog row

### 2. `governance/guides/visual-artifacts.md` §9 — trigger-set behavior (new section, appended)

Adopter-facing restatement of the AOG §17.8 policy: structural-first at zero infra, the automatic
trigger set (specs + delivery/closure declarations), on-demand for everything else. Cross-reference
existing §2 ("The two modes") and §7 ("Binding a visual to an artifact") rather than duplicating.

**Must include:**
- New `## 9. Automatic vs. on-demand production (the trigger set)` section, appended after §8
- Guide changelog row (this guide's changelog is undated-entries-by-date, not semver — follow its
  existing `| Date | Change |` format)

### 3. Close the delivery/closure Visual-Bindings gap

Add a **Visual Bindings** section to each of the four delivery/closure templates
(`governance/templates/delivery-notice.md`, `epic-closure-notice.md`,
`milestone-closure-declaration.md`, `phase-closure-declaration.md`), matching the existing pattern
in `phase-spec.md` / `milestone-spec.md` / `epic-spec.md` (optional section, §7 binding schema
referenced not restated, omit if no visual). Extend the guide's §7 placement table
(`visual-artifacts.md:407-413`) with four new rows mapping each delivery/closure artifact to its
template's new section — keep the existing five spec rows unchanged.

**Must include:**
- Visual Bindings section added to all four delivery/closure templates
- §7 placement table extended (4 new rows; existing 5 unchanged)

### 4. §17.2 cross-reference note

A minimal edit — one sentence or a table footnote in §17.2 pointing to §17.8 for *when* a visual
is automatic, since §17.2 currently answers only *what kind*. Do not expand §17.2's scope beyond
this pointer.

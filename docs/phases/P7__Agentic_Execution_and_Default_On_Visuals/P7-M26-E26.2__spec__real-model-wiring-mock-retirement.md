# Epic E26.2 — Real-model wiring + mock retirement

## Context

E26.1 delivered `bin/run-dev-agent` (merged to `milestone/M26` at `e65f758`, suite 286/1): the
CONTRACT §7 adapter exists and the orchestrator's default `dev_command` now resolves to a real
file. But the live path is still not real: `.ai-project.yml:26` pins `epic_dev` to
`local:llama3:8b` — a model **verified unusable for tool-calling** (empty tool-call responses;
CONTRACT §1.4) — and the only flow that has ever driven `handle_epic_execution` end-to-end is
the P3 verify-loop harness pointing at `tests/mocks/mock_{dev,qa}.sh`. This Epic switches the
model and retires the mock-driven path from the live flow, so E26.3 can execute the first real
run.

> **Provenance:** Authored by the Milestone Chat (P7-M26) on 2026-07-12 per GH-8 adjacency.
> Second Epic of the **binding sequence E26.1 → E26.2 → E26.3** (HQ ruling 2026-07-11);
> depends on E26.1 (merged). The live run itself is **E26.3**, not this Epic.

> **Source:** M26 Milestone spec (Epic Detail → E26.2); P7 phase spec P7.1 steps 2–3; HQ ruling
> execution sequence.

**Grounding (verified on `milestone/M26` after the E26.1 merge, 2026-07-12):**

- `.ai-project.yml:26` — `epic_dev: local:llama3:8b`. (`epic_qa: local:qwen2.5-coder:7b` at L27
  is **not** in M26's directed scope — leave it.)
- `bin/ai-project-orchestrator:21` — `DEFAULT_MODELS` also hardcodes
  `"epic_dev": "local:llama3:8b"`. Whether the in-script default moves with the config is this
  Epic's consistency call — **recommended: yes, they should agree** (Milestone spec).
- `governance/ai-project-yml-spec.md` **L58, L330, L336** — the config reference doc documents
  `local:llama3:8b` as the `epic_dev` default/example. The acceptance criterion is *"`epic_dev`
  is off `llama3:8b` everywhere it is defined"* — if the default moves, these defining/default
  rows move with it (L336's generic prefix *example* may stay if reworded away from being the
  documented default).
- **Mock-consumer map (verified — narrower than the Milestone spec assumed):** the pytest suite
  never exercises the mocks. `tests/integration/test_agentic_mode.py` tests **daemon artifact
  routing** only (no `mock_dev`/`mock_qa`/`04_epic.json` references). The only consumer of
  `tests/mocks/mock_{dev,qa}.sh` is **`bin/verify-loop.sh`** — the P3-M12-E12.3 verification
  harness that writes `04_epic.json` triggers pointing at the mocks (L132/189/246/319/388).
- **Documented-flow map:** no live guide routes epic execution through the mocks. Mock mentions
  outside `tests/mocks/` + `verify-loop.sh` are **frozen P3 history** (completion docs — do not
  edit). `04_epic.json` *mechanism* references (README.md:441, `governance/agents/
  governance.agent.md` L194/L206, `.ai-project/queue/README.md`) describe the trigger mechanism,
  which **stays** — it is how E26.3 launches.

---

## Problem Statement

The adapter exists but nothing points the live flow at reality: the configured dev model cannot
tool-call, and the only proven end-to-end driver of the agentic loop is a mock harness. Until
`epic_dev` is a usable model and no live/documented flow routes through the mocks, the first
real run (E26.3) cannot happen.

---

## Goals

By the end of this Epic:

1. **The dev model is real:** `.ai-project.yml:26` `epic_dev` = `local:qwen2.5-coder:14b`.
2. **The consistency call is made and documented:** whether
   `DEFAULT_MODELS["epic_dev"]` (orchestrator L21) moves with the config —
   recommended **yes** — and `governance/ai-project-yml-spec.md`'s documented default moves
   consistently with that decision.
3. **The live path names the adapter:** the documented live epic-execution flow (queue README /
   any live doc describing the trigger) names `./bin/run-dev-agent` as `dev_command` — never a
   mock script.
4. **The mock-driven path is retired from the live flow**, with the CI-retention boundary
   decided and documented. **The trigger mechanism (`04_epic.json` in the queue) stays** — it is
   how the orchestrator receives epic work and what E26.3 uses with real values.
5. **Config and tests updated; full suite passes** — including a consistency guard so
   `epic_dev` cannot silently drift back (e.g. a test asserting the `.ai-project.yml` value and
   `DEFAULT_MODELS` agree per the documented decision, and that neither is `llama3:8b`).

## Scope of Work

### 1. Model switch

- `.ai-project.yml:26` — `epic_dev: local:llama3:8b` → `epic_dev: local:qwen2.5-coder:14b`.
- **Consistency call (decide + document):** `bin/ai-project-orchestrator:21`
  `DEFAULT_MODELS["epic_dev"]`. Recommended: move to `local:qwen2.5-coder:14b` so config and
  in-script default agree (an absent `models:` block should not silently resurrect an unusable
  model). Document the decision in the Delivery Notice.
- `governance/ai-project-yml-spec.md` L58/L330 (documented default) — update consistently with
  the `DEFAULT_MODELS` decision; L336 (prefix example) may be reworded rather than deleted.
  Bump that doc's version/`last_updated` per its own conventions if it carries them.

### 2. Live-path wiring

- Verify the live flow invokes the adapter: the orchestrator default (L317) already names
  `./bin/run-dev-agent` — confirm no live/documented flow overrides `dev_command` to a mock.
- Update the live trigger documentation (`.ai-project/queue/README.md`, and any live doc that
  describes the `04_epic.json` flow) so the documented example/description names
  `./bin/run-dev-agent` and a real `validation_command` — not `tests/mocks/*`.

### 3. Mock retirement + CI-retention boundary (your call — decide and document)

- **What must be true afterward (Milestone spec, binding):** no live or documented flow routes
  an epic through `mock_dev.sh`/`mock_qa.sh`, and `epic_dev` is off `llama3:8b`.
- **Recommended boundary** (grounded in the verified consumer map): **retain**
  `tests/mocks/mock_{dev,qa}.sh` and `bin/verify-loop.sh` as the loop-logic **regression
  harness**, explicitly labeled as such (header comments/docs stating they are verification-only,
  never the live path). The pytest suite does not use them, so no pytest change is forced by
  retention. Alternative (also valid): fold verify-loop scenarios into pytest and drop the shell
  harness — bigger than M26 needs; if chosen, justify in the Delivery Notice.
- Whatever boundary you choose: document it (Delivery Notice + a line in the retained files'
  headers), and grep-prove the live/documented flow is mock-free.

### 4. Tests

- Add a consistency guard (e.g. `tests/test_model_config.py`): `.ai-project.yml` `epic_dev` is
  `local:qwen2.5-coder:14b`; `DEFAULT_MODELS["epic_dev"]` agrees per the documented decision;
  neither is `llama3:8b`.
- Full suite passes (286/1 baseline + new).

## Execution Notes

- **This is a boundary decision, not a deletion spree** (Milestone spec). The verified consumer
  map makes it small: only `bin/verify-loop.sh` drives the mocks; pytest never does. Retention
  with explicit regression-only labeling is the recommended, lowest-risk boundary.
- **"Everywhere it is defined" includes the reference doc.** The yml-spec's default rows
  (L58/L330) define the default for adopters — leaving `llama3:8b` there fails the acceptance
  criterion even with config and script switched.
- **Grep to finish:** `grep -rn "llama3:8b"` outside frozen phase docs/artifacts should return
  nothing that *defines* `epic_dev`; `grep -rn "tests/mocks"` should hit only the regression
  harness + frozen history.
- Default-accept (PSG §11.6 / AOG §14) governs this Epic's own delivery: a clean delivery is
  accepted by silence; the epic-PR merge is human-authorized in-chat (SN-19); a Review Decision
  is the exception path only.

# Epic E29.1 — Naming-collision resolution (P7-GH-21)

## Context

M29 is the sole milestone of P8. E29.1 is the first of its three epics and closes carry-forward
P7-GH-21: a naming collision between the `.ai-project.yml` schema's `visual_artifacts.types`
value `diagrams` and AOG §16.3's endpoint-free "Structural" mode. E29.1 is a documentation/prose
epic — it does not touch `bin/ai-project-visual`'s generation logic, `bin/ai-project-orchestrator`'s
resolution/validation code, or any test assertion, **unless** the resolution direction chosen
during execution requires it (see Design Decision below — this is the load-bearing branch point
of the whole Epic).

> **Provenance:** Authored by the Milestone Chat (P8-M29) on 2026-07-15 per GH-8 adjacency. The
> Coding Agent implements it. E29.1 is recommended (not required) to land before E29.2 — see
> Dependencies.

> **Source:** M29 Milestone spec (Epic Detail → E29.1); P8 phase spec P8.1; P7 phase closure
> carry-forward P7-GH-21.

**Grounding (verified on `milestone/M29`, 2026-07-15):**

- `governance/ai-project-yml-spec.md:356` (§3.5 `types` field table row) — currently reads:
  `` `diagrams`: Mermaid/PlantUML structural; `infographics`: ComfyUI-generated imagery; `video`:
  ComfyUI video (optional). `` This is the exact collision: it describes `diagrams` as Structural
  output in the same table row where `infographics`/`video` are described as Generative, with no
  disambiguating note.
- `bin/ai-project-visual:1-34` (module docstring) — the `Usage:` example
  (`--type diagrams --output ./architecture.png`) and the `Configuration` example
  (`types: [diagrams, infographics, video]`) both use the schema's colliding value with no note
  that this is unconditionally a ComfyUI call.
- `bin/ai-project-visual:190-248` (confirmed by reading `parse_args`/`main`) — there is **no code
  path, for any `--type` value**, that produces Structural (Mermaid/PlantUML) output. `--type
  diagrams` always resolves through `default_workflow()` (a txt2img ComfyUI graph, lines 96-121)
  unless `--workflow` is supplied. By AOG §16.3's own definition ("Structural... no ComfyUI
  needed"; "Generative... via the configured ComfyUI endpoint, using the `bin/ai-project-visual`
  helper"), **every** `bin/ai-project-visual` call is Generative by construction — the helper
  itself has no Structural mode to collide with; the collision is purely in how the schema
  documents `diagrams` and how three prose surfaces echo it.
- `.ai-project/artifacts/reference/comfyui-endpoint/VISUAL-ARTIFACTS.md:19-21` — the prose
  correctly separates Structural ("Mermaid / PlantUML... No ComfyUI needed") from Generative
  ("imagery / video produced here"). Only the config example at line 67
  (`types: [diagrams, infographics, video]`) still lists `diagrams` as a bare `types` entry with
  no note distinguishing it from AOG §16.3's Structural diagrams.
- `.ai-project.yml:29-42` — this repo's own `visual_artifacts` comment already narrates the
  collision at length (added defensively in P7-M27, not fixed) and explicitly says fixing it is
  "not something this Epic's scope covers" (P7-M27-E27.1) — E29.1 is the epic that finally does.
- `governance/ai-project-yml-spec.md:3` — current version `2.3.0`.

**Additional grounding — blast-radius asymmetry between the two candidate directions (read
before deciding):**

- `bin/ai-project-orchestrator:28` — `VALID_VISUAL_ARTIFACT_TYPES = ("diagrams", "infographics",
  "video")`, the enum enforced by `validate_visual_artifacts()` (line 88). **This constant is not
  one of the four named surfaces in the Milestone spec's E29.1 Deliverables list.**
- `bin/ai-project-orchestrator:554-579` — inline unittest-style assertions inside the module
  itself reference `"diagrams"` as a literal value (e.g. `validate_visual_artifacts({"types":
  ["diagrams", "bogus"]})`).
- `tests/test_visual_artifacts_config.py:45-70,163-166` — six assertions hardcode `"diagrams"` as
  a literal schema value (validation happy-path, validation-error path, and a resolution-path
  test).
- `tests/integration/test_visual_artifacts_helper.py` — of the seven tests in this file, **six**
  hardcode `"diagrams"` as a literal `--type` value inside an isolated `tmp_path` fixture (lines
  83, 98/101, 122/145, 159, 172) that constructs its own `.ai-project.yml` independent of this
  repo's config. Only `test_helper_generates_against_endpoint` (line 68) resolves its `--type`
  dynamically from `REPO_VA.get("types")[0]`, i.e. from this repo's own config — that one test
  would follow a rename automatically.
- **Consequence:** if the resolution direction *renames* the schema's generative value (e.g.
  `diagrams` → some new token), the rename's true footprint is `bin/ai-project-orchestrator`'s
  enum constant + its own inline assertions + `tests/test_visual_artifacts_config.py` + six of
  seven tests in `tests/integration/test_visual_artifacts_helper.py` — **none of which appear in
  the Milestone spec's E29.1 Deliverables list**, which names only the four documentation/prose
  surfaces. A rename direction therefore either (a) expands E29.1's file scope beyond what the
  Milestone spec named, or (b) leaves the rename half-done across two epics (E29.1 documents a
  new name the code and tests do not yet use), which is exactly the "partial fix" the Milestone
  spec's Deliverable 1 forbids. A *reframing* direction (document that `types` is generative-only
  and Structural mode needs no `visual_artifacts` config, without renaming any value) touches only
  the four named surfaces and leaves the schema value, the orchestrator enum, and every existing
  test assertion unchanged. This asymmetry is grounding for the Design Decision below, not a
  pre-made choice.

## Problem Statement

`governance/ai-project-yml-spec.md` §3.5's own field table and this repo's own reference
documentation both describe the `visual_artifacts.types` value `diagrams` as producing
"Mermaid/PlantUML structural" output, while `bin/ai-project-visual`'s actual, unconditional
implementation makes every call — including `--type diagrams` — a ComfyUI generative call. This
contradicts AOG §16.3's own Structural/Generative split and has stood undisambiguated since at
least P7 (`.ai-project.yml`'s own comment names it and defers the fix). Until resolved, any reader
of the schema table, the helper's docstring, or `VISUAL-ARTIFACTS.md`'s config example reasonably
concludes `--type diagrams` produces endpoint-free Structural output — it does not.

---

## Goals

By the end of this Epic:

1. **A single, coherent naming scheme for `visual_artifacts.types`** that cannot be read as
   describing Structural (endpoint-free) output.
2. **`governance/ai-project-yml-spec.md` §3.5's field table no longer describes any `types` entry
   as "Mermaid/PlantUML structural."**
3. **`bin/ai-project-visual`'s docstring/help text matches** the resolved naming scheme, with no
   Usage or Configuration example implying Structural output.
4. **This repo's `.ai-project.yml` `visual_artifacts` comment matches** the resolved scheme
   (independent of, but sequenced before, E29.2's flag flip — the comment's own content changes
   regardless of whether `enabled` flips in this Epic or the next).
5. **`VISUAL-ARTIFACTS.md`'s config example matches** — its prose needs no change (already
   correct); only the example block does.
6. **`governance/ai-project-yml-spec.md` is version-bumped with a changelog row** documenting the
   schema-facing change (or, if the reframing direction makes no schema-value change, the
   changelog row documents the clarification made).
7. **Full test suite passes**, with no test newly broken by whichever direction is chosen.

## Design Decision (yours to resolve — decide, document, move; escalate only if truly blocked)

**This is the one open design point in this Epic, per the Milestone Chat's Question Policy — pick
a direction, document the reasoning in the Delivery Notice, and proceed. Do not escalate to ask
which direction to take.**

Two candidate directions (from the Milestone spec, non-exhaustive):

- **(A) Rename** the schema's generative `diagrams` value to a name that cannot be read as
  Structural (e.g., a name signaling "diagram-style generated image").
- **(B) Reframe** `types` as generative-only categories, documenting explicitly that Structural
  mode needs no `visual_artifacts` config at all (it never calls `bin/ai-project-visual`) —
  leaving the schema value `diagrams` unchanged, but making unmistakably clear in all four
  surfaces that it names a ComfyUI-generative txt2img call, not Mermaid/PlantUML output.

Weigh the blast-radius grounding above before choosing:

- Direction (A) is not containable within this Epic's four named deliverable surfaces alone —
  the orchestrator's enum, its own inline assertions, and the majority of both visual-artifacts
  test modules hardcode the literal string `diagrams` and would need to change in the same
  delivery to avoid a partial, inconsistent rename. If you choose (A), you must pull all of those
  surfaces into this Epic's own scope and deliverables — do not leave the rename half-landed for
  E29.2 to discover.
- Direction (B) is fully containable within the four named surfaces: it changes what the
  `diagrams` value is *documented and described as*, not what string it is, so the orchestrator
  enum, its inline assertions, and every existing test assertion referencing `"diagrams"` remain
  correct with zero code changes.

Whichever direction is chosen, it **MUST** touch every one of the four named surfaces in
Deliverables below — a partial fix leaving one surface still describing a generative call as
Structural does not close P7-GH-21 (Milestone spec, verbatim).

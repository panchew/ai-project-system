# Epic E29.3 — Precision validation

## Context

M29's third and final epic. E29.2 (merged to `milestone/M29`, PR #129) proved the live ComfyUI
endpoint call works reliably — it fixed a stale checkpoint default and a seed-caching timeout
bug that no prior milestone had ever exercised, since `enabled` had always been `false`. E29.3
answers the question P6/P7 left open: not whether `bin/ai-project-visual` *renders successfully*
(P6 already verified that for FLUX-schnell, SDXL, and LTX-Video), but whether the output is
*precise enough* to explain something technical. This is the first time this project's own
governance chats have ever produced and judged a real generated artifact — there is no prior
run to compare against.

> **Provenance:** Authored by the Milestone Chat (P8-M29) on 2026-07-15 per GH-8 adjacency. The
> Coding Agent implements it. Depends on E29.2 (merged) — cannot run before the capability is
> enabled and the endpoint call is proven.

> **Source:** M29 Milestone spec (Epic Detail → E29.3); P8 phase spec P8.1; SN-20 ratified
> decision 3; P7 closure's own open question.

## Problem Statement

P6 verified that FLUX-schnell, SDXL, and LTX-Video each produce valid output from
`bin/ai-project-visual` against the live endpoint — valid in the sense of "renders without
error," not judged against any explanatory-precision bar. No prior milestone performed that
judgment. Until this Epic, "the capability works" and "the capability is good enough to explain
something technical" have been silently conflated.

---

## Goals

By the end of this Epic:

1. **One workflow-diagram-style case exists**, produced via Generative mode against the live
   endpoint, depicting a real governance or code flow from this project.
2. **One short explainer-clip case (LTX-Video) exists**, narrating a real proposed→implemented
   arc for exactly one governance node (single-parent, AOG §17.7).
3. **Both are hosted by link and bound per the §7 schema** — never committed as binaries — with
   `Level: Epic` bindings recorded in this Epic's own spec/Delivery Notice.
4. **Each case has a documented pass/partial/fail finding** against "could a reader unfamiliar
   with the underlying flow follow it from the artifact alone?" — not "did it render."
5. **The finding is surfaced, not resolved, to the CFO** as evidence for SN-20 Carry-Over item 3.

## Scope of Work

### 1. Diagram-style case (Generative)

Produce one image via `bin/ai-project-visual --type diagrams` (or `infographics`, whichever the
chosen workflow's category fits — both resolve to Generative per E29.1's Direction B) against the
live endpoint, using `flux-schnell.json` (best text/label legibility) or `sdxl.json` from the
reference bundle, depicting a real governance/code flow (Design Decision §3). Write the local
output to a working path (not committed), host it, and record a `Level: Epic`, `State:
implemented` binding (§7 schema) in this Epic's spec or Delivery Notice.

**Must include:**
- One real generative call against `http://localhost:8188`, non-empty output confirmed
- Hosted by link (never committed as a binary)
- A complete §7 binding block (Link, What: diagram, Level: Epic, State: implemented,
  Description)

### 2. Explainer-clip case (LTX-Video)

Produce one `.webm` via `bin/ai-project-visual --type video --workflow
.ai-project/artifacts/reference/comfyui-endpoint/ltxv-video.json`, narrating the chosen node's
proposed→implemented arc (Design Decision §2). Cite the preserved bundle; do not re-transcribe
the workflow (guide §8, Open Design Question A). Host and bind (`What: clip`, `Level: Epic`,
`State: implemented` — a clip narrates the whole arc, so implemented is the natural state per
guide §8).

**Must include:**
- One real LTX-Video call against the live endpoint, valid non-empty `.webm` confirmed
- Hosted by link (never committed)
- A complete §7 binding block

### 3. Precision judgment

For each case, judge against: **"could a reader unfamiliar with the underlying flow follow it
from the artifact alone?"** — not "did it render without error" (P6 already answered that).
Record a pass / partial / fail per case with a short, specific justification (what the artifact
does or doesn't communicate, not a restatement of the bar itself).

**Must include:**
- A pass/partial/fail finding per case, each with concrete justification
- Findings written as evidence, not as a resolution of SN-20 Carry-Over item 3

### 4. CFO surfacing

Write up both findings for the CFO in the Delivery Notice, explicitly framed as evidence toward
SN-20 Carry-Over item 3 (whether a separate governed ComfyUI-workflow project is still wanted) —
state the findings, do not recommend a resolution.

**Must include:**
- A clearly labeled "Finding for the CFO" section in the Delivery Notice, evidence-framed

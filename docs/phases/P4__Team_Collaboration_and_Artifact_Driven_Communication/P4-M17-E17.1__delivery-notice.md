# Epic Delivery Notice — P4-M17-E17.1

**Epic:** P4-M17-E17.1 — Fix Daemon Orchestrator Path Resolution
**Status:** Execution Complete, Delivered for Review
**Delivery Date:** 2026-06-17

## Execution Summary

The daemon failed at startup with "orchestrator not found" whenever it ran from a
governance submodule with `--project-root` pointing at the consuming project. The
fix replaces the single hard-coded orchestrator path with an ordered, cached search
that also falls back to the daemon's own directory — which always ships the
orchestrator. The fix is transparent (no manual setup after clone) and does not
change the documented invocation, so no user-facing configuration changed.

## Root Cause Analysis

**Symptom:** Projects consuming governance as a submodule and starting the daemon via
`governance/bin/ai-project-daemon --project-root . start` failed with "orchestrator
not found", blocking all Epic execution. Projects on the v3.0.0+ layout were
unaffected.

**Where the daemon looked:** `bin/ai-project-daemon` computed
`ORCHESTRATOR_BIN = PROJECT_ROOT / "bin" / "ai-project-orchestrator"`. The
`--project-root` override deliberately repoints `PROJECT_ROOT` at the *consuming*
project root (correct for queue/locks/logs) — but it **also** repointed the
orchestrator lookup there.

**Why v2.0.0 fails:** In the submodule layout the orchestrator binary ships *inside*
the governance package, next to the daemon (`<submodule>/bin/ai-project-orchestrator`).
The consuming project's own `bin/` does not contain it. So
`PROJECT_ROOT/bin/ai-project-orchestrator` resolves to a path that does not exist →
"orchestrator not found".

**Why v3.0.0+ works:** In the self-referential / v3.0.0+ layout, `PROJECT_ROOT` and the
daemon's directory coincide (`<repo>/bin/`), so the orchestrator happens to sit at the
single path the daemon checked. The bug was latent — it only surfaced once
`PROJECT_ROOT` and the daemon's location diverged (the submodule case).

**Root cause:** The orchestrator path was derived from `PROJECT_ROOT` (a project-data
anchor) rather than from the daemon's own location (where the orchestrator actually
ships). The two anchors are identical only in the self-referential layout.

## Solution Chosen

**Option A — Fallback path search** (from the Epic spec's three evaluated options).

- **Option B (bump submodule to v3.0.0+)** was rejected: it does not fix the underlying
  path-derivation bug (it only hides it for one layout), forces every consuming project
  to re-pin, and risks unrelated breaking changes.
- **Option C (build on-demand)** was rejected: it adds a build toolchain dependency and
  first-run latency for a problem that is purely path resolution.
- **Option A** fixes the actual root cause, requires no submodule re-pin, and is
  performance-neutral once cached.

`resolve_orchestrator_bin()` searches, in order, caching the first hit:

1. `<PROJECT_ROOT>/bin/ai-project-orchestrator` — self-referential / vendored
2. `<PROJECT_ROOT>/governance/bin/ai-project-orchestrator` — legacy convention
3. `<PROJECT_ROOT>/.governance/bin/ai-project-orchestrator` — canonical submodule
4. `<daemon dir>/ai-project-orchestrator` — orchestrator shipped beside the daemon

Candidate 4 (the daemon's own directory) is the authoritative fallback that fixes the
submodule case regardless of how `--project-root` is set. The result is cached after the
first lookup (one extra `stat` at most), and the cache is reset whenever `--project-root`
changes the root. If no candidate exists, the daemon prints a clear error naming every
path it tried.

# Epic P4-M17-E17.1: Fix Daemon Orchestrator Path Resolution

## Problem Statement

When a project clones `ai-project-system` with the v2.0.0 daemon submodule, the
orchestrator binary is not present in the expected location. The daemon fails at startup
with "orchestrator not found," blocking all Epic execution. Projects using v3.0.0+ are
unaffected because that version bundles the orchestrator, but any project pinned to
v2.0.0 cannot run.

This is a HIGH-risk item from the P4 phase spec. It must be resolved before M17 closes.

---

## Requirements

### Functional Requirements

1. **Root Cause Identified**
   - Determine exactly which path the daemon searches for the orchestrator
   - Determine why v2.0.0 does not include the binary
   - Determine why v3.0.0+ works (bundles binary or different path logic)
   - Document findings in a Root Cause Analysis section of the Epic Completion Report

2. **Fix Implemented**
   - Choose and implement one of the three evaluated options (see Design below)
   - Fix must be transparent to the user: no manual intervention required after `git clone`
   - Daemon startup must succeed on a clean checkout without setting environment variables

3. **Version Compatibility**
   - Fix must support both v2.0.0 and v3.0.0+ submodule pins
   - No regression for projects already working on v3.0.0+

4. **Documentation Updated**
   - If path logic changes, update `governance/setup-guide.md` (or equivalent) to
     reflect the new search order
   - Remove "orchestrator not found" from any troubleshooting guides that list it as
     a known manual-fix issue
   - Add a CHANGELOG entry documenting the fix and affected versions

### Non-Functional Requirements

- **No user-visible configuration change:** The fix is internal to the daemon
- **Performance neutral:** Path resolution must not add measurable startup latency
  beyond a single filesystem stat call (cache the result after first lookup)
- **Clean failure:** If orchestrator cannot be found after all paths are exhausted,
  the daemon must print a clear error message naming the paths it tried

## Design

### Evaluated Options

**Option A — Fallback path search**
The daemon searches a second path (`governance/bin/`) after the primary path fails.
- Pro: Works with v2.0.0 without changing the submodule pin; no breaking changes
- Con: Two filesystem stats on first launch; must be cached

**Option B — Update submodule to v3.0.0+**
Pin the daemon submodule to v3.0.0+ which bundles the orchestrator.
- Pro: Single canonical path; no fallback logic needed
- Con: May carry breaking changes in v3.0.0+; requires compatibility verification

**Option C — Build orchestrator on-demand**
During daemon first-start, detect a missing orchestrator and build it from source.
- Pro: Always available regardless of submodule version
- Con: Adds build toolchain as a dependency; slower first start

The executing agent must evaluate all three options against the root cause findings
and choose the best fit. The chosen option must be documented in the Completion Report.

### Path Resolution Logic (reference)

Current assumed search order (v2.0.0 daemon):
1. `bin/ai-orchestrator` (relative to repo root)

Proposed search order if Option A is implemented:
1. `bin/ai-orchestrator`
2. `governance/bin/ai-orchestrator`
3. `<submodule_root>/bin/ai-orchestrator`

Path resolution result must be cached after first successful lookup.

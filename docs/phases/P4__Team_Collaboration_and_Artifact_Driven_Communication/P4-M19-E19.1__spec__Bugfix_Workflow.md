# Epic P4-M19-E19.1: Bugfix Workflow

## Problem Statement

Phase P4's success criteria include a working Bugfix Workflow: a production issue can
be reported to HQ Chat and result in a Bugfix Epic with SLA tracking, CFO Deployment
Authorization before any production push, and a post-mortem for Critical/High severity.
None of these are implemented. The design exists (`governance/systems/bugfix-epic-workflow.md`)
but it is not wired into the HQ Chat Starter, no Deployment Authorization artifact type
exists, and there is no post-mortem template.

This Epic implements the complete Bugfix Workflow end-to-end and closes this P4 success
criterion. It also resolves three carry-over items from prior milestones.

---

## Requirements

### Functional Requirements

**1. docs/bugfixes/ Directory and B#.# Convention**

Establish `docs/bugfixes/` as the canonical location for Bugfix Epic specs:
- `docs/bugfixes/README.md` documents the B#.# naming convention
- B#.# format: `B<severity-number>.<sequence>` where severity numbers follow the
  convention defined in `governance/systems/bugfix-epic-workflow.md`
  (or establish: B1.x = Critical, B2.x = High, B3.x = Medium, B4.x = Low)
- Example filename: `B1.1__spec__auth-session-expiry.md`

**2. HQ Chat Bugfix Handler**

Update `governance/systems/hq-execution-chat-starter.md` with a "Handling Production
Issues (Bugfix Epics)" section covering:
- Step 1: Evaluate — is this a Bugfix Epic (urgent, production-affecting) or defer to
  next planned Epic?
- Step 2: Create minimal Bugfix Epic spec: title, severity (Critical/High/Medium/Low),
  description (one paragraph), affected systems, proposed fix direction
- Step 3: Commit spec to `docs/bugfixes/B#.#__spec__<slug>.md`
- Step 4: Issue Epic Delivery Authorization to the executing agent
- Step 5: Track SLA — start 4-hour clock from Completion Notice receipt
- Step 6: If SLA missed — flag as urgent, notify CFO, do not skip review

**3. Deployment Authorization Artifact**

New file: `governance/templates/deployment-authorization.md`

YAML front-matter schema:
```yaml
type: deployment-authorization
epic: <B#.# or P#-M#-E#.#>
project: <project-slug>
issued_by: <role name>
date: <YYYY-MM-DD>
environment: <production | staging>
decision: <authorized | rejected>
```

Required sections:
- What is being deployed (commit SHA or tag, brief description)
- Risk assessment (brief: what could go wrong, how it was mitigated)
- Authorization statement (or rejection reason)
- Conditions (if any — e.g., "deploy only during maintenance window")

Include a filled example in the template.

**4. SLA Tracking and Escalation**

Update `governance/systems/bugfix-epic-workflow.md`:
- Add SLA section: 4-hour review window measured from the timestamp of the Completion
  Notice artifact
- On SLA miss: HQ Chat issues urgent flag to CFO; review still required before deploy
- Deployment Authorization is required for all Bugfix Epics that touch production
- Add a reference to `governance/templates/post-mortem.md`

**5. Post-Mortem Template**

New file: `governance/templates/post-mortem.md`

Required sections:
- Incident Summary (one paragraph: what happened, when, impact)
- Timeline (ordered list of key events with timestamps)
- Root Cause (what was the actual cause)
- Resolution (what fixed it)
- Prevention (what changes prevent recurrence)
- Action Items (numbered list with owner and due date)

YAML front-matter:
```yaml
type: post-mortem
epic: <B#.#>
severity: <critical | high>
incident_date: <YYYY-MM-DD>
resolved_date: <YYYY-MM-DD>
authored_by: <role>
```

Required for Critical and High severity Bugfix Epics only. Medium and Low are optional.

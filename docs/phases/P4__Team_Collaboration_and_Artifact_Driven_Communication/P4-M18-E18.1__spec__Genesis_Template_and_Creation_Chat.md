# Epic P4-M18-E18.1: Genesis Template and Creation Chat

## Problem Statement

The AI Project System has no canonical "how to begin." A new user — human or AI agent —
who wants to start a fresh project must reverse-engineer the governance structure from
existing projects or wade through multiple governance documents to discover what files to
create, in what order, and with what content. `start-a-project.md` covers the mechanics
(`ai-project init`, governance-as-submodule) but stops short of telling the user what to
produce: it does not define the Creation Chat role, the inputs it needs, or the artifacts
it must commit before a Phase Chat can be opened.

This gap means the system's "front door" is missing. Every subsequent workflow (Phase
Chat, Milestone Chat, Epic execution) is well-defined, but the step before all of them
— bootstrapping a new project from a brief — is not.

---

## Requirements

### Functional Requirements

**1. Genesis Template (`governance/templates/genesis.md`)**

A new file that a Creation Chat (or a human acting as one) fills out when starting a
project. It is the single artifact that must exist before a Phase Chat can open.

Required content:
- YAML front-matter schema:
  - `type: genesis`
  - `project`: project name (slug)
  - `created_by`: role or name of creator
  - `date`: ISO date
  - `phase_1_name`: short name of Phase 1
  - `status`: `draft` | `complete`
- **Project Brief section:** goal, problem statement, initial team (roles)
- **HQ Context Packet section:** what HQ Chat needs to function — project name,
  governance path, phase 1 scope summary, key constraints
- **Phase 1 Scope section:** name, goal, 2–4 milestone stubs with one-line descriptions
- **Creation Chat Decisions section:** what the Creation Chat decided (project name
  confirmed, Phase 1 scope accepted, team roles assigned)
- **Next Step section:** what to do with this artifact (open Phase Chat, pass genesis.md
  as context)
- A filled example embedded in the template (commented out or in a dedicated example file)

**2. Creation Chat Role Definition**

A short document or section (may live in the genesis template itself or in
`governance/systems/`) that defines the Creation Chat role:
- **Inputs:** project brief (goal, rough scope, team), governance repo path
- **Authority:** may define Phase 1 scope and name; may assign initial team roles;
  may not authorize execution (that is Phase Chat's responsibility)
- **Outputs:** `genesis.md` committed to the repo; a ready-to-open Phase Chat context
- **Stops when:** `genesis.md` is committed and the user is handed the Phase Chat starter

**3. `start-a-project.md` Update**

Extend the existing guide to include the Creation Chat flow:
- Before "Run `ai-project init`": explain the Creation Chat step
- After init: explain that `genesis.md` must be filled out and committed
- Reference the Phase Chat starter as the next step after genesis is complete
- Remove any remaining "copy files manually" instructions (M15 removed most; verify
  none remain)

**4. Validated Walkthrough**

A real new-project setup is executed using the genesis template:
- Start from a blank directory (or a fresh `ai-project init`)
- Fill out `genesis.md` following the template
- Verify: HQ context packet section is coherent, Phase 1 scope is actionable
- Verify: the output could be handed to a Phase Chat without additional explanation
- Commit the completed genesis.md as the walkthrough artifact (in the Delivery Notice
  or as a separate `genesis-walkthrough.md` under `docs/` or `examples/`)

### Non-Functional Requirements

- **Concise template:** genesis.md must be readable in under 5 minutes by someone
  with no prior knowledge of the system
- **Self-contained:** the template's guidance text must make each field's purpose
  obvious without reading any other document
- **Backward compatible:** changes to `start-a-project.md` must not break the
  existing `ai-project init` + governance-as-submodule flow described in M15

## Design

### Genesis Template Structure

```yaml
---
type: genesis
project: <slug>
created_by: <role>
date: <YYYY-MM-DD>
phase_1_name: <Phase 1 short name>
status: draft | complete
---
```

```markdown
# Genesis — <Project Name>

## Project Brief
**Goal:** …
**Problem:** …
**Initial Team:**
| Role | Person | Authority |
|------|--------|-----------|
| CFO  | …      | Phase scope, production |
| Phase Lead | … | Milestone planning |

## HQ Context Packet
(Filled automatically by Creation Chat; used to open Phase Chat)
- Project: …
- Governance path: governance/
- Phase 1 scope: …
- Key constraints: …

## Phase 1 Scope
**Name:** …
**Goal:** …
**Milestone stubs:**
- M1: … (one line)
- M2: … (one line)
- M3: … (one line)

## Creation Chat Decisions
- Project name confirmed: …
- Phase 1 scope accepted: …
- Team roles assigned: …

## Next Step
Open Phase Chat using `governance/systems/phase-execution-chat-starter.md` with
this genesis.md as the mandatory context packet.
```

### Role Definition Placement

Prefer adding a "Creation Chat" entry to `governance/systems/chat-hierarchy.md`
(the existing hierarchy document) rather than creating a new file. This keeps all
role definitions in one place.

### Walkthrough Artifact

Produce a completed genesis.md for a fictitious project (e.g., the same "Task
Management App" used in the M16 example) and commit it under
`examples/genesis-walkthrough/genesis.md`. This makes the walkthrough a permanent
reference for future Creation Chat sessions.

## Notes

- The genesis template is the entry point for every future project. Keep it prescriptive
  but not verbose — a Creation Chat should be able to fill it in one focused session.
- The "HQ Context Packet" section is the handoff to Phase Chat. If Phase Chat can open
  with only genesis.md as input and no additional questions, the template is correct.
- Do not add fields for things Phase Chat decides (milestone specs, epic assignments).
  Genesis scopes only: project identity, Phase 1 boundaries, team composition.

## Implementation Plan

### Phase 1: Design Post-Mortem Generator (Day 1 AM)
Define Post-Mortem Generator class:
- Trigger on Delivery Notice for bugfix with C/H severity
- Generate template with standard sections
- Capture timeline, root cause, resolution, prevention
- Store in artifacts directory

### Phase 2: Severity Detection (Day 1 PM)
Implement detection:
- Parse Delivery Notice metadata
- Extract bugfix ID (B#.#)
- Extract severity (critical, high, medium, low)
- Filter: only process if severity is Critical or High
- Log skipped items (medium/low severity)

### Phase 3: Template Generation (Day 2 AM)
Implement template:
- Timeline section: discovery, reporting, fix, deployment, impact
- Root Cause section: why did this bug occur?
- Resolution section: what fix was applied?
- Prevention section: what changes prevent recurrence?
- Owners section: on-call, developer, reviewer

### Phase 4: Content Capture (Day 2 PM)
Implement content capture:
- Extract timeline from Bugfix Epic metadata
- Extract root cause from Epic description
- Extract fix details from PR description
- Extract prevention ideas from team input
- Combine into complete post-mortem

### Phase 5: Storage & Commit (Day 3 AM)
Implement storage:
- Create `.ai-project/artifacts/bugfixes/` directory
- File naming: `<timestamp>__<bugfix_id>__postmortem.md`
- Commit post-mortem to repository
- Update artifact index

### Phase 6: CFO Reporting (Day 3 PM)
Implement reporting:
- Detect Critical/High bugfixes completed
- Generate report: bugfix ID, severity, title, impact
- Store report for CFO dashboard
- Notify CFO of new post-mortem

### Phase 7: Testing (Day 4 AM)
Create comprehensive tests:
- Happy path: C/H bugfix completed → post-mortem generated
- Skipped: L/M bugfix completed → no post-mortem
- Template: all sections present and well-formed
- Storage: file created, committed, indexed
- 15+ test cases

### Phase 8: Documentation (Day 4 PM)
Create documentation:
- Post-mortem template reference
- Generation flowchart
- Example completed post-mortem
- CFO guide: how to read post-mortems

## Post-Mortem Template Structure

```markdown
---
artifact_type: bugfix_postmortem
bugfix_id: B#.#
severity: critical|high
timestamp: <ISO-8601 UTC>
---

# Post-Mortem: B#.# — <Issue Title>

## Timeline
- Discovered: <YYYY-MM-DD HH:MM UTC>
- Reported: <YYYY-MM-DD HH:MM UTC>
- Fix Deployed: <YYYY-MM-DD HH:MM UTC>
- Impact: <X minutes downtime / Y users affected>

## Root Cause
<Detailed analysis of why the bug occurred>

## Resolution
<What fix was applied and why it works>

## Prevention
<What changes will prevent this from happening again>

## Owners
- On-call: <name>
- Developer: <name>
- Reviewer: <name>
```

   - E15.3 checks severity and decides whether to generate post-mortem

3. **E15.2 (SLA & Gate):**

   - E15.3 triggers after Delivery Notice (after deployment)
   - No timing conflict

4. **CFO Dashboard:**
   - Post-mortem reports aggregated for CFO
   - CFO can browse recent post-mortems
   - Helps CFO understand production issue trends

## Severity Rules

- **Critical:** Production downtime, data loss, security breach — ALWAYS post-mortem
- **High:** Significant feature impairment, user workflow blocked — ALWAYS post-mortem
- **Medium:** Minor feature issue, workaround available — NO post-mortem
- **Low:** Cosmetic issue, edge case — NO post-mortem

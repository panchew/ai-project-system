# Epic P4-M19-E19.2: Creation Chat Ongoing Artifacts

## Design Constraint (Binding)

> Creation Chat is the single visible human interface. All governance (HQ, Phase,
> Milestone, Epic) runs as background agents communicating via artifacts. Design
> decisions at every level must optimize for this: complexity invisible to the user,
> only decisions and outcomes surface. The Progress Digest in particular must be
> high-signal and low-noise — the user should not need to dig into phase or milestone
> artifacts to understand project state.

This constraint governs every template in this Epic. A template that requires the
user to cross-reference other documents to fill it in has failed this constraint.

## Problem Statement

M18 (Inception Artifacts) delivered the bootstrap half of the Creation Chat: the
Genesis template, the Level 0 role definition in `chat-hierarchy.md`, and the updated
`start-a-project.md`. What was not delivered is the **ongoing half**:

- How does the Creation Chat hand off concerns and decisions to HQ Chat between
  sessions? (**Steering Note** — no template or schema exists)
- How does HQ Chat keep the Creation Chat informed of project state without requiring
  the user to dig through governance artifacts? (**Progress Digest** — no template)
- How does the Layer-8 operator record manual interventions so patterns can be detected
  and formalized? (**Bouncer Work log** — no concept exists in the system)
- How does a Creation Chat session resume after a reset without losing continuity?
  (**Re-instantiation ritual** — not documented)

Without these, Creation Chat is a one-shot bootstrap tool, not the permanent
institution the system design requires.

## Requirements

### Functional Requirements

**1. Steering Note Schema and Template**

New file: `governance/templates/steering-note.md`

The reference instance is already committed and is the authoritative schema source:
`.ai-project/artifacts/steering-notes/2026-06-19__creation-chat__steering-note.md`

The template YAML front-matter must be compatible with this instance:
```yaml
artifact_type: steering_note
artifact_version: 1.0
timestamp: <ISO-8601>
issuer_chat: <chat name>
target: <recipient chat name>
project_name: <project-slug>
concerns:
  - id: <SN-number>
    severity: <critical | high | medium | low>
    title: <one-line summary>
decisions:
  - <binding decision text>
```

Required body sections:
- **Purpose** — one paragraph explaining this session's Steering Note
- **Concerns for HQ Triage** — one sub-section per concern (id, severity, detail,
  required action)
- **Decisions Already Made** — binding decisions not for HQ to re-debate
- **Carry-Over Open Items** — non-blocking items passed forward
- **Next Action** — what HQ Chat should do next

Naming convention: `<ISO-date>__<issuer-chat-slug>__steering-note.md`
Storage: `.ai-project/artifacts/steering-notes/`

Include a filled example (may reference the 2026-06-19 instance in the template header).

**2. Progress Digest Schema and Template**

New file: `governance/templates/progress-digest.md`

Flows HQ → Creation Chat on a periodic basis. The user reads this as the primary
summary of project state — it must be self-contained and high-signal.

YAML front-matter:
```yaml
artifact_type: progress_digest
artifact_version: 1.0
timestamp: <ISO-8601>
issuer_chat: HQ Chat
target: Creation Chat
project_name: <project-slug>
period_covered: <ISO-date range, e.g. 2026-06-14 to 2026-06-20>
```

Required sections (no more, no fewer):
1. **Phase Status** — one line per milestone: name, status (✅ complete / 🔄 in
   progress / ⏳ planned), blocking issue if any
2. **Open Decisions** — decisions the user needs to make or confirm; numbered list;
   each item states the question and the deadline or trigger
3. **Next Actions** — 3–5 items maximum; each: what, who initiates, by when
4. **Blocking Concerns** — zero to three items; state "None" if clean

Naming convention: `<ISO-date>__hq__progress-digest.md`
Storage: `.ai-project/artifacts/progress-digests/`

**3. Bouncer Work Log Schema and Template**

New file: `governance/templates/bouncer-work-log.md`

Records Layer-8 manual interventions: data fixes, direct user requests, one-off console
operations — the gap between what the system does and what reality demands.

**Design target: fill in under 2 minutes.** If it takes longer, simplify the template.

YAML front-matter (minimal):
```yaml
artifact_type: bouncer_work_log
timestamp: <ISO-8601>
project: <project-slug>
severity: <data-fix | user-request | system-op | other>
```

Body (four fields only):
1. **What happened** — one sentence describing the situation requiring intervention
2. **What I did** — one sentence describing the manual action taken
3. **Side effects** — (optional) anything that may need follow-up; omit if none
4. **Pattern flag** — `[ ] This is the 3rd+ occurrence of this type → write Steering Note`

Naming convention: `<ISO-datetime>__bouncer-work__<slug>.md`
Storage: `.ai-project/artifacts/bouncer-work-logs/`

The pattern-detection loop the template supports:
```
real-life operation
  → bouncer work happens (manual, no commit)
    → logged in Bouncer Work log (lightweight)
      → pattern (3+ occurrences) → Steering Note → formal Epic
```

**4. Re-instantiation Ritual**

New file: `governance/systems/creation-chat-guide.md`

Describes how to reset a Creation Chat session while preserving continuity via artifacts.
Must specify exactly:

1. **Before reset:** produce and commit a Steering Note to
   `.ai-project/artifacts/steering-notes/<timestamp>__creation-chat__steering-note.md`
   capturing: open concerns, binding decisions from this session, carry-over items,
   next action

2. **What to include** in the pre-reset Steering Note: everything the next session
   needs — not a narrative, but structured concerns and decisions

3. **How to re-open:** pass exactly three artifacts to the new session:
   - The project's committed `genesis.md` (from the project root or governance root)
   - Most recent Steering Note (from `.ai-project/artifacts/steering-notes/`)
   - Most recent Progress Digest, if one exists (from `.ai-project/artifacts/progress-digests/`)

4. **What the new session receives:** a complete picture of project state with no
   session memory required; the new session opens as if continuing uninterrupted

The guide should also document:
- When to write a Steering Note (end of session, before reset, when a blocking concern
  arises mid-session)
- When a Progress Digest is expected (HQ Chat sends one at the start of each new phase
  or on request)
- How Bouncer Work logs feed into Steering Notes (pattern detection)

## Notes

- The 2-minute fill test for the Bouncer Work log is mandatory, not a guideline. If the
  template takes longer than 2 minutes to fill during the implementation test, shorten
  it until it passes. Complexity is the enemy of adoption here.
- The Progress Digest is the primary daily artifact the user sees. It must be tighter
  than any other governance document. If in doubt: cut a section, not add one.
- E19.2 may execute in parallel with E19.1 after E19.1 is dispatched. There is no
  hard ordering dependency between them.

# Epic E30.1 — Token-burn instrumentation

## Context

M30 is the first P9 milestone (`is_final: false`). E30.1 is the first of its three epics and
the hard prerequisite for both siblings: E30.2's audit report, frontier-vs-local policy, and
`.ai-project.yml` `models:` refresh all derive from the dataset this Epic captures, and
E30.3's sizing decision cannot precede this Epic's data. P9 exists because a model-tier
policy was written before any consumption evidence existed and failed in the field
(premium-quota exhaustion — the phase's founding evidence, SN-22, CFO-ratified). This Epic
replaces guessing with measurement.

> **Provenance:** Authored by the Milestone Chat (P9-M30) on 2026-07-17 per adjacency. The
> Coding Agent implements it. E30.1 runs first — E30.2 is blocked on its dataset (hard
> dependency, Milestone spec Sequencing).

> **Source:** M30 Milestone spec (Epic Detail → E30.1); P9 phase spec §P9.1; SN-22
> workstream 1.

**Grounding (verified on `milestone/M30`, 2026-07-17):**

- **No captured consumption data exists anywhere in the repo** — `git grep` finds no token
  dataset, no usage report, no per-level accounting. Prior local-model work (issue #126
  context) produced order-of-magnitude *estimates* only (AOG+PSG core ~24K tokens; full
  governance corpus roughly 10× that). These motivate M30 and do not meet its bar (Hard
  Constraint below).
- **Harness session transcripts exist and carry real per-message token accounting.** Claude
  Code persists every session as JSONL under
  `~/.claude/projects/<project-slug>/*.jsonl` (e.g.
  `~/.claude/projects/-home-panchew-soft-dev-ai-project-system/`), and each assistant
  message embeds a `usage` block:
  `{"input_tokens": …, "cache_creation_input_tokens": …, "cache_read_input_tokens": …,
  "output_tokens": …}` (verified against a live session file 2026-07-17). This is captured
  paid-side data that already exists on the CFO's machine — no new spend is required to
  measure past sessions. **Caveats:** the files live *outside* the repo (machine-local,
  uncommitted); they are unlabeled — nothing in a session file says "this was a Phase Chat
  doing planning" — so level/task-type attribution is part of the mechanism design; and they
  contain full conversation content, so the committed dataset must carry aggregated numbers,
  never raw transcripts.
- **The local/orchestrator path already persists auditable context.**
  `bin/run-dev-agent:40-44,126-143,212-227` writes, per agentic run,
  `.ai-project/artifacts/agentic-runs/<epic_id>/` containing `context.md` (the exact scoped
  context handed to the runner — tokenizable), `transcript.json` (the runner's output), and
  `run-metadata.json` (model, runner, exit code, timing — **no token counts today**). One
  real run exists: `.ai-project/artifacts/agentic-runs/P7-M26-E26.3-PROVE/`. Local (ollama)
  token spend costs no money but competes for the same context-handling machinery — it is
  in-scope for measurement, distinguishable in the dataset from paid spend.
- **Governance-corpus overhead is directly measurable by tokenizing what a chat loads.**
  The corpus is in `governance/` (AOG, PSG, yml-spec, templates, systems/); what each chat
  level actually loads is defined by its starter + the governance references it names.
  Tokenizing those inputs per level yields the overhead figure separable from task spend
  (the Milestone spec's requirement 3). Tokenizer choice (e.g. a local tokenizer as proxy vs
  provider-reported counts) is part of the mechanism design decision — document the choice
  and its error bars.
- **Test baseline:** 307 tests collected on `milestone/M30` (verified 2026-07-17,
  `pytest --collect-only -q`), matching the Milestone spec's "307 baseline, no new skips."

## Problem Statement

The original model-tier policy (local-only at Epic level, frontier everywhere else) was
written with zero consumption evidence and failed in practice — it exhausted the CFO's
premium quota and left them without frontier reasoning when it mattered. Replacing it
requires knowing what a chat at each level, doing each task type, actually costs, and how
much of that cost is governance corpus rather than task work. No such measurement exists;
only estimates do. E30.1 builds the mechanism and captures the data.

---

## Goals

By the end of this Epic:

1. **A measurement mechanism exists and is documented** — what it measures, how, and its
   known blind spots (including cells it cannot see).
2. **Real captured data is committed to the repo** covering:
   - **per chat level:** Phase, Milestone, Epic — plus HQ and Creation for the record;
   - **per task type:** planning, execution, review, closure;
   - **governance-corpus overhead** at each level, separable from task spend.
3. **Every uncapturable cell has an explicit gap record** — a recorded gap, never a
   substituted guess (Hard Constraint).
4. **The dataset is consumable by E30.2** — committed at a stable, documented location, in a
   form the audit report can cite cell-by-cell.
5. **Full test suite passes** (307 baseline, no new skips).

## Hard Constraint (binding — embedded verbatim from the Milestone spec)

> **The frontier-vs-local policy and the `models:` refresh MUST be derived from the captured
> measurements — not from pre-existing assumptions.** Real captured data is the bar;
> estimates do not count (phase acceptance criterion). If a measurement cannot be captured
> for some level or task type, **record the gap explicitly** in the report rather than
> substituting a guess — a policy row grounded in a recorded gap is acceptable; a policy row
> grounded in an unlabeled assumption is not. This constraint governs E30.2 directly and
> sizes E30.3: no reduction work may be scoped from the prior 24K/157K estimates alone.

For E30.1 specifically this means: the dataset you commit is the sole evidence base the rest
of M30 (and M31's binding-order consumption) stands on. Do not backfill any cell from the
prior estimates; do not label an estimate as a measurement; record every hole as a gap.

## Design Decision (yours to resolve — decide, document, move; do not escalate to ask which mechanism to build)

**The measurement mechanism is this Epic's one open design point** (Milestone spec: "a
design decision for the Milestone/Epic Chat, not fixed by this spec"). Candidate directions
(non-exhaustive, combinable):

- **(A) Harness/API usage logs.** Parse the per-message `usage` blocks in the Claude Code
  session JSONL files (`~/.claude/projects/<project-slug>/*.jsonl`). Strengths: real
  provider-reported counts for the paid side, already captured, covers past sessions at no
  new spend. Weaknesses: machine-local and unlabeled — the mechanism must define how
  sessions are attributed to chat level and task type (session-to-chat mapping is the hard
  part), and must aggregate before committing (transcripts contain conversation content).
- **(B) Transcript/context token counting.** Tokenize stored inputs directly: the
  governance corpus per level, chat starters, `agentic-runs/<epic>/context.md`. Strengths:
  directly yields the governance-corpus-overhead figure, works for local runs, fully
  reproducible from committed files. Weaknesses: a local tokenizer is a proxy for
  provider-billed counts (document the error bars); measures loaded context, not
  conversation spend.
- **(C) Orchestrator-path instrumentation.** Extend `bin/run-dev-agent` /
  `run-metadata.json` to record token counts per agentic run (e.g. from the runner
  transcript or ollama's reported counts). Strengths: durable forward-looking capture for
  the local path. Weaknesses: only covers Epic-level agentic runs; one historical run
  exists today, so backward coverage is thin.

A **hybrid is likely the honest answer** — (A) for paid per-level/per-task spend, (B) for
corpus overhead, (C) optional for forward local capture — but the choice is yours: pick,
document the reasoning and blind spots in the mechanism doc, and proceed. Whatever is
chosen MUST produce the level × task-type matrix with corpus overhead separable, and MUST
record a gap for any cell it cannot honestly fill.

## Technical Constraints

- **Privacy:** the committed dataset carries aggregated token numbers and attributions
  only — never raw session transcripts or conversation content. Harness JSONL files stay
  where they are (machine-local); only derived numbers enter the repo.
- **Repo surfaces in scope:** the dataset + mechanism doc under `.ai-project/artifacts/`
  (location per Deliverable 2); optionally `bin/run-dev-agent` and a small
  parser/aggregator script **only if** the chosen mechanism requires them. Nothing else.
- **Do NOT touch:** `.ai-project.yml` (any field — `models:` is E30.2's), any governance
  document (`governance/`), the audit report (doesn't exist yet — E30.2), any
  context-loading behavior (E30.3's surface).
- **Paid-spend pacing:** any capture step that spends new paid tokens is CFO-paced. Prefer
  measuring already-captured data (past sessions) first; new paid captures are optional
  extras, and a pacing stall converts to a gap record, not a wait.

## Execution Notes

- **The dataset's shape is the contract with E30.2.** Before finalizing, sanity-check that
  each audit question the Milestone spec assigns E30.2 (where frontier tokens go; which
  spends needed frontier reasoning; which a local model could have carried; corpus-overhead
  findings) can be answered — or gap-recorded — from your dataset alone. A dataset that
  forces E30.2 back to raw transcripts has failed this Epic's purpose.
- **Attribution honesty over coverage.** A smaller matrix of confidently-attributed cells
  plus explicit gaps beats a full matrix of shaky attributions. Where a session's chat
  level or task type is ambiguous, either document the attribution rule that resolves it or
  record the cell as a gap — do not guess silently (Hard Constraint).
- **Verify the grounding's anchors at execution time** — this spec cites file paths and
  line numbers as of 2026-07-17; confirm each before relying on it (GH-2 discipline).
- Default-accept (PSG §11.6 / AOG §12) governs this Epic's delivery: a clean delivery is
  accepted by silence; the epic-PR merge is human-authorized in-chat (SN-19); a Review
  Decision is the exception path only.

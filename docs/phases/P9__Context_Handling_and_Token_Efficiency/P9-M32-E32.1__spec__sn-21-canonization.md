# Epic E32.1 — SN-21 canonization

## Context

System HQ has operated in the field since 2026-07-16 across all 8 governed projects on the
CFO's machine, discovered zero-cost via the existing read-only MCP bridge
(`list_governance_state` indexes artifact directories by name). It writes two artifact
types — `system_request` (project → system) and `system_response` (system → project) —
following the Artifact Communication Protocol's existing frontmatter+body, ISO-8601 UTC
timestamp, and immutability conventions, with `status: pending | in_progress | done |
declined | escalated`. None of this is written into `governance/` today: no schema, no
hierarchy placement, no normative authority statement. SN-21 (Creation Chat, CFO-ratified)
triaged this as canonize-now, in P9, not observe-and-wait — the pattern is live, load-
bearing for SN-22's "every governed project makes progress" goal, and the CFO has asked for
a recurring re-instantiation seed (E32.2, sequenced after this Epic).

**Grounding (verified on `milestone/M32` @ `e12c13c`, 2026-07-20):**

  Types` section (line 38) with exactly two live types today: `### 1. Delivery Notice`
  (line 40) and `### 2. Review Decision` (line 169), plus a retired `### 3. Post-merge
  "Delivery Notice"` section (line 315, historical only — not a slot to reuse). Both live

  Structure` YAML-frontmatter-plus-body template, and a fenced `#### Examples` block. A
  `system_request`/`system_response` pair, if added here, would be `### 4.` and `### 5.` (or
  one `### 4.` entry covering both directions of the pair, mirroring how Delivery Notice and
  Review Decision are already a request/response pair across the Epic↔Milestone↔Phase
  chain) — the document's own numbering and structure are the precedent to match, not
  reinvent.
- `governance/systems/chat-hierarchy.md` (effective 2026-07-19) is titled "the single
  authoritative end-to-end reference for the complete AI Project System chat hierarchy" and
  its "The Four-Level Chat Hierarchy" section (line 15) is explicit that the diagram and
  table describe **four levels within a single project** (Creation/Level 0 bootstrap, then
  HQ/Phase/Milestone/Epic as Levels 1–4). Nothing in the document today describes a
  participant that spans multiple projects on one machine. The "Artifact Scope Adjacency"
  section (line 619) and "Communication Protocol" section (line 650) both assume the same
  single-project, one-parent-per-level shape. System HQ does not fit anywhere in that shape
  as written — SN-21's own framing, "closest in spirit to Layer-8/CFO support staff," is a
  hint that it sits *above and across* the whole diagram, not inside it.
- No occurrence of `system_request`, `system_response`, or "System HQ" exists anywhere
  under `governance/` today (`grep -rn "system_request\|system_response\|System HQ"
  governance/` returns nothing) — this Epic is the first governance-surface mention of
  either.
- `~/.ai-project/SYSTEM-GOVERNANCE.md` (outside this repo) is the field adoption record —
  informative context for what field practice actually looks like, not an edit target for
  this Epic.
- Test baseline: 363 tests collected on `milestone/M32` (M31's closing baseline, unchanged
  — M32 has not touched code yet).

## Problem Statement

Field practice has outrun the written framework. System HQ writes `system_request`/
`system_response` artifacts today, with no schema anyone can check a new artifact against,
no stated place in the hierarchy a reader can consult to understand what System HQ is
relative to the four-level chain, and no normative statement of what it may and may not do.
A reader encountering a `system_request` file in the wild has no governance document to
turn to.

---

## Goals

By the end of this Epic:

1. **`system_request`/`system_response` schemas exist in governance**, in a decided home,
   matching SN-21's field usage (storage paths, naming, status vocabulary) rather than
   inventing new conventions.
2. **System HQ's place relative to `chat-hierarchy.md` is decided and recorded**, in a form
   that cannot be misread as a fifth per-project level slotted into Levels 0–4.
3. **A normative authority-boundary statement exists**, locatable from both the schema home
   and the hierarchy-placement location: System HQ executes within tool authority; it never
   makes review, merge, or scope decisions; `status: escalated` is mandatory for anything
   review/merge/scope-shaped.

---

- Touch P8-GH-1, P8-GH-3, or P8-GH-2's restatement — that is E32.3's independent surface.
- Redesign System HQ's actual behavior. SN-21's own framing is "the framework has a working
  extension point it never named" — this Epic documents what already runs; it does not
  invent new mechanics.

## Hard Constraints (binding — carried verbatim from the Milestone spec into this Epic)

1. **No authority expansion.** Every description of System HQ's authority — in the schema
   home, the hierarchy-placement location, or anywhere else this Epic writes — must state
   execute-never-decide explicitly. Silence on the boundary anywhere is not acceptable.
   `status: escalated` is the mandatory path for anything review/merge/scope-shaped.
2. Suite green at every merge — 363 baseline, no regressions, no skips introduced to route
   around changes. (This Epic is documentation/schema-only; the suite should be unaffected,
   but the check still runs.)

*(Hard Constraints 2 and 3 from the Milestone spec — grep-verifiable hygiene and P8-GH-2
restatement — are E32.3's surface, not this Epic's; not restated here as this Epic does not
touch either.)*

## Design Decisions (yours to resolve — decide, document, move; do not escalate to ask)

1. **Schema home.** Two candidates, both legitimate:
   - **(A) Inside `artifact-communication-protocol.md`'s existing `## Artifact Types`
     section**, as new numbered type(s) alongside Delivery Notice and Review Decision. Pro:
     one document remains the single canonical home for every artifact type in the system;
     a reader who already knows to look there finds this pair too. Con: the existing types
     are all *intra-project*, Epic↔Milestone↔Phase↔HQ; `system_request`/`system_response`
     are the first *cross-project* pair, which may read as a mismatch inside a document
     whose own "Core Principles" (line 27) and "Communication Flow Diagram" (line 338)
     describe a single-project chain.
   - **(B) A companion system-participant document**, cross-referenced from the protocol
     (a "Reference" line added to the protocol's existing `## Reference` section, line
     437). Pro: keeps the cross-project pair from crowding a document whose existing
     examples, changelog, and flow diagram are all single-project; gives System HQ's
     material a home that can grow (e.g., if E32.2's seed or future System HQ documentation
     needs a natural place to live nearby) without further stretching the protocol
     document's scope. Con: a second document to know about.
   - Either way: the storage/naming conventions and status vocabulary are **already fixed
     by SN-21's field usage** (`.ai-project/artifacts/system-requests/`,
     `.ai-project/artifacts/system-responses/`, `status: pending | in_progress | done |
     declined | escalated`) — this Epic documents them, it does not invent new ones.
2. **Hierarchy-placement form.** SN-21's own framing: "closest in spirit to Layer-8/CFO
   support staff." Candidate directions:
   - An **out-of-hierarchy annex** in `chat-hierarchy.md` — a new section, clearly titled
     to signal it is not a fifth level (e.g., something in the spirit of "System HQ —
     Out-of-Hierarchy, Cross-Project"), with a pointer from the "The Four-Level Chat
     Hierarchy" section's introduction so a reader hits it early.
   - An **explicitly-orthogonal new level**, structurally distinct from Levels 0–4 (a
     different heading tier, different table, explicit "this is not Level 5" language) —
     riskier: any level-shaped presentation invites misreading as "inside" the four-level
     chain no matter how many disclaimers surround it.
   - An **out-of-hierarchy pointer only** — a short paragraph in `chat-hierarchy.md`
     directing the reader to the schema home (Design Decision 1) for the substantive
     material, rather than duplicating System HQ's description in both places.
   - Whichever direction, the deliverable must make it **structurally obvious**, not just
     stated once, that System HQ is one desk per *machine* spanning every governed project,
     not a per-project chat — a reader skimming headings alone should not come away
     thinking it is "Level 5."

## Execution Notes

- **This is field documentation, not invention.** Resist redesigning System HQ's behavior
  while canonizing it — the storage paths, naming convention, and status vocabulary are
  fixed by what already runs in the field (SN-21), not open for this Epic to change.
- **The hierarchy-placement decision is the harder of the two** — `chat-hierarchy.md`'s
  entire document is built around a single-project, four-level shape (see Grounding). Read
  the whole document before deciding where System HQ's annex goes; a placement that reads
  naturally next to "The Four-Level Chat Hierarchy" risks implying inclusion inside it.
- **E32.2 depends on this Epic's authority-boundary language landing first** — write it
  once, clearly, in a place E32.2's seed can point to rather than restate.
- Default-accept (PSG §11.6 / AOG §12) governs this Epic's delivery: a clean delivery is
  accepted by silence; the epic-PR merge is human-authorized in-chat (SN-19); a Review
  Decision is the exception path only.

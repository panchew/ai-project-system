# Epic E32.2 — System Chat re-instantiation seed

## Context

Creation Chat has a working re-instantiation pattern: `governance/templates/genesis.md` /
`governance/templates/seed.md`, with an explicit "Rule 5 — Re-instantiation" in `seed.md`
("paste this Genesis artifact plus the current Project Brief into a new session. The
Creation Chat continues as an institution regardless of which session window holds it.").
System HQ has no analogue. SN-21 Required Action 4 names a recurring re-instantiation seed
as a concrete requirement, confirmed by the CFO (SN-22): the CFO currently has no recorded,
repeatable way to spawn System HQ daily. E32.1 (sequenced first, per the Milestone spec)
canonizes the schema and authority-boundary language this Epic must cross-reference.

> **Provenance:** Authored by the Milestone Chat (P9-M32) on 2026-07-20 per adjacency,
> Stage 1 (epic planning). The Coding Agent implements it.

> **Source:** SN-21 Required Action 4
> (`.ai-project/artifacts/steering-notes/2026-07-16__creation-chat__steering-note__system-hq-adoption.md`);
> P9 phase spec §P9.3; SN-22 (CFO input); M32 Milestone spec (Epic Detail → E32.2).

**Grounding (verified on `milestone/M32` @ `6c1ac8e`, 2026-07-20):**

- `governance/templates/genesis.md` (front-matter `type: genesis`) and
  `governance/templates/seed.md` (front-matter `artifact_type: seed`, `artifact_version:
  1.0`) are both **per-project** templates: `genesis.md`'s own header comment calls it "the
  single artifact that must exist before a Phase Chat opens," scoped to one project's
  identity, Phase 1 boundaries, and team. `seed.md`'s "Rule 5 — Re-instantiation" (line 108)
  is the closest existing analogue to what this Epic needs to build for System HQ, but its
  re-instantiation mechanics ("paste this Genesis artifact plus the current Project Brief")
  assume a single project's own Creation Chat, not a cross-project desk.
- Both templates already carry **two prior additions this Epic must preserve unreworked**:
  P9-M31-E31.3's "Prerequisite Verification (do this first — P9-M31-E31.3)" section (model
  self-verification against `models.creation`, present near the top of both files) and the
  general manual-mode guardrail instruction pattern it established. Neither template's
  Prerequisite Verification section applies to System HQ directly (System HQ is not a
  per-project `creation` key) — this Epic's seed needs its own equivalent verification
  language, not a copy of theirs, if System HQ has (or gains) a model expectation of its
  own; if it does not, say so rather than silently omitting the section.
- `governance/templates/` currently holds 23 files, all per-project artifacts (specs,
  starters, notices, the genesis/seed pair) — none is a cross-project, machine-level
  artifact. A System Chat seed placed there would be the first template in that directory
  that is not project-scoped.
- E32.1 (sequenced first) is this Epic's direct dependency: the seed's authority-boundary
  language and artifact-schema references must point at whatever E32.1 actually delivers,
  not at this spec's own paraphrase of the Milestone spec's Binding Context.
- Test baseline: 363 tests collected on `milestone/M32` (unchanged by E32.1, which is
  documentation/schema-only).

## Problem Statement

No recurring seed exists for the CFO to spawn System HQ daily, unlike Creation Chat's
Genesis/seed pattern. SN-21 names this explicitly as a concrete requirement. Without it,
each System HQ instantiation either re-derives its own identity and authority boundary from
scratch (risking drift from what E32.1 canonizes) or depends on the CFO manually
reconstructing context every time — exactly the kind of informal, un-auditable practice the
rest of this framework's artifact-first model exists to avoid.

---

## Goals

By the end of this Epic:

1. **A System Chat re-instantiation seed artifact exists**, usable by the CFO to spawn
   System HQ recurrently (SN-21: "ideally daily"), analogous in spirit to Genesis/seed but
   reflecting System HQ's cross-project, execute-never-decide identity rather than a
   per-project Creation Chat's.
2. **The seed cross-references E32.1's canonized authority boundary and schema home**
   rather than restating them divergently — single source of truth.
3. **The seed's own instructions grant no review/merge/scope authority** to System HQ,
   consistent with Hard Constraint 1.

- Touch E32.1's schema or hierarchy-placement material beyond referencing it — if E32.1's
  delivery seems incomplete or wrong for this Epic's purposes, escalate to the Milestone
  Chat rather than reworking E32.1's surface directly.
- Build the MCP bridge write path or a scheduled request-sweep/SLA mechanism — SN-21
  carry-overs, explicitly deferred, and out of this repo's jurisdiction if ever built.
- Modify `ai-project-system-mcp` in any way.
- Touch E32.3's surface (P8-GH-1, P8-GH-3, P8-GH-2 restatement) — fully independent.
- Rework `genesis.md`/`seed.md`'s existing per-project content, including E31.3's guardrail
  instruction already present in both — this Epic may add a System-HQ-specific
  Prerequisite-Verification-style section to its **own new** seed artifact, but must not
  disturb the existing per-project templates' content.

## Hard Constraints (binding — carried verbatim from the Milestone spec into this Epic)

1. **No authority expansion.** The seed's own instructions must state execute-never-decide
   explicitly wherever they describe what System HQ may do — silence on the boundary is not
   acceptable. `status: escalated` is the mandatory path for anything review/merge/
   scope-shaped the seed's instructions touch on.
2. Suite green at every merge — 363 baseline, no regressions, no skips introduced to route
   around changes. (Documentation-only; the suite should be unaffected, but the check still
   runs.)

*(Milestone Hard Constraints 2 and 3 — grep-verifiable hygiene, P8-GH-2 restatement — are
E32.3's surface, not this Epic's.)*

## Design Decisions (yours to resolve — decide, document, move; do not escalate to ask)

1. **The seed's concrete form and home.** Two candidates:
   - **(A) A dedicated template under `governance/templates/`**, mirroring `genesis.md`/
     `seed.md`'s pattern structurally (front-matter + Rules-of-Engagement-style sections +
     a "What to Do Right Now" close) so it reads familiarly to anyone who knows the
     Creation Chat pattern. Pro: consistency with the one working precedent this framework
     has for a re-instantiation artifact; a reader who understands `seed.md` understands
     this by analogy. Con: `governance/templates/` is otherwise a purely per-project
     directory (see Grounding) — placing a cross-project artifact there could read as
     implying System HQ is "just another project template," the opposite of what E32.1's
     hierarchy-placement work is trying to establish.
   - **(B) A system-tier document outside the per-project template set** (e.g., adjacent
     to wherever E32.1 places System HQ's schema/hierarchy material, or a new top-level
     location reflecting that System HQ is one desk per machine, not per project). Pro:
     structurally honest about System HQ not being a per-project artifact; keeps
     `governance/templates/`'s existing meaning (a directory of per-project scaffolding)
     intact. Con: a genuinely new kind of location in this repo, with no existing
     precedent to lean on.
   - Whichever you choose, the seed must still contain what `seed.md`'s Rule 5
     demonstrates is the essential re-instantiation mechanic: a self-contained artifact
     that can be hand-fed into a fresh session with no other document required to
     reconstruct System HQ's identity and constraints.
2. **What the seed must say, minimally**, drawing the analogy to `seed.md`'s "Rules of
   Engagement" and "What to Do Right Now" sections but adapted for System HQ's actual job
   (executing `system_request`s across projects, never deciding): its cross-project scope,
   its execute-never-decide boundary (cross-referencing E32.1, not restating), how it
   discovers pending `system_request`s (per SN-21's field record — via the existing
   read-only MCP bridge / `list_governance_state`), and what it must do when a request is
   review/merge/scope-shaped (`status: escalated`, per E32.1).

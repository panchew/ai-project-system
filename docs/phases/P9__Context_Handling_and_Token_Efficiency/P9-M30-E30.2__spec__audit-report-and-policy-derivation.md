# Epic E30.2 — Audit report + policy derivation

## Context

E30.1 is delivered and merged (`milestone/M30` @ `e7aef45`): the token-burn dataset exists
at `.ai-project/artifacts/reference/token-measurement/` with the mechanism doc, the level ×
task-type matrix, gap records G1–G10, and a "Contract with E30.2" section mapping every M30
audit question to dataset cells. E30.2 consumes that dataset — and nothing else — to
produce the audit report, the recorded frontier-vs-local policy, and the `.ai-project.yml`
`models:` refresh. **This epic is the M30 → M31 binding-order link:** M31's manual-mode
guardrail verifies chats against the refreshed `models:` block, and M31's agentic
paid-vs-local logic applies the recorded policy. Deliver both as things another milestone
can consume.

> after E30.1's acceptance and merge (hard dependency satisfied). The Coding Agent
> implements it.

> **Source:** M30 Milestone spec (Epic Detail → E30.2); P9 phase spec §P9.1; phase success
> criteria 1–2; SN-22 workstream 1.

**Grounding (verified on `milestone/M30` @ `e7aef45`, 2026-07-17):**

- **The dataset (your sole evidence base).**
  `.ai-project/artifacts/reference/token-measurement/token-burn-dataset.{json,md}` +
  `README.md`. 72 paid sessions (2026-06-12 → 2026-07-17), aggregates only. Measured
  matrix cells: epic×execution (n=38), milestone×planning (2), milestone×review (1),
  phase×planning (1), hq×planning (3); creation measured as level totals; mixed/
  unattributed buckets reported whole; every empty cell carries a numbered gap or
  structural record (G1–G10). Paid (§§1–3) and local (§5) are separate; §4 is the
  proxy-tokenized corpus overhead. Attribution rows carry confidence flags
  (`level_rule`/`task_rule`; `branch-fallback` and signal-based rules are
  lower-confidence) — weigh them.
- **The stale `models:` block** — `.ai-project.yml:22-27`: `hq: remote:gpt-4o`,
  `phase: remote:claude-3-5-sonnet`, `milestone: remote:claude-3-5-sonnet`,
  `epic_dev: local:qwen2.5-coder:14b`, `epic_qa: local:qwen2.5-coder:7b`.
- **The dataset's §2 by-model table falsifies the stale names directly:** the models that
  actually ran in the window are `claude-fable-5`, `claude-opus-4-8`, `claude-sonnet-4-6`,
  `claude-sonnet-5`. Neither `gpt-4o` nor `claude-3-5-sonnet` appears in a single session.
  The refresh is not a rename — it is replacing fiction with the measured reality.
- **The stale names also live in the yml-spec's own §3.4 table.**
  `governance/ai-project-yml-spec.md` (v2.3.1) §3.4 hardcodes `remote:gpt-4o` /
  `remote:claude-3-5-sonnet` as the documented **defaults** and as Allowed-Formats
  examples for `hq`/`phase`/`milestone`. A pure value refresh of `.ai-project.yml` leaves
  the schema's defaults stale — see the Design Decisions section for how to handle this
  honestly (it interacts with the policy-home choice).
- **Price weighting is required to turn volumes into cost.** The dataset keeps the four
  usage components separate on purpose: cache reads dominate raw volume (e.g.
  epic×execution: 173.2M cache-read vs 5.6M cache-creation vs 1.5M output) but bill at
  ≈0.1× base input, while cache creation bills ≈1.25× and output carries its own rate. An
  audit that sums raw token counts without documented price weighting will misstate where
  the money goes. Document the weights used (with their source) in the report.
- **Local evidence is thin and the dataset says so:** one run (404 output tokens, G9 input
  gap). "Which spends a local model could have carried" is therefore a judgment E30.2
  makes *against* the measured paid rows (task shapes, session sizes, model mix) with the
  thin local evidence and its gaps cited as such — the Hard Constraint's gap-grounded
  policy rows exist for exactly this.
- **The dataset's level set is wider than the `models:` key set.** The matrix measures
  creation/hq/phase/milestone/epic; `models:` has keys `hq`, `phase`, `milestone`,
  `epic_dev`, `epic_qa` (no `creation` key). Adding a key would change `models:`
  semantics — see Design Decisions.
- **Test baseline:** 307 tests collected, all passing on `milestone/M30` (verified at
  E30.1 acceptance).

## Problem Statement

The system has never had an evidence-grounded answer to "when is a paid frontier model
worth it, and when does a local model suffice?" — the original assumption (local at Epic,
frontier everywhere else) predated all evidence, failed in the field (premium-quota
exhaustion), and still sits falsified in `.ai-project.yml` as model names that never ran.
E30.1 captured the evidence. E30.2 turns it into: an audit report a reader can trust, a
recorded policy M31 can apply, and a `models:` block M31's guardrail can verify against.

---

## Goals

By the end of this Epic:

1. **A committed measurement/audit report** stating: per-level and per-task-type
   consumption (from E30.1's data, with documented price weighting); where frontier/paid
   tokens actually go; which expenditures needed frontier reasoning and which a local
   model could have carried (judgment grounded in the measured rows and cited gaps);
   governance-corpus overhead findings; the G1–G10 gap records carried forward.
2. **The recorded frontier-vs-local policy** in its decided documentation home — for each
   chat level and task type (or recorded gap): paid or local as default, and why, each row
   tracing to the report.
3. **`.ai-project.yml`'s `models:` block refreshed** to the evidence-grounded mapping — no
   `gpt-4o` or `claude-3-5-sonnet` remnant. This is the block M31's guardrail verifies.
4. **The yml-spec handled honestly:** version bump + changelog row if and only if `models:`
   semantics change; the §3.4 stale-defaults question answered explicitly either way.
5. **Full test suite passes** (307 baseline, no new skips).

---

## Non-Goals

This Epic explicitly does **not**:

- **Build M31's mode switch, guardrail, or agentic paid-vs-local decision logic** — E30.2
  records the policy; M31 applies it. Nothing here executes policy at runtime.
- **Do context-load reduction or size it** — E30.3's surface (the report's corpus-overhead
  findings are E30.3's evidence frame, nothing more).
- **Recapture or extend measurements.** If the dataset cannot answer a question, the
  answer is a carried-forward gap, not a new capture (a targeted rerun of
  `bin/measure-token-burn` to refresh the snapshot is permitted but not required — if
  rerun, commit the regenerated dataset in the same delivery and note it).
- **Roll the policy out to other governed projects** — future triage; this epic records it
  in this source repo only (Milestone spec, Out of Scope).
- **Change `.ai-project.yml` fields other than `models:`** — `cfo_review_gate`,
  `visual_artifacts`, `governance` are untouchable here.

## Hard Constraint (binding — embedded verbatim from the Milestone spec)

> **The frontier-vs-local policy and the `models:` refresh MUST be derived from the
> captured measurements — not from pre-existing assumptions.** Real captured data is the
> bar; estimates do not count (phase acceptance criterion). If a measurement cannot be
> captured for some level or task type, **record the gap explicitly** in the report rather
> than substituting a guess — a policy row grounded in a recorded gap is acceptable; a
> policy row grounded in an unlabeled assumption is not. This constraint governs E30.2
> directly and sizes E30.3: no reduction work may be scoped from the prior 24K/157K
> estimates alone.

For E30.2 specifically: **every claim in the report and every row of the policy must cite
its dataset cell (section/row) or its gap record (G-id).** Where the data is
lower-confidence (branch-fallback attribution, mixed buckets, thin local evidence), the
citation says so. The prior 24K/157K estimates may be *mentioned* only as history — §4 of
the dataset now carries the measured corpus numbers; use those.

## Design Decisions (yours to resolve — decide, document, move; do not escalate to ask)

1. **The policy's documentation home** (the Milestone spec's open design point):
   governance doc, yml-spec section, or both. Considerations: M31 must consume it
   programmatically-ish (guardrail + decision logic), the CFO must be able to read it, and
   it must version cleanly. Whatever you choose, **document the choice and reasoning in
   the report** and cross-link home ↔ report ↔ `models:` block.
2. **The `models:` refresh shape.** A pure value refresh (same five keys, new values)
   needs no yml-spec bump. But weigh what the evidence actually supports: the dataset
   measures per task type, and levels the key set doesn't cover (creation). If the honest
   policy needs semantics the current schema can't express (new keys, per-task routing, a
   fallback entry), that is a **semantics change**: bump the yml-spec version, add the
   changelog row, and update §3.4's field table + validation rules (14–17) coherently.
   Do not contort the policy to avoid a bump, and do not bump for a pure value refresh.
3. **The yml-spec §3.4 stale-defaults question.** Even on a pure value refresh, §3.4's
   defaults table still documents `remote:gpt-4o` / `remote:claude-3-5-sonnet` as
   defaults. Decide explicitly: update the defaults to match the refreshed mapping (that
   is a schema-documentation change — bump + changelog), or leave them with a recorded
   rationale (e.g. defaults are format illustrations for adopting repos, superseded by
   the recorded policy — say where). **Silence is not an option;** the report must state
   which was done and why. Note the milestone acceptance grep covers `.ai-project.yml`
   only — the spec-table decision is about honesty, not passing the grep.
4. **The report's committed location.** Recommended:
   `.ai-project/artifacts/reference/token-measurement/audit-report.md` (beside its
   evidence; the reference-artifact convention) — your final call, documented, stable,
   linkable by M31.

## Technical Constraints

- **Evidence discipline:** the dataset (+ its README) is the sole measurement source. No
  new session parsing, no raw-transcript reads, no external benchmarks presented as
  measurements. Judgments are allowed — labeled as judgments, grounded in cited rows.
- **In scope:** the report file; the policy home (per Design Decision 1 — a governance
  doc and/or yml-spec section); `.ai-project.yml` `models:` block + its comment;
  yml-spec §3.4/changelog iff triggered; tests only if a semantics change requires
  validation updates.
- **Do NOT touch:** any other `.ai-project.yml` field; `bin/measure-token-burn` or the
  dataset files (except a documented full regeneration, Non-Goals); `bin/run-dev-agent`;
  AOG/PSG **unless** the chosen policy home is a governance doc — in which case the edit
  is additive (the policy section/doc), not a rewrite of existing normative text.
- **Price weighting must be documented** with the rates used and their source, in the
  report, wherever volumes are converted to cost.

## Execution Notes

- **Start from the dataset README's "Contract with E30.2" section** — it maps each audit
  question to the sections built to answer it. If you find a question the dataset cannot
  answer and no G-record covers, that is a *new* gap: record it in the report explicitly
  (numbered, continuing the G-series), don't paper over it.
- **The needed-frontier vs local-capable split is the report's hardest and most valuable
  judgment.** Ground it in what the rows show (task shapes, output sizes, session
  complexity, model mix) and say plainly where the thin local evidence (one run, G9)
  limits confidence. A confident-sounding table with unlabeled assumptions violates the
  Hard Constraint; a hedged table with cited evidence and cited gaps is the deliverable.
- **Mind the attribution confidence flags** — `branch-fallback` and mixed-bucket rows are
  lower-confidence by the mechanism's own documentation; weight or caveat accordingly.
- **The refreshed `models:` block must be internally consistent with the policy** — if
  the policy says "milestone planning: paid frontier," the `milestone:` key can't say
  `local:...`. M31's guardrail will hold chats to this block; write it as the
  verification target it is.
- **Verify the grounding's anchors at execution time** (yml-spec §3.4 line positions,
  `.ai-project.yml:22-27`, dataset paths) — GH-2 discipline.
- Default-accept (PSG §11.6 / AOG §12) governs this Epic's delivery: a clean delivery is
  accepted by silence; the epic-PR merge is human-authorized in-chat (SN-19); a Review
  Decision is the exception path only.

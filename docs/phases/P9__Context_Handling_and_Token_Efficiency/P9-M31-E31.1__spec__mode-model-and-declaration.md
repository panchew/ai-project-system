# Epic E31.1 — Mode model + declaration mechanism

## Context

M31 opens P9's second milestone: giving Phase/Milestone/Epic chats a per-instance
manual/agentic mode switch, grounding the agentic path's paid-vs-local choice in M30's
recorded policy, and making manual chats verify their own model at startup. **E31.1 is the
hard first link** — E31.2 (agentic decision logic) and E31.3 (manual guardrail) both attach
to the mode model this epic records. Neither may branch before E31.1 merges.

> **Provenance:** Authored by the Milestone Chat (P9-M31) on 2026-07-19 per adjacency, as
> the first of three Epics. The Coding Agent implements it.

> **Source:** M31 Milestone spec (Epic Detail → E31.1); P9 phase spec §P9.2; SN-22
> workstream 2 (ratified decision 3).

**Grounding (verified on `milestone/M31` @ branch point from `phase/P9` `a3281c3`,
2026-07-19):**

- **No recorded mode model exists today.** Every chat to date has run manually. The P7
  agentic mechanism (`bin/ai-project-orchestrator` dispatching to `bin/run-dev-agent`) is
  built and functions on `phase/P9` at v6.0.1 — but nothing records *which* instances may
  run through it, what "agentic" means at each working level, or that Creation/HQ never do.
  This epic supplies that missing governance layer; it does not touch the orchestrator or
  runner code (E31.2's surface).
- **`.ai-project.yml`'s `models:` block is not a mode switch.** Per the recorded policy's
  Domain note
  (`.ai-project/artifacts/reference/token-measurement/model-routing-policy.md`), the block
  "configures *unattended agentic execution*" — it is a paid-vs-local routing table for
  when a level *is* agentic, not a declaration of whether it is. Conflating the two would
  make a project-wide config value stand in for a per-instance choice, which directly
  contradicts SN-22 ("per instance, one by one" — Binding Context item 1). Keep them
  orthogonal.
- **Naming collision risk:** `governance/systems/chat-hierarchy.md` (§Hierarchy Summary
  Table, ~line 24) already uses the word **"Mode"** to mean *which level* a chat instance
  is (HQ/Phase/Milestone/Epic mode). This epic introduces a second, orthogonal axis
  (manual-or-agentic) for the same instance. Reusing "mode" for both will produce sentences
  that parse two ways ("Milestone mode in agentic mode"). **Pick a distinct term for the
  new axis** (e.g. "Execution Mode") and do not overload the existing "Mode" column's
  meaning — a Design Decision below, not a suggestion to ignore.
- **Creation and HQ have no agentic mechanism today and SN-22 keeps it that way
  permanently** — this is not a temporary gap to schedule around; it is the thing E31.1
  records normatively (Binding Context item 1).
- **Test baseline:** 307 tests collected, all passing on `phase/P9` at the branch point.

---

## Problem Statement

The mode concept — manual chats vs. an agentic path that already exists mechanically —
lives only as unrecorded practice. Nothing declares which concrete instance of a
Phase/Milestone/Epic chat is running manually or agentically, what each mode concretely
means at each level, or that Creation and HQ never go agentic. Until this is recorded,
E31.2's decision logic has no declared instance to key off of, and E31.3's guardrail has
no manual-chat set to check.

---

## Goals

By the end of this Epic:

1. **A recorded mode model exists**: manual vs. agentic semantics per working level (Phase
   / Milestone / Epic), a per-instance declaration mechanism, and absence-means-manual as
   the default (Hard Constraint 2).
2. **Creation Chat and HQ Chat are recorded manual-only, permanently**, normatively, in the
   decided governance home — not a deferral note.
3. **A working-level chat instance can demonstrably be started in either mode**, with the
   mode recorded per instance — phase acceptance criterion; evidence committed, not
   asserted.
4. **The G7 (one-task-one-session) recommendation's disposition is recorded** — adopted as
   labeled guidance in the mode model's session-discipline prose, or explicitly not
   adopted; either is acceptable, silence is not (Deliverable 5).

---

## Non-Goals

This Epic explicitly does **not**:

- **Build the agentic paid-vs-local decision logic** — E31.2's surface. E31.1 records that
  agentic instances exist and what they mean; it does not implement how they choose a
  model per task.
- **Build the manual-mode startup guardrail** — E31.3's surface. E31.1 records who is
  manual and what a mismatch would mean in principle; it does not implement verify-and-
  refuse behavior.
- **Touch `bin/ai-project-orchestrator`, `bin/run-dev-agent`, or the consistency-guard
  tests** — those are E31.2 surfaces.
- **Change Creation/HQ's manual-permanence in either direction.** It is recorded here as
  already-settled policy (SN-22), not decided or revisited.
- **Re-derive or re-debate M30's policy rows.** Not this epic's concern at all — E31.1
  never reads or writes the policy file.
- **Make agentic the default anywhere.** Absence of a per-instance declaration MUST resolve
  to manual, in every level's semantics this epic records (Hard Constraint 2).

---

## Hard Constraints (binding — carried verbatim from the Milestone spec into this Epic)

1. **Refusal means refusal.** (E31.3's enforcement arm; E31.1 must not record semantics
   that would let a future guardrail treat a mismatch as a warning.)
2. **No agentic default.** Nothing this Epic records may make any instance agentic without
   an explicit per-instance choice; the mode model's own text must say absence-means-manual
   in the same place it defines the levels — this is the constraint E31.1 directly executes.
3. **Policy consumed, not re-authored.** E31.1 does not touch M30's policy; if the mode
   model needs to reference it (e.g., "agentic epic instances apply the recorded policy"),
   reference by link, never restate or reinterpret the rows.
4. **Local loadability never assumed.** Not directly E31.1's surface (no local-model code
   here), but the mode model's agentic-semantics text must not imply a local model is
   always available — leave that qualification to E31.2.
5. **Suite green at every merge** — 307 baseline, no regressions, no new skips.

---

## Design Decisions (yours to resolve — decide, document, move; do not escalate to ask)

1. **The declaration mechanism** (SN-22 leaves this open). Candidate directions
   (non-exhaustive):
   - **(A) A field in `.ai-project.yml`.** Project-global config, checked in once. Fits
     poorly against "per instance, one by one" (Binding Context item 1) unless scoped
     carefully — a single repo-wide field cannot represent "this specific Milestone Chat
     session is agentic, the next one is manual" without becoming a stateful, constantly-
     edited value, which invites drift and merge noise.
   - **(B) A section in the concrete instance's own Execution Chat Starter.** Every Phase /
     Milestone / Epic instance already gets one committed starter file, produced fresh by
     the parent chat when the instance is spun up (this Epic's own starter is an example).
     A declared-mode field there is genuinely per-instance, git-tracked, and produced at
     the natural moment (instance creation) by the natural author (the parent chat).
   - **(C) Both** — a project-level default in `.ai-project.yml` (rarely used, e.g. to
     express "this repo has never gone agentic yet") plus the per-instance override in each
     starter. Only justified if a project-level default earns its keep; do not add it
     speculatively.
   - Whatever is chosen must satisfy: a reader can determine any instance's mode from its
     declaration; absence of a declaration resolves to manual (Hard Constraint 2); the
     mechanism is checkable by E31.3's guardrail without reaching into chat state that
     isn't git-tracked. If (A) or (C) touches `.ai-project.yml`, bump
     `governance/ai-project-yml-spec.md` with a changelog row (v2.4.0 is current).
2. **The governance home for the mode model + manual-permanence rule.** Candidates:
   `governance/systems/chat-hierarchy.md` (already the single authoritative reference for
   the four levels — natural home for "what each level's modes mean"), the yml-spec (if the
   declaration mechanism lives there), AOG (if framed as a session-behavior rule alongside
   §3.7–§3.10). Recommend anchoring the normative semantics in `chat-hierarchy.md` (it
   already owns "what each level is") and cross-linking from wherever the declaration
   mechanism physically lives, but the choice and reasoning are yours.
   - **Resolve the naming collision explicitly** (see Grounding): do not reuse
     `chat-hierarchy.md`'s existing "Mode" column (HQ/Phase/Milestone/Epic mode) for the
     new manual/agentic axis. Name the new axis distinctly (e.g. "Execution Mode") and say
     so where you introduce it, so the two axes never read as one.
3. **G7 adoption call** (session-discipline prose, Deliverable 5). Adopt the M30 closure
   recommendation ("one task, one session") into the mode model's prose as labeled,
   measured-evidence-based guidance, or record explicitly that it is not adopted and why.
   Either is Hard-Constraint-compliant; it is a documented call, not a gate.

  session and an actual agentic session (the existing P7 orchestrator path is sufficient
  for the agentic side — this epic does not need to invent new agentic infrastructure, only
  point at a real dispatch and record its declared mode).

## Execution Notes

- **Resolve the naming collision before writing the mode model's prose**, not after — pick
  the new axis's term first (e.g. "Execution Mode") so every subsequent sentence in the
  deliverable is unambiguous from the start, rather than requiring a find-and-replace pass.
- **The agentic-mode text should describe what "agentic" means at each level without
  implementing it.** For example: "an agentic Epic instance is dispatched via
  `bin/ai-project-orchestrator` and runs unattended against the level's assigned model" is
  a description this epic can and should write; "and here is how it picks paid vs. local"
  is E31.2's sentence, not this epic's.
- **The demonstration evidence is the epic's most concrete deliverable** — do not let it
  become a table describing two hypothetical starts. Actually declare an instance manual,
  actually declare (or dispatch) one agentic, and commit what that looked like (a starter
  excerpt, a dispatch record, or both) at a stable path.
- **Verify the grounding's anchors at execution time** (`chat-hierarchy.md` line numbers,
  yml-spec's current version, the policy's Domain-note wording) — GH-2 discipline; this
  spec's line citations are as of the M31 branch point and may drift.
- Default-accept (PSG §11.6 / AOG §12) governs this Epic's delivery: a clean delivery is
  accepted by silence; the epic-PR merge is human-authorized in-chat (SN-19); a Review
  Decision is the exception path only.

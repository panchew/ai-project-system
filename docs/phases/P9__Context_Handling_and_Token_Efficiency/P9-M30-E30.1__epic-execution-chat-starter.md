### Summary

Build the token-burn measurement mechanism and capture real consumption data: per chat
level (Phase / Milestone / Epic, plus HQ and Creation for the record), per task type
(planning, execution, review, closure), with governance-corpus overhead separable from task
spend. Commit the dataset (aggregated numbers, never raw transcripts) in a stable location
E30.2 can audit, with an explicit gap record for every cell that cannot be captured.

### Binding constraints (carry into every decision)

**Hard Constraint (verbatim from the Milestone spec):**

> **The frontier-vs-local policy and the `models:` refresh MUST be derived from the
> captured measurements — not from pre-existing assumptions.** Real captured data is the
> bar; estimates do not count (phase acceptance criterion). If a measurement cannot be
> captured for some level or task type, **record the gap explicitly** in the report rather
> than substituting a guess — a policy row grounded in a recorded gap is acceptable; a
> policy row grounded in an unlabeled assumption is not. This constraint governs E30.2
> directly and sizes E30.3: no reduction work may be scoped from the prior 24K/157K
> estimates alone.

- The prior estimates (AOG+PSG ~24K; corpus ~10×) are motivation, **never dataset values**.
- The committed dataset carries **aggregated numbers only** — no raw session transcripts or
  conversation content enters the repo.
- **No policy drafting, no `.ai-project.yml` edits, no governance-doc edits, no
  context-load changes** — those are E30.2/E30.3 surfaces.
- Paid-spend pacing is CFO-side: prefer measuring already-captured past sessions; a pacing
  stall on new captures converts to a gap record, not a wait.

### Design Decision (yours to resolve — decide, document, move; do not escalate to ask which mechanism to build)

Candidate directions (non-exhaustive, combinable — see the Epic spec's grounding):
- **(A) Harness/API usage logs** — parse `usage` blocks from the Claude Code session JSONL
  files; real paid-side counts, already captured; the hard part is attributing sessions to
  chat level and task type, and aggregating before committing.
- **(B) Transcript/context token counting** — tokenize the governance corpus per level,
  starters, and `agentic-runs/<epic>/context.md`; directly yields corpus overhead; local
  tokenizer is a proxy for billed counts (document error bars).
- **(C) Orchestrator-path instrumentation** — extend `bin/run-dev-agent` /
  `run-metadata.json` with token counts for forward local capture; Epic-level only.

A hybrid (A for paid spend, B for corpus overhead, C optional) is likely the honest answer,
but the choice is yours — document the reasoning and blind spots in the mechanism doc.
Whatever you choose MUST produce the level × task-type matrix with corpus overhead
separable, paid vs local distinguishable, and a gap record for every unfillable cell.

# Epic E31.2 — Agentic paid-vs-local decision logic

## Context

E31.1 is delivered and merged (`milestone/M31` @ `31eff27`, PR #140): the Execution Mode
model exists in `governance/systems/chat-hierarchy.md` ("Execution Mode: Manual vs.
Agentic" section), declared per-instance via a field on each Execution Chat Starter,
absence-means-manual. E31.1's own delivery is honest about a mechanical gap it leaves
open: **the orchestrator dispatch mechanism exists for the Epic level only** — Phase and
Milestone instances can be *declared* agentic in their starter today, but nothing dispatches
them agentically yet. E31.2 does not close that gap; it works within the one dispatch
surface that exists — `bin/ai-project-orchestrator`'s `handle_epic_execution` →
`bin/run-dev-agent` — and fixes what M30's closure handoff identified there: the falsified
`DEFAULT_MODELS` fallback, the narrow guard-test coverage, the absent local-unavailable
handling, and the missing row-P5 run evidence.

> **Provenance:** Authored by the Milestone Chat (P9-M31) on 2026-07-19 per adjacency,
> after E31.1's acceptance and merge (hard dependency satisfied). The Coding Agent
> implements it.

> **Source:** M31 Milestone spec (Epic Detail → E31.2); P9 phase spec §P9.2; SN-22
> workstream 2; M30 closure handoffs (`DEFAULT_MODELS` alignment, guard-test extension,
> row-P5 experiment, GPU awareness).

**Grounding (verified on `milestone/M31` @ `31eff27`, 2026-07-19):**

- **`bin/ai-project-orchestrator:17-23` `DEFAULT_MODELS` still hardcodes the falsified
  names** — `hq: remote:gpt-4o`, `phase: remote:claude-3-5-sonnet`,
  `milestone: remote:claude-3-5-sonnet`, `epic_dev: local:qwen2.5-coder:14b`,
  `epic_qa: local:qwen2.5-coder:7b`. `load_yml_config()` (~line 160-184) uses this dict as
  the base that `.ai-project.yml`'s `models:` block merges over — **when the yml is
  absent or fails to parse, these falsified values are what actually dispatches.**
  Runtime-load-bearing, not inert.
- **`.ai-project.yml:29-34`'s `models:` block is already correct** (refreshed by E30.2):
  `hq`/`phase`/`milestone` → `remote:claude-opus-4-8`, `epic_dev`/`epic_qa` →
  `local:qwen2.5-coder:14b`. This is the policy's own "Mapping to `.ai-project.yml`" table,
  verbatim.
- **`handle_epic_execution` (`bin/ai-project-orchestrator:320-`) is the only runtime
  dispatch surface that exists today.** It reads `epic_dev`/`epic_qa` straight from the
  merged config (`models_config.get("epic_dev", DEFAULT_MODELS["epic_dev"])`, likewise for
  `epic_qa`) with no per-task branching, no policy-row citation, and no distinguished
  handling for "the local model didn't load." There is no dispatch code path for
  `hq`/`phase`/`milestone` at all — those three keys exist in config only as a
  forward-looking value, per E31.1's documented gap. **Do not build one; that is future
  work outside this epic's Non-Goals.**
- **What "per task" concretely means here, honestly:** the policy's rows P1–P4 (creation,
  hq, phase, milestone) have no agentic dispatch mechanism to apply to — E31.2 cannot
  "decide paid-vs-local per task" for levels nothing dispatches. The rows with a real
  runtime surface are **P5** (epic × execution — is it paid or local?), **P6** (which local
  model the dev-agent lane uses when local), **P7** (which local model the qa-agent lane
  uses). E31.2's decision logic is scoped to those three rows, applied at the one dispatch
  point that exists. State this scoping explicitly in the delivery — do not imply a
  general-purpose per-level-per-task engine that does not exist.
- **`tests/test_model_config.py` covers only `epic_dev`** (4 tests: config value, in-script
  default agreement, off-`llama3:8b` check, yml-spec stale-default check) — `epic_qa`,
  `hq`, `phase`, `milestone` have no consistency guard at all. A silent edit to any of
  those four keys in either `DEFAULT_MODELS` or `.ai-project.yml` today passes the suite.
- **No local-unavailable handling exists anywhere in the path.** `bin/run-dev-agent`
  passes the runner's exit code through unaltered (0/2/3/4 — comment at line ~229); a
  connection-refused or model-not-found failure from Ollama surfaces as whatever generic
  exit code the runner happens to return, indistinguishable from a task failure. GPU
  contention with ComfyUI (issue #126) makes this a live risk, not a hypothetical.
- **The row-P5 designated experiment has no run evidence yet.** The policy names "M31
  dual-mode runs at epic level" as its revisit trigger; E31.1's demonstration run
  (`P9-M31-E31.1-PROVE`) proved the *Execution Mode declaration* mechanism, not the
  *policy-application* decision — it explicitly disclaims covering E31.2's surface
  (`P9-M31-E31.1__demonstration-evidence.md`, "What this does and does not prove").
  E31.2 needs its own run evidence.
- **Test baseline:** 307 tests collected, all passing on `milestone/M31` at the current
  head (verified 2026-07-19, post E31.1 merge).

## Problem Statement

The agentic dispatch path still carries the exact model names M30 measured as never
having run a single session in 72 captured sessions, as its **runtime fallback** — not
dead code, the live behavior whenever config is absent or unparseable. The one dispatch
surface that exists applies `.ai-project.yml`'s values uncritically, with no traceability
to the recorded policy, no protection against config/policy divergence beyond one key, and
no defined behavior when the local model it depends on cannot load. This epic closes those
four gaps at the surface that actually runs today.

---

## Goals

By the end of this Epic:

1. **The epic-level dispatch decision traces to the recorded policy** (rows P5–P7), not an
   opaque config lookup — the decision moves out of hardcoded level→tier mapping at the one
   place hardcoding still lives (`DEFAULT_MODELS`).
2. **`DEFAULT_MODELS` matches the refreshed `models:` block** — no falsified name survives
   anywhere in `bin/`.
3. **Consistency-guard tests cover every `models:` key** (`hq`, `phase`, `milestone`,
   `epic_dev`, `epic_qa`), and a policy↔block divergence fails the suite (Hard Constraint 3's
   enforcement arm).
4. **Local-unavailable behavior is defined and tested** — GPU contention never silently
   passes as success or reads as an ordinary task failure (Hard Constraint 4).
5. **Row-P5 run evidence exists** — a real agentic epic-execution run through the local
   lane, or an explicit GPU-contention gap record if Ollama is unavailable throughout the
   epic's execution window.

---

## Non-Goals

This Epic explicitly does **not**:

- **Build dispatch for Phase/Milestone/HQ levels.** No such mechanism exists
  (E31.1's documented gap); building one is a materially larger change than "align the
  decision logic" and is out of scope here.
- **Build E31.3's manual-mode guardrail** or touch anything about verifying a *manual*
  chat's model — this epic's surface is the agentic path only.
- **Re-derive, extend, or re-debate M30's policy rows.** If execution surfaces a genuine
  policy defect, the path is the Change Discipline (new cited evidence, policy file +
  `models:` block updated together) escalated via the Milestone Chat — never a silent
  divergence (Hard Constraint 3).
- **Auto-fallback a local-unavailable task to a paid remote model without an explicit
  per-instance choice.** That would itself be an undeclared mode/routing change — Hard
  Constraint 4 requires *defined, tested* unavailable-behavior, not "quietly upgrade to
  paid." A documented refusal/escalation is compliant; a silent paid fallback is not.
- **Touch `governance/systems/chat-hierarchy.md`, the Execution Chat Starter templates, or
  `.ai-project.yml`'s `models:` values** — those are E31.1's delivered surface (already
  correct) and out of this epic's edit scope, absent a genuine Change-Discipline defect.

---

## Hard Constraints (binding — carried verbatim from the Milestone spec into this Epic)

1. **Refusal means refusal.** Not this epic's primary surface (E31.3's), but any
   local-unavailable handling this epic adds must fail loudly and stop, never scroll past
   as a soft warning.
2. **No agentic default.** This epic does not change whether any instance is agentic
   (E31.1's surface); it only changes how an already-agentic epic dispatch picks a model.
3. **Policy consumed, not re-authored.** This epic's central constraint — applies policy
   rows P5–P7 as recorded; any apparent defect routes through the Change Discipline via the
   Milestone Chat, never a silent divergence. Guardrail/decision logic must treat
   policy↔block divergence as an error (Deliverable 3).
4. **Local loadability is never assumed** — this epic's other central constraint. Every
   local-model code path in the epic-execution dispatch needs a defined, tested behavior
   for "model not loadable now."
5. **Suite green at every merge** — 307 baseline, no regressions, no skips introduced to
   route around changes.

## Design Decisions (yours to resolve — decide, document, move; do not escalate to ask)

1. **What the "decides paid-vs-local per task" logic concretely is**, given only
   epic×execution has a dispatch mechanism (see Grounding). Candidates:
   - **(A) Traceability-only:** `handle_epic_execution` resolves `dev_model`/`qa_model`
     exactly as today (config value, `DEFAULT_MODELS` fallback), but the code and its
     surrounding documentation now cite policy rows P6/P7 explicitly — a reader can see
     *why* the value is what it is, not just *that* it is.
   - **(B) Traceability + runtime divergence check:** (A) plus the dispatch path itself
     asserts (not just a test) that the resolved value matches what the policy's mapping
     table records, refusing to dispatch on a mismatch (defense in depth beyond the guard
     tests in Deliverable 3).
   - Pick one, document why; (B) is stronger but adds a runtime dependency on parsing (or
     duplicating) the policy's mapping table — weigh that cost against the guard tests
     already catching the same class of drift at CI time.
2. **Local-unavailable handling design** (Hard Constraint 4). Candidates:
   - **(A)** `bin/run-dev-agent` detects a distinguished failure signal from the runner
     (connection-refused / model-not-found) and exits with its own documented, distinct
     exit code + one-line stderr reason — never silently falling back to a different model.
   - **(B)** `handle_epic_execution` catches that distinguished signal and produces an
     explicit escalation/gap record (the existing `generate_escalation_report`,
     ~line 430, is the natural extension point) rather than treating it as a generic task
     failure.
   - **(C)** Both, layered — (A) makes the signal distinguishable, (B) makes it actionable
     at the orchestrator level. Document the exit-code/signal contract precisely enough
     that a test can exercise it (e.g., point `AI_PROJECT_OLLAMA_ENDPOINT` at an
     unreachable port and assert the distinguished behavior, not a generic failure).
3. **Consistency-guard test extension shape.** Extend `tests/test_model_config.py` (or add
   a sibling file) to cover all five `models:` keys — `hq`/`phase`/`milestone` included,
   even though they have no dispatch mechanism yet (guarding the fallback values still
   matters: a stale `DEFAULT_MODELS["hq"]` is a real defect even before dispatch exists for
   it). Add a policy↔block divergence check: parsing `model-routing-policy.md`'s "Mapping
   to `.ai-project.yml`" table with a narrow, documented method (e.g., grepping the five
   key rows) is acceptable — do not build a general markdown parser for this.
4. **Row-P5 run-evidence location and shape.** Recommended:
   `.ai-project/artifacts/agentic-runs/<epic-or-proving-vehicle-id>/` (the existing
   convention) with a short evidence note cross-linked from the policy file's revisit
   trigger, or beside `model-routing-policy.md` — your final call, documented. If Ollama is
   contended throughout the epic's execution window, the explicit gap record (M30 gap-record
   discipline) goes in the same place instead and does not block the epic.

## Execution Notes

- **Start from the grounding's honest scoping statement** — "per task" means P5–P7 at the
  one dispatch surface that exists. Writing code or prose that implies a general per-level
  decision engine would misrepresent what this epic delivers; say plainly what exists and
  what doesn't (the same discipline E31.1 practiced with its own "what exists mechanically
  today" note).
- **The local-unavailable test is the epic's hardest deliverable to make honest.** A test
  that merely asserts "some exception is raised" when Ollama is down is weak; assert the
  *specific* documented exit code / message contract from Design Decision 2, so a future
  regression that silently swallows the failure is caught.
- **Reuse `generate_escalation_report`'s pattern rather than inventing a second escalation
  mechanism** — it already exists at `bin/ai-project-orchestrator:430` for exactly this
  class of "something went wrong, tell a human" case.
- **If Ollama is unreachable during your session, do not block on it** — the row-P5 gap
  record path is explicitly sanctioned (Non-Goals, Deliverable 5). Try first; record
  honestly if you can't.
- **Verify the grounding's anchors at execution time** (`bin/ai-project-orchestrator` line
  numbers, `.ai-project.yml:29-34`, the policy file's mapping table) — GH-2 discipline;
  this spec's line citations are as of `milestone/M31` @ `31eff27` and may drift.
- Default-accept (PSG §11.6 / AOG §14) governs this Epic's delivery: a clean delivery is

  Decision is the exception path only.

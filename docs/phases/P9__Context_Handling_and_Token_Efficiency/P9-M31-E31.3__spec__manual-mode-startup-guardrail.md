# Epic E31.3 — Manual-mode startup guardrail

## Context

E31.1 (mode model + declaration, `31eff27`, PR #140) and E31.2 (agentic paid-vs-local
decision logic, `ec85826`, PR #141) are both delivered and merged to `milestone/M31`. Both
addressed the **agentic** half of the founding failure: what agentic means, and how it
picks a model. Neither touched the **manual** half — nothing today verifies that a
human-driven chat is actually running on the model `.ai-project.yml` says it should be.
E31.3 closes that gap: the last piece of M31 and the direct fix for how the original
quota-exhaustion failure actually happened (a chat ran on whatever the harness handed it,
with no check against intended mapping).

> **Provenance:** Authored by the Milestone Chat (P9-M31) on 2026-07-19 per adjacency,
> after E31.1's and E31.2's acceptance and merge. The Coding Agent implements it.

> **Source:** M31 Milestone spec (Epic Detail → E31.3); P9 phase spec §P9.2; SN-22
> workstream 3 (ratified decision 4).

**Grounding (verified on `milestone/M31` @ `ec85826`, 2026-07-19):**

- **No self-model verification mechanism exists anywhere in governance today** — not in
  AOG, PSG, or `chat-hierarchy.md`. AOG has an Exit Ritual (§13); there is no session-start
  counterpart anywhere. `grep` for "self-model", "self-identif", "current model", "running
  model" across `governance/` returns nothing.
- **A concrete self-identification signal already exists in practice, outside governance:**
  the harness that runs this repo's chats (Claude Code) injects an `# Environment` block
  into every session's system context naming the running model — verified present in
  *this Milestone Chat's own session*, 2026-07-19: *"You are powered by the model named
  Sonnet 5. The exact model ID is claude-sonnet-5."* This is the only observed mechanism by
  which a manual chat could know what model it is running on. It is a **harness-provided
  self-report** — the chat reads a string the harness told it, with no independent,
  cryptographic way to verify that string is accurate. Document this as the mechanism's
  known limit (Deliverable 2 requires this explicitly), not a gap to silently paper over.
- **A live, non-hypothetical mismatch exists right now, in this very session:** this
  Milestone Chat (`milestone` level, manual — no Execution Mode field on its own starter)
  is running on `claude-sonnet-5` per its own harness-reported identity, while
  `.ai-project.yml:31`'s `milestone:` key names `remote:claude-opus-4-8`. **This is not a
  violation** — no guardrail exists yet to violate — but it is concrete, current evidence
  that the mismatch class this epic must catch is real, not theoretical. Consider using
  this exact case (or a deliberately constructed analog) as the epic's refusal-evidence
  deliverable, rather than inventing a synthetic scenario.
- **The `models:` block's key set does not cleanly cover every manual-capable level.**
  `.ai-project.yml:29-34` has `hq`, `phase`, `milestone`, `epic_dev`, `epic_qa`. That covers
  HQ, Phase, and Milestone directly. It does **not** cover:
  - **Creation** — no key exists (the recorded policy's row P1 explicitly says "No
    `models:` key exists or is needed" for Creation, because Creation was never in the
    agentic-dispatch key set the block was designed for). Creation must still be covered by
    this epic's verify-and-refuse check (milestone acceptance criterion 3) — the mapping
    definition must say what Creation's expected model *is*, which is new ground, not a
    lookup against an existing key.
  - **Epic (manual)** — `epic_dev`/`epic_qa` are a two-role split specific to the agentic
    Dev-QA loop (E31.2's surface); a *manual* Epic chat (a human reading an Epic Execution
    Chat Starter directly, Execution Mode absent or explicitly `manual`) has no
    single-value key of its own to verify against.
- **`.ai-project.yml` has no `models:` block at all on a freshly initialized project** —
  `bin/ai-project-init:254-267` writes only `project:` and `governance:` sections; `models:`
  is an optional block added later (this repo's was added by E30.2). The mapping
  definition and the guardrail's behavior must both have a documented answer for "no
  `models:` block, or no key for this level, is present at all" — that is a materially
  different case from "a key is present and doesn't match," and conflating the two would be
  dishonest.
- **The verify-and-refuse check has no code-execution boundary to run inside, for manual
  chats.** Agentic dispatch (E31.2) has real code (`handle_epic_execution`) that can exit
  non-zero and stop a process. A manual chat is a human-driven conversation with an LLM;
  there is no wrapper process to gate. The check this epic builds is necessarily a
  **documented instruction the chat itself must follow at session start** (read the
  harness's self-report, compare to the expected mapping, stop and state the mismatch if
  they disagree) — enforced the same way every other AOG/PSG "MUST" is enforced in this
  framework: by the agent's compliance with governing documentation, not by an external
  technical gate. State this honestly in the delivery (Hard Constraint 1's "refusal means
  refusal" governs what the *instruction* must say, not a claim that this epic adds a
  technical impossibility-to-proceed).
- **Template landscape:** the three Execution Chat Starter templates
  (`governance/templates/{phase,milestone,epic}-execution-chat-starter.md`) already carry
  E31.1's `Execution Mode` field and a "Prerequisite Verification (do this first)" section
  (the established location for git-tracked-ness checks) — the natural integration point
  for a model-verification step. **HQ and Creation use different templates**
  (`governance/templates/hq-chat-opener.md`; `governance/templates/genesis.md` /
  `seed.md`) — the milestone's "all manual chats including HQ and Creation" requirement
  means these are also in scope for the startup check, not just the three Execution Chat
  Starters the milestone spec's Deliverable 5 mentions by name.
- **Test baseline:** 349 tests collected, all passing on `milestone/M31` at the current
  head (verified 2026-07-19, post E31.2 merge — up from the 307 baseline via E31.2's 42
  new tests).

## Problem Statement

Nothing today checks that a manually driven chat is running on the model
`.ai-project.yml` assigns to its level. The original quota-exhaustion failure happened
partly because chats ran on whatever the harness selected, unverified against any intended
mapping — and that exact condition is reproducible right now: this Milestone Chat's own
session demonstrates it. E31.1 gave manual chats a declared Execution Mode; E31.2 gave the
agentic path a model decision grounded in evidence; neither gives a manual chat any way to
know, or refuse on, a model mismatch.

---

## Goals

By the end of this Epic:

1. **A level→model mapping definition for manual chats exists**, covering all five manual-
   capable targets (Creation, HQ, Phase, Milestone, Epic) — including the two the current
   `models:` key set doesn't reach (Creation, manual Epic) — and stating the absent-block/
   absent-key behavior explicitly.
2. **A self-model verification method is documented**, with its known limits stated plainly
   (harness self-report; not independently verifiable).
3. **A verify-and-refuse startup check exists for every manually started chat**, including
   HQ and Creation, on every template surface a manual chat actually starts from.
4. **Policy↔block divergence also refuses**, as an error, consistent with E31.2's guard-test
   enforcement of the same principle (Hard Constraint 3).
5. **Refusal evidence is committed** — a manual chat started on a mismatched model
   demonstrably refuses, not asserted.
6. **E30.3's scoping blocks and E30.4's reference-first rules survive every template edit**
   this epic makes, unreworked.

---

## Non-Goals

This Epic explicitly does **not**:

- **Rebuild or extend E31.2's agentic decision logic** — that surface is done; this epic is
  manual-only.
- **Change Creation/HQ's manual-permanence** — settled (SN-22); this epic covers them with
  the guardrail, it does not revisit whether they may ever go agentic.
- **Claim a technical enforcement guarantee stronger than "documented instruction + agent
  compliance" provides.** No code process wraps a manual chat; do not write delivery prose
  implying otherwise. A clearly stated, unambiguous, non-bypassable-*in-instruction*
  refusal rule is the deliverable — not a runtime sandbox that makes disobedience
  impossible.
- **Re-derive or re-debate M30's policy rows**, or edit `model-routing-policy.md`'s rows.
- **Resolve GPU scheduling** — out of P9 entirely (Non-Goal at the phase level).
- **Add a `models:`-block key for every conceivable future level** — only the two genuine
  gaps this epic's grounding identifies (Creation, manual Epic) need resolving; do not
  speculatively expand the schema further.

---

## Hard Constraints (binding — carried verbatim from the Milestone spec into this Epic)

1. **Refusal means refusal.** This epic's central constraint. The startup check's
   instruction must be unambiguous and unconditional on mismatch — no phrasing that reads
   as an advisory the chat could reasonably continue past. The acceptance evidence is a
   demonstrated refusal, committed in the delivery.
2. **No agentic default.** Not directly this epic's surface (it doesn't touch Execution
   Mode), but the mapping definition must not imply that a manual instance should switch to
   agentic on mismatch — a mismatch means *stop*, not *reroute*.
3. **Policy consumed, not re-authored.** This epic reads the recorded policy and
   `.ai-project.yml`'s `models:` block; it does not edit policy rows. Policy↔block
   divergence is treated as an error by the guardrail (Deliverable 4) — consistent with
   E31.2's enforcement of the identical principle on the agentic side.
4. **Local loadability never assumed.** Not this epic's surface directly (manual chats
   are not local/paid-routed the way agentic dispatch is), but if the mapping definition
   ever names a local model for a manual level, the same non-assumption applies.
5. **Suite green at every merge** — current baseline 349 (307 + E31.2's 42), no
   regressions, no skips introduced to route around changes.

## Design Decisions (yours to resolve — decide, document, move; do not escalate to ask)

1. **The level→model mapping definition for manual chats.** Candidates:
   - **(A) Reuse `.ai-project.yml`'s existing `models:` keys directly** for
     Phase/Milestone/HQ (they already have single values); add the two missing pieces —
     a new key for Creation (yml-spec bump + changelog) and a decision for manual Epic
     (a new single-value key distinct from the `epic_dev`/`epic_qa` role split, or an
     explicit statement that manual Epic verification reuses one of them, documented why).
   - **(B) A separate companion mapping** (e.g., a new block or a governance-doc table)
     specifically for manual-mode verification, reasoning that a human might legitimately
     want to run a manual chat on a different model than the agentic-dispatch assignment.
     If chosen, decide explicitly whether Hard Constraint 3's divergence-is-error extends
     to disagreement between this new mapping and `models:` — silence on that question
     would leave a real gap.
   - Whatever you choose must state the absent-block/absent-key behavior explicitly (see
     Grounding: freshly initialized projects have no `models:` block at all) — "cannot
     verify, therefore refuse" and "cannot verify, therefore an explicitly documented
     permissive default" are both legitimate answers; leaving it unstated is not.
2. **The self-model verification method.** The harness's system-prompt self-report (see
   Grounding — the `# Environment` block naming the model) is the only concrete signal
   observed to exist; document it as the mechanism, cite this session's own example as the
   demonstrated case, and state its limits plainly (self-report, harness-trust-dependent,
   not cryptographically verifiable). If you find or reasonably infer another verification
   channel available in this environment, document it as an alternative or addition — but
   do not invent a mechanism this repo's tooling doesn't actually have.
3. **Where the verify-and-refuse instruction lives and how it's phrased**, so it functions
   as a real refusal rather than an advisory. Recommended: the "Prerequisite Verification
   (do this first)" section already present in the three Execution Chat Starter templates
   (the established location for git-tracked-ness checks — Model Verification is a natural
   sibling step there), plus an equivalent addition to `hq-chat-opener.md` and
   `genesis.md`/`seed.md` (Creation has no "Prerequisite Verification" section today —
   decide where the equivalent step goes there).
4. **How policy↔block divergence is checked for the manual mapping** (Deliverable 4) —
   whether this reuses/extends E31.2's `tests/test_model_config.py` guard (if the mapping
   lives in `.ai-project.yml`) or needs its own check (if the mapping lives elsewhere,
   Design Decision 1B). Document the choice and keep it consistent with E31.2's existing
   divergence semantics (Milestone spec Dependencies and Sequencing: "whichever lands
   second conforms to the first").

## Execution Notes

- **This session's own live mismatch is real grounding, not a rhetorical device** — use it.
  If you construct the refusal-evidence deliverable around an actual manual chat instance
  (this one, or a fresh one) reading its own harness-reported model identity and comparing
  it to `.ai-project.yml`'s expected value for its level, and stating a refusal because
  `claude-sonnet-5` ≠ the configured value, that is real, honest evidence — stronger than a
  synthetic scenario.
- **Do not overclaim enforcement.** Say plainly, in the delivered mapping/verification
  documentation, that this is an instruction the agent must follow, not a technical
  impossibility-to-proceed — the same honesty standard E31.1 and E31.2 both practiced
  about their own mechanical gaps. A future reader trusting a false "cannot be bypassed"
  claim would be worse than an honest "this depends on agent compliance, per every other
  MUST in this framework."
- **The Creation/HQ template gap is easy to miss** — `hq-chat-opener.md` and
  `genesis.md`/`seed.md` are not in the "three Execution Chat Starter templates" set E31.1
  touched. Verify you've actually opened and edited them, not just the three from
  precedent.
- **Verify the grounding's anchors at execution time** (`.ai-project.yml` line numbers,
  the policy file's row P1 wording, `bin/ai-project-init`'s current yml-writing lines,
  the current harness environment self-report wording) — GH-2 discipline; this spec's
  citations are as of `milestone/M31` @ `ec85826` and this session's own context, both of

## Notes

- **This epic closes the founding failure's last open half.** M30 replaced the assumption
  with evidence; E31.1 gave the switch a declaration; E31.2 made the agentic path
  provably agree with the evidence; E31.3 makes a manual chat provably know, and refuse
  on, its own disagreement with the recorded mapping. All four pieces are needed; none
  alone would have prevented the original quota exhaustion.
- **The Creation/HQ coverage requirement is not a formality** — SN-22 named it explicitly
  because those two levels are the ones that never go agentic, ever, and are exactly the
  levels a silent model mismatch would be easiest to overlook (no orchestrator dispatch
  log to notice it in). Do not treat their template edits as an afterthought relative to
  the three Execution Chat Starters.
- **Honesty about what "refuse" technically means here is itself Hard-Constraint-adjacent
  material**, not incidental prose. This framework's entire enforcement model — outside
  the orchestrator's code path and the harness's human-merge-authorization gate — is
  documented-instruction compliance. Say so plainly rather than implying this epic invents
  a stronger guarantee.

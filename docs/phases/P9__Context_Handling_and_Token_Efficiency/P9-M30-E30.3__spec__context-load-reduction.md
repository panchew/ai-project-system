# Epic E30.3 — Evidence-driven context-load reduction

## Context

E30.1 (dataset) and E30.2 (audit report + policy + `models:` refresh) are merged
(`milestone/M30` @ `3ad159a`). E30.3 is the last M30 epic and the one whose **extent was
deliberately deferred until the evidence existed** — this spec was authored only after the
measurements were on the branch, per the Milestone spec ("the Milestone Chat scopes the
epic's actual extent *after* the measurement evidence exists, and records the sizing
rationale in the Epic spec"). The sizing decision below is that record.

> **Provenance:** Authored by the Milestone Chat (P9-M30) on 2026-07-17, after E30.1's and
> E30.2's acceptance and merge. The Coding Agent implements it.

> **Source:** M30 Milestone spec (Epic Detail → E30.3); P9 phase spec §P9.1; SN-22
> workstream 1 (context handling proper); audit report §4 (E30.3's designated evidence
> frame).

**Grounding (verified on `milestone/M30` @ `3ad159a`, 2026-07-17 — all figures from the
committed dataset/report, none from the superseded 24K/157K estimates):**

- **Per-level governance packs** (starter + required specs + PSG + AOG, dataset §4):
  phase 30,478 / milestone 36,614 / epic 29,336 proxy tokens (o200k, ±10–15%, G10).
  PSG + AOG + yml-spec alone = 29,663; `governance/` in full = 157,287 over 69 files.
- **Billed per-call context medians** (dataset §3, exact provider-billed): epic 76,135 /
  hq 101,163 / creation 102,515 / milestone 129,135 / phase 169,003 — what every API call
  re-reads.
- **Report finding 7:** the governance pack is a **material minority** of context load —
  roughly 20–40% upper bound of per-call re-read; the rest is conversation history, tool
  results, and harness overhead. Reduction must consider *total* per-call context, but
  the governance share is the slice this repo's documents actually control.
- **Report finding 9 (cost framing):** cache re-reads are 48.5% of weighted window cost
  (≈$302 of ≈$623); halving per-call re-read context at the parent-chat levels addresses
  an order of magnitude more spend than eliminating the entire epic-execution output
  component.
- **Report §2.2:** parent-chat mixed sessions (milestone 37% + phase 16.1% of spend,
  medians $11.71–$20.84/session) are the dominant sink — driven by session *length and
  mixing* (G7), which is behavioral/structural, not a document-size problem.
- **Report §8:** within-session task segmentation in `bin/measure-token-burn` is named
  future work (measurement precision, not reduction) — not this epic's surface.
- **`.ai-project.yml:3`** still reads `Spec: governance/ai-project-yml-spec.md v2.3.1`;
  the spec is v2.4.0 since E30.2. One-line hygiene fix assigned here by explicit human
  authorization at E30.2 acceptance (Milestone Chat session, 2026-07-17).
- **Test baseline:** 307 tests, all passing on `milestone/M30`.

## Sizing Decision (the Milestone Chat's, recorded per the Milestone spec)

**Decision: bounded reduction work is justified — the middle path.** Neither the minimal
finding-only outcome nor a sweeping context-architecture rework:

1. **Reduction work is justified** because the measured governance share of per-call
   re-read (up to ~20–40%, finding 7) multiplied by the dominant cache-read cost
   component (48.5%, finding 9) is real money at the costliest levels — this is not the
   "overhead is minor" branch the Milestone spec sanctions for a finding-only delivery.
2. **It is bounded to the governance-pack slice** because the majority of per-call
   context (history, tool results, harness overhead) is not controlled by anything this
   epic can edit. Inventing work against those components would violate the Milestone
   spec's "do not invent reduction work the numbers don't justify" — for them, the
   deliverable is the documented finding + recommendations to the parent chats (M31
   consumes the session-hygiene implications; measurement segmentation stays future
   work).
3. **Verification honesty:** before/after numbers use E30.1's mechanism, Direction B
   (pack tokenization) — immediately measurable and committed. Billed per-call medians
   can only move in *future* captured sessions; the epic must claim pack-level reduction
   with measured numbers and state plainly that billed-median improvement is a
   forward-looking expectation, verified by later captures — not claim it as achieved.

**Evidence basis:** dataset §§3–4; report §2.1–§2.2, §4 findings 7–9. **Traces to
measured data, not the prior estimates** (Hard Constraint).

## Problem Statement

Every governed chat pays a governance-pack load of ~29–37K tokens that is re-read (at
cache rates) on every API call, at levels whose per-call context runs 76–169K tokens and
whose cache re-reads are the single largest weighted cost component of the measured
window. The packs were assembled by accretion — full PSG + AOG + full specs at every
level — never scoped against what each level's role actually needs. E30.3 scopes them,
reduces what the evidence says is reducible, and documents honestly what lies beyond
document control.

---

## Goals

By the end of this Epic:

1. **A per-level context-scoping standard exists** — what a chat at each level (Phase /
   Milestone / Epic; HQ and Creation for the record) actually needs loaded, and what it
   does not — derived from the roles the governance documents themselves define.
2. **Measured pack reduction is delivered** for at least the Milestone- and Phase-level
   packs (the costliest per-call levels), with **before/after proxy-token numbers from
   E30.1's mechanism** committed alongside.
3. **The non-governance majority is documented, not hand-waved:** a committed finding
   stating what share of per-call context reduction cannot address (history/tool
   results/harness), with recommendations addressed to the parent chats/M31 — including
   the session-hygiene implication of the mixed-session finding (G7, report §2.2).
4. **Hygiene:** `.ai-project.yml:3` spec-version pointer updated to v2.4.0 (authorized
   at E30.2 acceptance).
5. **Full test suite passes** (307 baseline, no new skips).

---

## Non-Goals

This Epic explicitly does **not**:

- **Rework the harness, system prompts, memory, or tool-result handling** — outside repo
  control; documented as findings only.
- **Rewrite PSG/AOG content or change any governance rule.** Scoping decides what each
  level *loads*, not what the documents *say*. Normative text is untouchable here; if
  scoping reveals a document that should be split for loadability, record the
  recommendation — do not perform the split in this epic unless it is content-neutral
  (verbatim relocation with redirects) and the Delivery Notice proves it.
- **Build retrieval infrastructure or new caching machinery.** The dataset shows harness
  caching already works (cache reads bill at 0.1×) — the measured lever is *smaller
  packs*, not more cache. Retrieval-instead-of-loading may be recorded as a
  recommendation if the scoping analysis supports it; building it is not justified by
  the numbers this window.
- **Extend `bin/measure-token-burn` with within-session segmentation** — recorded future
  work (report §8), measurement territory, not reduction.
- **Touch `bin/ai-project-orchestrator` `DEFAULT_MODELS`** — M31's alignment task
  (report §8).
- **Claim billed-median improvements as achieved.** Only pack-level before/after numbers
  are provable inside this epic (Sizing Decision, point 3).

## Hard Constraint (binding — embedded verbatim from the Milestone spec)

> **The frontier-vs-local policy and the `models:` refresh MUST be derived from the
> captured measurements — not from pre-existing assumptions.** Real captured data is the
> bar; estimates do not count (phase acceptance criterion). If a measurement cannot be
> captured for some level or task type, **record the gap explicitly** in the report
> rather than substituting a guess — a policy row grounded in a recorded gap is
> acceptable; a policy row grounded in an unlabeled assumption is not. This constraint
> governs E30.2 directly and sizes E30.3: no reduction work may be scoped from the prior
> 24K/157K estimates alone.

For E30.3 specifically: this spec's sizing traces to dataset §§3–4 and report §4 (all
measured), not to the prior estimates. Downstream, **every reduction claim must show
before/after numbers from E30.1's mechanism** (Milestone spec, verbatim), and any cell
the scoping analysis cannot ground in measurement becomes a recorded gap (continuing the
G-series), never a guess.

## Design Decisions (yours to resolve — decide, document, move; do not escalate to ask)

1. **The scoping standard's documentation home** — a reference artifact beside the
   dataset/report (recommended:
   `.ai-project/artifacts/reference/token-measurement/context-scoping.md`, keeping the
   whole E30.1→E30.3 evidence chain in one directory) and/or a governance-side home.
   Document the choice; cross-link from the report directory either way.
2. **The reduction lever per level.** Candidates the evidence supports, in rough order
   of leverage: trimming what starters instruct chats to load (e.g., whether every level
   needs the full yml-spec, all templates, full sibling specs); pointing chats at
   sections rather than whole documents where the harness supports targeted reads;
   deduplicating content repeated between starters and specs (the M30 starters embed
   spec material verbatim — measure it). Choose per level; justify each choice against
   the pack-composition numbers you measure first (see Execution Notes).
3. **How before/after is presented** — extend `bin/measure-token-burn`'s Direction B
   pack definitions to match the new scoping (documented change to the pack manifest,
   regenerating the dataset files in the same delivery), or commit a separate
   before/after table citing the mechanism. Either is acceptable; the numbers must be
   reproducible by rerunning the mechanism.

## Execution Notes

- **Measure pack composition first.** Before cutting anything, break each level's pack
  into its components (PSG / AOG / yml-spec / starter / specs / templates) with
  per-component proxy counts — the dataset's §4 gives file-level numbers; you need the
  per-level assembly. The cut list falls out of the composition table; the composition
  table goes in the scoping standard as its evidence.
- **The duplication between starters and specs is the likely biggest single win** — the
  M30 starters embed Milestone-spec material verbatim (Hard Constraint, epic detail,
  sequencing). Measure it before assuming; if confirmed, the scoping standard's rule is
  load-one-reference-the-other, applied to the *templates* so future chats inherit it.
- **Honesty over magnitude.** A measured 20% pack reduction with clean numbers beats a
  claimed 50% resting on assumptions. If the composition analysis shows the packs are
  already tight at some level, say so for that level — the finding is a valid outcome
  per the Milestone spec, and this spec's sizing decision only mandates *implemented*
  reduction where the numbers support it (milestone/phase are expected to support it;
  verify).
- **State the G10 error bars** wherever proxy numbers appear; never present proxy counts
  as billed counts.
- **Verify the grounding's anchors at execution time** (GH-2 discipline) — dataset/report
  section numbers, `.ai-project.yml:3`, template paths.
- Default-accept (PSG §11.6 / AOG §14) governs this Epic's delivery: a clean delivery is
  accepted by silence; the epic-PR merge is human-authorized in-chat (SN-19); a Review
  Decision is the exception path only.

# Epic E48.4 — Footboard Readiness and Real Epic Run

## Context

**M48's question is whether the P12-proven path generalizes.** P12 ran one real Epic end to end on
`panchew-io` (`n=1`). M48's job is to make that `n=2` and `n=3` — and E48.4 is the `n=2` half, on
`footboard`.

E48.4 is an **`ai-project-system` proof-and-coordination Epic** (the E47.3 pattern), **not**
`footboard`'s parent. Its record and Delivery Notice land in this repository on `epic/E48.4`; the
project-side migration and the selected real Epic remain planned, accepted, and merged by
`footboard`'s own hierarchy. Cross-project direction is routed through the governed System HQ
channel — a request/response, and where work belongs to `footboard`, a steering note into `footboard`
HQ. Routing never commands and never accepts project work.

**Re-measured at planning (2026-09-09, this chat):**

- `footboard` — branch `chore/framework-v7.0.0-bump`, `HEAD` `d0c4c2a`, remote
  `https://github.com/panchew/footboard.git`.
- **Dirty in-flight planning work (21 items):** 2 modified (`docs/phases/P1__Online_1v1_MVP/P1__phase-spec.md`,
  `genesis.md`) and 19 untracked (HQ openers, phase starters, system requests/responses, `seed.md`,
  `AGENTS.md`, a phase-execution-chat-starter, and the `P1-M1-E1.1`…`E1.6` Epic spec + starter pairs).
  These are **preserved byte-for-byte outside this Epic's changes** (Finding 7).
- `.ai-project.yml` — `framework_version: v7.0.0`, governance pin `v7.0.0`, plus a seven-key
  `models:` block (`epic_dev`/`epic_qa`/`epic_manual` → `remote:deepseek-v4-flash`). Migration target:
  the released `v9.0.0`.
- **Accepted Milestone plan:** `P1-M1` lists `E1.1`–`E1.6`, each with a committed spec and Starter —
  real, pre-existing work that would be done anyway. `E1.1` (WebSocket Service Implementation) is the
  natural first candidate, but **selection is not this Epic's to make alone**; the chosen Epic's own
  spec, Starter, and parent acceptance are prerequisites.
- **Fleet registry:** `footboard` is `state: benched`, `state_basis: proposed` — the
  benched-to-eligible transition requires **explicit human authority** (Finding 4); neither this
  Starter nor enrollment grants it.

## Problem Statement

M48 must show that the P12 adapter path generalizes to a **second** fleet project — but `footboard`
is benched, on `v7.0.0` (released framework is `v9.0.0`), and carrying 21 items of dirty in-flight
planning work. A proof run that overwrites that work, fakes a migration with a version-string edit,
invents a proving task, or grants itself eligibility would poison the very evidence M48 exists to
produce. E48.4 therefore does the coordination and evidence work in `ai-project-system`, and routes
the actual migration and Epic execution through `footboard`'s own governance, with every
cross-repository step explicit and every authority human-granted.

## Goals

By the end of this Epic, the record must:

1. **Record the chosen integration baseline** and perform the migration in an **isolated worktree**,
   preserving the dirty checkout untouched.
2. **Complete a real v7.0.0→v9.0.0 governance migration** (pin, installed agent copies, adoption
   stamp, project configuration) — not a version-string edit — validated from the baseline.
3. **Validate `footboard`** and verify its remote/tracking and its **explicitly authorized**
   benched-to-eligible transition.
4. **Select one real Epic already present in `footboard`'s accepted Milestone plan**, and require its
   current spec, Starter, and parent acceptance before dispatch.
5. **Dispatch it headlessly through Drivr's `OpenCodeAdapter`** with the precommitted quality bar and
   evidence contract (E48.1) and the accepted deterministic gate (E48.2), preserving raw evidence and
   project commits.
6. **Obtain independent project-level review** and record defects, rework, elapsed time, intervention,
   completion judgment, and all available usage dimensions.

## Non-Goals

This Epic explicitly does **not** aim to:

- **Become `footboard`'s parent.** Project-side migration and product work are planned, accepted, and
  merged by `footboard`'s own hierarchy; E48.4 coordinates and records, it does not own them.
- **Touch the dirty checkout.** All mutation happens in an isolated worktree from a recorded
  integration baseline.
- **Invent proving work.** The dispatched Epic already exists in `footboard`'s accepted plan; M48
  authors no new Epic for it.
- **Grant eligibility.** The benched-to-eligible transition requires explicit human authority,
  recorded; E48.4 records whatever is granted, none by inference.
- **Change Drivr code.** M48 authorizes no Drivr implementation (Finding 6); if a required run needs
  new machinery, escalate.
- **Perform the migration as a version-string edit.** It is a v7.0.0→v9.0.0 migration of pin, agent,
  stamp, and configuration.
- **Decide `home_finance`.** That is E48.5's disposition.

## Scope of Work

### 1. Integration baseline and isolated worktree (D1)

Record the chosen integration baseline and isolate all project mutation.

**Must include:**
- A recorded **integration baseline** (repository, branch, commit SHA, date) from which the isolated
  worktree is created.
- An **isolated worktree + branch** for the migration; the dirty checkout is **never modified**. The
  record states byte-for-byte that the 21 dirty items remain outside this Epic's changes and unstaged.

### 2. Governance migration v7.0.0 → v9.0.0 (D2)

Plan and validate a real migration in the isolated worktree.

**Must include:**
- Reconcile the **governance pin**, **installed agent copies**, **adoption stamp**
  (`framework_version`), and **project configuration** to `v9.0.0`.
- Remove **no project-owned setting by template overwrite**; project-owned configuration survives.
- Validate the migrated project (validator clean, or each finding has a recorded disposition).

### 3. Validation, remote/tracking, and eligibility record (D3)

- Validate the project (post-migration) and verify its **remote/tracking** relationship.
- Record the **benched-to-eligible transition** with explicit human authority — or a named block if
  that authority is not supplied. This Epic grants nothing.

### 4. Real Epic selection and parent acceptance (D4)

- Select an Epic **already present** in `footboard`'s accepted `P1-M1` plan (`E1.1`–`E1.6`).
- Require its **current spec and Starter** to be produced or confirmed, and **accepted by
  `footboard`'s own parent chain**, before dispatch. Do not invent proving work.

### 5. Adapter dispatch with precommitted bar and evidence contract (D5)

- Instantiate the E48.1 **quality bar** (two-layer: activity floor + the selected Epic's quoted
  acceptance criteria at an immutable `target_commit_sha`, with independent review) and the **dispatch
  manifest** (bar commit ancestor, target worktree HEAD), on `epic/E48.4` — per E48.1's accepted
  contract and the Phase Ruling on E48.1.
- Dispatch headlessly through Drivr's `OpenCodeAdapter.execute` with an **explicit route**, using
  E48.2's accepted deterministic gate for the source suite.
- **Preserve raw events and project commits**; record the run under E48.1's run-record contract.

### 6. Independent review and the run record (D6)

- Obtain **independent project-level review** (not the run's own report, not the executor).
- Record defects, rework, elapsed time, intervention, completion judgment, and every available usage
  dimension (normalized, never estimated).

- [ ] **D4** — Real Epic selection from `footboard`'s accepted plan, with its spec/Starter parent-accepted before dispatch
- [ ] **D5** — The instantiated quality bar + dispatch manifest, the adapter dispatch with an explicit route, and preserved raw evidence + project commits
- [ ] **D6** — Independent project-level review and the run record (defects, rework, elapsed, intervention, judgment, usage)
- [ ] **Epic Delivery Notice**

## Binding Constraints

Settled above this epic — **not re-decidable here** (M48 milestone spec; E48.1/E48.2 accepted contracts):

1. **Static validation is not operational proof.** E48.4 exists to run the path.
2. **`remote:deepseek-v4-flash` is a model identity, not the executable route.** Record both.
3. **Credential diagnostics are presence-only.** Never load or print credential values.
4. **Eligibility requires explicit authority.** Neither this Starter nor enrollment grants it.
5. **The proven path invokes Drivr's `OpenCodeAdapter.execute`.** Raw `opencode run` alone is not proof.
6. **M48 authorizes no Drivr implementation.** New machinery is a named blocker and escalation.
7. **`footboard` has dirty in-flight work.** Use an isolated worktree and preserve it.
8. **Usage pairs with independently reviewed quality.** Missing telemetry is `unavailable`, never
   estimated or zero-filled.
9. **`undetermined`, missing evidence, credential absence, provider unavailability, authenticated
   resource refusal, and a confirmed blocker remain distinct.**
10. **A named, understood failure can satisfy the attempt requirement**; it cannot be hidden as `n=3`
    or automatically open M50.

## Technical Constraints

**Repository boundary (named):**
- `ai-project-system` — the E48.4 record and Delivery Notice, plus the **instantiated quality bar and
  dispatch manifest** (E48.1 contract / Phase Ruling on E48.1), on `epic/E48.4`.
- `footboard` — the project-side migration and the real Epic, under `footboard`'s own hierarchy and
  canonical review/PR/merge chain. E48.4 does **not** merge `footboard` branches.
- `drivr` — execution dependency only; **no code change**.

**Invocation:** `PYTHONPATH=. pytest -q` in `ai-project-system` for record edits; `bin/suite-gate`
(E48.2) for the source-suite gate; `OpenCodeAdapter.execute` (Drivr) for the run itself. The run is
verified with `bin/successful-nothing-instrument` via E48.1's `bin/drivr-events-to-instrument`
adapter.

**Constraint — no credentials:** no credential value, token, or secret-bearing environment value is
read into any committed artifact (M48 Binding Constraint 7).

## Dependencies

**Internal**
- **E48.1 (accepted)** — the run-record contract, quality-bar + dispatch-manifest contract, input
  adapter, and normalization path.
- **E48.2 (accepted)** — the deterministic source-suite gate (`bin/suite-gate`).

**External**
- **`footboard`** — the migration and the real Epic, under its own hierarchy.
- **Drivr** — the dispatch path (`OpenCodeAdapter`), no code change.
- **System HQ** — the cross-project request/response and steering-note channel.
- **Human authority** — the benched-to-eligible transition; `footboard`'s own parent acceptance of
  the selected Epic's spec/Starter.

**Blockers**
- None at planning. At execution, missing eligibility authority or missing parent acceptance of the
  selected Epic is a named block, not a silent skip.

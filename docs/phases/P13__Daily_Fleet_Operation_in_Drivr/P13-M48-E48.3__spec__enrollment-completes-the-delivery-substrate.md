# Epic E48.3 — Enrollment Completes the Delivery Substrate

## Context

**Governed delivery depends on PRs, but initialization has never created a route to one.**

SN-45 names the gap: the framework assumes a configured remote, while `bin/ai-project-init`
establishes none. The P13 opening ruling ties SN-45 to Decision 2 (Drivr received a private remote
so its acceptance chain became operable) — the same defect met from the other side. M48 owns closing
it; M55 reverifies it in practice.

**Re-measured at planning (2026-09-08, this chat):** `bin/ai-project-init` runs `git init`, adds the
governance submodule (which adds a remote for the *submodule*, not the project), commits the
scaffold, and installs the HQ agent — and carries **no project-remote option at all**. The only
git-related flags are `--skip-git` and `--skip-submodule`. There is no enrollment step, no `origin`,
and no verification that a configured remote/tracking relationship exists or works. A brand-new
project exits init with a local repository and zero path to a PR.

The M48 milestone spec's E48.3 detail is carried here **as the scope, not re-derived**:

- Close SN-45 in the supported initialization path with **remote present, remote absent,
  invalid/failing remote, and intentional local-only** coverage.
- Keep **remote enrollment distinct from fleet activation and dispatch** — enrollment alone does
  not auto-activate or dispatch a project.
- **Never create, store, or print credentials.**

## Problem Statement

A project initialized today is delivery-incapable: it has a local repository and no remote, and
there is no explicit step that establishes and verifies the configured remote/tracking relationship.
The result is that governed delivery (which assumes PRs) silently degrades to local-only work that
can never be merged, and the framework has no way to distinguish **delivery-ready** from
**local-only** from **remote absent** — let alone to fail closed on the difference.

Two failure modes are the ones this Epic must specifically not reproduce:

1. **Reachability is not a relationship.** A naive check that "the remote exists" (`git ls-remote
   <url>`) proves only that the URL is reachable and lists refs. It does **not** prove that the
   project branch has an upstream tracking relationship, that the project's own commit was actually
   pushed, or that the remote's ref equals the local ref. Enrollment verification must prove all
   three, or it proves nothing.
2. **"Local-only" is not a state that can be inferred.** An intentional local-only choice must be a
   **durable, explicitly recorded disposition**, not a transient result and not the same thing as
   "no remote configured." Absent a durable record, "local-only" is indistinguishable from "never
   enrolled," and the fail-closed gate has nothing to read.

## Goals

By the end of this Epic, the system must:

1. Add an **explicit, fail-closed enrollment step/option** to the supported initialization path that
   establishes and **verifies the remote/tracking relationship end to end** (remote set, tracking
   relationship recorded, commit pushed, ref equality) without embedding credentials.
2. Preserve an **intentional local-only choice as a durable, recorded disposition** — explicitly
   represented, distinct from both delivery-ready and remote-absent.
3. Cover **remote present, remote absent, invalid/failing remote, and intentional local-only** cases,
   each with a distinct, tested outcome.
4. Document the boundary between **creating/configuring a remote** and **fleet eligibility** — and
   ensure enrollment changes neither fleet eligibility nor execution state.

## Non-Goals

This Epic explicitly does **not** aim to:

- **Auto-activate or dispatch a project.** Enrollment is configuration, not eligibility, not
  activation, not dispatch (dispatch extension is M50+ work and outside M48 entirely).
- **Create, store, or print credentials.** Any authentication needed to reach a remote is external
  to this Epic; the remote URL and tracking branch are config, not a secret.
- **Change fleet-registry state.** Enrollment never writes `active`/`benched`/`archived`.
- **Change Drivr code.** No Drivr implementation is authorized by M48.

## Scope of Work

### 1. The enrollment step/option (D1)

Add an explicit enrollment capability to the supported initialization path.

**Must include:**
- A way to supply a remote (an option or an explicit post-init step) that sets the remote and the
  tracking relationship.
- **End-to-end verification, not reachability** (see D2): a completed enrollment has proven the
  remote/tracking relationship, not merely that a URL answers.
- **Fail-closed** behaviour: an invalid or unreachable remote is a stated failure, not a silent skip
  and not a completed enrollment.

### 2. The four outcomes, with real verification semantics (D2)

Make each case an explicit, tested result. **Verification for "present" proves the whole
relationship**, against a local bare-repo fixture (no network, no credentials):

- **Remote present — delivery-ready.** The enrollment sets the remote (`origin`) and the upstream
  tracking relationship, pushes the current branch, and then verifies **all three** of: (a) the
  tracking relationship is recorded (`<branch>@{upstream}` resolves); (b) the pushed branch exists on
  the remote; (c) **ref equality** — the remote's ref for that branch equals the local branch SHA.
  Only all three satisfied is `delivery-ready`. `git ls-remote` reachability alone is explicitly
  **not** sufficient.
- **Remote absent.** No remote configured and no local-only disposition recorded → reported as not
  delivery-ready (fail-closed, stated reason).
- **Invalid/failing remote.** Remote configured but verification fails (unreachable, or reachable
  but push/ref-equality fails) → stated failure, reason recorded, not delivery-ready.
- **Intentional local-only.** A **durable disposition record** is committed (see D2a) naming the
  intent, distinct from "remote absent" (which is an *absence*, not an *intent*) and distinct from
  "delivery-ready."

### 2a. The durable local-only disposition (D2a)

An intentional local-only choice is a **durable, committed record**, not a transient result.

**Must include:**
- A defined disposition artifact — e.g. a committed `.ai-project/enrollment.yml` (or a field on the
  project config) — carrying `mode: local-only` and a reason, so the choice survives restarts and is
  readable by the delivery gate.
- A rule that `mode: local-only` is the **only** thing that permits a project to be "not
  delivery-ready but not remote-absent"; the absence of any record plus the absence of a remote
  stays fail-closed.

### 3. The eligibility boundary (D3)

Document, in the artifact and the code comments, that enrollment **creates/configures a remote and
records a disposition** and does **not** change fleet eligibility or execution state. Enrollment
alone never activates or dispatches.

### 4. Regression coverage (D4)

Automated tests covering all four outcomes (present with the three-part verification, absent,
failing, local-only with the durable record), plus the invariant that enrollment never writes a
credential value and never emits one in diagnostics.

## Deliverables

This Epic must produce:

- [ ] **D1** — Explicit fail-closed enrollment step/option in `bin/ai-project-init` (or the supported path), establishing and verifying the remote/tracking relationship end to end
- [ ] **D2** — The four outcomes (present-with-three-part-verification / absent / failing / local-only) as explicit, tested results
- [ ] **D2a** — The durable local-only disposition record, distinct from delivery-ready and remote-absent
- [ ] **D3** — Documented eligibility boundary: enrollment ≠ fleet activation ≠ dispatch
- [ ] **D4** — Regression tests for all four outcomes + the durable disposition + the no-credential invariant
- [ ] **Epic Delivery Notice**

## Binding Constraints

Settled above this epic — **not re-decidable here** (M48 milestone spec):

1. **Static validation is not operational proof.** An enrollment step that only *writes* a config
   line without *verifying* the remote is not the fix — and reachability is not verification.
2. **Eligibility requires explicit authority.** Enrollment never grants it, never infers it.
3. **Never create, store, or print credentials.**
4. **M48 authorizes no Drivr implementation.**
5. **`undetermined`, missing evidence, credential absence, and an authenticated refusal remain
   distinct.** An enrollment that cannot verify a remote because credentials are absent reports that
   distinctly, not as "no remote."

## Definition of Done

Epic E48.3 is complete when:

- [ ] A newly initialized project cannot be reported delivery-ready without a verified remote
      (tracking recorded + pushed branch + ref equality) **or** a durable local-only disposition
- [ ] The enrollment step verifies the remote/tracking relationship fail-closed on
      invalid/unreachable/failing remotes
- [ ] All four outcomes (present / absent / failing / local-only) are explicit and automated-tested,
      and local-only is represented by a durable, committed disposition distinct from remote-absent
- [ ] Diagnostics contain no credential values
- [ ] Enrollment alone changes neither fleet eligibility nor execution state (verified by test and documented)
- [ ] Suite green (`PYTHONPATH=. pytest -q`)
- [ ] Every validation claim states repository, ref, date, command/check, and result; no claim covers
      another repository's suite (M48 Binding Constraint 9 — repository claims are bounded)
- [ ] Delivery Notice committed; PR opened from `epic/E48.3` to `milestone/M48`

## Acceptance Criteria

- [ ] A newly initialized project cannot be reported delivery-ready without a verified remote or
      an explicit, durable local-only disposition
- [ ] Diagnostics contain no credential values
- [ ] Enrollment alone changes neither fleet eligibility nor execution state
- [ ] Automated tests cover all supported outcomes (including the three-part verification and the
      durable local-only record)

## Technical Constraints

**Repository:** all E48.3 code, tests, documentation, and the Delivery Notice land in
`ai-project-system` on `epic/E48.3`. The subject is `bin/ai-project-init` (and its tests), this
repository only.

**Invocation:** `PYTHONPATH=. pytest -q`. Enrollment tests must not require a real external remote;
they use local `git init --bare` fixtures so the full relationship (tracking + push + ref equality)
can be established and verified without network and without any credential.

**Constraint — no credentials:** the remote URL and tracking branch are configuration. No token,
PAT, SSH passphrase, or secret-bearing value is accepted into, stored in, or printed by the
enrollment path.

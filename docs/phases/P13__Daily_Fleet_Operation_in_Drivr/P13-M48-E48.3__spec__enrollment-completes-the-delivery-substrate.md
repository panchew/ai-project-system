# Epic E48.3 — Enrollment Completes the Delivery Substrate

## Context

**Governed delivery depends on PRs, but initialization has never created a route to one.**

SN-45 names the gap: the framework assumes a configured remote, while `bin/ai-project-init`
establishes none. The opening ruling ties SN-45 directly to Decision 2 (Drivr received a private
remote so its acceptance chain became operable) — the same defect met from the other side. M48 owns
closing it, verified again at M55.

**Re-measured at planning (2026-09-08, this chat):** `bin/ai-project-init` runs `git init`, adds the
governance submodule (which adds a remote for the *submodule*, not the project), commits the
scaffold, and installs the HQ agent — and carries **no project-remote option at all**. The only
git-related flags are `--skip-git` and `--skip-submodule`. There is no enrollment step, no
`origin`, and no verification that a configured remote/tracking relationship exists or works. A
brand-new project exits init with a local repository and zero path to a PR.

The M48 milestone spec's E48.3 detail is carried here **as the scope**, not re-derived:

- Close SN-45 in the supported initialization path with **remote present, remote absent,
  invalid/failing remote, and intentional local-only** coverage.
- Keep **remote enrollment distinct from fleet activation and dispatch** — enrollment alone does
  not auto-activate or dispatch a project.
- **Never create, store, or print credentials.**

## Problem Statement

A project initialized today is delivery-incapable: it has a local repository and no remote, and
there is no explicit step that says "establish and verify the configured remote/tracking
relationship." The result is that governed delivery (which assumes PRs) silently degrades to
local-only work that can never be merged, and the framework has no way to distinguish "delivery-
ready" from "local-only" — let alone to fail closed on the difference.

## Goals

By the end of this Epic, the system must:

1. Add an **explicit, fail-closed enrollment step/option** to the supported initialization path that
   can establish and verify the configured remote/tracking relationship without embedding
   credentials.
2. Preserve an **intentional local-only choice as an explicit result**, not a silent state read as
   fleet-ready.
3. Cover **remote present, remote absent, invalid/failing remote, and intentional local-only** cases.
4. Document the boundary between **creating/configuring a remote** and **fleet eligibility** — and
   ensure enrollment changes neither fleet eligibility nor execution state.

## Non-Goals

This Epic explicitly does **not** aim to:

- **Auto-activate or dispatch a project.** Enrollment is configuration, not eligibility, not
  activation, not dispatch (M48: dispatch extension is M50+ work and outside M48 entirely).
- **Create, store, or print credentials.** Any authentication needed to reach a remote is external
  to this Epic; the remote URL and tracking branch are config, not a secret.
- **Change fleet-registry state.** Enrollment never writes `active`/`benched`/`archived`.
- **Change Drivr code.** No Drivr implementation is authorized by M48.

## Scope of Work

### 1. The enrollment step/option (D1)

Add an explicit enrollment capability to the supported initialization path.

**Must include:**
- A way to supply a remote (e.g. an option or an explicit post-init step) that sets the remote and
  verifies the tracking relationship.
- **Fail-closed** behaviour: an invalid or unreachable remote is a stated failure, not a silent
  skip and not a completed enrollment.

### 2. The four outcomes (D2)

Make each of the four cases an explicit, tested result:
- **Remote present** — remote configured and verified; project is delivery-ready.
- **Remote absent** — no remote configured; reported as not delivery-ready (fail-closed, stated).
- **Invalid/failing remote** — remote configured but verification fails; stated failure, reason
  recorded.
- **Intentional local-only** — an explicit opt-out recorded as local-only, distinct from
  "delivery-ready" and distinct from "remote absent."

### 3. The eligibility boundary (D3)

Document, in the artifact and the code comments, that enrollment **creates/configures a remote**
and does **not** change fleet eligibility or execution state. Enrollment alone never activates or
dispatches.

### 4. Regression coverage (D4)

Automated tests covering all four outcomes, plus the invariant that enrollment never writes a
credential value and never emits one in diagnostics.

## Deliverables

This Epic must produce:

- [ ] **D1** — Explicit fail-closed enrollment step/option in `bin/ai-project-init` (or the supported path), verifying the remote/tracking relationship
- [ ] **D2** — The four outcomes (present / absent / failing / local-only) as explicit, tested results
- [ ] **D3** — Documented eligibility boundary: enrollment ≠ fleet activation ≠ dispatch
- [ ] **D4** — Regression tests for all four outcomes + no-credential invariant
- [ ] **Epic Delivery Notice**

## Binding Constraints

Settled above this epic — **not re-decidable here** (M48 milestone spec):

1. **Static validation is not operational proof.** An enrollment step that only *writes* a config
   line without *verifying* the remote is not the fix.
2. **Eligibility requires explicit authority.** Enrollment never grants it, never infers it.
3. **Never create, store, or print credentials.**
4. **M48 authorizes no Drivr implementation.**
5. **`undetermined`, missing evidence, credential absence, and an authenticated refusal remain
   distinct.** An enrollment that cannot verify a remote because credentials are absent reports that
   distinctly, not as "no remote."

## Definition of Done

Epic E48.3 is complete when:

- [ ] A newly initialized project cannot be reported delivery-ready without a verified remote or an
      explicit local-only disposition
- [ ] The enrollment step verifies the remote/tracking relationship fail-closed on invalid/unreachable remotes
- [ ] All four outcomes (present / absent / failing / local-only) are explicit and automated-tested
- [ ] Diagnostics contain no credential values
- [ ] Enrollment alone changes neither fleet eligibility nor execution state (verified by test and documented)
- [ ] Suite green (`PYTHONPATH=. pytest -q`)
- [ ] Every claim states repository, ref, date, and verification command (`P11-GH-2`)
- [ ] Delivery Notice committed; PR opened from `epic/P13-M48-E48.3` to `milestone/M48`

## Technical Constraints

**Repository:** all E48.3 code, tests, documentation, and the Delivery Notice land in
`ai-project-system` on `epic/P13-M48-E48.3`. The subject is `bin/ai-project-init` (and its tests),
this repository only.

**Invocation:** `PYTHONPATH=. pytest -q`. Enrollment tests must not require a real external remote;
they use local `file://` or in-temp-dir `git init --bare` fixtures, so a remote can be established
and verified without network and without any credential.

**Constraint — no credentials:** the remote URL and tracking branch are configuration. No token,
PAT, SSH passphrase, or secret-bearing value is accepted into, stored in, or printed by the
enrollment path.

**Traps already paid for by this project:**
- **A config line without verification.** Writing `remote` into `.git/config` is not enrollment;
  verification (e.g. `git ls-remote` against a local bare repo) is the proof.

  a silent default.
- **Emitting credentials.** The path never reads or prints authentication material.

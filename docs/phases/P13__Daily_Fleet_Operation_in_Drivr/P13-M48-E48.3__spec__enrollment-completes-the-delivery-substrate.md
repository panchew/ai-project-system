# Epic E48.3 — Enrollment Completes the Delivery Substrate

## Context

**Governed delivery depends on PRs, but initialization has never created a route to one.**

SN-45 names the gap: the framework assumes a configured remote, while `bin/ai-project-init`
establishes none. The P13 opening ruling ties SN-45 to Decision 2 (Drivr received a private remote
so its acceptance chain became operable) — the same defect met from the other side. M48 owns closing
it; M55 reverifies it in practice.

**Re-measured at planning (2026-09-08, this chat):** `bin/ai-project-init` runs `git init`, adds the
governance submodule (which adds a remote for the *submodule*, not the project), commits the
scaffold, then **amends** that commit to include the HQ agent file. It exposes only `--skip-git` and
`--skip-submodule` as git-related flags — no project-remote option, no `origin`, no tracking
verification. Two facts matter for this Epic: (1) there is no enrollment step at all; (2) the
project's **final `HEAD` is only known after the post-init amend**, so any enrollment that runs or
verifies before that amend reads a pre-amend SHA.

The M48 milestone spec's E48.3 detail is carried here **as the scope, not re-derived**: close SN-45
in the supported initialization path with remote present/absent/invalid-failing/intentional-local-only
coverage; keep enrollment distinct from fleet activation and dispatch; never create, store, or print
credentials.

## Problem Statement

A project initialized today is delivery-incapable: it has a local repository and no remote, and
there is no explicit step that establishes and verifies the remote/tracking relationship. The result
is that governed delivery silently degrades to local-only work that can never be merged, and the
framework has no way to distinguish **delivery-ready** from **local-only** from **remote absent** —
let alone to fail closed on the difference.

Six failure modes are the ones this Epic must specifically not reproduce:

1. **Reachability is not a relationship.** `git ls-remote <url>` proves only that the URL answers.
   It does not prove a tracking relationship, a pushed branch, or ref equality. Verification must
   prove all three.
2. **Local-only is not delivery-ready.** An intentional local-only choice is a valid, durable
   disposition — but it is **explicitly non-delivery-ready**. It must never satisfy the
   delivery-ready predicate; only the three-part remote verification does.
3. **A partial contract.** A command that cannot report the current state (including `absent`), has
   no value for `delivery-ready`'s `detail`, no mapping for credential-URL rejection, and no fixed
   local-only artifact is prose, not a runnable, testable step.
4. **Ordering and recovery.** Enrollment that runs before the final commit amendment verifies and
   pushes a pre-amend SHA; a pre-existing `origin`, a partial push/upstream setup, or a failed
   verification must have a **deterministic** authoritative state and idempotent retry.
5. **Secret safety.** A credential-bearing remote URL must never reach `.git/config`, Git's own
   diagnostics (which echo URLs) must be redacted, and the credential-absent vs authenticated-refusal
   distinction must be classifiable from redacted diagnostics.
6. **Closure-sequence coherence.** The Delivery Notice (pre-review) and the PR (post-authorization)
   are different stages and must not be made to confirm each other.

## Goals

By the end of this Epic, the system must:

1. Commit **one executable, total enrollment command** — `bin/ai-project-enroll <project-dir>
   [--remote <url> | --local-only]` — with a status/query mode (no flag) that reports the current
   disposition, mutually exclusive `--remote`/`--local-only` modes, an output schema, a complete
   reason taxonomy, and exit semantics.
2. Make **delivery-ready require the three-part remote verification exclusively**; keep local-only a
   durable, recorded disposition that is **explicitly non-delivery-ready**.
3. Preserve **distinct** `verified`, `absent`, `credential-absent`, `authenticated-refusal`,
   `verification-failure`, `local-only`, `undetermined`, and `invalid-url` states.
4. Define **deterministic mutation ordering and recovery**: enrollment after the final commit
   amendment, ref equality against final `HEAD`, one rule for pre-existing `origin`, a defined
   authoritative post-failure state, and idempotent retry without unsafe remote deletion.
5. Enforce **secret safety**: reject credential-bearing remote URLs (with a defined status/detail/
   exit and `remote: null`), redact Git diagnostics, classify credential-absent vs
   authenticated-refusal, and prove by test (including a synthetic stderr sentinel).
6. Document the boundary between enrollment and fleet eligibility; enrollment never changes fleet
   eligibility or execution state.

## Non-Goals

This Epic explicitly does **not** aim to:

- **Auto-activate or dispatch a project.** Enrollment is configuration, not eligibility, not
  activation, not dispatch (dispatch extension is M50+ and outside M48).
- **Create, store, or print credentials.** Any authentication needed to reach a remote is external;
  the remote URL and tracking branch are config, not a secret.
- **Change fleet-registry state.** Enrollment never writes `active`/`benched`/`archived`.
- **Change Drivr code.** No Drivr implementation is authorized by M48.

## Scope of Work

### 1. The executable, total enrollment command and status contract (D1)

Commit **one** supported command — `bin/ai-project-enroll <project-dir> [--remote <url> | --local-only]`.

**Invocation modes (total):**
- **Status/query (no flag):** **freshly verify Git** and report the current disposition — it does
  **not** trust a persisted delivery-ready claim. Query re-runs the three-part verification against
  live Git state (tracking / pushed / ref equality) and reports the observed truth. This is how
  `absent` and an existing `local-only`/`delivery-ready` disposition are read back, and how a stale
  persisted record is surfaced (see transition precedence below).
- **Enroll remote (`--remote <url>`):** full enrollment + three-part verification.
- **Enroll local-only (`--local-only`):** record the durable disposition. `--remote` and
  `--local-only` are mutually exclusive.

**Query truth and transition precedence (fixed, four cases):**
- **no `origin` and no local-only record** → `absent`.
- **no `origin` plus a valid local-only record** → `local-only`.
- **`origin` plus any local-only record** → `verification-failure` (conflict; the stale record is
  named).
- **`origin` without a local-only record** → a fresh read-only three-part verification.
- A persisted record **never** asserts delivery readiness; `delivery-ready` is only ever reported from
  a live three-part verification. Query checks **both** the fetch and push URLs.

**Output schema (all modes, machine-parseable, e.g. JSON):**
`{"status": <delivery-ready|local-only|not-delivery-ready>, "detail": <verified|absent|credential-absent|authenticated-refusal|verification-failure|local-only|undetermined|invalid-url>, "reason": <redacted str>, "remote": <url|null>, "tracking": <true|false|null>, "pushed": <true|false|null>, "ref_equal": <true|false|null>}`

- `tracking`, `pushed`, `ref_equal` are each **`true | false | null`**. `null` means the observation
  could not be made (authentication / transport / `undetermined` prevented it); `null` is never
  converted to `false`. `pushed` means the target branch was **observed on the remote**, not merely
  that a push command was attempted.

**Reason taxonomy — total (a `detail` for every `status`):**
- `verified` — `status: delivery-ready`; the three-part verification passed. (This is the required
  `detail` for delivery-ready; there is no other way to reach `delivery-ready`.)
- `local-only` — `status: local-only`; the durable disposition was recorded; non-delivery-ready.
- `absent` — `status: not-delivery-ready`; no remote and no local-only disposition (query mode).
- `credential-absent` — `status: not-delivery-ready`; transport could not obtain credentials.
- `authenticated-refusal` — `status: not-delivery-ready`; transport reached the remote and was refused.
- `verification-failure` — `status: not-delivery-ready`; one of the three verification steps failed
  (push failed / tracking not recorded / ref mismatch / pre-existing-origin conflict / origin+local-only conflict).
- `undetermined` — `status: not-delivery-ready`; the step could not reach a determination.
- `invalid-url` — `status: not-delivery-ready`; a credential-bearing **supplied or stored** URL was
  rejected; `remote: null`, no transport invocation, and the reason is non-secret.

**Exit semantics:**
- **Query (no flag) is read-only** and exits `0` for freshly verified `delivery-ready` or a recorded
  `local-only`; **every `not-delivery-ready` result exits `1`** (query records nothing).
- **`--remote`/`--local-only` (mutation)** exit `0` when the disposition was recorded, non-zero for
  `not-delivery-ready`.
- A credential-bearing supplied or stored URL yields `not-delivery-ready`/`invalid-url`, `remote:
  null`, exit `1`, and **no transport invocation**.
- `delivery-ready` is only ever emitted by the three-part verification.

### 2. Three-part verification — delivery-ready exclusively (D2)

`delivery-ready` requires **all three** of: (a) the upstream tracking relationship is recorded
(`<branch>@{upstream}` resolves); (b) the current branch is **observed on the remote** (`pushed:
true` — observed, not merely attempted); (c) **ref equality** — the remote's ref for that branch
equals the **final local `HEAD`** SHA. All three, or not delivery-ready; the `detail` is then
`verified`, and nothing else.

### 2a. The durable local-only disposition — committed lifecycle (D2a)

- **Fixed path:** `.ai-project/enrollment.yml`.
- **Fixed schema:** `enrollment: { mode: local-only, reason: <str>, recorded_at: <ISO8601> }`.
- **Committed lifecycle (Git-feasible):** `--local-only` is allowed **only without an `origin`**. It
  requires a **clean worktree**, writes `.ai-project/enrollment.yml`, **stages only that path**, and
  **commits it** as `chore: record local-only enrollment`. Repeating it with the same valid record
  and no `origin` is a **no-op success**. With an `origin`, it **fails without mutation**.
- **Status reader:** `bin/ai-project-enroll <project-dir>` with no flag (query) reports the
  disposition per D1's four-case precedence; `local-only` is **non-delivery-ready** and never
  satisfies the delivery-ready predicate.

### 3. The eligibility boundary (D3)

Document, in the artifact and code comments, that enrollment **configures a remote / records a
disposition** and does **not** change fleet eligibility or execution state. Enrollment alone never
activates or dispatches.

### 4. Mutation ordering, deterministic recovery, and initializer integration (D4)

- **Ordering:** enrollment runs **after** the initializer's final commit amendment, and ref-equality
  verification is against the **final `HEAD`** (never a pre-amend SHA).
- **Initializer integration — specified, not optional:** `bin/ai-project-init` performs its **final
  agent amend before forwarding** to enrollment. `--enroll-remote <url>` and `--enroll-local-only`
  are validated **before project creation**, with fixed precedence: **both options supplied → usage
  exit `2`**; otherwise, **an enrollment option combined with `--skip-git` → usage exit `3`**. The
  standalone `bin/ai-project-enroll` remains the supported path for existing projects; the init
  option is a thin forwarder, not a second implementation.
- **`--remote` transition:** validate the requested URL **and any existing `origin` before
  mutation**. A **different** existing `origin` URL fails without mutation. With a local-only record,
  `--remote` requires a **clean worktree**, **removes only that record**, and commits the removal as
  `chore: transition to remote enrollment`; **that new `HEAD` is the SHA pushed and verified**. A
  same-URL `origin` is re-verified. Once a push has changed remote state, a later failure **never
  deletes or rewinds the remote**.
- **Authoritative post-failure state:** after a failed verification, the remote stays set and the
  state is `status: not-delivery-ready`, `detail: verification-failure`. **Each boolean preserves its
  independently observed value** — `tracking`/`pushed`/`ref_equal` are `true|false|null`; a ref
  mismatch with valid tracking reports `tracking: true, ref_equal: false`; an unobservable value is
  `null`, never forced to `false`. The failure is carried by `detail` + `reason`.
- **Retry/idempotency:** retry **resumes from the retained local/remote state** — it re-verifies the
  current `HEAD` and completes any missing tracking/ref step without duplicating, deleting, or
  rewinding state.

### 5. Secret safety — adversarial, with classification (D5)

- **Reject credential-bearing remote URLs before any write or transport:** a **supplied or stored**
  URL carrying userinfo (`https://user:token@host`) or a token-shaped query/fragment is rejected with
  `status: not-delivery-ready`, `detail: invalid-url`, exit `1`, `remote: null`, no transport
  invocation, and a non-secret reason — **before `.git/config` is touched**. An existing
  credential-bearing `origin` is likewise emitted as `remote: null`, never the credential URL.
- **Redact Git diagnostics:** Git's stderr (which can echo the URL) is redacted before it is printed
  or recorded; reason strings never contain a credential-bearing URL or sentinel secret.
- **Classification rules (deterministic, ambiguity-first, keyed on redacted, lowercased Git stderr):**
  compute the **refusal-token** match and the **credential-absence-token** match **independently**,
  then classify:
  - **both or neither** → `undetermined`;
  - **refusal only** → `authenticated-refusal`;
  - **credential-absence only** → `credential-absent`.
  Refusal tokens: `authentication failed`, `401`, `403`, `permission denied`, `access denied`.
  Credential-absence tokens: `could not read username`, `could not read password`, `no credentials`,
  `terminal prompts disabled`, `could not read from remote`.
  **`repository not found` alone is not refusal evidence** (it is a known non-auth Git failure →
  `verification-failure`). Known non-auth Git failures and failed three-part checks remain
  `verification-failure`. Ambiguity (both families, or neither with no non-auth match) is detected
  **before** any ordered-match decision, so identical stderr always classifies identically.
- **Two distinct test classes:** (a) credential-URL rejection proves the synthetic secret never
  reaches `.git/config` or output; (b) a **synthetic fake-Git-stderr fixture** containing a sentinel
  secret is passed through the redactor and the classifier, asserting the sentinel is absent from
  output and the classification is correct. (a) alone cannot exercise (b), because rejection happens
  before Git runs.

### 6. Regression coverage (D6)

Tests cover: the three-part verification; all eight `detail` states (including credential-absent vs
authenticated-refusal, and the query-mode `absent`); the durable local-only record and its reader; the
ordering (post-amend, final `HEAD`) rule; the pre-existing-origin rule, post-failure state, and
idempotent retry; credential-URL rejection; and the fake-stderr redaction + classification.

## Binding Constraints

Settled above this epic — **not re-decidable here** (M48 milestone spec):

1. **Static validation is not operational proof.** An enrollment step that only writes a config line
   without verifying is not the fix — and reachability is not verification.
2. **Eligibility requires explicit authority.** Enrollment never grants it, never infers it.
3. **Never create, store, or print credentials.**
4. **M48 authorizes no Drivr implementation.**
5. **`undetermined`, missing evidence, credential absence, and an authenticated refusal remain
   distinct.** `credential-absent` (no credentials obtainable) and `authenticated-refusal` (remote
   refused) are different states, classified from redacted diagnostics.

- [ ] `delivery-ready` is emitted **only** by the three-part verification (detail `verified`), and a
      durable local-only disposition (detail `local-only`) is **non-delivery-ready**
- [ ] `bin/ai-project-enroll` is a committed, total command: query is read-only and exits `0` for
      freshly verified `delivery-ready`/recorded `local-only`, `1` for every `not-delivery-ready`;
      the four-case query precedence holds; `tracking`/`pushed`/`ref_equal` are `true|false|null`

- [ ] The local-only artifact has a **committed lifecycle**: clean worktree, staged-only commit
      (`chore: record local-only enrollment`), no-op repeat, fail-without-mutation on `origin`; the
      `--remote` transition commits the record removal (`chore: transition to remote enrollment`) and
      pushes that new `HEAD`
- [ ] The initializer performs its final amend before forwarding, and validates options with usage
      exit `2` (both options) / exit `3` (option + `--skip-git`) before project creation
- [ ] Credential-bearing URLs are rejected before `.git/config`; Git diagnostics are redacted; a
      synthetic fake-stderr sentinel is absent from output; classification is ambiguity-first
      (both/neither → `undetermined`; `repository not found` alone is not refusal)
- [ ] Diagnostics contain no credential values
- [ ] Enrollment alone changes neither fleet eligibility nor execution state (verified by test and documented)
- [ ] Suite green (`PYTHONPATH=. pytest -q`)
- [ ] Every validation claim states repository, ref, date, command/check, and result; no claim covers
      another repository's suite (M48 Binding Constraint 9 — repository claims are bounded)

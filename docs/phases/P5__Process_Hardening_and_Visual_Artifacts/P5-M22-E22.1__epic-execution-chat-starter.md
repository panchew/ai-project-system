### Summary

Deliver the **config layer** for visual artifacts (VA-1): document a `visual_artifacts` block in
`governance/ai-project-yml-spec.md`, validate it in the **existing** `.ai-project.yml` handling,
test valid/invalid/absent cases, and set the block to `enabled: false` in this repo's
`.ai-project.yml`. This is the hard prerequisite for E22.2.

### Problem Statement

The framework has no configuration switch for visual artifacts. Until `.ai-project.yml` can express
`visual_artifacts.enabled`, `comfyui_url`, and `types` — and the spec documents and a handler
validates that block — nothing downstream (AOG guidance, the ComfyUI helper, the integration test
in E22.2) has a contract to read. This Epic supplies that contract: opt-in, default-off, validated.

### Goals

1. **Document** the `visual_artifacts` block in `governance/ai-project-yml-spec.md` (§3 schema +
   §3.1 full-schema reference + §4 validation rules + example), as an optional opt-in block.
2. **Validate** the block in the **existing** config handling (no parallel validator): `enabled`
   boolean; `types` ∈ {`diagrams`, `infographics`, `video`}; `comfyui_url` a well-formed URL when
   present; block optional (absent ⇒ disabled).
3. **Test** valid, invalid (`enabled` / `types` / `comfyui_url`), and absent/default cases; full
   suite green.
4. **Configure** this repo's `.ai-project.yml` with the block, `enabled: false`.

## Required Content — the block and where it lives

**Canonical block shape** (from the Milestone spec):

```yaml
visual_artifacts:
  enabled: false              # opt-in; default false
  comfyui_url: http://localhost:8188
  types:
    - diagrams                # Mermaid/PlantUML structural
    - infographics            # ComfyUI-generated imagery
    - video                   # ComfyUI video (optional)
```

**Mirror the established pattern.** The `models` block (`governance/ai-project-yml-spec.md` §3.4 +
§4 rules 14–17) and `overrides` (§3.3 + §4 rules 9–13) are the template for an optional block:
schema shape, §4 rule style (**warning** for unknown keys, **error** for bad values), and test
style. Read those first and follow them.

**Two existing handlers — extend, do not duplicate:**
- `bin/ai-project-init` (**bash**) — `validate_ai_project_yml_content()` validates `.ai-project.yml`
  at scaffold time (the §6 "validate against §4 rules" path).
- `bin/ai-project-orchestrator` (**Python**) — `load_yml_config()` (`yaml.safe_load`) currently
  reads only `models`; it carries inline `unittest` tests.

The validation locus is your design decision, with three hard constraints: (a) reuse existing
handling — **no parallel validator**; (b) match the documented §4 rules exactly; (c) an absent
block is valid and means disabled (no error, no warning). Match the language of whichever handler
you extend.

**Versioning:** bump the spec version (minor: **2.0.0 → 2.1.0**), add a Changelog row citing
E22.1 (P5-M22), and update the `# Spec: ... v2.0.0` header comment in `.ai-project.yml` to match.

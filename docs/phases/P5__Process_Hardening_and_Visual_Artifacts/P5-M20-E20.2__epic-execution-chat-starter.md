### Summary

Close GH-2: document a working-tree isolation convention so two concurrently-active chats
cannot switch branches under each other and commit to the wrong place silently. Also resolve
the lint false-positive (folded in per Phase Chat decision) so `milestone/M20` is green.

### Problem Statement

A Milestone Chat and an Epic Chat shared one working tree. While the Milestone Chat had an
in-flight commit, the Epic Chat checked out a new branch — the Milestone Chat's subsequent
commit landed on the wrong branch silently. No convention assigned tree ownership per chat.
(This recurred live during E20.1's review — the working tree was found switched onto the epic
branch under the Milestone Chat. Real demonstration of the gap.)

### Goals

1. Add a "Working-Tree Isolation" section to `governance/systems/chat-hierarchy.md` with the
   rule, practical guidance, and a worked `git worktree` example.
2. Add a corresponding rule to `governance/AI-OPERATING-GUIDELINES.md` §3 that references the
   isolation requirement.
3. Fix the `test_no_branch_name_typos_in_starters` lint false-positive so planned milestones
   (M21+) are accepted while genuine typos still fail — restoring a green suite.

## Required Content (verbatim intent)

The "Working-Tree Isolation" section in `chat-hierarchy.md` must contain:

- **Rule:** one `git worktree` per concurrently-active chat; a chat never operates in a
  tree another concurrent chat may switch.
- **Practical guidance:** `git worktree add ../worktree-<role>-<id> <branch>`
  — worked example: `git worktree add ../worktree-milestone-M21 milestone/M21`
- **Scope:** applies whenever two or more chats are active simultaneously.

The AOG §3 (Types of AI Chats / Chat Rules) addition must state the isolation requirement
and cross-reference the `chat-hierarchy.md` "Working-Tree Isolation" section.

**Keep the `milestone/M21` example as written** — do not change the milestone number to dodge
the lint. Instead fix the lint (next section).

the rule narrowly.

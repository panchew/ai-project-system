# Epic P5-M20-E20.5 — Hierarchical communication protocol (GH-9)

## Context

Milestone M20 hardens five governance process gaps. This Epic — the **final** epic of M20 —
closes **GH-9**: the model defines upward artifacts (Escalation/Completion Notices) but never
defined how directives propagate **downward**, especially when one parent must reach several
concurrent children.

SN-12 (2026-06-25, concern SN-12b) made the communication model a set of binding decisions:
upward is 1-to-1, downward is solved by the spec file (not broadcasting), the level spec file is
dual-role (planning artifact + live contract), and mid-flight changes escalate **up** rather
than reaching into running child sessions.

> **Source:** SN-12 (2026-06-25), concern SN-12b — binding decisions.

---

## Problem Statement

Without a defined downward channel, a parent with multiple concurrent children is tempted to
reach into each running child session to push a change — an unauditable, race-prone pattern
("downward reach"). And without a stated upward rule, levels may skip a parent to reach a
grandparent. The consequences: directives that never enter the record, children executing
against unstated changes, and a collapsed escalation chain.

---

By the end of this Epic, the system must:

## Scope of Work

### 1. "Communication Protocol" section in `chat-hierarchy.md`

Add a new section to `governance/systems/chat-hierarchy.md` covering the four SN-12b decisions:

- **Upward — 1-to-1, one level at a time.** Every level has exactly one parent. Escalations and
  completion notices travel up one level; the receiving level decides whether to absorb or
  escalate further. No level skips its parent to reach a grandparent.
- **Downward — the spec file is the channel, not broadcasting.** A parent communicates a
  directive/amendment/correction by amending its own spec file; children (including those
  mid-execution) read from that same source at any time. One write, many readers.
- **The level spec file is dual-role:** a *planning artifact* (what was planned) **and** a *live
  contract* (the authoritative state of scope/constraints/directives, including amendments).
- **Mid-flight updates escalate UP, never reach into running sessions.** If a directive changes
  after children are running, the parent amends the spec and — if the change is blocking —
  escalates **up** to its parent to decide whether to pause/cancel affected children. Downward
  reach into running sessions is not permitted.

### 2. AOG §3 and PSG

Add the corresponding rules to `governance/AI-OPERATING-GUIDELINES.md` §3 (cross-referencing the
chat-hierarchy.md section, mirroring the §3.8/§3.9 pattern) and to
`governance/PROJECT-SYSTEM-GUIDELINES.md` (the upward-1to1 / spec-as-channel / mid-flight-
escalate-up principles at the level of a system rule).

### 3. Amendment-issuing guidance in the two starter templates

Add to both `governance/templates/phase-execution-chat-starter.md` and
`governance/templates/milestone-execution-chat-starter.md` short guidance on how to issue an
amendment mid-flight: **amend the spec, note the change (e.g., an amendment-history entry), and
notify the parent chat** — do not reach into running child sessions.

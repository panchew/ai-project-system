## Notes

**Validation locus decision (the Epic-level design call the spec left open).** Validation lives in
the **Python loader** `bin/ai-project-orchestrator` (`load_yml_config` → `validate_visual_artifacts`),
**not** in `bin/ai-project-init`'s bash `validate_ai_project_yml_content`. Rationale:

1. **Single-source / no parallel validator (a hard constraint).** The structured checks the §4
   rules require — boolean type, set-membership for `types`, URL well-formedness for `comfyui_url`,
   unknown-key warnings — are clean and unambiguous in Python and brittle in grep-based bash.
   Putting them in one place keeps validation single-source.
2. **The bash validator never sees the block.** `validate_ai_project_yml_content` only validates the
   minimal content `create_ai_project_yml` scaffolds, which does not (and, for an opt-in default-off
   capability, should not) include `visual_artifacts`. Adding grep checks there would be dead code.
3. **`load_yml_config` already parses the real `.ai-project.yml` with `yaml.safe_load` and reads
   `models`** — it is the natural, existing home for reading and validating a sibling optional
   block, and it carries the inline-`unittest` precedent the spec points to.

Per §4 semantics, an invalid value raises a validation **error** (propagated as `ValueError`;
`main()` catches it and exits non-zero with a clean message), while an unknown key emits a
**warning** and is ignored. An absent block is valid and means disabled.

**No E22.2 scope touched** — AOG, `seed.md`, the ComfyUI helper, and the integration guide/test are
untouched, per the Epic's scope boundary.

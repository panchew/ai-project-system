# Epic P5-M22-E22.1 — Configuration and spec (VA-1 config layer)

## Context

Milestone M22 delivers visual artifacts as a first-class, opt-in capability. This Epic delivers
the **config layer**: it teaches `.ai-project.yml` to carry a `visual_artifacts` block, documents
that block in the configuration spec, validates it in the existing config handling, and sets the
block to `enabled: false` in this repo. Everything downstream (AOG guidance, the ComfyUI helper,
the integration test) reads the block this Epic defines — so E22.1 lands first and E22.2 branches
from the merged result.

> **Provenance:** Authored by the Milestone Chat (P5-M22) under its own authority on 2026-06-28.
> Per the GH-8 adjacency rule (E20.4, now governance law), the Phase Chat produced only the
> Milestone spec and the Milestone Execution Chat Starter; the Milestone Chat authors this Epic
> spec and its Epic Execution Chat Starter.

> **Source:** P5 phase spec, P5-VA-1 (config layer); M22 Milestone spec, "Epic Detail → E22.1";
> SN-11 binding decision 1 (opt-in via `visual_artifacts.enabled`, default `false`).

**Grounding (verified on `milestone/M22`, 2026-06-28):**
- `.ai-project.yml` is at the **repo root** and opts in to features simply today
  (`cfo_review_gate: enabled`). It already carries a `models:` block.
- The spec to extend is `governance/ai-project-yml-spec.md` (**currently v2.0.0**). Relevant
  sections: **§3 Schema**, **§3.1 Full Schema Reference**, **§3.3 / §3.4 Optional Fields**
  (`overrides`, `models` — the established "optional block" pattern), **§4 Validation Rules**
  (rules 1–17; rules **14–17** for the `models` block are the closest precedent for an optional
  block with set-membership / format validation, unknown-key **warning**, invalid-value
  **error**), and the **Changelog** at the foot of the file.
- `.ai-project.yml` is parsed/consumed by **two existing handlers** — extend them; do **not**
  introduce a parallel validator (Milestone grounding):
  - `bin/ai-project-init` (**bash**) — `validate_ai_project_yml_content()` performs grep-based
    field/section validation at scaffold time (this is the §6 "validate against §4 rules" point).
  - `bin/ai-project-orchestrator` (**Python**) — `load_yml_config()` uses `yaml.safe_load()` but
    currently reads only the `models` block; it carries inline `unittest` tests
    (`test_load_yml_config_default` / `_custom`).
- Tests: `tests/test_ongoing_artifacts.py` already does
  `yaml.safe_load(AI_PROJECT_YML.read_text())` and asserts on `cfo_review_gate` — the natural home
  for "this repo's `.ai-project.yml` carries the block with `enabled: false`."

---

## Problem Statement

The governance framework has no notion of visual artifacts at the configuration layer. An adopter
who wants concept imagery, an architecture diagram, or a UI mockup has **no configuration switch**
to enable the capability, no documented schema for where the generative endpoint lives, and no
validation to catch a malformed block. Until `.ai-project.yml` can express
`visual_artifacts.enabled`, the endpoint URL, and the allowed artifact types — and until the spec
documents and the handlers validate that block — none of the downstream M22 work (AOG guidance,
the ComfyUI helper, the integration test in E22.2) has a contract to read. This Epic supplies that
contract.

---

## Goals

By the end of this Epic, the system must:

1. **Document** the `visual_artifacts` block in `governance/ai-project-yml-spec.md` — schema
   (§3 / §3.1), validation rules (§4), and a worked example — as an **optional, opt-in** block
   that mirrors the existing `cfo_review_gate` / `models` opt-in philosophy.
2. **Validate** the block in the **existing** `.ai-project.yml` handling (no parallel validator):
   `enabled` is boolean; `types` ∈ {`diagrams`, `infographics`, `video`}; `comfyui_url` is a
   well-formed URL when present; the whole block is **optional** (absent ⇒ disabled).
3. **Test** valid blocks, invalid values, and the absent / default-false case, with the full suite
   green.
4. **Configure** this repo: add the `visual_artifacts` block to the root `.ai-project.yml` with
   `enabled: false`.

## Scope of Work

### 1. Spec extension — `governance/ai-project-yml-spec.md`

Document the `visual_artifacts` block as a new **optional** field, following the shape already
used for `overrides` (§3.3) and `models` (§3.4):

- **§3.1 Full Schema Reference** — add the block to the annotated full-schema example.
- **§3 Schema (new optional-fields subsection)** — define the block, its fields, types, defaults,
  allowed values, and behavioral effect (absent or `enabled: false` ⇒ capability off).
- **§4 Validation Rules** — add numbered rules mirroring the `models` rules (14–17):
  the block is optional; `enabled` must be boolean; `types` entries must each be one of
  {`diagrams`, `infographics`, `video`}; `comfyui_url`, when present, must be a well-formed URL;
  unknown keys in the block produce a **warning**; invalid values produce an **error**.
- **Example** — add a worked `visual_artifacts` example (and reference it from §9/§10 if
  consistent with house style).
- **Versioning** — bump the spec version (minor: **2.0.0 → 2.1.0**) and add a **Changelog** row
  citing this Epic (E22.1, P5-M22). Update the `# Spec: ... v2.0.0` header comment in
  `.ai-project.yml` to match.

The canonical block shape (from the Milestone spec):

```yaml
visual_artifacts:
  enabled: false              # opt-in; default false
  comfyui_url: http://localhost:8188
  types:
    - diagrams                # Mermaid/PlantUML structural
    - infographics            # ComfyUI-generated imagery
    - video                   # ComfyUI video (optional)
```

### 2. Validation — extend the existing handling

Validate the block where `.ai-project.yml` is already validated, **without** adding a parallel
validator. The primary validation point is `bin/ai-project-init`'s
`validate_ai_project_yml_content()` (the §6 "validate against §4 rules" path); if structured
value checks (set membership for `types`, URL well-formedness for `comfyui_url`) are cleaner in
the Python loader, extend `bin/ai-project-orchestrator`'s `load_yml_config()` instead/in addition
— but keep validation **single-source** and consistent with the documented §4 rules. The choice of
locus is an Epic-level implementation decision; the constraints are: (a) reuse existing handling,
(b) match the §4 rules exactly, (c) absent block ⇒ disabled, no error.

Required behavior:
- Absent block ⇒ valid, capability disabled (no error, no warning).
- `enabled` present and non-boolean ⇒ validation **error**.
- A `types` entry outside {`diagrams`, `infographics`, `video`} ⇒ validation **error**.
- `comfyui_url` present and not a well-formed URL ⇒ validation **error**.
- Unknown key inside the block ⇒ validation **warning** (mirrors `models`/`overrides`).

### 3. Tests

- **Valid** `visual_artifacts` block parses/validates cleanly.
- **Invalid** `enabled` (non-boolean), **invalid** `types` member, and **malformed**
  `comfyui_url` each fail validation.
- **Absent / default** block ⇒ valid and treated as disabled.
- Add a repo-config assertion in `tests/test_ongoing_artifacts.py` (alongside the existing
  `cfo_review_gate` check) that this repo's `.ai-project.yml` carries `visual_artifacts` with
  `enabled: false`.
- Loader tests follow the existing `bin/ai-project-orchestrator` inline-`unittest` precedent if
  the loader is the validation locus.

### 4. Repo config — `.ai-project.yml`

Add the block to the root `.ai-project.yml` with `enabled: false` (capability off in the source
repo, per the Milestone's "keep the suite green without a live endpoint" rule). Keep
`comfyui_url`/`types` present-but-inert as documentation of the contract, or omit them — either is
valid given `enabled: false`; choose what the validation tests assert.

## Technical Constraints

- **Format:** Markdown (spec) + the existing implementation languages — `bin/ai-project-init` is
  **bash**, `bin/ai-project-orchestrator` and the test suite are **Python** (`pytest`). Match the
  language of whichever handler you extend.
- **No parallel validator:** reuse the existing config handling; do not add a second config loader
  or a standalone validation module.
- **Mirror the established pattern:** the `overrides` (§3.3) and `models` (§3.4) blocks are the
  template for an optional block — schema shape, §4 rule style (warning for unknown keys, error
  for bad values), and test style.
- **Opt-in / default-off:** absent block ⇒ disabled; `enabled: false` is this repo's value and
  the documented default.
- **Scope of files:** `governance/ai-project-yml-spec.md`, the chosen existing handler(s) under
  `bin/`, the relevant test file(s) under `tests/`, and the root `.ai-project.yml`. Do **not**
  touch AOG, `seed.md`, the integration guide, or any helper — those are E22.2.

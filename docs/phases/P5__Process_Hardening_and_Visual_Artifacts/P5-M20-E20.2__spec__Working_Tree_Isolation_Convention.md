# Epic P5-M20-E20.2 — Working-tree isolation convention (GH-2)

## Context

Milestone M20 hardens five governance process gaps. This Epic closes **GH-2**: the absence
of a documented working-tree ownership convention for concurrently-active chats.

During M19, a Milestone Chat and an Epic Chat shared a single working tree. While the
Milestone Chat had an in-flight commit, the Epic Chat checked out a new branch — and the
Milestone Chat's subsequent commit landed on the wrong branch silently. No convention
assigned tree ownership per chat, so the collision was invisible until much later.

> **Live worked example (this milestone):** during E20.1's Stage-2 review the working tree
> was found switched onto `epic/P5-M20-E20.1` under the Milestone Chat — the exact shared-tree
> hazard described above. It was caught and corrected (switch back to `milestone/M20` before
> committing), but it is a real, in-milestone demonstration of why this convention is needed.

> **Source:** M19 Escalation Notice, Gap 2.

---

## Problem Statement

When two or more chats operate concurrently against one working tree, a branch checkout by
one chat silently changes the branch the other chat will commit to. Git provides
`git worktree` to give each line of work its own checked-out tree, but the project documents
no convention requiring it. The result is silent mis-targeted commits — a class of error that
is hard to detect (the commit "succeeds") and expensive to unwind (history must be rewritten
or cherry-picked across branches).

---

## Goals

By the end of this Epic, the system must:

1. Document a "Working-Tree Isolation" convention in `governance/systems/chat-hierarchy.md`
   with the rule, practical guidance, and a worked `git worktree` example.
2. Add a corresponding rule to `governance/AI-OPERATING-GUIDELINES.md` §3 (Chat Rules) that
   states the isolation requirement and cross-references the chat-hierarchy.md section.
3. (Per Phase Chat decision 2026-06-25 — see "Folded-in scope") Resolve the
   `test_no_branch_name_typos_in_starters` lint false-positive so that planned-but-not-yet-
   created milestones (e.g., the M21 worked example this Epic's own starter uses) are
   accepted, restoring a green suite on `milestone/M20`.

## Scope of Work

### 1. "Working-Tree Isolation" section in `chat-hierarchy.md`

Add a new section to `governance/systems/chat-hierarchy.md` containing, **verbatim in intent**:

- **Rule:** one `git worktree` per concurrently-active chat; a chat never operates in a tree
  another concurrent chat may switch.
- **Practical guidance:** `git worktree add ../worktree-<role>-<id> <branch>` — worked
  example: `git worktree add ../worktree-milestone-M21 milestone/M21`.
- **Scope:** applies whenever two or more chats are active simultaneously.

### 2. AOG §3 rule reference

Add a corresponding rule to `governance/AI-OPERATING-GUIDELINES.md` §3 (Types of AI Chats /
Chat Rules) stating the isolation requirement and cross-referencing the new
`chat-hierarchy.md` "Working-Tree Isolation" section.

### 3. Folded-in scope — lint false-positive fix (per Phase Chat decision 2026-06-25)

`tests/test_starter_lint.py::test_no_branch_name_typos_in_starters` currently flags
`milestone/M21` (used in this Epic's spec-mandated worktree example) as a typo because no
`M21` starter file exists yet. M21 is a genuinely planned milestone (the M20 spec names "M21
adoption clarity, M22 visual artifacts"). Teach the lint to accept planned milestones —
i.e., milestone references beyond the highest existing milestone are valid when they are
plausibly-formatted (`M<n>`), not flagged as typos — **without** weakening its ability to
catch genuine stray-digit typos (e.g., `M144`).

**Must include:**
- A minimal, well-commented change to `tests/test_starter_lint.py` so the M21 worked example
  passes while real typos still fail.
- The full test suite green on `milestone/M20` after this Epic merges.

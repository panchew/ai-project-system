# Epic P5-M20-E20.1 — Prerequisite git-tracking verification (GH-1)

## Context

Milestone M20 hardens five governance process gaps surfaced during P4 and P5 execution.
This Epic closes **GH-1**, the highest-leverage of the five because it governs whether any
dependent chat can trust its own starting premise.

During M19, a prerequisite artifact was declared "✅ committed" in a spec, but the file was
in fact **untracked in git**. The Stage 1 prerequisite check verified only that the file
existed on the working-tree disk. Because disk presence is not proof of commit, the check
passed while the artifact was absent from the repository — a *false-green prerequisite*. A
fresh worktree clone (precisely the isolation convention E20.2 introduces) would have lacked
the artifact entirely, and the dependent chat would have proceeded on a false premise.

The Milestone and Epic Execution Chat Starter templates both encode this disk-existence
assumption structurally (the Milestone template's "Spec Existence Requirement" section; the
Epic template's "Epic Specification" block). This Epic replaces that assumption with an
explicit git-tracking verification.

> **Source:** M19 Escalation Notice, Gap 1. This very milestone is held to the hardened
> check — every M20 prerequisite was verified with `git ls-files --error-unmatch <path>` on
> `phase/P5` before this Epic was opened (dogfooding the fix).

---

## Problem Statement

The starter templates that gate every Milestone and Epic chat verify that a prerequisite
*exists on disk*, not that it is *committed to git on the expected branch*. The two are not
equivalent:

- A file can exist in a working tree but be untracked (never `git add`-ed), staged but not
  committed, or committed only on a different branch.
- Any of these passes a "file exists" check yet is absent from a fresh clone or a sibling
  worktree.

The result is a prerequisite that reads "satisfied" while the dependent work is built on
something the repository does not actually contain — a silent, hard-to-detect failure that
only surfaces later (e.g., in a clean worktree or after a branch switch), far from its cause.

---

## Goals

By the end of this Epic, the system must:

1. Make `git ls-files --error-unmatch <path>` on the expected branch the prerequisite
   verification instruction in the **Milestone** Execution Chat Starter template (replacing
   the disk-existence "Spec Existence Requirement").
2. Add an equivalent prerequisite git-tracking verification instruction to the **Epic**
   Execution Chat Starter template, adjacent to the Epic Spec reference / `Commit:` line.
3. Include a one-sentence inline rationale in **both** templates so a reader understands the
   check is intentional (disk presence is not proof of commit).
4. Add committed, passing test coverage asserting the literal string
   `git ls-files --error-unmatch` is present in **both** template files.

---

## Non-Goals

This Epic explicitly does **not** aim to:

- Build automation, a git hook, or a CI gate that *runs* the verification at runtime — M20
  hardens the documented process; enforcement tooling is out of scope.
- Restructure, reflow, or reorganize either template beyond the minimal edit needed.
- Modify any governance document other than the two named templates and the test file.
- Touch the Phase Execution Chat Starter template (E20.4/E20.5 own changes there).

## Scope of Work

### 1. Amend the Milestone Execution Chat Starter template

`governance/templates/milestone-execution-chat-starter.md` — the **"Spec Existence
Requirement"** section today reads, in effect, *"The Milestone spec MUST exist at the path
specified above before this session begins."* Amend it so the requirement is satisfied by
**git-tracking verification on the expected branch**, using `git ls-files --error-unmatch
<path>`, not disk presence.

**Must include:**
- The literal command `git ls-files --error-unmatch <path>` (with `<path>` as a placeholder).
- A statement that verification is performed **on the expected branch**.
- The smallest possible edit — do not restructure the section or the document.

### 2. Amend the Epic Execution Chat Starter template

`governance/templates/epic-execution-chat-starter.md` — there is no standalone prerequisite
section. Add an explicit prerequisite git-tracking verification instruction adjacent to the
**"Epic Specification"** block (near the `Commit:` reference), covering the Epic spec and any
declared prerequisite artifacts.

**Must include:**
- The literal command `git ls-files --error-unmatch <path>` on the expected branch.
- Placement that an executing Coding Agent will encounter before relying on the spec.

### 3. Inline rationale (both templates)

One sentence in each template explaining *why* the check is git-tracking and not
disk-existence — e.g., *"Disk presence is not proof of commit: an untracked file passes a
file-exists check but is absent from a fresh worktree clone, producing a false-green
prerequisite."*

### 4. Test coverage

A test asserting the literal string `git ls-files --error-unmatch` appears in **both**
template files. Add `tests/test_template_prerequisite_wording.py`, **or** extend the existing
`tests/test_starter_lint.py`. Pure-stdlib `pytest`, no new dependencies, following the style
of the existing lint test.

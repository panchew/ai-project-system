# Epic E13.2 — File-Driven Trigger Discovery & Scheduler

## Context

Epic E13.1 established the detached daemon process runner (`ai-project-daemon`) and its control interface (start, stop, status, logs). With the background execution layer in place, the daemon now requires a mechanism to discover newly submitted execution jobs and schedule them for run.

This Epic addresses that need by implementing the background job polling engine within the daemon. The daemon will continuously monitor the file-driven queue directory `.ai-project/queue/` for new JSON trigger files, order them lexicographically, acquire execution locks, and invoke the python orchestrator in a single-threaded queue-processing model.

---

## Problem Statement

To fully automate the agentic execution cluster, we must remove human-in-the-loop manual orchestrator invocations. When parent sessions write epic task specifications into `.ai-project/queue/`, the system must automatically discover these triggers, parse them, invoke the containerized validation sandbox loop, and update status. 

This discovery and scheduling process must run safely inside the daemon background loop, prevent race conditions through lock coordination, handle empty queue sleep intervals efficiently, and log all scheduler actions cleanly.

---

## Goals

By the end of this Epic, the system must:

1. Build a robust queue-watcher loop within `bin/ai-project-daemon` that continuously checks `.ai-project/queue/`.
2. Discover files matching `*.json` trigger patterns and sort them lexicographically to ensure strict chronological/priority execution ordering.
3. Establish safe, non-blocking orchestration triggers that invoke the `bin/ai-project-orchestrator` process on discovered triggers.
4. Integrate the orchestrator's native `.ai-project/locks/execution.lock` check to prevent scheduled jobs from interrupting an active execution.
5. Log all scheduler discovery, execution start, success outcomes, or failures to the central daemon log file.

---

## Non-Goals

This Epic explicitly does **not** aim to:

- Support parallel orchestrator container runs (only one job runs at a time).
- Build a network socket or web-hook receiver to push events (strictly directory/file polling).
- Automate git branch merges upon successful execution (this is handled in E13.3).

---

## Scope of Work

### 1. File Queue Polling Loop
Add a continuous, low-overhead loop inside the background daemon daemonized runner.

**Must include:**
- Periodic directory checking of `.ai-project/queue/` with configurable polling interval (default 5-10 seconds) to avoid CPU thrashing.
- Graceful sleep intervals when the queue is empty.
- Lexicographical sorting of JSON files in the queue (e.g., `01_phase.json`, `04_epic.json`) to process files in priority order.

### 2. Orchestrator Process Triggering
When a trigger file is discovered, initiate the actual execution flow.

**Must include:**
- Lock check: Before invoking the orchestrator, ensure no other process holds `.ai-project/locks/execution.lock`. If locked, defer processing until the next tick.
- Subprocess execution: Invoke `bin/ai-project-orchestrator` to execute the discovered trigger.
- Stream capture: Direct the output of the orchestrator subprocess into the central log `.ai-project/logs/daemon.log` with clear prefix labels (e.g. `[ORCHESTRATOR]`).
- Clean trigger file cleanup/archiving depending on the return code (relying on the orchestrator's native archiving for failed files, or performing a daemon-level cleanup for unprocessed files).

### 3. Error Handling and Recovery
The scheduler must survive subprocess failures.

**Must include:**
- Catching subprocess crash exceptions.
- Logging detailed error summaries of orchestrator failures.
- Continued queue polling: Ensure a failing orchestrator task does not crash the daemon process itself.

## Definition of Done

Epic E13.2 is complete when:

- [ ] Background queue watching correctly discovers new files placed in `.ai-project/queue/`.
- [ ] Lexicographical priority ordering is verified.
- [ ] Orchestrator runs are triggered correctly, respect existing execution locks, and log output cleanly.
- [ ] Daemon remains stable and continues polling even if the orchestrator process crashes or exits with an error code.
- [ ] Unit tests covering the scheduler loop and trigger actions pass successfully via `bin/ai-project-daemon --test`.
- [ ] Epic Completion Report is completed and committed.
- [ ] Pull request is opened to the `milestone/M13` branch.

---

## Acceptance Criteria

- [ ] Placing an active trigger JSON file into `.ai-project/queue/` while the daemon is running automatically starts the orchestrator execution loop within the defined polling interval.
- [ ] Multiple triggers in the queue are processed sequentially in lexicographical order (e.g., `01_trigger.json` before `02_trigger.json`).
- [ ] If an orchestrator run is currently active (execution lock file is present), the daemon does not launch a second instance and logs a "deferring execution" event.
- [ ] Orchestrator outputs are prefix-logged directly into `.ai-project/logs/daemon.log`.
- [ ] Deleting or renaming a trigger file while the daemon is sleeping does not result in errors.

---

## Technical Constraints

**Format:** Python 3 standard library functions only.  
**Technology:** Built directly within the existing `bin/ai-project-daemon` script.  
**Config:** Polling sleep intervals should be configurable (via an environment variable or standard daemon argument, default: 5s).  
**Execution:** Orchestrator invocations must use absolute python environment paths to ensure stability.

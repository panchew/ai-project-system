## Verification Scenarios and Results

Running `./bin/verify-loop.sh` executes the following four scenarios:

### 1. Scenario 1: Immediate Success
- **Setup:** Validation command is configured to succeed initially (`mock_qa.sh always_success`).
- **Mechanics:** Runs the validation inside the Docker sandbox.
- **Results:** ✅ **Passed**. The orchestrator exits with code `0`, deletes the trigger file `04_epic.json`, creates a successful Git commit, and generates no feedback or escalation reports.

### 2. Scenario 2: Successful Self-Repair
- **Setup:** Validation command checks for `.ai-project/dev_fixed.txt` which does not initially exist.
- **Mechanics:** 
  - Attempt 1: Validation fails. Orchestrator writes feedback and runs `mock_dev.sh`.
  - Attempt 2: `mock_dev.sh` runs again. Validation runs and succeeds (as `mock_dev.sh` has created the state file).
- **Results:** ✅ **Passed**. The orchestrator exits with code `0`, deletes the feedback file and the trigger file, creates a Git commit, and leaves the repository in a clean, completed state.

### 3. Scenario 3: Max Retries Exhausted (Escalation)
- **Setup:** Validation command is configured to always fail (`mock_qa.sh always_fail`).
- **Mechanics:** 
  - Fails on Attempts 1, 2, and 3.
  - At each failure, logs feedback.json and executes `mock_dev.sh`.
  - Upon attempt 3 exhaustion, archives the trigger to `04_epic.json.failed` and generates an escalation report.
- **Results:** ✅ **Passed**. The orchestrator exits with code `1`, retains/archives the trigger, generates the structured markdown report under `/docs/admin/escalation-report-MOCK-EPIC.md`, and creates no Git commit.

### 4. Scenario 4: Lockfile Guard
- **Setup:** A pre-existing lockfile `.ai-project/locks/execution.lock` is created manually.
- **Mechanics:** Launches the orchestrator.
- **Results:** ✅ **Passed**. The orchestrator immediately terminates with exit code `1` and refuses to run. Trigger file remains intact.

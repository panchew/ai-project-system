# Epic E13.1 — CLI Daemon Process & Control Suite

## Context

Milestone M12 delivered containerized sandboxing and the closed-loop developer-QA validation mechanics, allowing autonomous agents to execute, self-correct, and verify code quality. However, the system currently requires manual shell execution of the orchestrator to initiate a cycle.

To achieve a fully automated, 24/7 autonomous software development pipeline, the orchestrator needs to run unattended as a background service. This Epic initiates that transition by building a robust user-space daemon manager (`ai-project-daemon`) in Python. It provides the process double-forking mechanisms, signal handling, state safety, PID file locks, logging redirections, and standard CLI control commands (`start`, `stop`, `status`, `logs`) necessary to manage the daemon's lifecycle safely on a host.

---

## Problem Statement

Without a persistent background service, agents cannot poll for task queues or respond to triggers automatically. Relying on manually launched or foreground screen/tmux sessions is fragile, non-standard, and prone to silent failures. 

To solve this, we need a standard UNIX double-fork process daemon in user-space. This daemon must run continuously, log its output to a rotating background log, and expose a clean, fail-safe CLI interface that prevents duplicate instances, cleanly cleans up stale locks on crash, and allows operator query and termination.

---

## Goals

By the end of this Epic, the system must:

1. Provide a reliable, python-based, user-space daemon executable (`bin/ai-project-daemon`) that cleanly detaches into the background.
2. Implement standard lifecycle operations: `start`, `stop`, `status`, and `logs`.
3. Support a robust PID file mechanism at `.ai-project/locks/daemon.pid` to prevent multiple parallel daemon instances and recover from stale/dead PIDs.
4. Redirect standard output and error streams to `.ai-project/logs/daemon.log` with file backup and safety truncation.
5. Provide graceful shutdown handling for `SIGTERM` and `SIGINT`, ensuring lockfile removal and subprocess terminations.

---

## Non-Goals

This Epic explicitly does **not** aim to:

- Provide deep integrations with systemd, init.d, or launchd configuration files.
- Implement the actual trigger file discovery or job queue logic (this is deferred to E13.2).
- Support running multiple parallel daemon processes on the same repository (strictly single-process daemon active).

---

## Scope of Work

### 1. Process Daemonization (`bin/ai-project-daemon`)
A new executable Python script `bin/ai-project-daemon` must be created with high-integrity UNIX double-forking logic to detach the running terminal session.

**Must include:**
- A robust, clean UNIX double-fork sequence (`fork` twice, `setsid`, set standard umask, change working directory to project root, close standard fd 0, 1, 2).
- Graceful termination signal handling for `SIGTERM` and `SIGINT` to unlink locks and terminate safely.
- Log redirection of stdout/stderr to `.ai-project/logs/daemon.log`.

### 2. PID and Lock File Management
The CLI suite must prevent multiple concurrent daemon processes.

**Must include:**
- Writing the active daemon process ID (PID) to `.ai-project/locks/daemon.pid`.
- Alive-check safety: If a PID file exists on `start`, check if that PID is actually active using standard non-lethal signals (`os.kill(pid, 0)`).
- Crash recovery: If the file contains a stale/dead PID, clean it up automatically, print a warning, and proceed to start.

### 3. Lifecycle Commands Suite
Expose CLI endpoints for managing and inspecting the daemon process:
- `bin/ai-project-daemon start`: Launches the background daemon.
- `bin/ai-project-daemon stop`: Gracefully stops the background daemon, waits up to 5s for process termination, and removes the PID file.
- `bin/ai-project-daemon status`: Prints daemon status (Running with PID, Stopped, Stale PID file found) and returns standard POSIX exit codes (0 for running, non-zero for stopped/error).
- `bin/ai-project-daemon logs`: Prints the content of `.ai-project/logs/daemon.log` to standard output.

## Acceptance Criteria

- [ ] Running `bin/ai-project-daemon start` detaches the process, creates a background loop, and writes the correct PID to `.ai-project/locks/daemon.pid`.
- [ ] Running `bin/ai-project-daemon start` again while active fails gracefully with "Daemon is already running".
- [ ] If the daemon is forcibly killed (`kill -9`) leaving a stale PID file, a subsequent `start` successfully cleans the stale lock, starts a new daemon, and logs the recovery event.
- [ ] Running `bin/ai-project-daemon stop` terminates the daemon gracefully, logs "Daemon stopped", and unlinks the PID file.
- [ ] Output from the daemon is correctly captured and redirected to `.ai-project/logs/daemon.log`.

## Technical Constraints

**Format:** Python 3 (following standard library wherever possible for compatibility).  
**Technology:** Python standard library (`os`, `sys`, `signal`, `time`, `argparse`, `pathlib`). No external process daemonization packages (e.g. `python-daemon` is NOT allowed, to prevent extra dependency overhead).  
**Location:** Executable located at `bin/ai-project-daemon`. PID lock located at `.ai-project/locks/daemon.pid`. Log file located at `.ai-project/logs/daemon.log`.  
**Permissions:** `bin/ai-project-daemon` must be marked executable (`chmod +x`).

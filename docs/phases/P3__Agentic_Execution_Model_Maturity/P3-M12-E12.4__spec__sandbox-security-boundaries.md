# Epic E12.4 — Sandbox Security Boundaries & Lock Recovery

## Context

As the AI Project System matures into a 24/7 unattended development environment (Phase P3), autonomous agents execute code, build projects, and run validation test suites continuously. 

Milestone M12 introduces containerized isolation to shield the host environment from any potential compromise or side-effects of untrusted agent execution. Prior to Epic E12.4, the orchestrator utilized basic file touch locks and lacked runtime containment boundary checks, leaving the system susceptible to stale locks (if the orchestrator crashed or was forcefully killed) and vulnerable to potential volume-mount filesystem escalations.

This Epic addresses these gaps by establishing absolute isolation boundaries, process signal trapping, and self-healing locks.

---

## Problem Statement

The AI Project Orchestrator has three distinct operational security and resilience risks:
1. **Stale Lock Blocking:** If the orchestrator crashes or is terminated abruptly, the static lock file remains in `.ai-project/locks/execution.lock`, permanently blocking subsequent runs until manual human intervention clears the lock.
2. **Orphaned Containers on Signal Interrupt:** When the orchestrator receives termination signals (`SIGINT`, `SIGTERM`), spawned Docker containers continue running in the background as detached orphans, wasting host resources and risking conflicting operations.
3. **Volume Mount Contamination:** If the sandbox configurations or trigger payloads are manipulated, arbitrary volumes could be mapped to host filesystems outside the project root directory, breaching host boundary protection.

---

## Goals

By the end of this Epic, the system must:

1. **Write and Read PID Locks:** Write the orchestrator PID to `.ai-project/locks/execution.lock` and inspect it on startup to automatically recover and delete the lock if the owning process is dead.
2. **Handle Signals Gracefully:** Trap `SIGINT` and `SIGTERM` signals in Python, log the termination event, forcefully stop/kill all spawned container instances, delete the lockfile, and exit with code 130.
3. **Enforce Mount Volume Boundaries:** Validate that all volume mounts map strictly inside the container's `/workspace` folder and restrict mounted host paths to the project root directory.

---

## Non-Goals

This Epic explicitly does **not** aim to:

- Manage multi-container networking (e.g. Docker Compose or Kubernetes integration).
- Implement background process daemon management (deferred to Milestone M13).
- Provide complex user group mapping in the sandbox container beyond the default `sandbox` user.

---

## Scope of Work

### 1. PID-Based Lock Handling
- Write active orchestrator PID into `.ai-project/locks/execution.lock` upon lock acquisition.
- Read PID on startup, execute an active check (`os.kill(pid, 0)`), and auto-recover if dead.

### 2. Signal Trapping and Orphan Prevention
- Hook Python signal registers for `SIGINT` and `SIGTERM`.
- Maintain a runtime global registry of spawned containers (`ACTIVE_CONTAINERS`).
- Stop and kill active containers by name and label filters on signal receipt.

### 3. File Boundary Safeguards
- Verify that container volume source paths are restricted to the host project root.
- Validate that volume targets map strictly to `/workspace` or its subdirectories.

This Epic must produce:

- [x] PID-based lockfile reading, validation, and auto-recovery in `bin/ai-project-orchestrator`.
- [x] Signal handlers for SIGINT/SIGTERM with full container and lockfile cleanup in `bin/ai-project-orchestrator`.
- [x] Host path and container path volume validations in `bin/ai-project-orchestrator`.
- [x] Verification Scenarios 4 & 5 implemented in `bin/verify-loop.sh` to assert active/dead PID lock handling.
- [x] Epic Completion Report.

---

## Definition of Done

Epic E12.4 is complete when:

- [x] The orchestrator successfully writes its PID to the lockfile upon locking.
- [x] A stale lock belonging to a dead process is automatically detected, cleaned, and recovered on startup.
- [x] Receiving a terminating signal triggers container shutdown and lock release.
- [x] Attempts to mount folders outside the project root are caught and raise a ValueError.
- [x] All unit tests run and pass.
- [x] All 5 verify-loop scenarios run and pass successfully.
- [x] Epic Completion Report is written and committed to the repository.

---

## Acceptance Criteria

- [x] The orchestrator can auto-recover from a dead process lockfile without human intervention.
- [x] Terminating the orchestrator clears the lock file and stops the spawned Docker sandbox.
- [x] No container volume mounts are allowed to read/write to folders outside the project root directory.

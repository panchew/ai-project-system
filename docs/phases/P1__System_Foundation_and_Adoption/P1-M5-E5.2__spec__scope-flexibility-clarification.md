# Epic E5.2 — Scope Flexibility Clarification

## Context

During human review of Epic E5.1 (Unplanned Progress Branch Model), a critical usability issue was identified with the governance language:

**The Issue:**
- E5.1 governance suggests unplanned branches should be tightly scoped to single topic
- Branch naming convention (`unplanned/<topic-slug>`) implies restrictive single-topic scope
- Rule "Must be scoped to a topic (not a dumping ground)" discourages multi-topic exploration
- Reality: Unplanned branches should allow drift across multiple aspects during exploration

**User observation (from E5.1 review):**
> "The only thing I didn't agree with was the strict requirement to separate changes by scope. I think that a branch of this nature should allow for drifting into several aspects. When I feel like going back to governance, I can instruct Coding Agent to separate changes by scope and create several commits. When planning, the commits will be accessible for cherry-picking."

**Core insight:** Organization happens before integration, not during exploration. Freedom during exploration, discipline during integration.

This Epic clarifies the governance to reflect real workflow needs.

---

## Problem Statement

Current governance (PROJECT-SYSTEM-GUIDELINES.md v1.4.0 section 8A and AI-OPERATING-GUIDELINES.md v1.3.0 section 3.3) does not adequately support the intended workflow for unplanned branches:

**What governance currently implies:**
- Unplanned branches should be narrowly scoped to single topic
- Branch name must describe the single topic
- Multi-topic work is discouraged

**What users actually need:**
- Freedom to explore multiple topics/aspects in one unplanned branch
- Ability to make exploratory commits without organization overhead
- Organization by scope happens later (before integration), not during exploration
- Cherry-picking organized commits during Epic integration

**Impact:**
- Users may avoid unplanned branches due to perceived scope restrictions
- Governance doesn't match real creative workflow patterns
- Model feels more rigid than intended

**Solution:** Clarify governance language to explicitly allow multi-topic exploration, emphasize organization happens before integration.

---

## Goals

By the end of this Epic, governance must:

1. Explicitly allow multi-topic work in unplanned branches
2. Clarify that branch naming is descriptive, not restrictive
3. Emphasize organization happens before integration, not during exploration
4. Preserve "not a dumping ground" principle (meaningful work, not random garbage)
5. Maintain integration discipline (planning gate still required)

---

## Non-Goals

This Epic explicitly does **not** aim to:

- Change the core unplanned branch model (lifecycle, integration process remain the same)
- Remove all scope guidance (meaningful work vs. random commits still matters)
- Eliminate organization requirement (commits must be organized before integration)
- Change branch naming convention format (`unplanned/*` stays)
- Retroactively change E5.1 deliverables (this is a refinement, not a fix)

## Scope of Work

### **1. PROJECT-SYSTEM-GUIDELINES.md Update**

**File:** `docs/PROJECT-SYSTEM-GUIDELINES.md` (currently v1.4.0)

**Section to update:** 8A "Unplanned Progress Branches"

**Changes required:**

**A. Update "Branch naming" subsection:**

**Current:**
```markdown
**Branch naming:** `unplanned/<topic-slug>`
```

**Change to:**
```markdown
**Branch naming:** `unplanned/<descriptive-slug>`

Branch names should be descriptive but not restrictive. Single-topic names (e.g., `unplanned/delivery-notice-improvements`) and multi-topic names (e.g., `unplanned/m5-explorations`, `unplanned/governance-clarifications`) are both valid. The slug helps identify the general area of work but does not constrain scope.
```

**B. Update "Rules" section:**

**Current rule:**
```markdown
- Unplanned branches MUST be scoped to a topic (not a dumping ground)
```

**Change to:**
```markdown
- Unplanned branches MUST contain meaningful work (not a dumping ground for random unrelated commits)
- Unplanned branches MAY contain multi-topic exploratory work
- Organization by scope happens before integration, not during exploration
```

**C. Update lifecycle "Stage 2: Work" description:**

**Current:**
```markdown
2. **Work:** Commits are made to capture ideas, prototypes, improvements
```

**Change to:**
```markdown
2. **Work:** Commits are made freely to capture ideas, prototypes, improvements across any topics. Multi-topic drift is allowed and expected. When ready to return to governance, organize commits by scope (via rebase, commit splitting, reordering, or clear commit messages) to facilitate cherry-picking during integration. Freedom during exploration, discipline during integration.
```

**D. Add clarification to example workflow (optional but recommended):**

After step 2 in the example workflow, add:
```markdown
   - (Branch may accumulate commits across multiple topics — this is expected)
```

After step 5 in the example workflow, add:
```markdown
   - (If branch contains multi-topic work, HQ may create multiple Epics, each cherry-picking relevant commits)
```

# E33.2 Runtime Decision — Ollama vs llama.cpp + Qwen3.6

**Every reason below traces to the E33.2 run (see the run record; Runs A/B).** No reason is asserted
that the run did not show (Hard Constraint). Where the run could not observe something, this document
says so and escalates it rather than inventing a decision.

## Decision

1. **Keep Ollama as the local-inference runtime.** It demonstrably works for the governed
   Agentic/Local path: both models loaded, the endpoint stayed reachable, and the tool-calling loop
   executed correctly (Run B) on the same Ollama runtime that E31.2's guard checks.
2. **The binding lever the run revealed is the *model*, not the runtime.** `qwen2.5-coder:14b` (the
   configured `epic_dev`/`epic_qa`) is **insufficient** for reliable agentic epic work; a 30B-class
   coder (`qwen3-coder:30b`) did the job on the *same* runtime. Recommend raising the model tier.
   **This Epic records that; it does NOT edit `.ai-project.yml` `models:`** (Non-Goal) — the routing
   change is a separate authorized act (candidate for M34).
3. **The CFO's reference stack (llama.cpp + Qwen3.6 27B Q8_0, ~42 GB) could not be trialed on the
   proving hardware** and is therefore **not decided by this run** — recorded as a partial blocker +
   escalation (below), not resolved by abstraction.

## The four dimensions (run's own observations)

### Quality
- **Run A (14b):** unacceptable. Zero usable output — emitted a markdown-fenced JSON *plan* instead
  of executing the tool protocol (SN-3 mode). 0 tool rounds, no files changed.
- **Run B (30b):** acceptable/mergeable. Correct `__init__.py` export change + valid test; package
  imports cleanly; **suite 210 passed / 1 skipped**. Model capability is the decisive quality
  variable, and it is a *model* difference on one runtime.

### Throughput
- Run A: 223 tok / 18.3 s ≈ **12.2 tok/s** end-to-end — but moot (produced nothing).
- Run B: 829 tok / 88.6 s ≈ **9.4 tok/s** end-to-end (includes tool-execution time; raw model rate
  is higher). Workable for epic-sized units; the larger model is slower but actually finishes.
- The CFO reference figure (~32 tok/s for Qwen3.6-27B-Q8_0 on Mac unified memory) is **not
  comparable** — different hardware, different runtime, not measured here.

### Loadability (the ~42 GB Q8_0 question — the phase's headline risk)
- On the proving box (**16 GB VRAM RTX 5060 Ti + 30 GB RAM, ~3.9 GB free**): `qwen2.5-coder:14b`
  (9 GB) loads comfortably; `qwen3-coder:30b` Q4_K_M (18.6 GB) **exceeds VRAM and partially offloads
  to RAM** (12.9 GB VRAM + 21.4 GB total) but still runs.
- **A ~42 GB Q8_0 model would not be loadable here** — it exceeds 16 GB VRAM outright and would
  overwhelm ~30 GB system RAM. The CFO's ~42 GB figure was for **Mac unified memory**; this Linux
  proving host is a different, tighter envelope. On *this* hardware the Q8_0 reference stack is
  infeasible; a smaller quant (e.g. Q4/Q5, ~18–27 GB) is the loadable ceiling.

### Review burden
- **The exit code is not trustworthy for either model — in opposite directions:**
  - Run A returned **exit 0 / "completed" while delivering nothing** (false positive). A reviewer
    trusting the exit code ships an empty epic; the validation_command (`pytest`) would also pass on
    the unchanged repo, so QA-by-exit-code would *not* catch the missing work.
  - Run B returned **exit 2 / did-not-converge while the work was correct and green** (false
    negative), because it wasted 3/10 iterations on a denied `pip install -e .` and ran out of
    budget before a final green pytest.
- Human/paid review was therefore **mandatory** to establish ground truth (inspect transcript +
  diff + run the suite). Minor as-produced warts in Run B: no trailing newline on `__init__.py`; a
  superfluous `sys.path` shim in the test. Review burden is **moderate-to-high** and is a
  *measurement-trust* problem, which is exactly E33.3's object (feed this forward).

## Partial blocker + escalation (Hard Constraint)

The specific **llama.cpp + Qwen3.6 27B Q8_0** comparison the CFO is drawn to **could not be run**:
llama.cpp is not installed on the proving host (`llama-server`/`llama-cli` absent) and Qwen3.6-27B is
not present; and at Q8_0 (~42 GB) it is not loadable on this 16 GB-VRAM / 30 GB-RAM box regardless.
Per the Hard Constraint, this is **recorded as a blocker and escalated to the Milestone → Phase
Chat**, not papered over with an un-run judgment. To settle the llama.cpp fork on its own terms, the
Phase/CFO must either provide hardware matching the ~42 GB unified-memory reference (e.g. the Mac the
figure came from) or authorize a *loadable-quant* llama.cpp trial (Qwen3.6-27B at Q4/Q5). Until then,
**Ollama stands** as the proven runtime and the actionable lever is the **model tier**, both of which
the run *did* observe.

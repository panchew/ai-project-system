# E34.3 Carry-Forward Note — one discharged, one still recorded

Two items travel with this Epic. One is **closed by it**; the other is **deliberately not**, and
saying which is which is the whole purpose of this note.

---

## 1. DISCHARGED — the M33 Closure Declaration's `models:` routing carry-forward

**The carry-forward, as written** (`.ai-project/artifacts/closure-declarations/2026-07-21T02_00_00Z__P10-M33__milestone_closure_declaration.md`):

> **The `models:` routing edit is NOT done.** The settled runtime choice is "Ollama + a raised model
> tier," but `.ai-project.yml` `models.epic_dev`/`epic_qa` remain `local:qwen2.5-coder:14b` — the
> model E33.2 proved **unusable** for agentic epic work. Both real runs selected `qwen3-coder:30b` as
> a *documented dispatch deviation*. **M34 should make the routing change**, or the next agentic
> dispatch will again default to a model known to produce false-positive empty completions.

**Status: discharged by this Epic.** `epic_dev`/`epic_qa` now read `local:qwen3-coder:30b` across
every surface that decides what a dispatch actually loads — `.ai-project.yml`, the orchestrator's
`DEFAULT_MODELS` fallback (the no-config path the carry-forward's "next agentic dispatch will again
default to" clause actually names), policy rows P6/P7 and their mapping rows, the yml spec, and the
divergence guard. The dispatch deviation E33.4 had to make by hand
(`AI_PROJECT_ACTIVE_MODEL=local:qwen3-coder:30b`) is no longer needed: the configuration now says
what the runs proved.

**What "discharged" does and does not mean here.** It means the recorded edit was made and the trap
is closed. It does **not** mean the raised tier is validated beyond its two runs — see the standing
caveats below. Discharging a carry-forward is not the same as closing a gap.

**Standing caveats that survive this discharge** (all recorded on policy row P6/P7, not hidden):

- **G12 — no quality signal captured.** Two real epics completed; neither produced a quality measure.
  The 30b is evidenced as *able to do the work*, not as *doing it well*.
- **G11 — zero captured QA-role runs.** `epic_qa` moved on the dev lane's evidence and its own
  pre-existing gap-grounded reasoning. See §3.
- **Loadability is the standing fragility.** `qwen3-coder:30b` at Q4_K_M is 18.6 GB and **exceeds**
  the proving box's 16 GB VRAM, partially offloading to system RAM (12.9 GB VRAM / 21.4 GB total).
  It ran ~9.4 tok/s against the 14b's 12.2 on the same epic. **Slower, but it finishes** — that is
  the trade being ratified, and a host with less RAM headroom may not make it.
- **Exit-code untrust is unchanged by this Epic.** It is *why* the 14b value was removed (E33.2 Run A
  concealed zero work behind exit 0), not something this Epic fixes. E33.4's exit 2 over complete,
  green work is the same coin's other face. Verification still reads the transcript and the target
  repo, never the exit status.

## 2. STILL RECORDED, NOT FIXED — P10-GH-1 (`framework_version` unschema'd)

`framework_version` remains a **convention-only** top-level key in `.ai-project.yml`: real projects
carry it, nothing in `governance/ai-project-yml-spec.md` defines it, and no validation rule reaches
it. E33.1 surfaced this; the M33 Closure Declaration recommended recording it as a GH item.

**This Epic did not touch it, by instruction and on the merits.** Schema-blessing a key is a
framework *capability* change — a new field, a new validation rule, a new adopter obligation. E34.3
is a value change that introduces no field, no key, and no validation rule. Folding a schema
addition into it would have made a documentation refresh into a contract change, and would have
buried the decision inside an unrelated diff.

**P10-GH-1 carries forward to the P10 phase closure declaration**, alongside P10-GH-2 and P10-GH-3
(recorded by the 2026-07-28 HQ Ruling).

## 3. The honesty item — P7 moved without QA-lane evidence

Recorded here as well as on the row, because it is the claim most likely to be over-read from this
diff: **`epic_qa` changed value, and gap G11 did not close.**

The runner dispatches dev and QA from one model in practice — E33.2's run record states plainly that
*"Run A is the configured `epic_dev`/`epic_qa` model"* — so M33 produced **no isolated QA-role run**.
E33.2 and E33.4 are **dev-lane** evidence. Row P7 therefore moves on exactly the reasoning it already
carried (*gap-grounded interim default: the one local model with any run evidence*), with its
referent updated from the falsified 14b to the 30b. **No QA-lane evidence is claimed, and G11 stays
open on the row with its own unfired revisit trigger: the first isolated QA-role run.**

## 4. What the next agentic run inherits

E34.3 performs **no** Agentic/Local run — it is the epic that makes the *next* one safe. The next
dispatch (M34's E34.2 territory) inherits:

- routing that no longer defaults to a model proven to emit exit 0 with zero work — **from config
  and from the no-config default path both**;
- a model that will partially offload to RAM on the proving box, and will be slower for it;
- an exit code that still cannot be trusted in either direction.

The first two are this Epic's doing. The third is not, and no one should read a green suite here as
having addressed it.

## The one thing this Epic must get right

**A back-test where the model can read the answer is not evidence — it is a very expensive way to
confirm that documents contain their own conclusions.**

Every one of the five defects is documented *in this repository*, in a delivery notice, a closure
declaration, or a carry-forward note, usually with the finding and its resolution stated plainly. A
local model pointed at the repo and asked "review this" will find the answer, not derive it. **The
result would be worthless and, worse, would look like a pass.**

Two requirements follow, and they are the methodological core of the delivery:

**1. Blind the inputs.** For each defect, construct the review packet from **the material as it stood
at the moment of the decision** — what a Stage-2 reviewer actually had in front of them — with every
document that *states the finding* excluded. The model gets the evidence; it does not get the verdict,
the fix, the carry-forward note, or any later document referencing them. **Each packet must be
committed** so the blinding is auditable: a reader must be able to confirm the model was not shown
the answer, rather than take the Epic's word for it.

**2. Pre-register the scoring rubric.** Write down, **before running anything**, what counts as a
**catch**, a **miss**, and a **false alarm** for each of the five defects — and commit that in the
same commit as the packets, before the run. Without pre-registration, "the model raised a vaguely
adjacent concern" becomes a catch on re-reading, and the evaluation cannot fail. A rubric written
after seeing the output is not a rubric; it is a rationalization.

**Corollary — do not re-run until it passes.** Record the results of the runs you make, all of them.
If the model is run more than once on the same packet (a legitimate thing to do for a
non-deterministic system), **report every run**, and say so — do not select the best. Silent
best-of-N would falsify the very property being measured.

**Note the two directions being measured.** Defects 2 and 5 are cases where the reviewer must **flag
something that looked fine** (a green exit; a red test). Defects 3 is the inverse — the reviewer must
**not** condemn work that was actually correct. A model that flags everything scores well on 2 and 5
and fails 3; that asymmetry is the point of including both, and the rubric must be able to
distinguish a genuine catch from indiscriminate alarm. **False alarms are recorded, not ignored.**

Five is a floor. Extending the set is permitted where it strengthens the judgment; **padding it is
not rewarded** — a clean pass or fail on the five, with clear reasoning, is a full success
(Milestone spec, Notes).

## Method (the Epic Chat owns the details; these are the fixed points)

1. **Build the packets** — one per defect, from the real material, blinded per above. Commit them.
2. **Pre-register the rubric** — catch / miss / false alarm criteria per defect. Commit it **with the
   packets, before any run.**
3. **Run the candidate model** against each packet, posing the Stage-2 review question appropriate to
   that defect's kind (three kinds are represented: a completion-signal judgment, a
   decomposition/scope judgment, and a test-correctness judgment). Capture raw outputs verbatim.
4. **Score against the pre-registered rubric.** Record catch/miss/false-alarm per defect, with the
   quoted model text that earned each score.
5. **Judge** — pass or fail, with reasons, on whether a local model is a **candidate** for the
   Milestone-locality cell.

**The phase spec's stated expectation** — a manual Milestone Chat run on a local model, per the
already-live Manual/Local cell — needs no new capability. The Epic Chat may find a better vehicle;
whatever it chooses, the requirement is that a local model actually reviewed real, blinded material.

## Hard Constraint (carried from the Milestone spec)

**E35.5's evidence must be real, not invented.** The judgment must derive from **an actual local-model
review of real material** — never a memo arguing what such a review would probably find. This is
run-first ordering in the same sense M33's runtime decision was, and it is the one place in M35 where
a document alone is not a deliverable.

**Nothing built.** Conducting an evaluation is in scope; building a reusable evaluation harness,
framework, or CLI is not. One-off packets, prompts, and captured outputs committed as **evidence** are
the deliverable; a generalized tool is drift — **stop and escalate to the Milestone Chat** if the work
starts turning into one.

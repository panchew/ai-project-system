# Epic E34.1 — `ai-project-system-mcp` superseded-agent fix + v7.0.0 (closes P6-GH-15)

## Context

**P6-GH-15 has been open since P6 and is the oldest live governance defect in the fleet:** a real
enrolled project running a *superseded* agent file while the framework moved four major versions
past it. E33.1's Failure Mode 5 named `ai-project-system-mcp` as the known live case and handed it
to M34. This Epic closes it — in the wild, in the target repo, confirmable from evidence.

E33.1's bump procedure (`.ai-project/artifacts/reference/v7-bump-procedure/README.md`, Direction B)
is the lever. It was validated on the proving pair, but **the proving pair did not exercise the
paths this project needs** — E33.1 says so itself: *"P6-GH-15 … did NOT bite the proving pair."*
E34.1 is the first application of the procedure to a project that actually trips its per-project
judgment calls, and it should expect to feed findings back.

> artifact-scope). The Coding Agent implements it. Independent of E34.2 and E34.3 (E34.3 merged at

**Drift #1 — the submodule path is `governance/`, not `.governance/`.** `.gitmodules` declares
`path = governance`. **Every command in E33.1's procedure hardcodes `.governance`** — Steps 1, 2, 3,
5 and the confirmation method all break verbatim on this project. This is not a documentation nit;
running the procedure as written fails or, worse, half-succeeds. The procedure's Failure Mode 7
anticipates `.ai-project.yml` structural variance but **not submodule-path variance.**

**Drift #2 — `hq.agent.md` is not a superseded agent. It is a placeholder stub.** Its full contents:

> `# HQ Chat Agent` / *"This agent is under development in Milestone M8. For now, use this as a
> placeholder for the governance-aware HQ Chat agent. When M8 is complete, this file will be
> replaced with the full HQ agent implementation."*

P6-GH-15 was recorded as "the superseded `hq.agent.md` lives here." The reality is **worse in
provenance and easier in execution**: this project has never had a working agent at all. There is
nothing to preserve, migrate, or diff. Delete and install canonical. Record the correction — the
governance record should say what was actually found.

**Drift #3 — `.ai-project.yml` has no `governance.ref` key, and `version` holds a SHA.** The block
is `source` / `version` / `submodule_path` only. Procedure Step 4 says edit *"`governance.version`
6.0.0 → 7.0.0"* and *"`governance.ref` v6.0.0 → v7.0.0"* — the first field holds something
structurally different from what the step assumes, and the second does not exist. The confirmation
method's `grep -E '^  (version|ref):'` expects both. **Decide and document** (see Open Decision).

**Drift #4 — the target's working tree is dirty with tracked-file changes.** `registry.yml` is
modified (+10 lines, a fleet registry listing eleven project paths) and `.ai-project/artifacts/` is
untracked. Procedure Failure Mode 6 anticipates *untracked* content; **it does not anticipate a
modified tracked file.** This is the CFO's uncommitted work sitting in the blast radius of a
`git add -A`. It must survive this Epic untouched.

## Open Decision (yours — decide, document, proceed)

**How to record the pin in `.ai-project.yml` given there is no `ref` key.** Two defensible answers:

- **(a) Add `ref: v7.0.0` alongside `version: 7.0.0`** — makes the file match the proving pair's
  shape and satisfies the confirmation method's grep verbatim. Costs one added key.
- **(b) Set `version: 7.0.0` only** — minimal edit, respects Failure Mode 7's "structure varies per
  project; do not template-replace," and records the confirmation deviation instead.

**Recommendation: (a).** The whole point of this Epic is that this project drifted by being
*different*, and P6-GH-15 is what that drift produced. Converging its shape onto the pair's is the
cheaper long-term position, and it makes the standard confirmation method work unmodified — which
matters because M34's bar is *confirmable*. Take (b) only if adding the key conflicts with something
you find in the file. Either way, **state which you chose and why** in the confirmation evidence.

## The confirmation method, adapted (use this, not the verbatim original)

```sh
# run from the target repo
grep '^framework_version:' .ai-project.yml          # -> framework_version: v7.0.0
grep -E '^  (version|ref):' .ai-project.yml         # -> 7.0.0 / v7.0.0  (per your Open Decision)
git submodule status governance                     # -> 8044451... governance (v7.0.0)
sha256sum .ai-project/agents/governance.agent.md    # -> 66404389f29fa1ff8e829015b70ab8b33373dc3ac3eca3f2faea121d3da3441e
ls .ai-project/agents/                              # -> governance.agent.md ONLY (no hq.agent.md)
grep -n 'branch' .gitmodules                        # -> no raw SHA
git status --porcelain                              # -> registry.yml still modified, artifacts/ still untracked
```

The agent checksum `66404389…` (14711 bytes) is **independently re-verified** against this repo's
`v7.0.0` tag as of 2026-07-29 — it is the canonical value, not a copied figure. A mismatch means the
agent copy step was skipped and the project is running a stale agent while claiming v7.0.0
(Failure Mode 3).

The last two lines are E34.1-specific: they prove the fix landed **and** that the owner's
uncommitted work was not swept up.

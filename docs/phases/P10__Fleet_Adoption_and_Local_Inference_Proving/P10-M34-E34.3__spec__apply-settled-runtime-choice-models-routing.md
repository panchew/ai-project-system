# Epic E34.3 — Apply the settled runtime choice (`models:` routing edit)

## Context

M33 settled the local-runtime question by running it, not by arguing it: **keep Ollama; raise the
model tier.** E33.2 proved `qwen2.5-coder:14b` — the model `.ai-project.yml` still routes agentic
epic work to — produces *false-positive empty completions* (exit 0, zero files changed, SN-3
markdown-plan mode), while `qwen3-coder:30b` did mergeable work on the **same** runtime. E33.4 then
ran a second real epic on `qwen3-coder:30b` against `home_finance` and completed real work.

Both M33 epics recorded the lever and, per their own Non-Goals, **deliberately did not edit
`.ai-project.yml`** — E33.4 dispatched with an `AI_PROJECT_ACTIVE_MODEL` override and wrote down
that the routing edit is "a separate authorized act." E34.3 **is** that act.

This epic operationalizes an already-ratified decision. It introduces **no new decision, no new
capability, and no new schema.** It is a value change across the coupled surfaces that must move in
lockstep, plus the evidence citation that makes the change grounded rather than asserted.

> **Provenance:** Authored by the Milestone Chat (P10-M34) on 2026-07-28 per adjacency (PSG §1A
> artifact-scope). The Coding Agent implements it. E34.3 is independent of E34.1 and must land
> **before** any E34.2 agentic run (Milestone spec §Dependencies and Sequencing).

## The one thing this Epic must get right

**This is a policy-ROW change, not a mapping refresh — and the two have different gates.**

The HQ Ruling of 2026-07-28 (`.ai-project/artifacts/rulings/2026-07-28__ai-project-system-hq__ruling__paid-frontier-model-mapping-refresh.md`)
moved the five paid-frontier keys to `claude-opus-5` and was explicitly a **mapping refresh**: rows
P1–P4 decide a *tier* ("Paid frontier"), never a model, so refreshing the mapping table did not
touch a row and the Change-discipline evidence rule was not engaged.

**Rows P6 and P7 are different in kind.** They name the model *in the row's own Decision column*
(`**local:qwen2.5-coder:14b**`). Changing them therefore **is** a row change, and
`model-routing-policy.md` §Change discipline binds it: *"Policy rows change only with new cited
evidence (a new dataset capture, M31 run records, or a quality signal per G12) — never by
assumption."*

That gate is **satisfied**, and the epic must show it is satisfied rather than assume it:

| Row | Recorded revisit trigger | The evidence that fires it |
|---|---|---|
| **P6** (`epic_dev`) | *"Additional M31 local runs"* | E33.2 Run A/Run B (comparative, same runtime) + E33.4 (second real epic on `qwen3-coder:30b`, `home_finance`). Direct, cited, falsifying: Run A is the row's current value producing zero work. |
| **P7** (`epic_qa`) | *"First M31 QA-role run"* | **Not fired.** See below. |

**Be honest about P7.** The runner dispatches dev and QA from one model in practice (E33.2's run
record: *"Run A is the configured `epic_dev`/`epic_qa` model"*), so M33 produced **no isolated
QA-role run**. Gap **G11** (zero captured QA-role runs) is still open and this Epic does not close
it. P7 therefore moves on **exactly the reasoning it already carries** — *gap-grounded interim
default: the one local model with any run evidence* — with the referent updated from
`qwen2.5-coder:14b` to `qwen3-coder:30b`. Write it that way. Do **not** claim E33.2/E33.4 gave the
QA lane its own evidence, and do **not** silently drop G11 from P7's gap column.

## The surface set (verify before editing; this is the load-bearing list)

A `models:` value in this repo is **not** a one-file edit. `tests/test_model_config.py`'s
divergence guard cross-checks config against the policy table and the orchestrator constant, so a
partial application leaves the suite **red** — that is the guard working, not a regression to route
around. The HQ Ruling's own application table is the precedent to follow (it lists the six files it
touched for the remote keys).

Expected surfaces for `epic_dev`/`epic_qa` (line numbers are a 2026-07-28 read — **re-grep, do not
trust them**):

| File | What moves |
|---|---|
| `.ai-project.yml` | `models.epic_dev`, `models.epic_qa` (~L41–42) |
| `.ai-project/artifacts/reference/token-measurement/model-routing-policy.md` | **Rows P6, P7** (Decision + Evidence + Gaps + revisit-trigger columns) *and* the "Mapping to `.ai-project.yml`" table rows (~L43–44, L53–54) |
| `governance/ai-project-yml-spec.md` | §3.1 schema comments (~L60–61), §3.4 field table defaults/examples (~L342–343), format-constraint examples (~L367) **if** they assert a default; version bump + changelog entry |
| `bin/ai-project-orchestrator` | `DEFAULT_MODELS["epic_dev"]`, `DEFAULT_MODELS["epic_qa"]` (~L27–28) — **this is why the acceptance criterion says "no longer *defaults* to"**: a project with no `models:` block falls through to this constant |
| `tests/test_model_config.py` | `EXPECTED_EPIC_DEV` (~L55) and the module docstring's stated value (~L6) |

**Judgment call, and the reason it belongs in scope:** the Milestone spec's DoD names only
`.ai-project.yml`. Taken literally that would leave `DEFAULT_MODELS` still handing the broken model
to any project without a `models:` block — and would leave the suite red besides. The Milestone
**acceptance criterion** ("the epic routing no longer *defaults* to the model E33.2 proved produces
false-positive empty completions") reaches the constant, and the divergence guard forces lockstep.
The full surface set is therefore in scope. This is recorded as a Milestone-Chat decision, not a
scope expansion for the Epic Chat to re-litigate.

**Fixture tags are not policy.** `tests/integration/test_run_dev_agent_adapter.py`'s
`STUB_MODEL_TAG` is an arbitrary string in adapter plumbing tests. Change it only if leaving it
breaks something; it carries no policy meaning either way. Say which you did.

## The value to write

Evidence points to **`local:qwen3-coder:30b`** for both keys. **Confirm the exact tag** against
E33.2's run record and E33.4's run record before writing it — the string must match a model the
runtime can actually load, not a plausible-looking name.

Confirmed available on the proving host at planning time (`/api/tags`, 2026-07-28):
`qwen3-coder:30b`, 30.5B params, **Q4_K_M, 18.6 GB**.

**Record the loadability envelope honestly alongside the change** — this is a real constraint, not
a footnote. From E33.2 and E33.4's run records, on the proving box (16 GB VRAM RTX 5060 Ti + 30 GB
RAM): `qwen3-coder:30b` **exceeds VRAM and partially offloads to RAM** (12.9 GB VRAM / 21.4 GB
total). It runs and finishes, at ~9.4 tok/s end-to-end versus the 14b's 12.2 tok/s. The raised tier
is **slower but actually completes** — that is the trade being ratified, and a reader of this
change should not have to reconstruct it.

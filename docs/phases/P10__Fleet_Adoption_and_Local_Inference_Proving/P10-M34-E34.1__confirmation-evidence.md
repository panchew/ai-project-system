## Open Decision — how to record the pin given there was no `ref` key

**Chosen: (a) add `ref: v7.0.0` alongside `version: "7.0.0"`.**

The spec recommended (a) on convergence grounds and allowed (b) *"only if adding the key conflicts
with something you find in the file."* Nothing conflicted — and reading the yml-spec at v7.0.0
turned the recommendation into a requirement:

- `governance/ai-project-yml-spec.md` marks **`governance.ref` REQUIRED** (field table, and
  validation rule 3: *"All four required fields are present: `governance.source`,
  `governance.version`, `governance.ref`, `project.name`, `project.description`"*).
- `governance.version` is specified as a **quoted semver**, with a raw non-semver value listed under
  *Invalid*.

So the target's `.ai-project.yml` was not merely *shaped differently* — it was **schema-invalid on
two fields**: `ref` missing, and `version` holding a 40-char SHA where a quoted semver belongs.
Option (b) would have knowingly left a required field absent. (a) was the only defensible answer.
Both fields now match the proving pair's shape and the standard confirmation method works unmodified.

**Related finding, recorded not fixed (out of scope):** `project.description` is *also* REQUIRED by
the same validation rule and is *also* absent from this target. It is unrelated to the v7.0.0 bump,
so E34.1 did not add it. **Recommend the Milestone Chat record this as a GH item** — the fleet
likely has more schema-invalid `.ai-project.yml` files than this one, and nothing currently validates
them.

## Second decision — `.gitmodules` `branch = <raw SHA>` (not anticipated by the spec)

The spec required the raw SHA gone from `.gitmodules` but did not say what to put in its place.
Two options: set `branch = v7.0.0`, or delete the line. **Chosen: delete the line.**

Reasoning: **both proving-pair projects carry no `branch` key at all** — `path` + `url` only. The
key's presence here was itself the anomaly, and its value (a commit SHA) is not something git can
resolve as a branch in the one operation the field exists for (`git submodule update --remote`,
which reads `refs/remotes/origin/<branch>`). Writing `v7.0.0` there would swap one unresolvable
value for another while *looking* correct. Deleting it applies the same convergence logic the spec
used for Open Decision (a), and loses no information: the pin is still recorded as a tag in
`.ai-project.yml` (`ref: v7.0.0`) and enforced by the gitlink, which is a SHA by design in every
project including the proving pair.

Acceptance Criterion 2 ("the pin is a tag, not a SHA, in every place the project records it") is met
on this reading: the only human-authored record of the pin is now `ref: v7.0.0`.

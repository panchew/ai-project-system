# Epic E24.1 — Proposed-vs-implemented comprehension behavior (P6-VC-3)

## Context

Milestone M23 delivered the **mechanism** for the visual layer: by-link storage (AOG §17.5 / guide
§4 — generated visuals are referenced by link, never committed) and the **§7 binding convention** —
a five-element block (Link + What / Level / **State** / Description) with a defined home per level.
Crucially, M23's guide §7 already states that **`State` is a field, not a second schema**: a level
*may* carry both a `proposed` binding (the visual intent, before build) and an `implemented` binding
(what was actually built), distinguished by the `State` field.

But a mechanism that *can* be used is not a behavior that *is* used. Nothing in the framework yet
tells an agent that producing **both** a proposed and an implemented visual is the **routine
default** at every level, how generous to be, or that the cheap path (Structural text:
Mermaid/PlantUML) should carry most of the coverage. This Epic delivers that **behavior**: it
establishes, in AOG §17, the two-track expectation as the routine default when the capability is
enabled — **"nothing is too much"**, **Structural-first** — and extends the guide's per-level worked
examples to show a *proposed* and an *implemented* example at each level, each recorded via the
existing §7 binding's `State` field.

This is **governance/behavior, not plumbing and not new schema.** The producer (ComfyUI
FLUX/SDXL/LTX-Video) and the helper (`bin/ai-project-visual`) are done and verified (SN-16); the §7
binding block and its `State` field are done and merged (M23 / E23.2). E24.1 directs how the
framework *uses* them — it does **not** rebuild the mechanism or redefine the binding block.

**Grounding (verified on `phase/P6` / `milestone/M24` — anchors this Epic plans against):**

- **The mechanism already exists — do not rebuild it.** Guide §7 defines the five-element binding
  and states explicitly: *"**State is a field, not a second schema.** A level may carry both a
  `proposed` binding (the visual intent, before build) and an `implemented` binding (what was
  actually built) — the same five-element block, distinguished by **State**."* E24.1 establishes the
  *expectation to routinely produce both*; it does **not** introduce a new schema.
- **AOG §17 is the home for the behavior.** §17 currently runs §17.1 opt-in gating, §17.2 per-level
  abstraction (the level→visual-type table), §17.3 two modes (Structural / Generative), §17.4
  tool-capability gating, §17.5 what-to-commit (by-link). The two-track expectation lands as a **new
  subsection** (e.g. **§17.6 "Proposed vs. implemented"**); §17.2 / §17.3 may each gain a sentence
  tying the per-level abstraction and the Structural-first preference to the two tracks. (Exact
  subsection number is this Epic's design call within M24's scope — §17.6 given the current
  structure.)
- **Structural-first is why generous coverage is cheap.** §17.3 / guide §2 already prefer Structural
  (Mermaid/PlantUML — text, free, no endpoint) for architecture/scope/component/flow diagrams;
  Generative (ComfyUI) is for concept/vision/mockups/clips. E24.1 makes the "nothing is too much"
  bar affordable by leaning on Structural for most of the coverage — most proposed/implemented pairs
  are two text diagrams, not two endpoint calls.
- **Per-level examples attach to the guide.** Guide §5 "Per-level worked examples" currently shows
  **one** visual per level (Creation / HQ / Phase / Milestone / Epic). E24.1 extends each level to
  show a **proposed** and an **implemented** example, each recorded as a §7 binding (distinguished by
  `State`) — reusing, not restating, the §7 schema documented once in §7.
- **AOG version history for §17 changes:** §17 added at AOG v2.2.0 (E22.2); by-link reversal at
  v2.3.0 (E23.1). A new §17 subsection is a minor bump → **v2.4.0** with a Changelog row.

## Problem Statement

M23 gave every level a §7 home for a link + metadata, with a `State` field that *can* hold
`proposed` or `implemented`. But nothing tells an agent that producing **both** is the routine
default at every level, nor how generous to be, nor that the cheap Structural path should carry most
of the coverage. The result: agents will record at most one visual per level (whatever they happen
to make), the proposed-vs-implemented two-track signal that M23 built the `State` field to carry
will go largely unused, and the "nothing is too much" coverage bar (CFO-set, SN-15/SN-16) has no
operative instruction behind it. The visual layer stays a latent capability instead of a continuous
proposed→implemented narrative the CFO can follow. This Epic closes that gap by making the two-track
behavior the documented default and by showing, per level, exactly what proposed and implemented
look like.

---

## Goals

By the end of this Epic, the system must:

1. **Establish the two-track expectation in AOG §17.** A new subsection directs every level to
   produce **both** a *proposed* visual (before build) and an *implemented* visual (after) as the
   **routine default** when `visual_artifacts.enabled: true`, stating the **"nothing is too much"**
   coverage bar and the **Structural-first** preference.
2. **Show per-level proposed/implemented examples in the guide.** Guide §5 shows, for each level
   (Creation / HQ / Phase / Milestone / Epic), what a *proposed* and an *implemented* visual look
   like, each recorded as a §7 binding via the `State` field.
3. **Reuse the §7 schema, never restate it.** The behavior references the binding schema documented
   once in guide §7; it does **not** redefine, duplicate, or alter the five-element block or the
   `State` field, and it does **not** regress by-link.
4. **Record the behavior** in the AOG Changelog (minor bump → v2.4.0) and the guide Changelog, and
   **keep the suite green** (no plumbing touched; the integration test still skips at
   `enabled: false`).

## Non-Goals

This Epic explicitly does **not** aim to:

- **Redefine or restate the §7 binding schema or its `State` field.** E23.2 delivered the
  five-element block and the proposed/implemented `State`. E24.1 directs its *routine use* and
  references it; it does not re-document the schema. (`State is a field, not a second schema` — the
  schema is documented once, in §7.)
- **Define the clip convention or clip behavior.** The clip = one-parent rule, clip production, and
  the publish path are **E24.2** (P6-VC-4). E24.1 establishes the two-track behavior a clip later
  narrates; it does not touch clips. (`clip` appears only where §7 already lists it as a `What`
  value — E24.1 adds nothing there.)
- **Regress by-link or touch storage prose.** AOG §17.5 / guide §4 (by-link, E23.1, merged) are read,
  not edited. Every example binds a **link**, never a committed `.ai-project/visuals/...` path.
- **Add plumbing.** No helper or producer change, no new config key, no upload step (Open Design
  Question B stays resolved from M23). ComfyUI and `bin/ai-project-visual` are unchanged.
- **Alter opt-in gating or tool-capability gating.** §17.1 and §17.4 stand; the two-track behavior
  is the default only *when enabled*, and a tool-less surface still produces Structural visuals only.
- Re-examine the three SN-16 ratified decisions or the "nothing is too much" / two-track CFO mandate.

## Scope of Work

### 1. AOG §17 — new subsection establishing the two-track expectation

Add a new subsection to `governance/AI-OPERATING-GUIDELINES.md` §17 (e.g. **§17.6 "Proposed vs.
implemented"**) establishing the behavior. The exact subsection number and wording are this Epic's
design call **within M24's scope**; the contract it must encode is fixed.

**Must include:**
- The **two-track expectation as the routine default**: when `visual_artifacts.enabled: true`, every
  level produces **both** a *proposed* visual (the intent, before build) and an *implemented* visual
  (what was actually built, after) — not one or the other.
- The **"nothing is too much" coverage bar**: be generous; err toward producing the pair rather than
  skipping it.
- The **Structural-first preference** as the reason generous coverage is affordable: most coverage is
  free Mermaid/PlantUML text (no endpoint, no cost), so the two-track default is cheap; reserve
  Generative for where a rendered image communicates better (concept/vision/mockups).
- An explicit pointer that the two tracks are recorded via the **§7 binding's `State` field**
  (`proposed` / `implemented`) — **referencing** guide §7, not restating the schema. State that a
  level may carry one binding of each `State`.
- Respect the existing gates: the behavior applies **only when enabled** (§17.1) and a tool-less
  surface produces Structural visuals only (§17.4) — a proposed visual that needs generation is
  recorded as intent and deferred, per §17.4, rather than fabricated.

**Light touch on adjacent subsections (optional, surgical):**
- §17.2 (per-level abstraction) and/or §17.3 (two modes) may each gain a single sentence tying the
  per-level abstraction and the Structural-first preference to the two tracks, so a reader meets the
  two-track idea where the related concept already lives. Do not restructure these subsections.

### 2. Guide §5 — per-level proposed/implemented worked examples

Extend `governance/guides/visual-artifacts.md` §5 "Per-level worked examples" so each level shows a
**proposed** and an **implemented** example, each recorded as a §7 binding via the `State` field. The
exact wording and diagram choices are this Epic's design call within M24's scope.

**Must include:**
- For each level — **Creation / HQ / Phase / Milestone / Epic** — a *proposed* example (the intent,
  before build) and an *implemented* example (what was built, after), consistent with that level's
  abstraction (the SN-11 table) and Structural-first where applicable.
- Each example recorded as a **§7 binding** with the appropriate `State` (`proposed` /
  `implemented`), using a **hosted link** for any generated visual (never a committed path). The
  binding **reuses** the §7 block — it points to §7's schema rather than re-documenting it.
- The examples must demonstrate the Structural-first economy: most pairs are two text diagrams; a
  Generative example (e.g. Creation concept imagery, an Epic mockup) shows the proposed→implemented
  pair where a render is warranted.
- Keep the existing single examples' intent; this is an **extension** of §5 (proposed + implemented
  per level), not a rewrite of the section's structure.

### 3. Changelogs

- Add a Changelog row to the **AOG** recording the new §17 subsection and the two-track default;
  bump the AOG to the next minor version (**v2.4.0**, following §17's history: v2.2.0 add → v2.3.0
  by-link → v2.4.0 two-track), citing E24.1 (P6-M24).
- Add a dated row to the **guide** Changelog recording the per-level proposed/implemented examples,
  citing E24.1 (P6-M24).

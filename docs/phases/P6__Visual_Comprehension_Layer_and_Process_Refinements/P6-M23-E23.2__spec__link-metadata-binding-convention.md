# Epic E23.2 — Link + metadata binding convention (P6-VC-2)

## Context

Milestone M23 has two halves. E23.1 (merged to `milestone/M23`) reversed the v5.0.0
commit-the-binary storage model to **by-link**: generated visual material is referenced by link and
never committed to git. This Epic delivers the **second half** — the **binding convention** that
makes by-link survivable. Once the binary is out of git, the only thing in git is a **link**, and a
bare link rots. The framework therefore needs a small, load-bearing block of **metadata** beside the
link, and a defined **place per level** to record it.

This Epic **depends on E23.1** and is written against the by-link model it established: a binding
attaches a **link** (never a committed `.ai-project/visuals/...` path) to a governing artifact.
Both epics edit `governance/guides/visual-artifacts.md`; E23.1 is already merged, so E23.2 branches
from the merged `milestone/M23` and there is no live contention (use a worktree, GH-2, only if
needed).

This is **governance/documentation, not plumbing.** No helper or producer change. The Coding Agent
documents the schema in the guide and adds a defined binding placement to the relevant per-level
templates.

## Problem Statement

Under by-link (E23.1), the only thing that survives in git is a **link** — and a link rots: the
host moves, the file is renamed, the URL 404s, and the decision record loses the visual it
referenced. The framework has no defined way to record *what a link points to*, *which level it
belongs to*, *whether it shows the proposed or implemented state*, or a *human-readable description*
that outlives the link. It also has no defined **place** at each governance level to put that
record. Without both — a schema and a placement convention — by-link is fragile: agents will inline
bare URLs inconsistently, and the proposed-vs-implemented two-track signal (SN-16 decision) has
nowhere to live. This Epic supplies the schema and the per-level placement.

## Scope of Work

### 1. Binding schema — `governance/guides/visual-artifacts.md` (new section)

Document a concrete representation of a **visual binding**: a **link** plus four load-bearing
metadata fields. The exact textual representation (labeled list vs. compact table) is this Epic's
design call **within M23's scope**; whatever form is chosen must carry all five elements and bind a
**link**, never a committed path.

**Must include — the binding's five elements:**
- **Link** — the hosted URL of the generated visual (required; never a `.ai-project/visuals/...`
  committed path).
- **What** — the visual's kind: one of `image` / `infographic` / `mockup` / `diagram` / `clip`.
- **Level** — which governance level it binds to: `Creation` / `HQ` / `Phase` / `Milestone` /
  `Epic`.
- **State** — the two-track state: `proposed` or `implemented`.
- **Description** — a short text description that survives link rot (what the visual shows and why).

A recommended representation (the Coding Agent may refine the wording within the convention):

```markdown
**Visual binding**
- **Link:** <hosted URL>
- **What:** image | infographic | mockup | diagram | clip
- **Level:** Creation | HQ | Phase | Milestone | Epic
- **State:** proposed | implemented
- **Description:** <short text that survives link rot>
```

### 2. Per-level placement convention — `governance/guides/visual-artifacts.md` (same/adjacent section)

For each of the five levels, state **which** governance artifact a binding attaches to and **how the
link gets there**, using the verified homes:

**Must include:**
- **Creation** → the Project Brief's **_Visual success_** element (`seed.md` Rule 4) carries the
  binding.
- **HQ** → the **HQ-level governing record** (`genesis.md` HQ Context Packet / architecture record)
  carries the binding for the system-architecture visual.
- **Phase** → a **defined placement** in `phase-spec.md`.
- **Milestone** → a **defined placement** in `milestone-spec.md`.
- **Epic** → a **defined placement** in `epic-spec.md`.
- The convention must state explicitly that a binding records a **link** (never a committed path) and
  that proposed and implemented are tracked as the **two-track State** field — so a level can carry
  both a `proposed` binding (before build) and an `implemented` binding (after).

### 3. Template updates — the relevant per-level templates

Add a **defined place to record a binding** to each template, consistent with the schema and the
by-link model. Keep edits surgical and aligned with each template's existing style (HTML-comment
guidance, placeholder convention).

**Must include:**
- `seed.md` — note in Rule 4 that the *Visual success* element may carry a visual binding (link +
  metadata) using the schema.
- `genesis.md` — a defined binding spot in/near the HQ Context Packet for the HQ architecture visual.
- `phase-spec.md`, `milestone-spec.md`, `epic-spec.md` — a defined "Visual bindings" placement
  (a short section or labeled block) in each, with placeholder guidance, so each level has a home for
  zero or more bindings.

### 4. Guide changelog

Add a dated row to the guide's Changelog (added by E23.1) recording the binding-convention addition,
citing E23.2 (P6-M23).

- **Format:** Markdown (guide + templates). No code, no helper change, no upload step.
- **Bind a link, never a path:** every example and the schema must use a hosted **link**; do not
  reintroduce `.ai-project/visuals/<level>/...` committed paths (that would undo E23.1).

  front-matter untouched unless a field is genuinely needed.

  existing sections.
- **Leave structural-diagram guidance alone:** Mermaid/PlantUML stay text-in-git.
- **Scope of files:** `governance/guides/visual-artifacts.md` and the five templates above. Do
  **NOT** touch AOG §16.5 / guide §4 storage prose (E23.1, merged), `bin/ai-project-visual`, or the

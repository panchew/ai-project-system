### Summary

Add a **canonical phase-closure sequence** to PSG that lists **README update + version bump + git
tag as mandatory automatic steps**, mirroring the §1A (Epic) / §5B (Milestone) ordered-mandatory
pattern one level up — so **no out-of-band Steering Note** is needed to close a phase. Optionally
formalize the hand-made `phase-closure-declaration` as a template. Reconcile §5B's "Phase closure —
future work" line. **Documentation only** — no code, no automation, no script.

### Problem Statement

The framework mandates an Epic-closure sequence (§1A) and a Milestone-closure sequence (§5B), but
**no phase-closure sequence exists** — §5B even calls phase closure "future work." So README
update, version bump, and tag happen only via a human Steering Note (P5's `v5.0.0` closed this way),
the README drifts (a stale `226/226` banner survives; live count is `259 passed / 1 skipped`), and
the phase-closure declaration exists in four hand-made P2–P5 copies with no template. This Epic makes
the phase-closure steps canonical and mandatory.

### Goals

1. **Define a canonical phase-closure sequence in PSG** (recommended **§5C**, mirroring §5B) listing
   **README update, version bump, and git tag as mandatory automatic steps** — no Steering Note.
2. **(Optional, within scope) Add a `phase-closure-declaration.md` template** mirroring
   `milestone-closure-declaration.md`.
3. **Reconcile** §5B's "Phase closure — future work" line and any AOG phase-delivery text that must
   agree — **without** touching acceptance / Review-Decision language (that is E25.2).
4. **Record** the change (PSG Changelog + minor bump v2.1.0 → v2.2.0) and **keep the suite green**.

# Epic E23.1 — By-link storage reconciliation (P6-VC-1)

## Context

Milestone M23 reverses the v5.0.0 **commit-the-binary** storage model to **by-link** and then
defines the **link + metadata binding convention** (E23.2) that makes by-link survivable. This
Epic delivers the **reversal half**: it edits every shipped surface that today tells an adopter to
commit a generated binary into the version-controlled project, replacing that instruction with
"reference the visual by link; the adopter owns the storage backend." E23.2 branches from the
merged result and binds *links* (never committed paths), so E23.1 lands first.

This is **governance/documentation, not plumbing.** The producer (three ComfyUI workflows) and the
helper (`bin/ai-project-visual`) are complete and verified end-to-end (SN-16). M23 changes what the
framework *says about storing* the output — not how the output is generated. The helper's runtime
behaviour does **not** change in this Epic; only its output *guidance* (the docstring example path
and the `--output` help text) is clarified.

## Problem Statement

Shipped v5.0.0 guidance instructs adopters to **commit generated binaries** into
`.ai-project/visuals/<level>/<id>.<ext>` so each visual "travels with its decision record." The CFO
has reversed this (SN-16, ratified 2026-06-29): generated visual material is **referenced by link,
never committed to git**, and the **adopter owns the storage backend**. Version control is the wrong
home for generated binary blobs, and the framework has always been infrastructure-agnostic about
where adopter resources live (endpoints, agents — and now storage).

The reversal is not a wording tweak. The instruction to commit appears across four shipped surfaces;
if any one is missed, the framework contradicts itself and a generated binary leaks back into git.
The change must therefore touch every named surface, leave **no** instruction to commit a generated
binary anywhere, and be **recorded as a reversal of v5.0.0** in the changelogs so the history of the
decision is legible.

---

## Goals

By the end of this Epic, the system must:

1. **Describe by-link on every named surface.** The guide (§4 prose, §1 source-repo note, §5
   examples), AOG §16.5, and the `bin/ai-project-visual` output guidance all describe referencing
   visuals by link; **no instruction to commit a generated binary remains anywhere** in those
   surfaces (residual `.ai-project/visuals/` example paths count).
2. **Leave the helper's behaviour unchanged.** Only the helper's *guidance* (docstring example +
   `--output` help text) is clarified — `--output` writes a local working file to host and link,
   not a committed path. No upload step, no link-emitting step.
3. **Confirm the test is already by-link-consistent.** Verify the integration test writes to a temp
   path and asserts non-empty bytes (not a committed binary) and **record** that finding — without a
   make-work assertion edit.
4. **Record the reversal as a reversal of v5.0.0.** Both the AOG changelog and a guide changelog
   record the change explicitly as a reversal of v5.0.0 shipped guidance (the guide has no changelog
   today — adding one, or an equivalent dated reversal note in the guide, is part of the work).
5. **Leave structural-diagram guidance untouched.** Mermaid/PlantUML stay text-in-git, inline or as
   sibling `.mmd` / `.puml` files.

---

## Non-Goals

This Epic explicitly does **not** aim to:

- **Change the helper's runtime behaviour or add an upload/link-emitting step.** Open Design
  Question B is resolved: the helper stays a minimal one-shot `prompt → local file` tool. Only its
  output *guidance* is clarified. Hosting + linking is the agent's job, defined by **E23.2**.
- **Define the binding schema or the per-level placement convention.** That is **E23.2**. E23.1
  establishes the by-link model that E23.2 binds against.
- **Touch structural-diagram guidance.** Mermaid/PlantUML are text and continue to live in git.
- **Edit the §4 format table, the helper's generation path, or the test's pass/fail logic.** The
  reversal is about *storage guidance*, not formats, generation, or test behaviour.
- **Stand up or host a storage backend.** Where binaries live is the adopting team's decision.
- **Make a cosmetic edit to the integration test.** It is already by-link-consistent; verify and
  record, do not invent a change the by-link model does not require.
- Re-examine the three SN-16 ratified decisions or the resolution of Open Design Question B.

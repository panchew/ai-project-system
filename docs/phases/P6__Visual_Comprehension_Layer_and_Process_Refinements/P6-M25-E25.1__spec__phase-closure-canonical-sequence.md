# Epic E25.1 — Phase-closure canonical sequence (P6-GH-12)

## Context

The framework codifies a **mandatory** closure gate at every level *except* the top of the
hierarchy. **PSG §1A "Canonical Happy Path for Epic Closure (Mandatory)"** is an ordered,
"no step may be skipped" Epic sequence. **PSG §5B "Milestone Closure"** defines a structured
"7-Step Milestone Closure Process." But there is **no phase-closure canonical sequence.** §5B's
own consolidation rules even label the level above it *"Phase closure — future work."* That gap
is why phase delivery — README update, version bump, git tag — happens today only because a human
issues an out-of-band Steering Note (this is how P5 closed at `v5.0.0`).

The steps that make a phase delivery legible from `master` are exactly the ones left uncodified.
The repo README still shows a stale **"226/226 tests passing"** banner (a P4 number; P5's own
closure declaration records **259 passed / 1 skipped**) — precisely the drift a mandatory
README-update step prevents. And every phase P2–P5 hand-rolled a `P#__phase-closure-declaration.md`
with the same frontmatter shape, yet no template governs it: the artifact exists by convention, not
by canon.

This Epic closes P6-GH-12 by adding a **canonical phase-closure sequence** to PSG that lists
**README update + version bump + git tag as mandatory automatic steps** — mirroring the §1A / §5B
pattern — so no Steering Note is required to close a phase. It optionally formalizes the
hand-made declaration as a template. This is **governance text, not tooling**: no script, no
automation — the sequence is a mandatory process the Phase Chat follows, the same way §1A and §5B
are mandatory processes.

**Grounding (verified on `phase/P6` — anchors this Epic plans against):**

- **§1A is the Epic-closure pattern to mirror.** PSG §1A (line 27) is an 8-step ordered sequence
  closing with *"No step may be skipped, inferred, or collapsed."* — the mandatory-sequence idiom
  the phase-closure section should adopt.
- **§5B is the Milestone-closure pattern to mirror.** PSG §5B (line 149) defines a "7-Step
  Milestone Closure Process" and a "Milestone complete vs. fully closed" distinction. A phase
  section mirrors this shape one level up.
- **There is no phase-closure section today.** PSG has §1A (Epic) and §5B (Milestone) but **no
  §5C / no "Phase Closure" canonical sequence.** §5B's consolidation rules explicitly read
  *"Phase branches merge to develop or main (**Phase closure — future work**)"* — the framework
  itself flags phase closure as unbuilt. E25.1 builds it (and reconciles that "future work" line).
- **There is no phase-closure template.** `governance/templates/` holds `epic-closure-notice.md`
  and `milestone-closure-declaration.md` but **no phase-closure template.** Yet every phase P2–P5
  produced a `docs/phases/P#__.../P#__phase-closure-declaration.md` by hand, all sharing the same
  frontmatter (`type: phase-closure-declaration`, `phase`, `name`, `status`, `merge_commit`,
  `tag`, `master_head_at_closure`, `closed_date`, `closed_by`, `acceptance_model`) — a de-facto
  artifact with no canonical template. Formalizing it is deliverable 2 (optional within scope).
- **Stale-artifact evidence the sequence would catch.** README (`README.md` lines 11, 46) shows
  `226/226 tests passing` — a P4 figure. P5's closure declaration records the live count as
  **259 passed / 1 skipped**. A mandatory README-update step in phase closure prevents this drift.
- **PSG version for this change:** PSG is **v2.1.0** (Effective 2026-06-23). Adding a new mandatory
  section is a minor bump → **v2.2.0** with a Changelog row. (E25.1 runs before E25.2, so PSG is at
  v2.1.0 when this Epic starts; the Coding Agent confirms the live version + changelog before
  bumping.)

## Problem Statement

Phase closure is not canonical. The three steps that make a phase delivery legible from `master` —
**README update, version bump, git tag** — are mandatory nowhere in the framework, even though the
two levels below (§1A Epic closure, §5B Milestone closure) each codify a mandatory, no-step-skipped
sequence. As a result these steps happen only when a human remembers to issue a Steering Note
(P5's `v5.0.0` closed this way), the README drifts (a stale `226/226` banner survives on `master`),
and the phase-closure declaration artifact exists in four hand-made copies with no template. The
written framework has a hole exactly where the top-level delivery gate should be. This Epic fills
it: a mandatory phase-closure sequence that lists README/version/tag as automatic steps, mirroring
§1A / §5B, so a phase closes by canon rather than by out-of-band note — and, as the immediate
dogfood, so P6's own delivery (after M25) follows the sequence this Epic defines.

  tool. No CI step, no `bin/` change, no bot. (README/version/tag are steps the Phase Chat

## Scope of Work

### 1. PSG — canonical phase-closure sequence (primary deliverable)

Add a phase-closure canonical sequence to `governance/PROJECT-SYSTEM-GUIDELINES.md`. The
recommended home is a **new "§5C Phase Closure"** immediately after §5B, mirroring §5B's structure
one level up. (The exact section number/placement is this Epic's design call within M25's scope —
a §5C mirroring §5B, or a phase entry in the §1A closure family; §5C is recommended given the
current structure.)

**Must include:**
- An ordered, **mandatory** phase-closure process in the §1A / §5B idiom, closing with an explicit
  "no step may be skipped" statement.
- **README update, version bump, and git tag as mandatory automatic steps** of that sequence —
  performed as part of closure, **not** via an out-of-band Steering Note.
- A **"phase complete vs. phase fully closed / delivered"** distinction paralleling §5B's
  "complete vs. fully closed," and the consolidation target (`phase/P<id> → master`).
- The **phase-closure declaration artifact** as the recorded output of the sequence (pointing to
  the template if deliverable 2 is included).
- Consistency with the operating acceptance model: the sequence records closure under **SN-13
  default-accept** (a clean delivery is accepted by silence; a Review Decision is the exception
  path only). *E25.1 states this by reference to how closure is recorded; it does **not** author or
  reconcile the default-accept model itself — that is E25.2. If phrasing the two would collide,
  keep E25.1's wording minimal and leave the normative default-accept text to E25.2.*

### 2. Phase-closure declaration template (optional, within scope)

Optionally add `governance/templates/phase-closure-declaration.md` mirroring
`milestone-closure-declaration.md`, formalizing the frontmatter the four hand-made P2–P5
declarations already share (`type: phase-closure-declaration`, `phase`, `name`, `status`,
`merge_commit`, `tag`, `master_head_at_closure`, `closed_date`, `closed_by`, `acceptance_model`)
plus the Delivery Record / Process Record / "What the phase delivered" body. If added, the §5C
sequence references it; if omitted, §5C still names the declaration as the closure output. *Whether
to add the template is an Epic-level call; the phase spec makes it optional.*

### 3. Reconcile adjacent text

- **§5B consolidation rules:** update the *"Phase branches merge to develop or main (Phase closure
  — future work)"* line so it points to the new §5C sequence instead of calling phase closure
  "future work."
- **AOG phase-delivery / Stage-2 text:** grep AOG for phase-delivery / phase Stage-2 language;
  if any describes phase delivery in a way that must agree with the new mandatory steps, align it
  (add/point to README/version/tag). If none conflicts, record that in the Delivery Notice. *Do
  **not** edit AOG Stage-2 acceptance / Review-Decision language — that is E25.2's surface.*

### 4. Changelog + version bump

- Add a PSG Changelog row recording the new phase-closure sequence (and template, if added),
  citing E25.1 (P6-M25).
- Bump PSG **v2.1.0 → v2.2.0** (minor: new mandatory section). Confirm the live version/changelog
  before bumping (E25.1 precedes E25.2's PSG edits).

## Notes

- E25.1 fills the one missing rung in the closure ladder: §1A (Epic) and §5B (Milestone) are
  mandatory sequences; phase closure was left to a Steering Note. §5C makes it canon.
- **The dogfood is deliberate.** M25 is the final P6 milestone; on its consolidation the Phase Chat
  delivers `phase/P6 → master` (PR #95) by the very sequence E25.1 introduces — README update,
  version bump, tag — not by a one-off Steering Note as P5 did. The stale `226/226` banner is the
  first thing that mandatory README step retires.
- **The recurring risk is bleeding into E25.2.** Phase closure records *acceptance*, and acceptance
  is where default-accept lives. Keep E25.1 to the *sequence* (README/version/tag/declaration) and
  reference SN-13 by name only; the normative default-accept reconciliation is E25.2's job.
- Exact section number (§5C recommended), whether the declaration template is added, and the precise
  wording are **Epic-level design calls within M25's scope**; the milestone fixes the contract
  (mandatory README/version/tag phase-closure steps, no Steering Note), not the wording.
- Default-accept (SN-13) governs this Epic's own delivery: a clean delivery meeting DoD + acceptance
  + spec is auto-accepted; a Review Decision is the exception path only.

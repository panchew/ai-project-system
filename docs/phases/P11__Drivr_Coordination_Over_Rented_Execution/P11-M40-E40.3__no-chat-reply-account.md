# E40.3 — No Chat Reply Authorizes (D4)

**The claim:** no path exists by which a chat reply authorizes anything in this surface.

**The bar:** *no reader can find a second path by which authorization could arrive.* That bar cannot
be met by assurance, so this document is written as **an inventory a reader can re-run and a set of
attempts a reader can repeat** — not as a statement asking to be believed.

**Delegated decision 5, answered: the surface has no inbound text channel at all.** The Epic spec
names this as *"the simplest way to satisfy D4, and a legitimate, reasoned outcome."* It is also
what SN-24 already decided, in the CFO's own words:

> *"The no-authority-on-speech seam gets STRONGER, not weaker, under the daemon form. **A daemon has
> no speech at all — only gates.** SN-23's seam is preserved by construction rather than by
> discipline."*

**Construction rather than discipline** is the operative phrase. Nothing below relies on the surface
choosing not to obey an instruction. There is nothing that reads an instruction.

---

## 1. The complete inbound inventory

**Every inventory is a floor** (method obligation 6). §4 says what this one does not cover.

### 1.1 Routes — two

Printed by the daemon itself at startup, and asserted by `test_the_route_table_has_exactly_two_entries`:

```
routes: GET /approve/<gate>, POST /approve/<gate>
```

`GET` verifies and renders; **it never spends**. `POST` is the only mutating route.

Eleven other paths were requested against the live daemon and all returned **404**:
`/`, `/index.html`, `/gates`, `/queue`, `/approve`, `/approve/a/b`, `/authorizations`, `/admin`,
`/health`, `/api/approve`, `/.well-known/whatever`
(`test_there_is_nothing_else_to_reach`; four of them also in the operator transcript).

Five other methods — `PUT`, `DELETE`, `PATCH`, `OPTIONS`, `TRACE` — are refused by
`http.server.BaseHTTPRequestHandler` itself, because the handler **defines no `do_PUT`,
`do_DELETE`, or `do_PATCH` at all** (`test_unimplemented_methods_fail_closed`). Failing closed by
*absence* is sturdier than failing closed by a branch someone can edit.

### 1.2 Request fields read — one

```python
ACCEPTED_FIELDS: frozenset[str] = frozenset({"t"})
```

`t` is a signed token. **There is no second field**, no comment box, no message body, no free text,
and no field whose *content* is interpreted as an instruction.

The mechanism is not a filter that inspects and rejects. `_token_from_body` **asks for one key by
name** and never iterates the submitted fields:

> *"A body of `decision=approve&note=yes+ship+it` yields no `t` and is rejected as malformed — the
> prose is not refused, it is **never looked at.**"*

That distinction is the whole of D4. A filter that reads prose and decides it is not an
authorization is one rule change away from deciding that it is. A parser that never reads prose has
nothing to change.

### 1.3 Places that mint an authorization — one

Found by parsing the package's own AST rather than grepping, so a call split across lines or hidden
behind a comment would still be seen (`test_exactly_one_place_in_the_package_mints_an_authorization`):

```
[('app.py', 'redeem', 142)]
```

**One call site, in `Surface.redeem`** — which verifies the signature, then spends the link, then
mints. The order is itself asserted from the AST
(`test_the_one_minting_path_verifies_and_spends_first`), because the ordering is the guarantee.

### 1.4 Entry points that reach the surface — one

`drivr/bin/` holds three executables. `drivr-serve` (E40.1) and `drivr-gate-queue` (E40.2) contain
no reference to the surface at all (`test_no_other_entry_point_touches_the_surface`).

`bin/drivr-gate` has exactly two verbs — **`serve` and `mint`** — asserted by parsing its subparser
registrations (`test_the_cli_has_no_verb_that_authorizes`). **There is deliberately no `approve`
verb.** A CLI flag that recorded an authorization would be precisely the *"convenience path added
just for local testing"* that binding constraint 3 names as the shape this fails in — an
authorization arriving without a link, available to anyone who can run the binary.

### 1.5 Imports — all standard library, nothing that could notify anyone

Every import across the package is checked against an allowlist
(`test_the_surface_imports_nothing_that_could_notify_anyone`). There is **no HTTP client, no
messaging SDK, no notification service, no chat client, no webhook**.

So *"gates are in-app only; push and WhatsApp untouched"* is not a promise this epic makes. It is a
property of the dependency list: there is nothing here that could send anything anywhere, including
by accident. **SN-24's deferral is unchanged, and nothing was built toward it.**

## 2. The attempts — a reader saying yes, in words, and failing

Executed against the live daemon, 2026-08-17. **A valid, live, unspent link existed for
`merge-pr-212` at the time**, so the surface genuinely had an authorization it *could* have minted.
Verbatim:

```
$ curl -s -i -X POST -d 'decision=approve&reply=yes, go ahead&message=LGTM, merge it' http://127.0.0.1:8791/approve/merge-pr-212
HTTP/1.0 400 Bad Request
...
<h1>Rejected — malformed</h1><p>expected exactly one `t`, got 0</p><p><strong>No authorization was recorded.</strong></p>

$ curl -s -i -X POST -d 'approve=true&confirm=true' http://127.0.0.1:8791/approve/merge-pr-212
HTTP/1.0 400 Bad Request
...
<h1>Rejected — malformed</h1><p>expected exactly one `t`, got 0</p><p><strong>No authorization was recorded.</strong></p>
```

Read the rejection reason closely: **`expected exactly one 't', got 0`**. The surface did not
evaluate the words `approve`, `yes, go ahead` or `LGTM` and find them insufficient. It looked for a
token, found none, and stopped. The prose was never an input.

Eight further phrasings are exercised in the suite
(`test_a_chat_reply_submitted_to_the_only_inbound_channel_does_not_authorize`), including
`text=I+authorize+this` and `gate=merge-pr-211&decision=approve`, each asserting **both** a ≥400
status **and** that no authorization was minted.

### 2.1 The inverse, which is the one that could have hidden a bug

Prose riding *alongside* a valid token:

```
$ curl -s -i -X POST -d 'decision=reject&t=<valid token>&note=do not do this' http://127.0.0.1:8791/approve/merge-pr-212
HTTP/1.0 200 OK
...
<h1>Authorized — <code>merge-pr-212</code></h1>
```

**`decision=reject` had no effect — including no effect in the direction of rejecting.** This is the
demonstration in the direction that matters: had any code path read a `decision` field, this request
would have behaved differently from a bare token. It did not.

## 3. Why the link is not the authority

The distinction the Epic spec calls load-bearing: *"an epic that treats the link as the
authorization has rebuilt the chat reply with extra steps."*

A holder of a valid link has **the ability to** authorize. Only the surface **authorizes**, and it
does so by writing a record in its own state at the moment of redemption:

```json
{
  "authorized_at": "2026-08-17T22:32:38.349413Z",
  "channel": "signed-one-time-link",
  "gate": "merge-pr-211",
  "link_nonce": "CF2b6ihOGTPpOtS7SFfM-g"
}
```

`authorized_at` is **the surface's own clock**, not a field the holder supplied. `channel` is a
constant written into every record — which makes the claim auditable **from the artifacts alone**,
without reading the code: a record bearing any other channel would itself be evidence that a second
path exists.

The token is **not** recorded. A bearer credential must not enter a permanent record that outlives
the fifteen minutes it is good for.

## 4. What this inventory does not cover

**Method obligation 6: every inventory is a floor.** Stated so the bound is visible rather than
implied.

1. **It enumerates mechanisms this epic knew to look for.** A path arriving by a means not named
   here — a new `do_PATCH`, a field read through some third parser, an entry point outside `bin/` —
   would not appear in §1.
2. **The AST scan finds calls shaped `<something>.authorizations.mint(...)`.** A record written by
   some other means — `open()` directly into the authorizations directory, a differently-named
   helper — would not match. What limits this in practice is that such a file would also have to
   satisfy `AuthorizationLog.all()`'s reader, and would carry no `channel` field to pass §3's audit.
3. **`ACCEPTED_FIELDS` is a declaration with a tripwire, not the enforcement** — see the
   demonstration evidence §2.1, where widening it breaks exactly one test. The enforcement is that
   the parsers ask for `t` by name.
4. **Anything that can read the signing key can mint any link it likes.** The key is a file at mode
   `0600` and nothing more. On a single-operator machine a process that can read it can read
   everything else the operator owns; **if this system ever grows a second user or a remote surface,
   that reasoning expires with it.**

What the tests do provide is that **adding any of the covered paths breaks a named test** rather
than passing silently. That is the difference between a bounded claim and a hopeful one, and it is
what is being claimed here — not omniscience about paths nobody has thought of.

## 5. Constraint 3, and why the rule's shape recurs

The Epic starter noted that this epic's subject appears one level up, in its own governance rules:

> *Merge authorization arriving through the wrong channel is refused even when the human clearly
> means it. **That is the same principle you are building into the approval path.***

Both rules refuse an authorization **on the grounds of its channel, not its content**. In the
starter's case a human may plainly authorize a merge in the child chat and the rule still says: not
here, not like this (`P9-GH-1`). In this surface, a human may plainly type "yes, approve it" and the
answer is `expected exactly one 't', got 0`.

The reason is the same in both: an authorization whose validity depends on someone having *read it
correctly* is unbound — to a gate, to a single use, to a verifiable origin. Binding it to a channel
is what makes it checkable afterwards by someone who was not there.

**Constraint 3 is prohibited, not deferred**, and nothing in this delivery weakens it. There is no
convenience path, and there is none in the test fixtures either: the suite authorizes only by
redeeming real links through `Surface.redeem`.

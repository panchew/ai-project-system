# Epic E38.1 — Drivr Repository Inception and Enrollment

**Stage A, FIRST — binding. No other M38 epic starts before this one delivers.**

---

## Context

P11 is named for Drivr. **Drivr does not exist.**

M36 and M37 made this repository's record trustworthy — identifiers that resolve, documents that state
their own version, citations that point at one thing. Both were entirely in-repo. **E38.1 is the first
epic in this phase whose principal deliverable lands somewhere else**: a new repository at
`~/soft-dev/drivr`, governed by this framework, holding no governance corpus of its own.

Everything downstream needs it. E38.2's adapter surface has nowhere to live. E38.3's registry has no
host. M39's completion signal and M40's scheduler are two milestones away and both assume a repository
that can be worked in. **This epic's only job is to make that repository real, governed, and
confirmable** — and then stop.

SN-27's spine states what Drivr is: a **coordination daemon** that **rents both halves**. It rents
chat, and it rents execution. It invokes CLI tools that own the inference and spends its budget on
coordination over governance state. That is the whole identity, and this epic must not add to it.

---

## Problem Statement

**Verified 2026-08-07 on the host: `~/soft-dev` contains 14 project directories and none of them is
`drivr`.**

Three consequences, all of them immediate:

1. **Every downstream M38 epic is blocked.** E38.2 and E38.3 are declared parallel to each other and
   both sequenced after this one. The Stage A → Stage B gate sits behind E38.2, so all five remaining
   epics are behind this epic.
2. **There is no enrollment path for a brand-new project that this milestone has already validated.**
   The M33/E33.1 lever the milestone spec points at is a **bump** procedure for *already-enrolled*
   projects and says so in its own scope statement (see §Finding 1). The path for a new project is
   `bin/ai-project-init`, which no P10 or P11 epic exercised on a greenfield target.
3. **A claim about Drivr cannot be verified by reading this repository.** This is the M33/M34 pattern
   and it is the difference between a delivery and an assertion.

---

## Goals

By the end of this Epic:

1. **The Drivr repository exists** at a recorded location, is a git repository, and carries whatever
   minimum structure its stack choice implies.
2. **Drivr is enrolled under this framework** at a stated `framework_version`, with a `models:` block,
   through a path that is **recorded and reproducible** rather than improvised.
3. **Confirmation evidence captured *from Drivr* is committed in this repository**, so a reader here
   can verify Drivr's state without going and looking.
4. **Drivr's own test baseline is established and stated** — it does not inherit this repo's 393.
5. **The 11 recorded failure modes were consulted**, each classified as fired / applicable-and-avoided
   / structurally inapplicable, with anything genuinely new recorded as a finding.

---

## Non-Goals

This Epic explicitly does **not**:

- **Implement inference, a model loop, an engine, or an agent client.** Constraint 1, as an exclusion.
- **Build the adapter surface or any adapter.** That is E38.2, and it is deliberately a separate epic.
- **Build the registry, the classification pass, the validator, or any schema change.** That is E38.3.
- **Build a scheduler, a gate queue, a thin surface, or any completion judgment.** M39 and M40.
- **Write Drivr's coordination logic.** Inception means the repository and its governance, not its
  behaviour. An empty, governed, tested repository is the correct outcome of this epic.
- **Modify any other fleet project**, including this one beyond its own governance record.
- **Fix, extend, or refactor `bin/ai-project-init`.** If it misbehaves, record it and escalate — see
  §The specific drift to watch.
- **Amend `ai-project-yml-spec.md`.** `framework_version`'s schema entry is E38.3's, and E38.1 stamps a
  convention-only field knowingly (see §Finding 3).

## ⚠ Finding 1 — the procedure the milestone spec points at explicitly excludes this Epic's case

**This is the most important thing in this spec. Read it before planning any work.**

The milestone spec's E38.1 deliverable 2 says: *"Enrolled under this framework, using **M33/E33.1's
procedure and its 11 recorded failure modes** — use them, do not rediscover them."*

**The procedure is at `.ai-project/artifacts/reference/v7-bump-procedure/README.md`, and its own §Scope
says, verbatim:**

> *"This bumps **enrolled** projects — a project that already has a governance submodule
> (conventionally `.governance`, but **not always** — see Failure Mode 8) and a `.ai-project.yml`. **It
> is not the enrollment path for a brand-new project (that is `bin/ai-project-init`).** It does not run
> any project work; it only refreshes governance and stamps the version."*

**Drivr is a brand-new project.** The procedure does not apply to it as written, and its Failure Mode 1
is *"`ai-project-init` is not a refresh tool (Direction A trap). It creates; it does not update"* —
which is the *inverse* of E38.1's situation. E38.1 needs a tool that creates. That is the tool.

**This is a scope correction, not a contradiction, and not an escalation.** The milestone spec is right
that the 11 failure modes are hard-won and must not be rediscovered; it is imprecise in calling the
procedure the enrollment path for a repository that does not exist. **The resolution is binding on this
Epic:**

- **The enrollment path is `bin/ai-project-init`** — named as such by the procedure itself.
- **The 11 failure modes are consulted as a hazard checklist, not executed as steps.** Several are
  structurally inapplicable to a greenfield target and several fire hard. **Classify each one
  explicitly** in the Delivery Notice — *fired / applicable and avoided / structurally inapplicable* —
  with a one-line reason. A blanket *"consulted the 11 failure modes"* does not satisfy this.
- **The procedure's §Stamp location + confirmation method still applies**, because the stamp and the
  confirmation are the same act whether the project is new or bumped.

**Provisional classification, to be verified rather than inherited.** These are the planner's reading
and each is a claim the Epic must check:

| FM | Subject | Provisional |
|---|---|---|
| 1 | `ai-project-init` creates, does not update | **Inapplicable, inverted** — creating is exactly what E38.1 wants |
| 2 | Target's submodule has not pre-fetched the tag | **Applicable** — a fresh submodule must be pinned to a real, fetched ref |
| 3 | Installed `governance.agent.md` is an out-of-band copy a re-pin does not refresh | **Applicable** — verify what init actually installs |
| 4 | `framework_version` is not defined in the yml-spec | **Fires** — see Finding 3; this is `P10-GH-1` |
| 5 | P6-GH-15, superseded `hq.agent.md` | **Likely closed** — see Finding 4; **verify, do not assume** |
| 6 | Uncommitted content in the target | **Inapplicable** — no prior content exists |
| 7 | `.ai-project.yml` structure varies, incl. missing/mistyped fields | **Fires** — see Finding 2 |
| 8 | Submodule path is not always `.governance` | **Fires by construction** — see Finding 2 |
| 9 | `.gitmodules` can carry a second recorded pin, possibly a raw SHA | **Inapplicable** — no prior `.gitmodules` |
| 10 | `.gitmodules` can declare more than one submodule, incl. an orphan | **Inapplicable** — same reason |
| 11 | Branch base was unspecified, and dirty trees break it | **Applicable in altered form** — a new repo's first branch base is its own initial commit |

**Six inapplicable-or-altered, five live.** That ratio is itself the finding: **the lever was built for a
different job and it is being borrowed.** Say so in the Delivery Notice rather than implying a clean
reuse.

## ⚠ Finding 2 — `bin/ai-project-init` produces neither `framework_version` nor `models:`

**Measured by reading `bin/ai-project-init` on `phase/P11`, 2026-08-07.** `create_ai_project_yml()`
writes exactly this:

```yaml
project:
  name: <project_name>
  created_at: <ISO8601 UTC>

governance:
  source: <governance_source>
  version: <governance_version>
  submodule_path: governance/
```

Three consequences, all of them E38.1's to handle deliberately:

1. **No `framework_version`.** A project enrolled by running init alone joins the six configs that omit
   it. **The milestone spec requires Drivr to carry one**, so the stamp is a **deliberate post-init
   addition**, done per the procedure's §Stamp location + confirmation method.
2. **No `models:` block.** The milestone spec requires one. Also a deliberate post-init addition.
   Drivr's routing is E38.1's to choose and record — and the routing that governs *Drivr's own* future
   epics is a decision, not a copy of this repo's block.
3. **`submodule_path: governance/`, not `.governance`.** The convention Failure Mode 8 warns about is
   *violated by the framework's own tool, by default*. This is not a defect to fix here — it is a fact
   to record, and it means **any command written against `.governance` will not work on Drivr.**
   **Do not fix `ai-project-init`** (Non-Goals); record the observation and let it inform E38.3's
   validator, which will meet this same shape across the fleet.

**Do not discover these at execution time.** They are the reason enrollment here is *init plus two
recorded additions*, not *init*.

## ⚠ Finding 3 — Drivr's `framework_version` is convention-only when written, and that is correct

**Failure Mode 4 fires, and it is `P10-GH-1`**: `framework_version` is convention-only and is **not
defined** in `governance/ai-project-yml-spec.md`. Six of the twelve enrolled configs omit it entirely,
including this repository's own.

**E38.3 folds `P10-GH-1` in** — the Phase Chat decided that, with an escape if the registry turns out
not to read the field normatively. **E38.3 runs in parallel with E38.2, after this Epic.** So the
ordering is unavoidable: **E38.1 stamps a field that has no schema entry at the moment it is stamped,
and E38.3 blesses it afterwards.**

**That is fine and it must be recorded rather than quietly resolved.** Two obligations:

- **State the stamped value and state that it is convention-only at the time of writing**, citing
  `P10-GH-1` and E38.3 as where that changes.
- **Do not amend the yml-spec to get ahead of it.** That is E38.3's pass, it carries a Structural
  diagram obligation, and doing it here would take an epic's decision away from the epic that owns it.

### The value to stamp — and the reasoning to record

**The current framework tag is `v7.1.0`** (measured; P10 closed there). **The fleet's six stamps all
read `v7.0.0`**, because they were written during P10 before its own closure bump.

The phase spec §P11.3 says Drivr is enrolled *"at v7.1.0."* **Stamp `v7.1.0`** — it is the released
version Drivr is genuinely being enrolled against, and stamping `v7.0.0` to match the fleet would
record a falsehood for the sake of uniformity.

> **The consequence, stated so it is not a surprise to E38.3:** Drivr will be the **only** project on
> the machine at `v7.1.0`. When E38.3's validator runs against the real fleet it will meet **one
> project at `v7.1.0`, five at `v7.0.0`, and six with no stamp at all.** That is the true state of the
> fleet and the registry should record it as such. **It is not E38.1's job to make the fleet uniform.**

## Scope of Work

### 1. Choose Drivr's stack and minimum structure — **E38.1's design decision**

**This is yours to make, document, and proceed on. It is not an escalation.**

The constraints are **SN-24's headless-first** posture and *"as agentic as we can → lightest
infrastructure"* — **not a named technology.** What the choice must satisfy:

- **It must be able to invoke a CLI tool as a subprocess and read its exit code, stdout, and stderr.**
  That is the entirety of what the adapter surface (E38.2) needs from the runtime.
- **It must be able to read YAML** — the registry (E38.3) reads `.ai-project.yml` across the fleet.
- **It must be testable**, because deliverable 4 is a stated baseline and a baseline of zero tests is
  not a baseline.
- **It must be headless.** No GUI, no window, no interactive-only entry point. The thin surface is
  M40's and is explicitly not this.
- **It must not pull in an inference SDK, a model client, or an agent framework** — Constraint 1 is
  enforceable at the dependency list, and the dependency list is the cheapest place to enforce it.

**Record the choice and the reasoning in the Delivery Notice.** A future reader must be able to see why
the stack was chosen without asking anyone. **Lightest thing that satisfies the five bullets wins** —
if two candidates both satisfy them, take the one with fewer dependencies and say that was the
tiebreak.

### 2. Create the repository

- Created at a **recorded absolute location**. `~/soft-dev/drivr` is the expected home — it is where
  every other fleet project lives and where E38.3's classification pass will look. **If you choose
  otherwise, say why, and know that E38.3 enumerates `~/soft-dev` directories.**
- A **git repository** with an initial commit. **Failure Mode 11 in altered form**: a new repository's
  branch base is its own initial commit, so make that commit before branching for anything.
- Minimum structure per the stack choice. **Minimum means minimum** — an empty governed repository is
  the correct outcome, not a scaffolded application.

### 3. Enroll it — init, plus two recorded additions

1. **Run `bin/ai-project-init`** against the new repository. Record the exact invocation and its output.
2. **Add `framework_version: v7.1.0`**, per Finding 3, at the location the procedure's §Stamp location
   specifies, with its convention-only status recorded.
3. **Add a `models:` block**, chosen and reasoned. **The routing that governs Drivr's own future epics
   is a decision.** Record why each row is what it is.
4. **Verify the installed `governance.agent.md` is the canonical file by reading it in Drivr**
   (Finding 4) — not by reading the installer.

### 4. Establish and state Drivr's test baseline

- **Drivr does not inherit this repository's 393.** Its baseline is whatever its own suite reports on
  the day it is established.
- **A baseline of zero is not acceptable** — deliverable 4 requires a *stated baseline*, and a stated
  baseline of nothing measures nothing. **At minimum, Drivr's suite must contain a test that fails if
  the repository is broken in the way its stack makes most likely** (an import failure, a syntax error,
  a missing entry point). One real test is enough; a test that asserts `True` is not a test.
- **State the exact command** that produces the number. This repository has just cost a chat three
  wrong invocations to rediscover that `python` is not on `PATH` and `PYTHONPATH=.` is required. **Do
  not make Drivr's baseline a puzzle.**

### 5. Capture confirmation evidence FROM Drivr and commit it HERE

**This is the M33/M34 pattern and it is not optional.** A claim about Drivr's state is not verifiable
by reading this repository unless the evidence is brought here.

Commit, in this repository, at
`docs/phases/P11__Drivr_Coordination_Over_Rented_Execution/P11-M38-E38.1__confirmation-evidence.md`:

- **Drivr's absolute path**, and the `git rev-parse HEAD` of its initial state.
- **`.ai-project.yml`'s full content**, quoted verbatim — not summarized. **Constraint G1's general
  form applies:** an input with exactly one non-uniform element gets that element **quoted verbatim**
  rather than described. The version stamp is exactly that element.
- **The output of a command run inside Drivr** proving the governance submodule is present and pinned
  to a real ref.
- **The installed `governance.agent.md`'s identity** — its first heading and a hash, enough to
  distinguish canonical from superseded (Finding 4).
- **Drivr's suite command and its output**, verbatim.
- **The 11 failure modes, classified**, per Finding 1.

**Every command must be shown with its output.** *"I verified X"* is not evidence — **G2's general
form**: the reader re-measures; the executor's report is not the evidence.

## Binding Constraints — reproduced, not cited

**These are reproduced in full because a spec that cites a constraint has not delivered it.**

**1. Drivr rents both halves.** It implements **no inference, owns no model loop, grows no engine, and
builds no agent client.** SN-27's spine, stated as an exclusion so it cannot erode by increment. **An
epic that starts writing a model loop has left the phase, not just the milestone.** For E38.1 this is
enforceable at the dependency list — see §Scope 1.

**4. The registry has three states and the definitions are the CFO's** — active / benched / archived.
**Not E38.1's to build**, but named here because Drivr's own classification will be E38.3's to make and
E38.1 should not pre-empt it by writing one into Drivr.

**5. Drivr does NOT execute fleet-state transitions.** Recorded human action only. Nothing automatic.
Not E38.1's work, and nothing in inception should make it easier to violate later.

**9. Every delivery that amends a normative document in this repository carries a Structural diagram**
(Mermaid, fenced, in-repo, **no ComfyUI**). **This does NOT fire for E38.1.** This Epic amends no
document under `governance/`; its in-repo footprint is the epic record and the confirmation evidence.
**If you find yourself amending `governance/`, stop** — that is either E38.3's pass or an escalation.

**10. The metavariable constraint (M37 Finding 3).** *Any document that records having fixed a defect
is liable to restate the defect while doing so.* It fired twice in M37, the second time in an ordinary
changelog row. **For E38.1 the shape is specific: a document recording that `framework_version` is
convention-only must not itself cite the field in a form the schema will later reject.** Quote the
literal line; do not paraphrase it into a shape that looks normative.

**P10-GH-10 — read this before interpreting a red suite.**
`tests/test_artifact_router.py::test_daemon_extensions_error_branches` fails **~3 in 10 full-suite
runs**, passes in isolation, and is **untouched by anything in this Epic**. **A red suite on that test
alone is not evidence of an Epic defect.** Re-run and record **both** results — not only the green one.
Do not fix, skip, or mark it.

## The Hard Constraint — and the specific drift to watch

**Drivr rents. It does not build what it can invoke.**

> **The drift here is not the obvious one.** E38.1 is not going to accidentally write an inference
> engine. **It is going to be tempted to make Drivr useful.**
>
> Once a repository exists and its stack is chosen, a config loader is ten minutes, a CLI entry point
> is twenty, and a first pass at the adapter is an afternoon — **and all three will look like
> progress.** They are E38.2's and E38.3's, and taking them here removes those epics' design decisions
> from the epics that own them.
>
> **An empty, governed, tested, confirmable repository is a complete E38.1.** If that feels thin, it is
> because the epic was deliberately scoped that way: it is the binding first step for five others, and
> the only thing that matters is that it lands quickly and correctly.

**Two further boundaries:**

- **Do not build a scheduler, a gate queue, a thin surface, or any completion judgment.** M39 and M40,
  in binding order, and **M39 gates M40** because a scheduler over an untrustworthy completion signal
  produces constant false escalations or silent no-ops that read as success.
- **Do not fix `bin/ai-project-init`, `governance/ai-project-yml-spec.md`, or any other framework
  surface** you find wanting while enrolling. **Record it, name it individually in the Delivery Notice,
  and escalate to the Milestone Chat.** Noticing and declining is a deliverable in this milestone's
  lineage — E36.5 declined a two-character fix it was capable of making and HQ explicitly refused to
  undercut that judgment.

**If this Epic finds itself building any of the above, it stops and escalates to the Milestone Chat.**

## Execution Notes

**Order:**

1. **Check your branch.** Then verify prerequisites and the model check.
2. **Read the bump procedure's §Scope first** — before anything else — so Finding 1 is something you
   have seen rather than something you were told.
3. **Choose the stack**, against the five constraints, and write down the reasoning *before* creating
   anything. The reasoning is a deliverable and it is easier to write honestly before the code exists.
4. **Create the repository and its initial commit.**
5. **Run `bin/ai-project-init`**, capturing the invocation and output verbatim.
6. **Add the stamp and the `models:` block**, deliberately, recording both.
7. **Read the installed `governance.agent.md` in Drivr** and record its identity.
8. **Write the one real test** and establish the baseline.
9. **Capture the confirmation evidence**, every command with its output.
10. **Classify the 11 failure modes.**
11. **Re-measure this repo's suite**, state the command and the number.
12. **Commit, open the PR, produce the Delivery Notice, and stop.**

**The instruction that matters most:** this Epic is small on purpose and five epics are waiting on it.
**Land it clean and land it fast.** Every hour spent making Drivr useful is an hour spent doing another
epic's work with less information than that epic will have.

# Delivery Notice: P11-M40-E40.1 — The Serialized-Lane Scheduler, and the Completion-Signal Decision

## Summary

The serialized lane runs unattended, and the completion-signal question was decided on
measurement rather than inherited. **Five real runs were dispatched by the scheduler with no human
starting any of them**, across two repositories, and the evidence is committed here because
`drivr` has no git remote.

The epic's shape changed once during execution, on a measurement: **the ordered ledger turned out
to be projectable**, which the spec treated as plausible-but-unmeasured and M39 had recorded as
unavailable from any adapter. Answering it required running the engine — reading Drivr's parser
would have answered a different question at the wrong layer.

## What was delivered

**D1 — the scheduler.** `drivr/scheduling/`, with the two axes as **separate modules that do not
import each other**: `enrollment.py` (which projects may run — reads E38.3's fleet registry) and
`lane.py` (how many run at once — one, via `fcntl.flock` so the invariant survives a second
scheduler *process*). They are joined only in `scheduler.py`, and a test asserts the separation
rather than a docstring claiming it. Capacity is **not configurable**: a scheduler that can be
configured into concurrency has documented a default, not implemented a constraint.

**D2 — the completion-signal decision.** Direction 1 **+ direction 4's consumer half**. Recorded
in full with its measurement, including what `structured_events` actually contains and the six
things the scheduler does **not** know about a finished run.

**D3 — five unattended runs, captured and committed.** Three in the main set, two more under
`contention/`. Not all succeeded, and that is the point.

**D4 — the worktree question: taken**, as a mechanism, with its scope limit recorded.

**D5 — cross-repo evidence capture.** Each dispatch writes the engine's own stdout verbatim, the
judgment's full explanation, the disposition with its reason, and the record. That directory is
how evidence leaves `drivr` and gets committed here, so a reviewer re-reads primary evidence
rather than the scheduler's summary of it.

## The measurement that changed the epic's shape

§F2 established `parse_events` is non-lossy, so *"can an ordered ledger be projected?"* was a
question about **OpenCode's stream**, not Drivr's parser. Run 2026-08-17: the stream is typed
NDJSON, and a `tool_use` event carries the tool name, arguments, the engine's own result string, a
per-call status and per-call timing, **in order**.

**So `EFFECTS_VERIFIED` is now reachable from a live run** — and was reached, by unattended run
`…-39168925`, through E39.1's `covering-verification` ordering rule.

M39's recorded limit rested on an assumption about the stream that does not hold. **That is not a
defect in M39**, which deliberately did not look because nothing in M39 needed the answer.

## §F5: half-fixed, and the half that is not is stated and pinned

Consequence 1 is fixed. **Consequence 2 is not, and could not have been fixed in the projection.**
`_decide` never reads `Role.INSPECTION`; both inversions reproduce independently (G2).

The missing term was **the job's own expectation** — which the judgment cannot know and the
scheduler does. An inspecting job that changes nothing has completed; a mutating one has not. Same
verdict, same ledger, two correct dispositions. `Expectation` has no default and is **never
inferred from the task text**.

**`_decide` and the `Reading` vocabulary were not touched** (escalation trigger 1). Instead the
defect is **pinned by a test** that goes red if anyone fixes it, so the compensation can be
retired deliberately rather than rediscovered. What remains wrong is recorded: the compensation
protects the scheduler and nothing else — zero cost today, a cost that grows with the second
consumer of `drivr.judgment`.

## A silent, environment-dependent hang, found and fixed

`opencode run --format json` **blocks indefinitely emitting zero bytes on both stdout and
stderr** when stdin is an inherited open pipe. Three invocations were killed at 120 s, 300 s and
420 s having produced nothing; with `--print-logs --log-level DEBUG` the last line is
`message=init`, so **the hang precedes any model call**. `capture_output=True` redirects stdout
and stderr only, and Drivr's adapter never set `stdin` — so engine liveness was a property of how
the *scheduler* was launched. **D3 was not achievable until this was fixed.**

The guard is falsifiable and was falsified in both directions: with the fix removed it reports
`timed_out=True exit=None`; restored, it passes. **An earlier version of that test passed either
way** — pytest replaces the session's stdin with a non-blocking stand-in, and `communicate()`
closes the child's stdin — so it was rewritten to hold a real open pipe. Recorded because a guard
that cannot fail is worse than no guard.

## Runs that did not succeed, reported as such

**Main-set run 3 (`…-efcf592b`) was refused: `not-done`.** The model emitted
`<function=read>…</function>` **as plain text** instead of calling the tool, so the ledger was
observed and **empty** — `()`, not `None`. The negative is *earned*, and only because the two are
kept apart; an absent ledger correctly yields `undetermined` instead.

That reproduces, inside a real unattended dispatch, an intermittency measured during design:
**the same model and prompt shape produced real tool calls in 10 of 12 observed runs and prose
imitation in 2.** The lane's engine is not reliable. The ledger is what makes an unreliable run
visible instead of creditable.

## Constraint 7, applied to every run

Main-set run 1 was asked for a `framework_version` key that **`.ai-project.yml` does not
contain** — the same key M39's fabricated `VERDICT: PASS` cited with **zero tool calls**. Here,
with tools that worked, the model read the file and answered *"The file .ai-project.yml does not
contain a framework_version key."* Run 2's success claim was independently confirmed by the
judgment (effect, covering verification at `exit_code: 0`, and a `files_changed` snapshot the
model had no hand in). Run 3 claimed nothing and was refused. **No success claim was taken at
face value.** One data point on a different dispatch path — not a general claim about fabrication
rates.

## Escalations and recommendations for the Milestone Chat

1. **Recommended, not performed: teach `_decide` to read `Role.INSPECTION`.** This is escalation
   trigger 1 territory — validated code with two binding known cases — so E40.1 declined to touch
   it and compensated at the consumer instead. **The Milestone Chat's call**, including whether it
   belongs in this phase at all.
2. **The engine's tool-calling is intermittent** (2 failures in 12 observed runs, one inside a
   real unattended dispatch). It is not a blocker — the ledger catches it — but a lane whose engine
   silently declines to use tools ~15% of the time is a coordination fact M40's remaining epics may
   care about.
3. **D4 does not close `P11-GH-1`.** The mechanism binds the dispatch path; all four measured
   occurrences were on the manual path. Stated in the D4 record so it cannot be misread as closed.
4. **`P10-GH-9` part 1 of 2 remains open** — PSG §11.6 does not name the agentic case in its own
   text. Not this epic's to close (a PSG amendment, HQ's to authorize), and already recorded for
   M40's Closure Declaration. E40.5's guard was confirmed in place before dispatch was wired
   (39 tests passing), as its binding position requires.
5. **No new `GH-` ID was filed.** `P11-GH-3` remains contested and unallocated, and was not
   allocated. The two findings above are reported here rather than given IDs, per the starter.

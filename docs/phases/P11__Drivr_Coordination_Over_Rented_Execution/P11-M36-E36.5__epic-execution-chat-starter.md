## The Hard Boundary — the thing most likely to go wrong

**The audit reports. It does not remediate.**

**You will probably find something.** A clean result across three never-audited families would be the
surprising outcome. **Finding something is success — not a trigger to act.**

The temptation is asymmetric, and it is worth seeing coming: **fixing a collision you just found is a
two-line edit; escalating it is an artifact, a routing hop, and a wait.** That asymmetry is exactly
why the constraint exists. It is the pressure that turns a bounded cleanup into an open-ended one,
**inside the milestone whose entire value proposition is that cleanup lands bounded and governed.**

| What you find | What you do |
|---|---|
| No collision in a family | **Record it.** A clean family is a finding |
| The family allocates **no ID of its own** | **Record that as the finding.** Do not manufacture a check that does not apply |
| Collision in **project-internal, non-normative** artifacts | **Report and leave.** Do not renumber |
| Collision cited in the **normative tier** (`governance/`) | **ESCALATE** to the Milestone Chat (P11-M36) |
| A convention inconsistency (not a collision) | **Characterize and record** |

**Make escalating cheap for yourself.** If a normative-tier finding appears: write the notice using
`governance/templates/escalation-notice.md`, issue it to the **Milestone Chat (P11-M36)** — one level
up, per SN-25 — and **continue the rest of the audit.** Do not stop the epic. Do not fix it while you
are there.

**Beware the vacuous pass.** Two of the three families appear to carry **no `id:` field at all**. A
steering-note-shaped check run against them returns "no collisions" and **means nothing** — worse
than no audit, because it retires the question wrongly. **Define what "collision" means for each
family, write the definition down before you run anything, and record it.** That definition is a DoD
item.

## The five criteria

### Criterion 1 — Role: it assesses, it does not produce. **MET**

**Measurement.** The task text handed to the runner is recorded verbatim in
`qa-context.md` + the adapter's `QA_TASK_TEMPLATE`; it instructs the agent to judge each numbered
claim of a standard and emit `VERDICT: PASS`/`VERDICT: FAIL`, and states *"You are not implementing
anything, and you have no tools that could."* It is **not** `extract_dod(...)`, which is what
`bin/run-dev-agent` line 241 passes (`task_text = extract_dod(spec_text, spec_path)`) — the
*implement-this-DoD* instruction that F1 identifies as the trap. Pinned by
`tests/integration/test_run_qa_agent_adapter.py::test_task_text_is_an_assessment_not_the_definition_of_done`,
which fails if the standard's DoD text ever reaches `--task-text`.

**Scope of this claim, stated precisely:** criterion 1 is a property of **the dispatched task**, not
of the quality of the assessment returned. The run's assessment was in fact ungrounded (§The
finding). **The bar as written does not require the verdict to be grounded**, and that is a
limitation of the bar, not a defect in this measurement.

### Criterion 2 — Tools: it cannot mutate the working tree. **MET**

**Measurement.** `.ai-project/agents/qa-tools.json` is committed and reads, in full:

```
enabled            = ["read_file", "list_dir"]
allow_paths        = ["/workspace/**", "*/ai-project-system/**"]
allow_commands     = []
deny_commands      = ["*"]
allow_subcommands  = []
```

against the coding set's `enabled = ["read_file", "write_file", "edit_file", "list_dir",
"run_command", "git"]` with `allow_subcommands` including `add` and `commit`. The run's
`qa-run-metadata.json` binds the artifact to the file by **`tools_sha256`**
`83ff08e7…4cfb69e7` and records `tools_enabled` inline, so a reviewer checks a hash, not a claim.

**The enforcement layer, measured rather than assumed — and the obvious reading of the source is
wrong.** Executed on the host against `local-agent-runner` at commit `4ec1e8f`:

| Probe | Result |
|---|---|
| `tool_definitions(enabled=[read_file,list_dir])` | advertises exactly `['read_file', 'list_dir']` |
| `parse_tool_call({write_file…}, tools)` | `RepairableError`, kind **`unknown_tool`** |
| `parse_tool_call({edit_file…}, tools)` | `RepairableError`, kind **`unknown_tool`** |
| `parse_tool_call({git…}, tools)` | `RepairableError`, kind **`unknown_tool`** |
| `execute_tool('write_file', …)` called **directly** | **`ok=True` — the file was written** |
| `execute_tool('run_command', 'echo hi')` | `ok=False` — denied by empty `allow_commands` |
| `execute_tool('git', 'commit -m x')` | `ok=False` — denied by empty `allow_subcommands` |

**So the guarantee lives at `tool_calls._validate_call`, not at `tools.execute_tool`.**
`execute_tool` dispatches from its own `_HANDLERS` map and **never consults `enabled`** — a caller
that bypassed the loop could write. The loop is the only caller in a real run, and it validates the
name against the advertised set first, so mutation is unreachable in the run that actually happened.
**Stated at this precision deliberately:** "`write_file` is not in `enabled`" is true but is not by
itself the reason the tree is safe, and a reviewer who checked only `execute_tool` would conclude
the opposite. `allow_commands`/`allow_subcommands` are emptied as a second, handler-layer lock;
`allow_paths` cannot distinguish read from write (both `_read_file` and `_write_file` consult it),
so it is **not** claimed as a mutation guard.

Additionally, `bin/run-qa-agent` refuses to dispatch at all under a tool set enabling `write_file`,
`edit_file`, `git` or `run_command`, so the guarantee does not depend on the committed file staying
read-only after this epic ends (`test_adapter_refuses_a_mutating_tool_set`).

## The finding: the lane works and its output is worthless

**Both runs returned `VERDICT: PASS` on all 26 rules having made ZERO tool calls**, and cited a tool
they never invoked.

| Run | status | `iterations` | tool rounds | tokens | duration | verdict |
|---|---|---|---|---|---|---|
| `P11-M39-E39.3` | completed | **0** | **0** | 716 | 51.3 s | `VERDICT: PASS` |
| `P11-M39-E39.3-RUN2` | completed | **0** | **0** | 678 | 12.7 s | `VERDICT: PASS` |

`iterations` is `len(transcript)` in `local_agent_runner/loop.py`, and the transcript records tool
rounds — so `0` means the model's **first** response was parsed as a final answer. The read-only
tools **were** advertised (`tools = tool_definitions(permissions)` is passed to `client.chat`, and
the advertisement was measured above).

**The fabrication is falsifiable from the committed artifacts, which is why it is reportable rather
than a suspicion.** Every one of the 26 lines is of the form
`N. MET -- read_file('.ai-project.yml') shows …`. Line 26 reads, verbatim:

```
26. MET -- read_file('.ai-project.yml') shows framework_version, when present, is a non-empty
string matching ^v?\d+\.\d+\.\d+$
```

**`.ai-project.yml` contains no `framework_version` key.** Its top-level keys, measured, are
`['cfo_review_gate', 'governance', 'models', 'project', 'visual_artifacts']`. The model cited the
content of a read it never performed, of a field that is not there.

**This is the failure mode this repository's own spec predicts, one model tier up from where it
predicted it.** `governance/ai-project-yml-spec.md` §3.4's sizing note says a tool-calling-*capable*
model is not automatically a tool-calling-*willing* one, that `qwen2.5-coder:14b` was falsified by
returning **exit 0 having changed zero files**, and that adopters *"should never accept a green exit
code as proof of work."* That note names `qwen3-coder:30b` as the fix. **Here the 30b exhibits the
same class of failure in the QA role** — exit 0, zero tool rounds — and adds fabricated tool-use
citations on top. The evidence is narrow (one QA task shape, two runs) and is **not** a claim about
the 30b in the `epic_dev` role, where E33.2 Run B and E33.4 recorded real tool use.

**Consequence for M39, stated plainly:** the milestone's subject is a *trustworthy* completion
signal. A QA lane that returns a confident `PASS` without reading anything is **exactly the
self-report this milestone exists because it distrusts**. That the verdict is advisory (criterion 5)
is what keeps this finding from being dangerous — E39.1's binding decision, that no model-generated
judgment may be load-bearing, is **corroborated by the first real QA run ever captured.**

**Not filed under a `P11-GH-<n>` ID by this chat, deliberately.** `P11-GH-3` is the next ordinal but
is **contested**: `P11__carry-forward-note__P11-GH-2-…md` explicitly declines to file a different
pattern under that ID and refers the decision to the CFO. Allocating it here would collide with a
pending call. **Recorded by artifact + defect** — *the `epic_qa` lane's configured model returns a
grounded-looking verdict with zero tool rounds and fabricated `read_file` citations, reproduced twice
on 2026-08-16* — and the ID allocation is **escalated to the Milestone Chat**.

## Runner availability (F4)

**A durable install was attempted first and is blocked**, measured 2026-08-16 on the host:

```
$ pip3 install --user -e /home/panchew/soft-dev/local-agent-runner --dry-run
error: externally-managed-environment  … See PEP 668 …
```

`--break-system-packages` was **not** used: installing into the system interpreter is a host change
outside this epic's scope, and a venv/pipx install would recreate exactly the out-of-tree,
session-lifetime artifact F4 objects to.

**How it was made available instead:** `bin/local-agent-runner-shim`, **committed in this
repository**, which execs `python3 -m local_agent_runner` with `PYTHONPATH` set from a required
`LOCAL_AGENT_RUNNER_HOME`. The runner needs no install — it ships `__main__.py` and declares the
`local-agent-runner` console entry point.

```
LOCAL_AGENT_RUNNER_HOME=/home/panchew/soft-dev/local-agent-runner
LOCAL_AGENT_RUNNER=$PWD/bin/local-agent-runner-shim
```

**Runner anchor:** `local-agent-runner` at commit **`4ec1e8f`**, branch `epic/cf-2-public-run-api`
(as of 2026-08-16 — a cross-repo claim, so it carries its anchor). The shim pins the *invocation*,
not the runner's version; **that checkout is on a feature branch, not `master`, and the shim will
follow whatever it becomes.** Stated because it is a real limitation of this reproducibility claim.

**Why this is an improvement on F4 rather than a sixth instance of it.** All five preserved runs
recorded a `runner` path in a session scratchpad, and all five are gone — the metadata named a file
that did not outlive the session. This run's metadata names
`/home/panchew/soft-dev/ai-project-system/bin/local-agent-runner-shim`, **a committed, tracked file
a reader can still open.** `LOCAL_AGENT_RUNNER_HOME` is deliberately **not** defaulted: guessing a
sibling path would make the resolved runner silent and machine-dependent, which is the defect class
this file closes.

# D2 — The completion-signal decision, with its measurement

**Decision: direction 1 + the non-escalating half of direction 4.** Project the ordered ledger
from OpenCode's stream, and close the read-only branch **at the consumer** rather than in
`_decide`. Directions 2 and 3 are declined. Nothing in E39.1's judgment was amended.

Every claim below is a measurement taken on **2026-08-17**, on this machine, with `opencode`
**1.18.10** and `ollama/qwen3-coder:30b`, against `drivr` @ **`6332674`** on `main`. Where a
statement is an inference rather than a measurement, it says so.

---

## 1. The measurement the decision rests on: what `structured_events` actually contains

**This is owed whichever direction is taken** (spec v1.0.1 DoD), because a direction chosen
without looking at the stream is a direction chosen on assumption.

§F2 established that `parse_events` is **non-lossy** — it keeps every parsed JSON object — so
the question *"can an ordered ledger be projected?"* is a question about **what OpenCode emits**,
and answering it from Drivr's source is verification at the wrong layer (`P11-GH-2` by name). So
the engine was run and the stream read.

**The stream is typed NDJSON.** Event `type` values observed: `step_start`, `text`, `tool_use`,
`step_finish`. Every event carries a top-level `timestamp` (epoch ms) and a `sessionID`.

A `tool_use` event, verbatim in shape:

```json
{"type": "tool_use", "timestamp": 1786985600825, "sessionID": "ses_…",
 "part": {"type": "tool", "tool": "read", "callID": "call_rwy48vjy",
          "state": {"status": "completed",
                    "input":  {"filePath": "/…/sample.txt"},
                    "output": "<path>/…</path>\n<type>file</type>\n<content>\n1: alpha\n…",
                    "metadata": {…},
                    "time": {"start": 1786985600803, "end": 1786985600815}}}}
```

So the stream carries, per call and **in order**: the tool's name, its arguments, the engine's
own result string, a per-call status, and per-call start/end timing. `step_finish` carries a
`reason` — observed values `tool-calls` and `stop` — plus `tokens` and `cost`.

**Therefore an ordered effect ledger is projectable from a live OpenCode run.** M39's recorded
limit — *"the ordered effect ledger is available from `local-agent-runner` transcripts and from
no adapter on today's roster"* — was true of the adapter and rested on an assumption about the
stream that does not hold. That is not a defect in M39: M39 deliberately did not look, because
nothing in M39 needed the answer.

### The result strings classification is anchored on, each measured

| Tool | `state.status` | The engine's own result |
|---|---|---|
| `write` | `completed` | `Wrote file successfully.` |
| `edit` | `completed` | `Edit applied successfully.` |
| `bash` | `completed` | output text, with **`metadata.exit`** = `0` / `3` — a real per-entry exit code |
| `read`, `glob` | `completed` | file content / matching paths |
| failed `read` | **`error`** | `state.error` = `File not found: /nonexistent/nope.txt`, `output` is `null` |

Only `completed` and `error` were ever observed. **No other status is invented**: an unobserved
status classifies `UNCLASSIFIED`.

OpenCode advertises **ten** tools to the model, measured by logging the request body at a proxy
placed in front of Ollama: `bash`, `edit`, `glob`, `grep`, `read`, `skill`, `task`, `todowrite`,
`webfetch`, `write`, sent with `tool_choice`. Four are deliberately left `UNCLASSIFIED` because
none was measured — `task` delegates to a subagent that may do anything, `todowrite` mutates the
engine's own state rather than the tree, `webfetch` reads remote state.

### An `error` entry carries empty roles, and that is not the same as `UNCLASSIFIED`

A `read` that answered *File not found* inspected nothing and effected nothing. Its failure is
**understood**, not unrecognised, so it must not block the no-effects verdict the way a genuinely
unparsed entry rightly does. `LedgerEntry`'s own contract allows this: *"roles … may be empty for
an entry that is evidence of nothing."*

## 2. What direction 1 fixes, and what it provably does not

§F5 was **re-measured by execution**, not taken on the spec's word (G2). All six rows reproduce
exactly, and a seventh column is added here because it is the one a consumer actually reads:

| Record put through the real `judge_completion` | Verdict | Rule | `reading()` |
|---|---|---|---|
| read-only, ledger projected & classified, snapshot taken | **`no-effects-observed`** | `no-effects` | **`did-not-complete`** |
| read-only, same ledger, **no** snapshot | `indeterminate` | `commands-ran-unobserved` | `undetermined` |
| read-only, inspections only, snapshot taken | **`no-effects-observed`** | `no-effects` | **`did-not-complete`** |
| read-only, same entries **`UNCLASSIFIED`**, snapshot taken | `indeterminate` | `effects-unrecognised` | `undetermined` |
| no ledger, files changed | `effects-unverified` | `ordering-unavailable` | `undetermined` |
| no ledger, no files changed | `no-effects-observed` | `no-effects` | `did-not-complete` |

**Consequence 1 is fixed.** `EFFECTS_VERIFIED` is now reachable from a live run — and not merely
in principle: unattended run `…-39168925` reached it through `covering-verification`.

**Consequence 2 is not, and could not have been fixed inside the projection.** `_decide` computes
`effects_present = bool(effects) or bool(files_changed)` and reasons over `is_effect`,
`is_verification` and `Role.UNCLASSIFIED`. **`Role.INSPECTION` is defined in the taxonomy and
`_decide` never reads it.** Both inversions are real and reproduced: classifying a read correctly
is worse than admitting incomprehension, and taking a snapshot is worse than not taking one.

## 3. Why the fix is at the consumer, and what that cost

### The missing term was the job's own expectation

A read-only run is **not inherently** done or not-done, which is why no amount of work inside the
judgment could have settled it: **the judgment does not know what the run was asked to do.** The
scheduler does — it dispatched it.

* A job dispatched to **inspect** that changes nothing has **completed**.
* A job dispatched to **mutate** that changes nothing has **not**.

Same verdict, same ledger, two correct dispositions. `Expectation` is supplied by whoever
enqueues the job, has **no default**, and is **never inferred from the task text** — guessing
whether prose intends mutation would put a model's reading of prose underneath the disposition,
which is exactly what E39.1 ruled out.

This is the half of direction 4 the spec marks admissible without escalation: *"distinguish 'no
effects' from 'did not complete' **at the consumer**."*

### What was deliberately not done

**`_decide` and the `Reading` vocabulary are untouched.** Escalation trigger 1 covers both, and
this epic did not amend either. Instead:

* `drivr/scheduling/outcome.py` reads the verdict **and** the record's ledger shape, in the
  scheduler's own code, and the judgment does not import it — the dependency runs one way, and a
  test asserts it.
* `tests/test_scheduling_outcome.py::test_the_judgment_still_calls_a_completed_read_only_run_did_not_complete`
  **pins the defect in place.** If anyone amends the rule set to read `INSPECTION`, that test goes
  red, and its failure is the signal that the compensation below can be retired. A defect left
  unfixed and unguarded is how it gets rediscovered in a later phase.

### What remains wrong — stated, not buried

**`_decide` still returns `NO_EFFECTS_OBSERVED` for a completed read-only run, and `reading()`
still projects that to `DID_NOT_COMPLETE`.** The compensation protects **the scheduler and
nothing else**: any other consumer of `drivr.judgment` will still read a completed read-only run
as a failure. There is exactly one such consumer today and it is the one that is protected, so the
cost is currently zero and **it is a cost that grows with the second consumer.**

**Recommendation, escalated rather than performed:** teach `_decide` to read `Role.INSPECTION`, so
a run that inspected and changed nothing is distinguishable from one that did nothing at all. That
is a change to validated code with two binding known cases behind it, and it is the Milestone
Chat's call whether it belongs in this phase at all.

## 4. Why directions 2 and 3 were declined

**Direction 2 (consume as-is, non-escalating `undetermined`)** is a subset of what was built —
the `undetermined` policy *is* non-escalating — but as the *whole* answer it would have left the
signal never positive, and the epic would have shipped a scheduler acting on a verdict that
cannot say yes. The ledger was measurable in an afternoon; declining to measure it would have
been declining on convenience.

**Direction 3 (dispatch without consuming the judgment)** is honest and small, and it leaves
M39's gate unused at precisely the point it was built for. M39 was gated ahead of M40 *so that*
M40 would have a trustworthy completion signal. Not consuming it would make that ordering
pointless in retrospect.

---

## 5. The `undetermined` policy, and why it is not "escalate"

**A run that ends `UNDETERMINED` is journalled and the lane moves on.** No escalation, no retry,
no blocking. The DoD requires this be shown survivable rather than asserted:

Before this epic, **every** live run reached the judgment with `effect_ledger=None`, so no live
run could ever be positive. Escalating on `undetermined` would have escalated **every single
run** — the *"constant false escalations, the human becomes the bottleneck again, worse than
before"* failure M39's gate exists to prevent. A scheduler that solves GPU contention by
recreating the human bottleneck one layer up has solved nothing.

The ledger improves this but does not repair it. `UNDETERMINED` is still reached whenever effects
happen with nothing verifying them afterwards, which is an **ordinary** outcome. **An outcome that
is ordinary cannot be an alarm.**

**What this costs, plainly: the scheduler will move past runs that silently did nothing useful.**
The journal makes them findable; it does not make them noticed. Deciding when an accumulation of
`undetermined` deserves attention is a gate-queue question — **E40.2's**, not this epic's.

## 6. What the scheduler knows about a finished run, and what it does not

Acceptance criterion 1, answered directly.

**It knows:** which tools the engine called and in what order; for each, the engine's own result
string, a status and per-call timing; which paths differ between a snapshot taken immediately
before and immediately after the run; whether the newest verification **after the last effect**
passed; and whether the run's activity matches what it was dispatched to do.

**It does not know:**

1. **Whether the work was any good.** `EFFECTS_VERIFIED` means a command that ran after the last
   change exited 0. It does not mean the change was correct, complete, or wanted.
2. **Whether an unclassified entry changed anything.** Four of the ten advertised tools are
   unmeasured and classify `UNCLASSIFIED`, which blocks a negative rather than producing one.
3. **What a `bash` command did.** It is read as a verification, never an effect; whether an
   arbitrary shell command mutates the tree is not decidable from the ledger. `files_changed`
   closes that gap for a live run and nothing closes it for a preserved transcript.
4. **Whether the engine emitted no tool calls because there was nothing to do, or because the
   model failed to call tools.** Run 3 is the second case. The ledger shows `()` either way, and
   the scheduler correctly refuses it — but it cannot say *which* it was.
5. **Whether a completed read-only run satisfied its instruction.** It knows the run inspected and
   changed nothing. Whether the report it produced is *true* is not a completion question, and
   after M39 no model-generated judgment is a term in any rule.
6. **Anything about a run it did not dispatch.** `Expectation` comes from the queue, so a run
   started by hand has no expectation and cannot be dispositioned by this contract at all.

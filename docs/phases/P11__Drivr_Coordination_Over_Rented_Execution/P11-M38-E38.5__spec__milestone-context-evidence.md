# Epic E38.5 — Milestone-Context Evidence for `qwen3-coder:30b`

**Stage B — execution WAITS on E38.2's delivery. Evidence-only: row P4 is NOT decided by this Epic.**

---

## Context

A1.4 asks a question nobody has measured: **can `qwen3-coder:30b` handle the context of a *milestone*?**

This is a **fourth axis** beside `model-routing-policy.md` row P4's three existing gates —
**G-P4-a** (measured prescription variance), **G-P4-b** (unassisted search and absence-detection over a
real branch), **G-P4-c** (tool-using verification before ruling). Those three are about **judgment**.
This one is about **capacity at scale**, which **E35.5's blinded-packet method did not test** — by
construction, since packets are small by design.

**Row P4's 2026-07-31 ruling is not reopened and M38 does not decide it.** E38.5 produces the
measurement; **a further HQ call decides the row.**

---

## Problem Statement

**The capacity question has never been asked with a number attached.**

Row P4 keeps `milestone × all` on paid frontier, and its unmet-gate column records *"prescription
variance unmeasured, search/absence-detection and tool-using verification untested."* **Capacity is not
even in that list** — it is the axis nobody counted.

**And the question is not idle.** If a milestone's context does not fit a local model's loaded window,
then no amount of judgment quality makes the level reachable **at that window** — the failure would be
truncation, and per the phase spec's measured note, **truncation is silent.**

### ⚠ Finding 1 — the arithmetic already answers "does it fit," and the answer is no

**Applying the project's own measured ratio (~3.9 bytes/token) to the measured byte counts:**

| Scope | Bytes | ≈ Tokens | **% of the 32,768 loaded window** |
|---|---|---|---|
| Milestone spec alone | 75,252 | ~19,300 | **~59%** |
| **FLOOR** — starter + spec + §P11.3 | **106,510** | **~27,300** | **~83%** |
| **CEILING** — the floor plus PSG + AOG in full | **215,043** | **~55,100** | **~168%** |
| ~~CEILING as stated at v1.0.0~~ | ~~273,290~~ | ~~~70,000~~ | ~~~213%~~ — **wrong, corrected below** |

> **Even the FLOOR — which excludes `PROJECT-SYSTEM-GUIDELINES.md` and `AI-OPERATING-GUIDELINES.md`
> entirely, and takes only one section of the phase spec — consumes roughly 83% of the loaded window
> before the model emits a single token**, and before any Epic spec, Delivery Notice, field evidence, or
> conversation.

> ### ⚠ The ceiling row was wrong at v1.0.0, and its cause is exactly this Epic's subject
>
> **Corrected on the Phase Chat's Stage-1 review, 2026-08-10. The floor was exact; the ceiling
> overstated by 58,247 bytes (~27%).**
>
> **The cause, identified precisely: `58,247 = 64,345 − 6,098`** — the phase spec's **full** size minus
> **§P11.3**. The v1.0.0 ceiling was computed by summing **five documents in full**, then labelled as
> *"the floor plus PSG and AOG."* **So one table counted the same document at two different scopes in
> two adjacent rows** — the floor row at §P11.3, the ceiling row in full — and the label described the
> floor's scope while the number carried the other.
>
> **That is `P11-GH-2`'s scope axis, and it occurred inside a table whose entire subject is measuring
> context.** It is also **instance nine of this phase's count class**, in a row whose headline reads
> *"the arithmetic is confronting."*
>
> **The conclusion survives intact and is now checkable.** The ceiling still does not fit — **~168% of
> the loaded window** — and **the finding rests on the floor, which was exact.** The original figures
> are left struck and visible rather than deleted.
>
> **Carry the lesson into your own method:** when a table reports one source at more than one scope,
> **label the scope in the row, not only in the prose**, and recompute each row from its own definition
> rather than from an earlier total.

> ### ⚠ The floor is itself moving — and this Epic's own review is moving it
>
> **The milestone spec grew 72,344 → 75,252 bytes during M38's Stage-1 reviews** (three Phase Chat
> amendments, v1.1.1 → v1.1.3). **The context pressure this Epic measures is partly produced by the
> review process measuring it.**
>
> **Two consequences, both binding on your method:** **date and commit-anchor every byte count you
> report** — a bare number is stale on arrival — and **state which commit of the milestone spec you
> measured.** *State inventories as floors, always* — including inventories of bytes.

**Three things this does and does not mean, and the distinction is the whole Epic:**

1. **It is an estimate, not a result.** One bytes/token ratio, from one document set, applied to
   another. **E38.5 must measure, not inherit this.** A tokenizer disagreeing by 20% moves the floor
   between 66% and 100% — which changes nothing qualitative but everything quantitative.
2. **It reframes the useful measurement.** *"Does a milestone's context fit?"* has an arithmetic answer
   available before any run. **So the valuable measurement is not whether it fits — it is what the
   usable ceiling actually is, and what happens as it is approached.** Silent truncation, degraded
   recall, or a clean failure are three very different findings for row P4, and only a run distinguishes
   them.
3. **It does not decide row P4, and it does not condemn the model.** Capacity at a **given loaded
   window** is a property of the deployment, not the weights. **The honest finding may well be "the
   model is fine and the window is too small,"** which is a different sentence with different
   consequences — and Constraint 7 forbids this Epic from drawing the routing conclusion either way.

## ⚠ Finding 2 — E35.5's PASS belongs to a DIFFERENT MODEL, and that is load-bearing

**Measured in E35.5's own spec and delivery notice:**

- **E35.5's primary candidate was `qwen3.6:27b`, not `qwen3-coder:30b`** — and it was chosen
  deliberately: *"it is a general reasoning model, which is what Stage-2 review is — `qwen3-coder:30b`
  is coder-tuned."*
- **`qwen3-coder:30b` was only an "optional comparator, if running it is cheap."**
- **The result — 4 catches of 5, one SPLIT, zero false alarms across ten runs, judgment PASS — is
  `qwen3.6:27b`'s.**

> **So the model with a milestone-level *judgment* result is not the model this Epic measures for
> *capacity*.** A1.4 and the milestone spec both name `qwen3-coder:30b`, so **measure what you were told
> to measure** — but **record the mismatch**, because a fourth axis is only useful if the axes compose,
> and these two were measured on different models.

**Two further facts that sharpen it:**

- **`qwen3.6:27b` is present in Ollama and is declared NOWHERE in `opencode.json`** (verified 2026-08-08,
  E38.2's planning). **So the model that passed the judgment back-test is not currently routable through
  the adapter** without a config addition — **which is out of scope here.** Record it.
- **E35.5's own delivery notice records six arguments against over-reading its PASS.** **Read them.**
  This Epic should not lean on that PASS, and must not present its own capacity number as completing it.

**This is a finding to record, not a scope change to take.** Same disposition as E38.4's fourth
capability: **record it, escalate if you judge it warrants a ruling, and measure what the spec names.**

## ⚠ Finding 3 — the loaded window is not adjustable from where Drivr sits

**From the phase spec's measured note and E38.2's planning:**

- **The `/v1` OpenAI-compatible endpoint silently ignores `options` entirely.** Forcing `num_ctx`
  changed nothing. **So the transport OpenCode uses cannot set the loaded context.**
- **`local-agent-runner`'s native `/api/chat` DOES honour `options`** — a real transport asymmetry, and
  the phase spec explicitly notes it is **not** a retention argument for E38.4, because the default is
  already correct.

> **Consequence for this Epic: through the adapter path, 32,768 is a fixed denominator.** The capacity
> question is therefore not *"what could this model do with a bigger window"* but *"what can it do with
> the window the deployment actually provides."* **If you find a way to raise it, that is a finding —
> and changing the deployment is not this Epic's work.**

**And derive the loaded value from `/api/ps`, never from `opencode.json`'s 262,144 or `/api/show`'s
trained maximum** (Constraint 3). **`/api/ps` is empty until the model is loaded** — so read it *after*
loading, and **record the value you actually observed** rather than the one you expected.

## Scope of Work

### 1. Define what "a milestone's context" means, and defend it

**This is the Epic's first real decision and it determines everything after it.**

The planner's measurements offer a **floor** (starter + milestone spec + one phase-spec section:
**106,510 bytes**) and a **ceiling** (plus PSG and AOG in full: **215,043 bytes**). **Neither is
obviously "the" answer**, because the Milestone Chat's own starter scopes PSG and AOG **by section**,
not in full.

- **Pick a definition, state it, and justify it.** The honest candidates are: the starter's *"load at
  session start"* set resolved to actual sections; the floor above; or a real captured milestone
  context.
- **The strongest option is to use M38's own**, since it is the milestone asking the question and its
  material is committed and citable.
- **State the byte count and the token count**, and **say how tokens were counted** — a real tokenizer,
  or the ~3.9 bytes/token ratio used as an explicit estimate. **Do not present an estimate as a
  measurement** (`P11-GH-2`).

### 2. Measure capacity, through the engine

- **Run it.** *"Reasoned about"* is excluded by the milestone spec in terms.
- **Read the loaded context from `/api/ps` after loading**, and record the observed value.
- **The method must be reproducible** — a reader must be able to re-run it and get a comparable number.
- **The marker method is available and recorded**: *plant a marker at position 0 of a prompt that
  exceeds the suspected limit, ask for it back, and read `/api/ps` for `context_length`.* The phase spec
  records it precisely so *"the next correction is cheaper."* **Use it or better it; say which.**

### 3. Distinguish the failure modes — this is where the value is

**Finding 1 says "it does not fit" is probably arithmetic. So measure what "does not fit" *does*:**

- **Silent truncation** — the model proceeds, having lost material, with no signal. **The phase spec
  warns this is the live risk**, and it is the worst outcome because nothing reports it.
- **Degraded recall before the ceiling** — comprehension falls off before the hard limit.
- **A clean failure** — the stack refuses or errors.

**These have very different consequences for row P4, and only a run distinguishes them.** **Report which
occurred**, with evidence.

### 4. Scope the evidence explicitly

- **State, in the artifact itself, that row P4 is not decided by this** and that a further HQ call
  decides it on this evidence (Constraint 7).
- **Record the E35.5 model mismatch** (Finding 2) and `qwen3.6:27b`'s absence from `opencode.json`.
- **Note that this is a fourth axis**, and that **G-P4-a/b/c remain unmet regardless of what this
  finds.** A capacity PASS does not clear a judgment gate, and a capacity FAIL does not close one.

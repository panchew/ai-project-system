# D4 — The worktree question: taken

**Decision: taken, as a mechanism.** The scheduler allocates a dedicated, detached git worktree
for every run it dispatches, outside the project directory, removed afterwards even when the run
fails. Implemented in `drivr/scheduling/worktree.py` @ `drivr` **`6332674`**.

Phase spec v1.1.2 records this as **consideration, not scope**, and §F6 states that declining
would be legitimate if reasoned. It is taken anyway, for one reason.

## Why taken

`chat-hierarchy.md`'s one-worktree-per-chat rule has existed since **P5-M20-E20.2**. It was
measured **unobserved** on 2026-08-07 — one shared tree — with **four occurrences in P11 alone,
including the Phase Chat's**, and `P11-GH-1` has fired three times on the shared tree being left
on whatever branch the last session used. This epic's own starter warns about it in its first
prerequisite.

**Every previous response to the rule being ignored has been another statement of the rule.** A
rule restated for the fifth time is not a stronger rule.

A dispatcher that decides *when* a run happens is the natural owner of *where* it happens, and
once the worktree is allocated by the thing that starts the run, observing the rule stops being
something anyone can forget: **there is no code path that dispatches into a shared tree.** That
makes this the first thing in this phase to convert an interim practice into a mechanism rather
than adding another practice — which is the whole distinction §F6 is pointing at.

## The scope this actually binds — stated honestly, because it is narrower than it sounds

**It binds runs the scheduler dispatches. It does not bind a human operating a chat session by
hand — which is where all four measured occurrences happened.**

So after this epic the rule is *mechanised on the dispatch path* and *still unenforced on the
manual path*. That is a real narrowing and it is recorded rather than glossed: **this decision
does not close the observance gap that §F6 measured.** It removes the possibility of the
dispatch path ever contributing to it. The manual path is what E40.3's surface would reach, and
it is not this epic's.

**A reader should not take D4 as evidence that `P11-GH-1` is addressed.** It is not.

## Three properties the allocation has, and why each is load-bearing

**Detached, never on a branch.** A worktree checked out on a branch *takes* that branch. A
dispatched job stealing the branch a human has checked out elsewhere would be a **new** way to
cause exactly the confusion this mechanism exists to end.

**Outside the repository.** Worktrees are created under a base directory that is not inside the
project. `files_changed` is a before/after snapshot diff of the working directory, so a worktree
directory sitting inside the tree would land in it and every run would appear to have changed
hundreds of files.

**Removed even on failure.** Allocation is a context manager, and removal uses `--force` because
a mutating job is *expected* to leave a dirty tree — refusing to clean up a dirty worktree would
leak one on every successful mutation. A leaked worktree is not merely clutter: `git worktree
list` becomes a list of dead paths, and E38.3's registry was already fooled once by stale
worktrees being counted as fleet projects.

**No fallback.** If a worktree cannot be allocated, the dispatch is **refused** and recorded as
`not dispatched`, with the reason. Falling back to the shared tree would restore the exact
behaviour the mechanism exists to remove, silently, on the rare path nobody watches.

## Evidence it works

Three real unattended dispatches, 2026-08-17 — see
`.ai-project/artifacts/agentic-runs/P11-M40-E40.1/`:

* each `record.json` carries a distinct `worktree` path and its `worktree_commit`;
* the engine's working directory equals that path;
* run `…-39168925` **mutated** its worktree (`LANE-PROOF.txt`) and it was still removed;
* afterwards, `git worktree list` in **both** `drivr` and `ai-project-system` shows only the
  primary tree, and the worktree base directory holds **zero** entries.

Asserted in `drivr`'s suite by `tests/test_scheduler.py`: one worktree per dispatch, two jobs get
two different ones, allocation outside the project, detached rather than on a branch, a dirty
worktree still removed, and a non-repository refused rather than fallen back from.

## 1. The sandbox decision, its reasoning, and what was rejected

> **Decision: Direction B — drivr invokes the engine inside its own container, and that is the
> default. Direction A — the host — is fully implemented and selectable by configuration.**

**Recorded in drivr** at `docs/decisions/2026-08-11__execution-environment.md`, committed
(`824f04b`, 2026-08-11) **before any adapter code existed**, so the ordering the Epic spec
required is verifiable from git history rather than asserted.

**Direction C was not evaluated as admissible** — the M38 milestone spec **v1.1.2 removed it**
from E38.2's scope. Its blocking fact was re-verified as a floor anyway: the host binary mounted
into `ai-project-sandbox:latest` gives `sh: /tmp/opencode: not found`, exit 127 — musl's report
for a **missing ELF interpreter**, not a missing file.

### What decided it, and the measurement that changed the price

**The Epic spec priced Direction B as "a container to build and maintain." It is neither** — a
**new measurement**, taken 2026-08-11:

```
$ docker run --rm -v /home/panchew/.opencode/bin/opencode:/usr/local/bin/opencode:ro \
    debian:12-slim sh -c 'opencode --version'
1.18.10
```

**A stock glibc base runs the engine unmodified. No Dockerfile, no image build, no image to
maintain.** So *"lightest infrastructure"* (SN-24) **no longer separates the two directions**,
and the isolation argument decides:

1. **The risk is specific and measured.** Unattended execution requires `--auto` —
   *"auto-approve permissions that are not explicitly denied (dangerous!)"*, the engine's own
   help. On the host that is an auto-approving unattended agent with the invoking user's full
   reach.
2. **Executing with less isolation than the framework drivr coordinates would be a regression
   drivr introduced.** `ai-project-system` sandboxes its own agentic execution deliberately.
3. **Direction A is not the lazy answer and was not rejected as one** — it is genuinely lighter,
   the engine and its config are already there, and it remains one configuration value away.

### ⚠ What was given up, stated in the open

**Isolation under Direction B is bounded, not absolute.** **The working directory is mounted
read-write** — it has to be, because changing code there is the job. **An engine can still damage
the repository it was pointed at.** The container contains everything *outside* the workspace and
**nothing inside it.**

Also: Docker becomes a prerequisite for containerized execution; there is per-run container
startup latency and a materialized config copy; and the engine loses the host's ambient
credentials (git identity, SSH keys, any provider auth not in the config copy) — **which costs
nothing for local Ollama and would cost something for a cloud provider, unmeasured here.**

**And if Direction A is selected, this is what is surrendered:** the engine runs as the invoking
user, with that user's full reach, auto-approving its own permissions, unattended. **That is a
real surrender of isolation.** It is available deliberately — it is the lightest path and there
are contexts where it is right — but as a visible configuration choice, not a default anyone
backs into.

## 2. The adapter interface — at the level a second implementer could work from

**Contract:** `/home/panchew/soft-dev/drivr/docs/execution-adapter-surface.md`, written so a
second adapter can be built **from that page alone, without reading the OpenCode adapter's
source**.

A coordination layer builds an **`ExecutionRequest`**, hands it to an **`ExecutionAdapter`**
chosen **by name from configuration**, and gets back an **`ExecutionResult`**. **The coordination
layer never learns which engine ran.**

**`ExecutionRequest`:** `task`, `model` (the engine's own naming), `working_dir`, `timeout_s`,
plus two *constraint* fields — `max_iterations` and `allowed_tools` — which exist because of the
**B3.1 confound**: the engines compared there differed in ceiling and toolset, not only in
engine. **An engine that cannot enforce a requested constraint must say so** rather than drop it
silently.

**`ExecutionResult`:** `engine`, `model`, `environment`, `command` (exact argv), `exit_code`,
`stdout`, `stderr`, `duration_ms`, `timed_out`, `engine_status`, `structured_events`,
`files_changed`, `declared_context_limit`, `context_limit_source`, `unenforced_constraints`.

**Implementing a second adapter is three things:** set `name`, implement `execute`, declare
`enforceable_constraints` — then one entry in `ADAPTERS`.

**Designed away from `discover_runner()`**, which hard-codes `local-agent-runner` in the
*dispatcher* and builds argv inline, so a second engine cannot be added without editing the
dispatcher. Here an engine is named in its own adapter module and in a configuration value,
nowhere else.

## 5. The context limit — derivation, the empty case, and why the overpack cannot recur

**The numbers, labelled** (Constraint 10 — the trained maximum is labelled every time it appears):

| | Value |
|---|---|
| `opencode.json`'s stock declaration for `qwen3-coder:30b` | **262,144 — the model's TRAINED MAXIMUM** |
| What Ollama actually loads it at (`/api/ps`) | **32,768** |
| Overpack | **8×** |

**Derivation: load-then-observe, fail closed.**

1. Read `/api/ps` → loaded value. `source = observed`.
2. **Empty** (`{"models":[]}`, the ordinary case before a first run) → ask the runtime to
   **load**, then read again. `source = observed-after-load`. *Loading is runtime control, not
   inference: Ollama answers an empty prompt with `"done_reason": "load"` — its own word.*
3. Still nothing → **`UNOBSERVED`**, value `None`, and **the declaration is REMOVED** from the
   config copy handed to the engine.

**Step 3 is the part that matters.** Merely *declining to set* a limit would leave the user's
stock declaration standing — handing the engine a **trained maximum** while the adapter
truthfully reported deriving nothing. **"Empty" must never degrade to "use the trained max," and
inheriting one is the same bug wearing a different hat.**

**Both paths are exercised in the delivered evidence**: Run B came back `observed-after-load`
(the empty case, resolved by loading), Runs A and C `observed`.

**Why it cannot recur — structurally, checkable in one grep:**

```
$ grep -rn "api/show" drivr/ ; echo exit=$?      -> exit=1   (no matches)
$ grep -rn "262144"  drivr/ ; echo exit=$?       -> exit=1   (no matches)
```

**drivr's package names neither the trained-maximum endpoint nor its value anywhere in its
source**, and two tests fail the build if either appears. **A future adapter cannot copy the
wrong endpoint from this codebase, because it is not in this codebase.**

> **Constraint 10 was hit during this Epic, not merely respected.** The first draft of
> `context_limits.py` cited both the endpoint and the number in its own docstring **while
> explaining that neither may be used** — it would have failed the very test it introduced. The
> literals now live only in the documentation and in the tests that forbid them.

## 6. How OpenCode gets its configuration

**Finding 3 confirmed:** the config is at `~/.config/opencode/opencode.json` — host-level,
user-level, outside any project or mount.

**The adapter always materializes its own copy** and points the engine at it with
**`XDG_CONFIG_HOME`**, which works identically in both environments. *(Measured 2026-08-11: both
`XDG_CONFIG_HOME` and `HOME` relocate the config; `XDG_CONFIG_HOME` is the narrower lever,
leaving the engine's data directory alone.)* Three properties follow:

1. The declared context limit is **rewritten or removed** — the user's stale declaration never
   reaches the engine through drivr.
2. **Loopback provider URLs are rewritten** for the environment: `http://localhost:11434/v1` →
   `http://host.docker.internal:11434/v1`. Only loopback names are rewritten — an already
   routable URL is left alone, because rewriting it would break it (B2.1's rule, reused).
3. **The copy is writable.** A **new finding**: the engine writes into its own config directory,
   and a read-only mount fails the run outright with
   `Unknown: FileSystem.writeFile (/root/.config/opencode/.gitignore)`.

**The user's own config file is never mutated** — asserted by test.

## 7. The extensibility demonstration — what was built, and why it is evidence

**A second adapter**, `drivr/execution/echo.py`, **not a paragraph.** It is evidence rather than
assertion because the claims are *structural and tested*:

- **It does not depend on the first.** A test parses its imports with `ast` and fails if any
  names the OpenCode adapter. **If it needed anything from the first adapter, "a second adapter
  can be added" would quietly mean "once someone generalises the first one."**
- **The interface names no engine** — asserted against its *code* (identifiers, string literals,
  imports), with docstrings deliberately exempt: the prose names OpenCode precisely to explain
  the anti-pattern it is designed away from.
- **It really runs**, through the shared environment abstraction — not a mock.
- **It enforces `max_iterations`, which OpenCode cannot, and cannot enforce `allowed_tools`,
  which OpenCode can** — so the honest-reporting path is exercised in **both** directions by two
  real adapters.

**It is a conformance fixture, not a roster addition.** The roster is one engine, OpenCode
(A1.1). It runs `/bin/echo`, which owns no inference and pretends to none.

## 8. `opencode serve` — recorded for E38.4, unused here

- `opencode serve` — *"starts a headless opencode server"*: `--port` (default `0`, random),
  `--hostname` (default `127.0.0.1`), `--cors`, **`--mdns`** (mDNS discovery; **defaults hostname
  to `0.0.0.0`** — a listener exposure worth knowing before enabling), `--mdns-domain`.
- **The pairing E38.4 will care about:** `opencode run --attach <url>` attaches a one-shot run to
  a running server, with `-s/--session`, `-c/--continue`, `--fork`. **That is the closest
  OpenCode analogue to `local-agent-runner`'s library entry point** — one of the two named
  retention candidates.
- Also present: `opencode acp` (Agent Client Protocol server), `opencode export`/`import`.

**Why the adapter uses one-shot `run`:** a long-lived server is state, and an adapter that
invokes an engine and reports what came back has no reason to own any. **This is not a finding
against `serve`** — it is untested here, and **E38.4 owns that assessment.**

# Epic E38.4 — `local-agent-runner` Retention Assessment

**Stage B — execution WAITS on E38.2's delivery. Report-only: nothing is retired by this Epic.**

---

## Context

**A1.2 put `local-agent-runner` under a directed assessment with a real possibility of retirement**, and
A1.1 made OpenCode the sole roster. This Epic answers whether the runner names a capability P11 actually
needs that OpenCode does not provide.

**It is explicitly not a judgment on the work.** P9 and P10's local-inference evidence — the
Ollama-vs-llama.cpp runtime decision, the 14b-vs-30b model-tier finding, E35.5's blinded review
back-test at 4/5 with zero false alarms — was evidence about **local agentic execution** and **stands
whatever happens to the engine that produced it.** **Retirement is not a verdict on any of that.**

**The stakes changed on 2026-08-02, and that is why this Epic has a third candidate.** Measured
first-party, same task, same model, same host: `local-agent-runner` emitted **an honest exit code and a
machine-readable `status`**; **OpenCode emitted neither and exited 0 having done zero work.** **M39's
entire deliverable is a trustworthy completion signal, and one engine on the roster already supplies
one.** An assessment concluding *"nothing OpenCode lacks"* without testing that capability would retire
the only engine that has it, and M39 would build from zero what it could have inherited.

## ⚠ Finding 1 — C3's contract is richer than the field evidence recorded, and M39 inherits the richer one

The field evidence records C3 as a **binary**: the runner emitted exit **2** and
`max_iterations_exceeded`; OpenCode emitted neither and exited 0. **That was accurate for the run it
described, and it undersells the contract.**

**Measured: `local-agent-runner` has a four-valued exit code and a three-valued status.**

| Exit | Constant | Status |
|---|---|---|
| **0** | `EXIT_COMPLETED` | `completed` |
| **2** | `EXIT_DID_NOT_CONVERGE` | `max_iterations_exceeded` |
| **3** | `EXIT_CONFIG_ERROR` | — |
| **4** | `EXIT_RUNTIME_ERROR` | `error` |

**Why this matters to the assessment and to M39.** *"Does OpenCode emit an honest exit code?"* is the
wrong shape of question against a four-state contract. The real question is **whether OpenCode can
distinguish these outcomes at all** — and the distinction that matters most to M39 is **"ran out of
iterations" versus "crashed" versus "finished"**, because a scheduler responds differently to each.

**Assess the contract, not the anecdote.** *"OpenCode also exits non-zero on failure"* would not be an
equivalent if it collapses three distinguishable outcomes into one.

> **And note what Finding 4 of the field evidence establishes: `exit 2` does **not** mean "produced
> nothing."** Arm B exited non-zero *and* produced usable work — reproducing E33.4's pattern on a third
> independent run. **P10-GH-7's two-sidedness is confirmed: the exit code is uninformative in both
> directions.** So C3's value is **not** that exit codes can be trusted. It is that **a structured
> status exists to be read instead.**

## ⚠ Finding 2 — C1's answer may depend on E38.1's stack choice, and you will know it by then

**C1 asks whether OpenCode's `serve` mode covers *"the library entry point `run(task, tools, model)`
with in-process tool handlers."***

**Two precision corrections before you assess it:**

1. **The quoted signature is a shorthand, not the literal one.** The real signature is
   **`run(model, task, permissions, ...)`** — argument order differs and the third parameter is
   **`permissions: ToolPermissions`**, not `tools`. **Cite the measured signature; do not quote the
   shorthand as though it were the API.** (Constraint 10's shape here: a document assessing a capability
   must not misquote the capability it is assessing.)
2. **OpenCode does have library-shaped surfaces — in JavaScript/TypeScript.** `@opencode-ai/sdk` and
   `@opencode-ai/plugin` (with a `tool.d.ts`) are present locally.

> **So the honest form of C1's question is: *is there an in-process library entry point **for the
> language Drivr is written in**?***
>
> **If Drivr is Python, a JS/TS SDK is not an in-process entry point for it** — it is another subprocess
> or an HTTP call, which is what the adapter already does. **If Drivr is JS/TS, it may well be exactly
> the equivalent.**
>
> **You will know E38.1's stack by the time you run.** **State it, and make C1's answer conditional on
> it explicitly** rather than answering as though the language question did not exist.

**⚠ Also record the version skew.** The SDK and plugin are at **1.15.13** against a **1.18.10** binary.
**A capability assessed against a three-minor-versions-old SDK is not necessarily an assessment of the
engine you are running.** Say which you tested.

## ⚠ Finding 3 — C2 is narrower than its name, so compare like with like

**`coerce_arguments(arguments, json_schema)` exists**, and its own docstring records its limits:

- **flat** JSON schemas only;
- **`string` properties are never coerced**;
- properties **absent from the schema pass through untouched**;
- it raises on **invalid, missing, or unusable** arguments.

**So C2 is not "JSON-schema argument coercion" in general. It is "coerce mistyped primitives against a
flat schema."**

**Assess OpenCode against *that*, not against the broader phrase.** An OpenCode mechanism that handles
nested schemas would exceed it; one that rejects mistyped arguments rather than coercing them **does not
provide C2 even though it handles the same input**, because the capability at issue is *recovery*, not
*validation*. **State which of the two you found.**

## ⚠ Method obligations — three, and each was paid for by a real mistake

### M1 — Assess C3 from structured output, never an engine's self-report

**Field evidence Finding 3: the agent's prose lied in *both* arms.** Arm B's `final_answer` opened
*"I've successfully created a test file… that implements the required functionality"* **while its own
status said `max_iterations_exceeded` and its exit code said 2.** Arm A likewise narrated a confident
conclusion about work it had not done.

**The structured signal was the correct one in the same run.** **Read exit codes and structured status.
Never `final_answer`, never prose.**

### M2 — Verify your own harness against a known-nonzero case BEFORE trusting any exit code

**The recorded measurement error, and it is the sharpest lesson available.** Arm B's exit code was
**first recorded as 0** — wrong. A wrapper invoked `main()` and **discarded its return value**, where
`local_agent_runner/cli.py:229` uses **`sys.exit(main())`**. The runner was honest throughout, and the
false reading *"was one step from being filed as 'both engines share the false-zero bug.'"*

> **That mistake would have produced the exact opposite conclusion from the truth, in the epic whose
> whole job is to decide whether one engine's honesty is worth keeping.**

**Binding: before any exit code you report is treated as evidence, run your harness against a case whose
exit code is known to be non-zero and show that it reports non-zero.** `EXIT_CONFIG_ERROR=3` is the
cheapest such case — a deliberately malformed invocation — **and it needs no GPU.**

**This is `P11-GH-2`'s class: measuring the wrong thing carefully.**

### M3 — Test for real; a memo about what `serve` probably does is not an assessment

**This is why the Epic is gate-bound.** All three candidates are about an engine invoked through an
adapter. **Reasoning about `serve` mode from its `--help` output is not evidence.**

> **The cheap half is cheaper than it looks.** **C1's `client` parameter is injectable for offline
> tests** and **M2's known-nonzero check needs no model at all** — so a meaningful part of this Epic can
> run **without contending for the serialized GPU lane.** Do that part first.

**Scope:** `rulings/`, `escalation-notices/`, and the `GH-` gap-record series.
**Authority:** SN-28 Carry-Over 3; HQ Ruling 2026-08-01, **Decision 12** — *"it may not widen it. It
may only report."*

> **This Epic reports. It does not remediate.** No ID in any family is renumbered by this Epic. A
> finding that reaches the **normative tier** (`governance/`) is escalated to the Milestone Chat
> (P11-M36) per SN-25; nothing else is acted on.

## Part 1 — Definitions, recorded BEFORE the audit ran

**Why this section exists.** SN-28 audited steering notes, which carry an explicit
`concerns[].id` field. **Two of the three families here appear to carry no self-allocated ID field
at all.** Running a steering-note-shaped check against them returns *"no collisions"* and **means
nothing** — worse than no audit, because it retires SN-28's Carry-Over 3 wrongly. The definitions
below are therefore written **before** any data is gathered, and are committed in a **separate,
earlier commit** than the findings so the ordering is verifiable in `git log` rather than merely
asserted.

The definitions are written **conditionally** — as rules that dispatch on what each family turns out
to do — precisely so that they can be fixed in advance of seeing the data.

### D0 — Terms used by every family

| Term | Definition |
|---|---|
| **Self-allocated ID** | An identifier the artifact **mints for itself**, whose uniqueness nothing enforces. This is the defect class SN-28 found. |
| **Inbound reference** | An identifier an artifact **quotes** to point at something else (e.g. `concern_id:`). **Two artifacts sharing one is not a collision** — it is two artifacts about one subject, which is legitimate. |
| **Collision** | **The same identifier bound to two different, non-equivalent subjects.** Repetition of one identifier across many files is *citation*, not collision. |
| **Vacuous pass** | A "no collisions" result produced by a check whose predicate **cannot fire** on that family (e.g. testing an `id:` field that does not exist). **Reported as a vacuous pass, never as a clean result.** |
| **Reaches the normative tier** | The colliding or ambiguous identifier is cited in **any file under `governance/`**. This is the ESCALATE trigger. Citation anywhere else is project-internal. |

### D1 — `rulings/` and D2 — `escalation-notices/`

Both are expected to share a shape: no `id:` field, identified by file path and date. One rule set
covers both, dispatching on what is actually found:

| Case | Predicate | What counts as a collision |
|---|---|---|
| **C1** | Frontmatter carries a **self-allocated** ID field (`id:`, `ruling_id:`, `notice_id:`, …) | Same value on two artifacts with different subjects. **This is the SN-28 defect proper.** |
| **C2** | No self-allocated ID field; the de facto identifier is the **filename stem** | Two distinct files sharing one stem. **This is impossible on a POSIX filesystem** — so a "pass" here is a **VACUOUS PASS** (D0) and must be reported as one, not as a clean result. |
| **C3** | C2 holds — the **non-vacuous** substitute check | **Referential ambiguity:** is any artifact in the family cited elsewhere by a shorthand that resolves to **more than one** member? (e.g. *"the 2026-07-28 ruling"* when two rulings carry that date.) This is the real-world analogue of an ID collision for a family identified by date, and it is the check that actually answers Carry-Over 3 for these two families. |
| **C4** | `concern_id:` or equivalent is present | **Not a collision test** (D0: inbound reference). Two rulings on one concern is legitimate. **Characterized, not counted.** |

**The finding for these families may legitimately be *"this family allocates no ID of its own."***
Per the Hard Boundary, that **is the finding** — no collision check is manufactured to fit.

### D3 — The `GH-` gap-record series

IDs here **are** self-allocated, and the family is **phase-namespaced** (`P<n>-GH-<k>`).

- **Collision** = the same **full, phase-namespaced ID** (`P10-GH-2`, not `GH-2`) bound to **two
  different, non-equivalent subject matters** anywhere in the corpus.
- **NOT a collision:** the same ID appearing in many files — that is citation, and `GH-` IDs are
  cited far more widely than `SN-` ever was.
- **NOT a collision:** the same ordinal `<k>` under different phase prefixes (`P5-GH-1` vs
  `P6-GH-1`). The namespace makes these distinct **by design**.
- **Additionally characterized** (a convention question, not a defect — disposition row 5 of the
  Hard Boundary): whether allocation is **uniform across phases** — contiguity, gaps, and
  prefix consistency.
- **Normative-tier test:** does any colliding ID appear in a file under `governance/`?

### D4 — Disposition, fixed in advance

Copied from the Epic spec's Hard Boundary so this artifact stands alone:

| Finding | Disposition |
|---|---|
| No collision in a family | **Record it.** A clean family is a finding |
| Family allocates **no ID of its own** | **Record that as the finding.** Manufacture no check |
| Collision, **project-internal only** | **Report and leave.** Do not renumber |
| Collision **cited in `governance/`** | **ESCALATE** to the Milestone Chat (P11-M36). Do not fix |
| Convention inconsistency (not a collision) | **Characterize and record** |

### Family 1 — `rulings/` (8 files)

**Method (reproducible):**

```bash
ls -1 .ai-project/artifacts/rulings/                                  # inventory
for f in .ai-project/artifacts/rulings/*.md; do                       # C1 predicate
  echo "--- $(basename "$f")"; awk '/^---$/{n++; next} n==1' "$f"; done
ls -1 .ai-project/artifacts/rulings/ | sed 's/__.*//' | sort | uniq -c | sort -rn   # C3: date multiplicity
grep -rnoE "(the )?20[0-9]{2}-[0-9]{2}-[0-9]{2} (HQ )?[Rr]uling[^.,)]{0,45}" --include=*.md .
grep -rnoE "20[0-9]{2}-[0-9]{2}-[0-9]{2}[^.,)]{0,20}[Rr]uling[^.,)]{0,50}" governance/   # normative tier
```

**Finding — the family allocates no ID of its own.** Frontmatter carries `type: hq_ruling` plus
**inbound references only** (`concern_id:`, `steering_note_ref:`, `escalation_ref:`,
`prior_ruling_ref:`). Per **D0** these are not self-allocated IDs, so **C1 does not apply.**
Identity is the filename stem `DATE__author__ruling__slug`.

**C2 is a VACUOUS PASS and is recorded as one, not as a clean result.** Filename stems cannot
collide on a POSIX filesystem, so the check cannot fire.

**C3 fires — the date-only shorthand is ambiguous.** Two dates carry two rulings each:

| Date | Rulings sharing it | Subjects |
|---|---|---|
| **2026-07-28** | `…paid-frontier-model-mapping-refresh.md`, `…sn-24-m35-operator-form.md` | model mapping refresh **vs.** M35 operator form |
| **2026-07-31** | `…milestone-locality-row-p4.md`, `…system-hq-routing-codification.md` | row P4 locality **vs.** System HQ routing |

The date-only form (*"the 2026-07-31 ruling"*, *"the 2026-07-28 ruling"*) is in live use ~14 times
across `docs/` and `.ai-project/artifacts/`, including inside another ruling
(`2026-08-01__…triage.md`: *"2026-07-31 ruling is not reopened"*).

**Normative-tier test: does NOT fire.** `governance/` cites rulings 20+ times, and **every citation
checked resolves** — by subject (*"HQ Ruling on SN-25"*, *"the 2026-07-31 row P4 ruling"*, *"Status
of the Milestone locality cell"*), or by an accompanying full path (`chat-hierarchy.md:137`,
`:174`, `:279`; `system-hq.md:327`; `fleet-operator.md:225`). `system-hq.md:190` (*"placed here by
HQ Ruling 2026-07-31"*) is bare **on its face** but is resolved by its own §Reference path at
`:327` and by subject matter.

**Disposition: project-internal only → report and leave.** Not renumbered, not escalated.

**C4 characterization (not a collision test).** No `concern_id` value is duplicated. **3 of 8
rulings carry no `concern_id` at all** — a convention inconsistency, recorded per D4 row 5.

### Family 2 — `escalation-notices/` (5 files) — **ESCALATED**

**Method (reproducible):**

```bash
ls -1 .ai-project/artifacts/escalation-notices/
for f in .ai-project/artifacts/escalation-notices/*.md; do
  echo "--- $(basename "$f")"; awk '/^---$/{n++; next} n==1' "$f"; done

```

**Finding — the family allocates no ID of its own.** Same shape as Family 1: `type`, `milestone`,
`issued_by`, `issued_to`, `date`, `status`. **C1 does not apply; C2 is a VACUOUS PASS.**

**C3 fires, and this one reaches the normative tier.** Two notices share the milestone key
**`P10-M34`**, with unrelated subjects:

| File | Subject |
|---|---|
| `2026-07-28T20_00_00Z__P10-M34__escalation_notice.md` | *"`claude-opus-4-8` unavailable in a manual-chat harness surface"* |
| `2026-07-29T00_00_00Z__P10-M34__escalation_notice.md` | *"the M34 fleet set changed — `fieldledger-assesment` out…"* |

The shorthand **"P10-M34 Escalation Notice"** — milestone key only, no date — therefore resolves to
**two different notices**, and it appears in **two normative documents**:

- `governance/systems/chat-hierarchy.md:271` — *"this guardrail … halted every manual chat at once
  (P10-M34 Escalation Notice)"*
- `governance/ai-project-yml-spec.md:660` — v2.6.0 changelog, the paid-frontier refresh

Both mean the **2026-07-28** notice, and both are resolvable **by subject matter — not by the
identifier.** A reader resolving the citation by its identifier alone reaches two candidates. The
same shorthand also appears in `model-routing-policy.md:92` and `2026-07-28__hq-chat-opener.md:16`.

**Disposition: ESCALATED. Not fixed, not renumbered.**

### Family 3 — the `GH-` series (40 recorded / **38 live**) — **ESCALATED**

**Method (reproducible):**

```bash
grep -rhoE "\bP[0-9]+-GH-[0-9]+\b" --include=*.md --include=*.py . | sort -u -V   # full-ID inventory
awk -F'-GH-' '{print $1}' <that output> | uniq -c                                 # per-phase spread
grep -rn "P6-GH-1\b" --include=*.md .                                             # suspect bindings
grep -rnoP "(?<!P\d)(?<!P\d\d)(?<!-)\bGH-\d+" governance/                         # bare, namespace-stripped
grep -rhoE "P[0-9]+-GH-[0-9]+" governance/ | sort | uniq -c                       # prefixed, normative tier
```

> **A note on the negative lookbehind.** A naive `[^A-Za-z0-9]GH-[0-9]+` pattern matches the **tail
> of a prefixed ID** (`-GH-7` inside `P10-GH-7`) and reports ~20 false "bare" citations in
> `governance/`. The first run of this audit made exactly that error. The lookbehind form above is
> the correct one, and it returns **one** true bare citation.

**Finding — no full-ID collision. The family is collision-free under D3.** All 40 recorded IDs bind
to exactly one subject each.

**Live count is 38, not 40.** `P6-GH-1` and `P6-GH-2` survive **only as records of their own
renumber** — SN-15 (2026-06-28) reconciled them to `P6-GH-12` / `P6-GH-13`, and the sole remaining
occurrences are that steering note and an HQ opener describing it. They are quoted history, not
live allocations. **Precedent worth noting: this corpus has renumbered a `GH-` ID before and
recorded the mapping.**

**Convention is NOT uniform across phases** (D3's characterization obligation, D4 row 5):

| Phase | IDs | Counter |
|---|---|---|
| P5 | GH-1 … GH-10 | restarts at 1 |
| P6 | GH-10 … GH-15 (+ retired GH-1/2) | **continues P5's global counter** |
| P7 | GH-16 … GH-21 | **continues globally** |
| P8 | GH-1 … GH-3 | restarts at 1 |
| P9 | GH-1 … GH-3 | restarts at 1 |
| P10 | GH-1 … GH-10 | restarts at 1 |

**The prefix's meaning inverted between eras** — the deeper finding:

- **P5's** closure declaration **forward-allocates P6-prefixed IDs** (`P6-GH-10`, `P6-GH-11` are
  filed *in P5's record*). The prefix means **"the phase that will address it."**
- **P10's** closure declaration carries **`P10-`-prefixed IDs into P11** unchanged. The prefix means
  **"the phase that filed it."**

**Direct consequence — and the reason the normative-tier test fires:** `P5-GH-10` (*Delivery Notice
receipt protocol*) and `P6-GH-10` (*codify SN-13 default-accept*) are **different subjects sharing
ordinal 10**, and both are live.

**Normative-tier test: FIRES — exactly once, in the framework's highest-authority document.**

> `governance/PROJECT-SYSTEM-GUIDELINES.md:605`
> *"Codified by E25.2 (P6-M25); **closes GH-10**."*

This is the **only** truly namespace-stripped `GH-<n>` anywhere under `governance/` — every other
normative `GH-` citation (9 occurrences) carries its phase prefix. Bare `GH-10` is **ambiguous
between `P5-GH-10` and `P6-GH-10`**, two live and unrelated items. Context (E25.2, P6-M25, the
surrounding SN-13 text) resolves it to `P6-GH-10`; **the identifier does not.**

**This is precisely the SN-23 shape** that E36.1 was run to fix, in a document of higher authority
than any SN-23 citation was found in — a bare identifier that a reader resolves by number to the
wrong item. Corpus-wide, bare `GH-<n>` is heavily used in P5-era documents (47 occurrences in
`P5-M20__milestone-spec.md` alone), where a local phase context makes it readable; PSG has no such
local context.

**Disposition: ESCALATED. Not fixed, not renumbered.**

## What this audit did NOT do

Recorded explicitly, because the boundary is the point:

- **No ID was renumbered in any family.** Not one, including `GH-10`.
- **No mechanism was built** — no test, validator, linter, or registry for any family. B3.1's
  steering-note guard was E36.2's bounded exception and remains the only such guard.
- **PSG:605 was not edited**, though the edit is two characters (`GH-10` → `P6-GH-10`) and is
  almost certainly the right remediation. It amends a **normative** document, which this Epic is
  constrained not to touch, and the remediation decision is HQ's. **This is the asymmetry the Epic
  spec named in advance: the fix was cheaper than the escalation, and the escalation is what the
  constraint requires.**
- **Steering notes were not re-audited** — SN-28 did that; E36.1/E36.2 closed it.
- **M36 was not widened.** HQ Ruling 2026-08-01, Decision 12.

## Answering SN-28 Carry-Over 3, with evidence

**Do the unaudited families carry the unenforced-ID defect?**

- **`rulings/` and `escalation-notices/`: they carry no self-allocated ID at all**, so SN-28's
  defect *as such* cannot exist in them. What they carry instead is **referential ambiguity in the
  shorthand used to cite them** — same reader-level failure, different mechanism. Rulings:
  project-internal. Escalation notices: **reaches the normative tier.**
- **`GH-` series: no collision.** Its namespace held, across 38 live IDs and six phases, despite a
  convention that inverted meaning mid-corpus. **The defect is in citation practice, not
  allocation** — one namespace-stripped citation in PSG.

**Carry-Over 3 is answerable from this artifact without re-running the audit.**

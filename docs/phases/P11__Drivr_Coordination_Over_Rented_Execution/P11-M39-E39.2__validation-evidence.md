### 3.4 Constraint 2 — the exit code and `status` shown **available and ignored**

This is the epic's Trap 2, and it is where a clean-looking document is cheapest to produce. **The
transcript projection has no channel for the exit code at all** — verified, not assumed: injecting
`exit_code: 999` into a transcript payload leaves `record.annotations` byte-identical, on all six
cases. **So independence from the exit code cannot be demonstrated by injection here, and claiming
it on the strength of the verdict's `[ignored] exit_code` line would be exactly the vacuous
independence the spec names** — that line reads `verbatim: 'None'`, i.e. *ignored because absent*.

The demonstration therefore rests on two things that are **not** absences:

**(a) The exit code was read by this validation, from the sidecar, and the verdict went the other
way on both binding cases.**

| Case | `exit_code` *(sidecar — read by the harness)* | `status` *(transcript — read by the harness)* | **Verdict** |
|---|---|---|---|
| **E33.2 Run A** | **`0`** — reads *success* | **`completed`** — reads *success* | **`did-not-complete`** |
| **E33.4** | **`2`** — reads *failure* | **`max_iterations_exceeded`** — reads *failure* | **`completed`** |

**On both binding cases the verdict is the opposite of what both ruled-out signals imply.** If
either were a term in any rule, neither verdict is reachable. This is a demonstration on the real
corpus, not on fixtures, and it does not depend on the exit code being absent from the transcript.

**(b) `status` — which *does* have a channel — was mutated and the verdict did not move.**
`status` was rewritten to **every value observed anywhere in the corpus** (`completed`,
`max_iterations_exceeded`) crossed with four `final_answer` values (the flat refusal, success prose,
unexecuted tool-call JSON, and the field removed entirely), with an `exit_code` injected alongside:
**8 mutations × 6 cases = 48 trials, and the verdict and the rule that fired were invariant in all
48.**

E39.1's own suite demonstrates this against corpus-**shaped** fixtures by design. **This is the same
property demonstrated against the corpus itself**, which is the thing E39.1's suite deliberately
does not reach across repositories to touch.

### 3.7 Scores — against both declared conventions, and against the degenerate baselines

The scoring conventions were fixed in the harness before the held-out cases were loaded, and are
**inherited from `715099c`**, not invented here (§3.5). `Reading` is three-valued, so a single
accuracy number is not well defined without saying what `undetermined` counts as.

| | **Strict** *(undetermined = miss)* | **Non-contradiction** *(undetermined = no claim)* |
|---|---|---|
| **The judgment** | **2 / 6** | **0 contradictions / 6**, 4 no-claim |
| Binding pair only | **2 / 2** | 0 contradictions |
| *Always answer* ***completed*** | **5 / 6** | **1 contradiction** *(Run A)* |
| *Always answer* ***undetermined*** | **0 / 6** | 0 contradictions, 6 no-claim |

**Stated plainly, because it is the honest headline and it is not flattering: on strict scoring the
judgment scores 2/6, which is worse than answering *completed* every time.** The five-to-one
imbalance is what makes that possible, and it is why the baseline sits in the table rather than in a
footnote.

**The two degenerate baselines are both in the table on purpose.** Reporting only the
always-*completed* baseline would flatter the non-contradiction column, and reporting only
non-contradiction would flatter the judgment. **Neither degenerate strategy dominates it and it
dominates neither**: it beats always-*completed* on contradictions (0 vs 1) and loses to it on
strict; it beats always-*undetermined* on strict (2 vs 0) and ties on contradictions.

**On a corpus of six with one negative case, none of these numbers settles anything.** What the
binding pair establishes is narrower and is the thing the milestone actually asked for: **the two
runs that agree on every signal the fleet has ever read are now separated, correctly, by evidence.**

## 4. Limits — written so no reader could mistake this for a general guarantee

**1. Two cases falsify; they do not generalize.** The binding pair shows the judgment is *not* wrong
on the two runs that defeated every prior signal. **It does not show it is right in general**, and no
count of passing cases could.

**2. The corpus is imbalanced five to one.** Five *completed*, one *did not complete*. **A mechanism
that answers *completed* every time scores 5/6 on this corpus and 1/2 on the binding pair.** Any
accuracy figure read without that baseline beside it is misleading, and §3.7 puts both degenerate
baselines in the same table for that reason.

**3. There is exactly one negative case in the entire corpus.** Every claim that the judgment
correctly identifies a run that did nothing rests on **E33.2 Run A alone**. **One case is not a
false-positive rate.**

**4. Every case comes from one runner and none from OpenCode.** All six are `local-agent-runner`
transcripts. **Engine generality is untested — not weakly supported, untested.** And it is not merely
untested: E39.1 records that a live OpenCode run projects with `effect_ledger=None`, so ordering is
unavailable and **it can never reach `EFFECTS_VERIFIED`** — only `EFFECTS_UNVERIFIED`,
`NO_EFFECTS_OBSERVED` or `INDETERMINATE`. **M40 inherits an engine on today's roster that cannot
produce the positive verdict this epic validated**, and closing that means an adapter projecting an
ordered ledger, which was deliberately not built.

**5. The judgment answered `undetermined` on four of six cases.** That is the correct in-run reading —
those runs genuinely never verified their own work, and their ground truth was established by an
**out-of-run** verification the judgment does not perform. **But a coordinator that needs a
yes-or-no answer will get `undetermined` two thirds of the time on corpus-like runs**, and that is a
real operational limit for M40, not a technicality.

**6. Result-string matching is `local-agent-runner`'s vocabulary.** If the runner's wording changes,
entries become `UNCLASSIFIED` — visible in the verdict and blocking the negative verdict rather than
silently misread — but the ledger degrades.

**7. A mutation made by an arbitrary shell command is not seen as an effect**, because whether
`sed -i` changed the tree is not decidable from a ledger. `files_changed` would close this and **no
preserved run carries it.**

**8. This validation is historical, and that bounds what it can settle.** Six stored transcripts, no
new runs. **`G11` is not claimed and is not touched** — milestone constraint 4 is explicit that a
pass over historical transcripts **never** closes it. That is E39.3's, on a real captured `epic_qa`
run.

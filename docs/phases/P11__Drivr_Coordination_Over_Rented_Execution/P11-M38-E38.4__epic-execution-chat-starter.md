## Three findings you must not rediscover

### Finding 1 — C3's contract is richer than the field evidence recorded

The evidence records C3 as **binary** (exit 2 + `max_iterations_exceeded` vs nothing + exit 0). **That
was accurate for that run and it undersells the contract.** The runner has **four exit codes and three
status values.**

**So *"does OpenCode emit an honest exit code?"* is the wrong shape of question.** The real one:
**can OpenCode distinguish "ran out of iterations" from "crashed" from "finished"?** — because **a
scheduler responds differently to each**, and that is what M39 will need.

> **And remember Finding 4 of the evidence: `exit 2` does NOT mean "produced nothing."** Arm B exited
> non-zero *and* produced usable work. **P10-GH-7's two-sidedness is confirmed — the exit code is
> uninformative in both directions.** **C3's value is not that exit codes can be trusted. It is that a
> structured status exists to be read instead.**

### Finding 2 — C1's answer may depend on E38.1's stack, and you will know it

**Two corrections first:**

1. **`run(task, tools, model)` is a shorthand, not the signature.** The real one is
   **`run(model, task, permissions, ...)`** — different order, and the third parameter is
   **`permissions: ToolPermissions`**, not `tools`. **Cite the measured form.**
2. **OpenCode has library-shaped surfaces — in JavaScript/TypeScript.** `@opencode-ai/sdk` and
   `@opencode-ai/plugin` (which ships a **`tool.d.ts`**) are present at `~/.config/opencode/node_modules/`.

> **The honest form of C1: is there an in-process library entry point *for the language Drivr is written
> in*?** **If Drivr is Python, a JS/TS SDK is not one** — it is another subprocess or an HTTP call,
> which the adapter already does. **If Drivr is JS/TS, it may be exactly the equivalent.**
>
> **Read E38.1's stack decision and make C1's answer conditional on it explicitly.**

**⚠ Version skew: the SDK and plugin are `1.15.13`; the binary is `1.18.10`.** **A capability assessed
against a three-minor-versions-old SDK is not necessarily an assessment of the engine you are running.
Say which you tested.**

### Finding 3 — C2 is narrower than its name

`coerce_arguments`' own docstring records the limits: **flat schemas only**, **`string` properties are
never coerced**, **properties absent from the schema pass through untouched**, and it **raises** on
invalid or missing arguments.

**So C2 is "coerce mistyped primitives against a flat schema" — not "JSON-schema argument coercion" in
general.** **Assess OpenCode against that.** And **distinguish recovery from validation**: a mechanism
that *rejects* a mistyped argument **does not provide C2**, even though it handles the same input. The
capability at issue is **recovery**.

## ⚠ Three method obligations — each paid for by a real mistake

### M1 — Assess C3 from structured output, NEVER an engine's self-report

**The agent's prose lied in *both* arms.** Arm B's `final_answer` opened *"I've successfully created a
test file… that implements the required functionality"* **while its own status said
`max_iterations_exceeded` and its exit code said 2.** Arm A likewise narrated a confident conclusion
about work it had not done.

**The structured signal was correct in the same run.** **Read exit codes and structured status. Never
prose.**

### M2 — Verify YOUR OWN harness against a known-nonzero case, BEFORE trusting any exit code

**Arm B's exit code was first recorded as 0. That was wrong.** A wrapper invoked `main()` and
**discarded its return value**, where `local_agent_runner/cli.py:229` uses **`sys.exit(main())`**. The
runner was honest throughout, and the false reading *"was one step from being filed as 'both engines
share the false-zero bug.'"*

> **That mistake would have produced the exact opposite conclusion from the truth — in the epic whose
> whole job is to decide whether one engine's honesty is worth keeping.**

**BINDING: before any exit code you report is treated as evidence, run your harness against a case whose
exit code is known non-zero, and show it reports non-zero.** **`EXIT_CONFIG_ERROR=3` via a deliberately
malformed invocation is the cheapest such case — and it needs no GPU.** **There is no excuse for
skipping this.**

### M3 — Test for real; a memo about what `serve` probably does is not an assessment

**This is why the Epic is gate-bound.** **Reasoning from `--help` output is not evidence.**

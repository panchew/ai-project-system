### 1a. Two findings the planning measurement did not have

Both were produced by counting, and both are worse than the estimate they refine.

**The strict parser reaches 28 files of 822, not 48 of 203.** Running
`ArtifactParser.parse_file` over every `.md` file in both roots:

| Outcome | Files |
|---|---:|
| Parsed and validated | **28** |
| `ArtifactParseError` (no frontmatter, or frontmatter that is not valid YAML, or no `artifact_type`) | 708 |
| `ArtifactTypeError` (declared type outside `SCHEMA_REGISTRY`) | 44 |
| `ArtifactSchemaError` (**declared type IS registered, and fails its own schema**) | 42 |

The last row is the sharp one. **Only 114 files carry `artifact_type` at all; 70 of those
name a registered type; 42 of those 70 — 60% — fail the schema they declare.** The commonest
causes are `review_decision_timestamp` and `completion_notice_timestamp` parsed by YAML as
`datetime` rather than `str` (31 files between them).

So the spec's *"a queue built on `SCHEMA_REGISTRY` alone omits three quarters of the
corpus"* understates it: over both roots, such a queue sees **3.4%**.

**The corpus has three naming conventions for one idea, and 22% has no frontmatter at all.**

| Shape | Files | Share |
|---|---:|---:|
| `artifact_type:` present (schema key) | 114 | 14% |
| `type:` present (docs-tier key, **49 distinct values**) | 413 | 50% |
| No frontmatter block whatsoever | 180 | 22% |
| Frontmatter present but **not valid YAML** | 55 | 6.7% |

The 55 unparseable files fail identically: an unquoted YAML scalar containing `": "`, e.g.

```yaml
issued_to: Phase Chat (P11 — Drivr: Coordination over Rented Execution)
```

`.ai-project/artifacts/closure-declarations/2026-08-16T22_35_00Z__P11-M39__milestone_closure_declaration.md`
is one of them. These are **artifacts with real frontmatter that no reader can use** — a
different thing from having none, and the queue reports which.

## 2. Which roots — **both**

Delegated decision 1. `.ai-project/artifacts/` **and** `docs/`, giving **822** files.

Reading `.ai-project/artifacts/` alone sees **5 of 106 delivery notices — 4.7%**. A delivery
awaiting review is precisely what a gate queue exists to surface, so the narrow read fails
worst on the family that matters most, and fails silently. The cost is demonstrated by
running it in [the recomputation evidence](P11-M40-E40.2__recomputation-evidence.md), where
the one-root queue returns 19 items and **zero** unclassified — *tidier*, on 25% of the
corpus.

Neither root is "the wrong one". The corpus genuinely lives in two places by convention.
**The failure would be choosing one silently.**

## 3. Which families — a ladder, not a registry

Delegated decision 2, answered **hybrid**. Full schema coverage of 19 families was out of
reach for one epic, so the queue **classifies far more than it validates and prints both
numbers.** Each file is tried against each rung and stops at the first that answers.

| Rung | What it means | Files | Share |
|---|---|---:|---:|
| `strict` | Parsed **and schema-validated** by the repository's own `ArtifactParser` | 28 | 3.4% |
| `declared` | Carries `artifact_type`; strict parsing refused it, **and the refusal is kept on the entry** | 86 | 10.5% |
| `conventional` | Carries the docs-tier `type:` key | 413 | 50.2% |
| `located` | No usable frontmatter, but sits in a family directory | 50 | 6.1% |
| `unclassified` | **Nothing answered.** Goes on the queue as *needs a human* | 245 | 29.8% |

**28 + 86 + 413 + 50 + 245 = 822.** The ladder is exhaustive by construction and the
identity is asserted against the real corpus.

The recogniser names **49 families**, against the 19 family directories on disk — the docs
tier carries kinds (`spec`, `note`, `test-plan`, `post-mortem`) that have no directory.

**Rung 1 is the repository's own parser, loaded from the corpus being read** (`lib/` here,
`.governance/lib/` in an enrolled project) — Q1's *"a derived queue should stand on this, not
beside it."* Rungs 2–4 reuse that parser's own `FRONTMATTER_PATTERN`, so there is no second
definition of an artifact's *format*, only a coarser reading of what a file **says it is**
when the schema declines to speak. If no parser is found, rung 1 is reported as **"not found
— rung 1 never ran"** rather than quietly yielding zero validated files.

## 4. Which states make an item outstanding

Delegated decision 3 — **and this is the part where the obvious answer is wrong.**

### The rule this framework cannot use

The natural rule is *a demand with no matching answer*. Executed:

| Candidate rule | Entries |
|---|---:|
| delivery notice with no merge authorization | **98** |
| completion notice with no review decision | **29** |
| any artifact whose `status` is `planned` or `active` | **189** |

Neither of the first two is a backlog. **PSG §11.6 is why** — `governance/PROJECT-SYSTEM-GUIDELINES.md`
line 586:

> **Happy path (default-accept):** a parent chat accepts a **clean** child delivery — one
> meeting its Definition of Done, acceptance criteria, and spec — **by silence**. No Review
> Decision artifact is produced; the **merge plus the in-chat acknowledgment is the
> acceptance record**.

Under default-accept, **the absence of a review decision is the signature of a delivery that
was accepted**, not one that is waiting. The absence-based rule reads the framework's happy
path as its backlog. Worse, it reads *more* of it as the corpus grows and more deliveries are
cleanly accepted: **better recognition makes that rule worse.**

> That is the same shape M40's **F5** recorded one epic over — a perfect ordered ledger on a
> read-only run still returns `NO_EFFECTS_OBSERVED`, so better classification and more
> evidence each yield a *worse* verdict. **E40.2 met the same shape independently, at a
> different layer, from a different cause.** F5's cause is `_decide` never reading
> `Role.INSPECTION`; this one's is a normative rule that makes silence mean *accepted*.

The rejected rules are **data, not a comment** — they live in `RULES_NOT_APPLIED`, are
rendered into every queue, and are pinned by tests, because a rule that is merely
unimplemented gets reimplemented by the next person.

### The rules that are used

| State | Rule | Items on 2026-08-17 |
|---|---|---:|
| `declared-open` | The artifact's own `status` is one of `OPEN_STATUSES`. **A declaration is read; nothing is inferred.** | 21 |
| `unanswered` | A demand with no answering artifact for the same subject — applied **only** to `escalation_notice` and `system_request`, the two families where silence is not an accepted answer. §11.6 governs the parent→child *acceptance* gate and does not reach them. | 10 |
| `unpairable` | A demand of those families whose subject could not be established, so satisfaction is **not decidable**. Listed rather than guessed either way. | 0 |
| `needs-a-human` | **D4.** The recogniser could not classify the file at all. | 245 |
| | **total** | **276** |

`unpairable` is 0 today and the rule is kept: 0 is an executed result, not a missing rule,
and five entries sat in this state until the subject-matching defect in §7 was fixed.

## 5. How an empty or absent family is reported (Q4)

**A family with 0 files is printed with its zero. A family absent from the table was never
read.** That distinction is the whole answer: from the queue's side, *nothing is outstanding*
and *nothing is being read* are otherwise indistinguishable.

`validation-runs` and `bouncer-work-logs` both hold **0** artifacts and both appear in every
coverage report, marked *(empty — read, nothing in it)*.

The same discipline applies to an empty **state**: a section with no entries renders as
*"None. This is an executed result over 822 files, not an empty read"*, never as a blank.

## 6. What an unclassifiable artifact does (D4)

**It appears.** Every one of the 245 becomes exactly one `needs-a-human` entry carrying the
reason no rung placed it, and **the count of those entries equals the corpus's unclassified
count exactly** — an identity a reviewer can check by comparing two numbers rather than by
trusting the implementation.

> M39's judgment applies this one layer down: its `UNCLASSIFIED` role is *"recorded verbatim
> and never counted as anything"*, and incomprehension *"is never a negative finding."*
> **The queue does not convert its own incomprehension into an empty result.**

A real case, not a constructed one: `docs/bugfixes/B2.1__spec__sandbox-cannot-reach-ollama-endpoint.md`
declares `status: open`, carries neither `artifact_type` nor `type:`, and sits outside every
family directory. It surfaces as `needs-a-human` **with its open status in the reason** —
the queue can see it is very likely a real open gate and cannot say of what.

**An observation, reported and not remediated** (spec: *"surfacing a stale gate is a finding,
not a work item for this epic"*): `B2.1` is recorded as delivered and merged on 2026-08-07,
and its spec still reads `status: open`. Several of the 21 `declared-open` items are
similarly stale — seven completion notices from P4 still read `ready_for_review`. **The queue
is reporting the corpus accurately; the corpus is what is stale.**

## 7. Two defects found in this epic's own reader

Both were silent by construction, and both were found only by asserting against named files.

The subject pattern used `\b` on each side. **This corpus separates filename fields with
`__`, and `_` is a word character**, so `\b` finds no boundary on either side of a subject
written `…__P11-M36__…`:

| Defect | Effect |
|---|---|
| Trailing `\b` | `P11-M40-E40.3__spec__thing.md` resolved to **`P11-M40`** — every epic of a milestone collapsing onto the milestone, letting one artifact satisfy another's demand |
| Leading `\b` | `2026-08-03T00_00_00Z__P11-M36__escalation-notice.md` resolved to **nothing at all** — five escalation notices sat on the queue as `unpairable` with their subject sitting in the filename |

Fixing both moved subject extraction from **689 to 722 of 822**, and moved `unpairable` from
5 to 0. A regex that does not match raises nothing: **both defects would have degraded the
queue quietly**, which is the failure this epic exists to prevent, occurring inside the thing
built to prevent it.

Frontmatter order was also preferred over specificity at first, which is the same collapse by
a different route. The resolver now reads both sources and takes the **narrowest** subject.

## 8. Coverage — the floor, with a count and a date

**On 2026-08-17, against `ai-project-system` at `cf8bd7c`, the queue read 822 files from two
roots, classified 577 of them into 49 families, schema-validated 28, and surfaced 245 it
could not classify.**

**That is a floor, not a total.** Named things it does not see:

1. **An open gate whose `status` uses an unlisted spelling.** The key is uncontrolled — 30+
   distinct `status` values across the corpus, including **five spellings of *waiting***
   (`open`, `pending`, `pending-review`, `submitted-for-review`, `ready_for_review`).
   `OPEN_STATUSES` lists twelve; a sixth spelling of waiting is a gate this queue misses.
2. **A gate that exists only as a chat act.** Under §11.6 a clean delivery is accepted by
   silence and produces **no artifact at all**. Nothing derived from artifacts can see one,
   and no improvement to this queue will change that. **It is a property of the framework,
   not a limitation of the implementation.**
3. **Anything outside the two roots, and anything in any other repository.** This repo only.
4. **A demand from a family not in `DEMANDS`**, which holds two entries.
5. **A gate inside an artifact's prose.** Only frontmatter and filenames are read; no body
   text is interpreted.

## 9. Observations recorded, not acted on

Out of scope by the spec, recorded here for the Milestone Chat.

1. **The corpus is bi-located.** 101 of 106 delivery notices under `docs/`, 5 under
   `.ai-project/artifacts/`. Recorded as an observation — **a 600-file move is not this
   epic**, and the spec says so.
2. **42 of 70 registered-type artifacts fail their own schema.** The largest group — 31 —
   are timestamp fields holding **a date with a citation appended in prose**, for example
   `completion_notice_timestamp: 2026-06-25 (Delivery Notice, P5-M20-E20.1__delivery-notice.md)`,
   which the `iso8601` check rejects. Two more hold `None`. This is **not** a
   type-normalisation problem: `lib/artifact_parser.py` already converts YAML `datetime`
   values to strings for these keys before validating. The convention drifted in the
   artifacts, and nothing enforced the schema at authoring time — which is `P10-GH-5`'s
   shape (yml-spec validation unenforced) in a different file class. **Reported, not fixed.**
3. **55 artifacts carry frontmatter that is not valid YAML**, all from an unquoted scalar
   containing `": "`. Five are milestone closure declarations, including M39's.
4. **The `status` key is uncontrolled**, with five spellings of *waiting*. Any future
   status-driven mechanism inherits this.
5. **`needs-a-human` is dominated by ordinary documentation** — `docs/README.md`,
   `docs/artifact-parser-api.md` and the like. Distinguishing *an artifact that failed to
   classify* from *a file that was never an artifact* is the obvious next refinement.
   **Deliberately not attempted here:** any rule that decides a file "is not an artifact"
   drops it from the queue, which is the silent omission this epic exists to prevent, and it
   should be designed with that squarely in view rather than added as a convenience.

**No `GH-` ID is filed by this epic.** Method obligation 4 requires escalating before filing
one, and **`P11-GH-3` is contested and unallocated — it is not allocated here.**

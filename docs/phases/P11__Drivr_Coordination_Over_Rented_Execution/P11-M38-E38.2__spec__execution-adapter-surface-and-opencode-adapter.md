# Epic E38.2 — Execution Adapter Surface and the OpenCode Adapter

**Stage A. Holds the Stage A → Stage B gate. The milestone's load-bearing epic.**

---

## Context

**This is the epic P11 is really about.** SN-27's spine says Drivr **rents execution** — it invokes CLI
tools that own the inference and never grows an engine of its own. E38.2 builds the seam that renting
happens through.

**The interface is the architecture; the roster is configuration.** That was not a slogan when it was
decided — Amendment 1 proved it within two hours, when the roster collapsed from two engines to one and
*"the roster changed; the architecture did not."* **That is the strongest available evidence that the
surface, not the engine, was the right thing to commit to**, and it is why this Epic is judged on the
interface rather than on OpenCode.

E38.1 has delivered a repository. This Epic gives it the one capability everything downstream needs:
**the ability to invoke an engine and hear what came back.** E38.3 runs in parallel and needs nothing
from here. **E38.4, E38.5 and E38.6 all need this Epic to have delivered**, because all three are
evidence *about an engine invoked through an adapter*.

**M37 already paid for the lesson that makes this Epic's gate binding.** It planned an evidence epic
against a dispatch path that had not worked since 2026-07-12, and discovered it at execution time. That
cost one escalation, one HQ ruling, three spec revisions and a posture round-trip. **This Epic exists
partly so nobody pays that twice.**

---

## Problem Statement

**Execution is hard-wired to one engine that is under retirement assessment, and no engine is reachable
from inside this repository's sandbox.**

Three concrete facts:

1. **`bin/run-dev-agent`'s `discover_runner()` hard-codes `local-agent-runner`.** Measured on
   `milestone/M38`, lines 203–214: it honours a `LOCAL_AGENT_RUNNER` env override, else
   `shutil.which("local-agent-runner")`, else fails. **There is no adapter surface** — the engine's name
   is compiled into the dispatcher, and its argv shape (`--model / --task-text / --context / --tools /
   --transcript / --endpoint`) is built inline at lines 252–262. **A second engine cannot be added
   without editing the dispatcher**, which is exactly what Constraint 2 forbids.
2. **The engine A1.1 made the sole roster cannot run in the sandbox at all** — and this is stronger than
   the "ABSENT" the milestone spec recorded. See **Finding 1**.
3. **B2.1 fixed the blocker that fired first, not the one behind it.** Its own post-mortem says so.
   Ollama is reachable from inside the container; **no engine is there to reach it.**

## ⚠ THE UNSOLVED DESIGN QUESTION — this Epic's to answer, NOT to escalate

> **Does Drivr execute through *this* repository's `bin/ai-project-orchestrator` sandbox at all?**

**It is not obvious that it should.** Drivr is a **separate repository** and a **coordination daemon**
(SN-27): it invokes CLI tools that own the inference and spends its budget on coordination over
governance state. **Nothing in the spine requires it to borrow this repository's sandbox.**

**Three admissible directions. This spec prices them and prefers none.**

| Direction | What it buys | What it costs — **measured, see Findings** |
|---|---|---|
| **A — Drivr runs on the host**, invoking `opencode` directly | Lightest. Matches SN-24's *"as agentic as we can → lightest infrastructure."* OpenCode and its config are already there and working | **Gives up sandbox isolation.** Must be stated plainly, not omitted |
| **B — Drivr owns its own container** with OpenCode installed | Preserves isolation. Drivr's own infrastructure, not this repo's. Clean separation of concerns | A container to build and maintain; **must solve the same glibc/config problems** Finding 1 and Finding 3 describe, but inside Drivr's own boundary where they are Drivr's to solve |
| **C — this repo's sandbox gains OpenCode** | Smallest conceptual change here | **Far more expensive than the milestone spec knew.** Requires **changing the sandbox base image off Alpine** — not an `apk add` (Finding 1). Affects **every** sandboxed operation in the framework, and re-opens Route B.2's shape one engine over |

**This is E38.2's decision to make, document, and proceed on.** What is **binding** is:

- **The epic states which direction it took and why.**
- **It demonstrates an engine actually invoked end-to-end.** An adapter surface that has never invoked a
  real engine is a design document, not a deliverable.
- **If isolation is surrendered, that is stated plainly rather than omitted.**

> **⚠ The split trigger, and it is live.** The milestone spec records two revisit triggers for the split
> the Phase Chat declined. **One of them is this Epic outgrowing an epic.** If answering the sandbox
> question costs more than E38.2 can hold — for instance if the honest answer is Direction C and the
> base-image change turns into its own body of work — **that is the split trigger firing. Escalate to
> the Milestone Chat. Do not absorb it.** Being the epic that reports "this is bigger than an epic" is a
> success outcome, not a failure.

## ⚠ Finding 1 — OpenCode cannot run in the sandbox image. Not "absent" — *incompatible*.

**This is the most important measurement in this spec and it reprices Direction C.**

The milestone spec records `opencode` as **ABSENT** from the sandbox image. **That understates the
problem.** Measured 2026-08-08:

- **The sandbox image is Alpine Linux and is musl-only.** `/lib/ld-musl-x86_64.so.1` exists;
  **there is no `/lib64/ld-linux-x86-64.so.2`.** Confirmed *inside the container*.
- **The `opencode` binary is glibc-linked.** `file` reports *"dynamically linked, interpreter
  `/lib64/ld-linux-x86-64.so.2`, for GNU/Linux 3.2.0"*; `ldd` resolves `libc.so.6` from
  `/usr/lib/x86_64-linux-gnu/`.
- **Empirically proven, not inferred.** Mounting the host binary into the container and running it
  gives:

  ```
  sh: /tmp/opencode: not found
  ```

  **The file is present and readable.** That message is musl's report for a **missing ELF
  interpreter** — the classic glibc-binary-on-Alpine failure, and one of the more misleading error
  strings in Linux.
- **The binary is 179 MB**, against a 534 MB image.

**Consequence, and it is E38.2's to weigh rather than mine to decide.** *"This repo's sandbox gains
OpenCode"* is **not `apk add opencode`**. It requires either **changing the sandbox base image off
Alpine** — which affects **every** sandboxed operation in this framework, not just Drivr's — or a
`gcompat`-style shim under a 179 MB dynamically-linked binary, which is fragile and unproven here.

> **The milestone spec's own framing of Direction C — *"smallest change here, but couples Drivr's
> execution to this repository's image and re-opens the Route B.2 shape one engine over"* — was
> directionally right and materially understated. It is not the smallest change. It may be the
> largest.**

**Do not treat this as deciding the question.** Direction C remains admissible; it is now **priced**. If
E38.2 chooses it anyway with reasons, that is a legitimate outcome — **but it is also the likeliest path
to the split trigger, and the spec says so in advance so the escalation is cheap rather than
embarrassing.**

## ⚠ Finding 2 — Constraint 3 has an ordering problem, and it is exactly how the 8× overpack happened

**Constraint 3 says: derive the declared context limit from what `/api/ps` reports as LOADED, never from
the model's trained maximum.** That is right. **It is also not directly executable as written**, and
here is why:

| Endpoint | Reports | Available when? |
|---|---|---|
| **`/api/ps`** | the **loaded** context — `"context_length": 32768` | **only after the model is loaded.** With nothing loaded it returns **`{"models":[]}`** |
| **`/api/show`** | `qwen3moe.context_length` = **262144** — the **trained maximum** | **always** |

**Both measured 2026-08-08.** The `/api/ps` behaviour was verified by loading `qwen2.5-coder:7b` with a
one-token generate and reading the value back — **deliberately using a small model rather than forcing a
30B load onto a GPU that is shared with ComfyUI and runs a serialized lane.**

> **This is the mechanism that produced the bug.** The always-available endpoint returns **262144**.
> `opencode.json` declares **262144**. **The overpack is not a typo — it is what you get by reading the
> endpoint that answers without being asked twice.**

**Therefore the adapter must handle an ordering problem, and how is E38.2's design decision:**

- **`/api/ps` is empty before first load**, so an adapter that reads it at startup gets nothing.
- **Reading `/api/show` instead is the bug**, not the fallback.
- Admissible shapes include: load-then-query; query-after-first-invocation and cache; refuse to declare
  a limit until one is observed; or fail closed. **Pick one, document it, and make the failure mode
  explicit.**
- **What is binding: the 262,144-vs-32,768 overpack cannot recur, and the adapter must never derive a
  declared limit from a trained maximum** — including when `/api/ps` is empty. **"Empty" must not
  degrade to "use the trained max."**

**Two adjacent facts worth carrying, neither of them E38.2's to fix:**

- **`llama3.1:8b` declares `"context": 131072` in `opencode.json` and has never been measured.** It may
  be a second overpack. **Out of scope — record it, do not chase it.**
- **`qwen3.6:27b` is present in Ollama and is declared nowhere in `opencode.json`.** Also out of scope.

## ⚠ Finding 3 — OpenCode's configuration lives on the host, outside any project

**`~/.config/opencode/opencode.json`** — user-level, host-level, **outside any repository or mount**. It
carries the provider block (`ollama` via `@ai-sdk/openai-compatible`, `baseURL
http://localhost:11434/v1`), the model roster, and the per-model `limit.context` values.

**This bears on all three directions and is easy to discover late:**

- **Direction A (host):** it is simply there. Nothing to solve — **and that is a real point in
  Direction A's favour that should be weighed rather than assumed away.**
- **Direction B (Drivr's container):** the config must be **provided** — mounted, generated, or
  templated. Note its `baseURL` is **`localhost:11434`**, which inside any container means *the
  container*, not the host. **B2.1's loopback→gateway rewrite exists for exactly this class of
  mistake**, and Drivr's container would need its own equivalent.
- **Direction C (this repo's sandbox):** same problem, plus Finding 1's.

**The general shape, worth stating because it will recur:** *an engine's configuration is part of its
runtime environment, and a decision about where the engine runs is also a decision about where its
configuration comes from.* **Whichever direction is chosen, the epic records how OpenCode gets its
configuration in that environment.**

## ⚠ Finding 4 — the CLI surface, measured, so the adapter is designed against facts

`opencode` **v1.18.10**, measured 2026-08-08. **Two invocation modes matter:**

**`opencode run [message..]`** — one-shot. Relevant flags:

| Flag | Why it matters |
|---|---|
| `--format default\|json` | **`json` emits raw JSON events.** The most likely basis for a machine-readable result — **and directly relevant to C3, which E38.4 assesses** |
| `-m, --model` | `provider/model` form, e.g. `ollama/qwen3-coder:30b` |
| `--agent` | selects a configured agent |
| `--auto` | **auto-approve permissions that are not explicitly denied.** Flagged *"(dangerous!)"* by its own help. **Required for unattended runs; note the trade-off wherever it is used** |
| `--dir` | directory to run in |
| `--attach <url>` | attach to a running server |
| `-s, --session` / `-c, --continue` | session continuation |

**`opencode serve`** — *"starts a headless opencode server"*, with `--port`, `--hostname`, `--cors`.
**This is the mode E38.4 assesses `local-agent-runner`'s three retention candidates against**, so
whatever E38.2 learns about `serve` is an input E38.4 inherits. **Record it even if the adapter does not
use it.**

> **The relevant known defect, and it is not E38.2's to fix.** `opencode run` **exits 0 on zero work** —
> measured first-party in `.ai-project/artifacts/field-evidence/2026-08-02__B3.1-engine-comparison.md`,
> matching upstream issue #14551. **The adapter reports what the engine reported. It does not correct
> it.** See §The Hard Constraint.

## Scope of Work

### 1. Answer the sandbox question — first, and in writing

**Before building the adapter.** The answer determines what the adapter is built against, and
discovering it afterwards is how M37 went wrong.

- **Evaluate all three directions**, against Findings 1 and 3 and against SN-24's *lightest
  infrastructure*.
- **Record the decision and its reasoning** where a reader can find it — in Drivr, and summarized in the
  Delivery Notice.
- **If isolation is surrendered, say so plainly.** Not in a footnote. A reader must be able to see what
  was given up and why it was judged acceptable.
- **If the answer proves bigger than this Epic, escalate** — the split trigger.

### 2. Design and build the adapter interface — **the deliverable**

**Shape is E38.2's design decision.** What it must satisfy:

- **It is the thing a second engine plugs into.** The coordination layer talks to the interface; it does
  not know the engine's name. **`discover_runner()` is the anti-pattern to design away from** — the
  engine's identity is compiled into the dispatcher there, which is precisely why a second engine cannot
  be added.
- **It carries what an invocation needs and what it returns** — at minimum: the task, the model, the
  working directory, and back: what the engine reported, its exit status, and its output. **Design the
  return shape knowing exit codes are untrustworthy in both directions** (P10-GH-7) — **and knowing
  that judging that is M39's job, not yours.**
- **It is documented at the level a second implementer could use** — without reading the OpenCode
  adapter's source.

### 3. Build the OpenCode adapter

- Invokes **`opencode` v1.18.10** for real.
- **Derives the declared context limit from `/api/ps`**, per Constraint 3 and Finding 2, with the
  empty-`/api/ps` case handled explicitly and its failure mode stated. **Never from a trained maximum.**
- **Records how OpenCode gets its configuration** in the chosen environment (Finding 3).

### 4. Invoke an engine end-to-end and capture the evidence — **the centre of gravity**

**This is what makes the Epic a delivery rather than a design document.**

- A **real invocation**, with **what it was asked and what came back**, captured verbatim.
- **The dispatch path and environment stated** — which engine, through which adapter, in what
  environment.
- **The evidence captured from wherever it ran and committed in this repository** — the M33/M34 pattern.
  **A claim about Drivr is not verifiable by reading this repo.**
- **Show the command and its output. `G2`'s general form: the reviewer re-measures; the executor's
  report is not the evidence.**

> **Choose a task whose ground truth you can check.** A run that "succeeded" by the engine's own account
> is exactly what the field evidence caught lying. **You are demonstrating the adapter works, not that
> the engine is good** — a run that faithfully reports a *failure* is a perfectly good demonstration,
> and arguably a better one.

### 5. Demonstrate extensibility — shown, not asserted

- **A stub or a second thin adapter is admissible evidence. A paragraph claiming extensibility is not.**
- The bar from Constraint 2: **a second adapter could be added without touching the coordination
  layer.** Make that checkable.

## Binding Constraints — reproduced, not cited

**1. Drivr rents both halves.** It implements **no inference, owns no model loop, grows no engine, and
builds no agent client.** SN-27's spine, as an exclusion so it cannot erode by increment. **An epic that
starts writing a model loop has left the phase, not just the milestone.** Enforceable at the dependency
list — the cheapest place to check it.

**2. The interface is the deliverable; the roster is configuration.** E38.2 is successful **only if a
second adapter could be added without touching the coordination layer** — *demonstrated by the
interface, not asserted.* **Today's roster is one tool: OpenCode** (A1.1).

**3. Derive the declared context limit from what `/api/ps` reports as LOADED**, never from the model's
trained maximum. `opencode.json` declares `"context": 262144` for `qwen3-coder:30b` against **32,768**
actually loaded — an **8× overpack** that makes long sessions truncate silently. Ollama measured at
**0.30.0**; **the `/v1` endpoint silently ignores `options`**, so the adapter cannot set the loaded
context through that transport and does not need to. **See Finding 2 for the ordering problem this
creates.**

**9. Every delivery that amends a normative document in this repository carries a Structural diagram**
(Mermaid, fenced, in-repo, **no ComfyUI**). **Whether this fires depends on where the work lands.** It
does **not** fire for Drivr-side code. **If nothing under `governance/` is amended, say so explicitly**
rather than omitting the section — so a reviewer can see the obligation was evaluated.

**10. The metavariable constraint (M37 Finding 3).** *Any document that records having fixed a defect is
liable to restate the defect while doing so.* **The shape here is specific: a document explaining that
the declared limit must not come from the trained maximum must not itself cite 262144 as though it were
the limit.** Quote it as the trained maximum, always, and label it.

**P10-GH-10 — before interpreting a red suite.**
`tests/test_artifact_router.py::test_daemon_extensions_error_branches` fails **~3 in 10 full-suite
runs**, passes in isolation, **untouched by anything here.** **A red suite on that test alone is not
evidence of an Epic defect.** Re-run and record **both** results. Do not fix, skip, or mark it.

## The Hard Constraint — and the drift that is *specific to this Epic*

**Drivr rents. It does not build what it can invoke.**

> **This Epic is where the milestone's named drift actually lives, and it will not feel like drift.**
>
> **E38.2 needs to know whether an invocation succeeded in order to return anything useful. That is not
> a licence to build M39's completion judgment.**
>
> The path is short and every step looks reasonable. The adapter returns an exit code. The exit code is
> known to lie — **measured, first-party: OpenCode exited 0 having done zero work.** So the adapter
> checks whether files changed. Then whether the change was on-topic. **By step three it is a
> trustworthiness layer, and M39 has been pre-empted by an epic with less information than M39 will
> have.**
>
> **The line: the adapter may REPORT what the engine reported. It must not JUDGE it.** Reporting
> includes surfacing the exit code, the structured status if one exists, stdout, stderr, and what
> changed on disk. **Judging is deciding whether those add up to "done."**
>
> **P10-GH-7 stands unfixed, M39 owns it, and M39 gates M40** — precisely because a scheduler over an
> untrustworthy signal produces constant false escalations or silent no-ops that read as success. **An
> epic that starts judging completion has crossed the phase's hard gate from the wrong side.**

**Also not yours:** a scheduler, a derived gate queue, a thin surface (**M40**); the three retention
candidates (**E38.4**); the milestone-context measurement (**E38.5**); the local/paid comparison
(**E38.6**). **All four are a short step from a working adapter and all four will look like progress.**

**If this Epic finds itself building any of that, it stops and escalates to the Milestone Chat.**

### On `run-dev-agent` — deliberately not touched

`bin/run-dev-agent`'s `discover_runner()` is the **motivating example** of what the adapter surface
fixes, and this spec quotes it as such. **It is not this Epic's to refactor.**

Rewiring this repository's dispatcher to go through Drivr's adapter would couple the framework's own
execution path to Drivr on the day Drivr's adapter first runs — **a far larger change than it looks, and
one nobody has authorized.** **Read it, learn from it, leave it.** If you judge it should be rewired,
**record the recommendation and escalate. That is a success outcome.**

  comparison notes that arm B ran with a **constrained** toolset, a **10-iteration ceiling**, and scoped
  context, while OpenCode ran unbounded — and concludes: *"if constraint is what kept arm B on task,
  then the adapter surface should impose the constraint regardless of which engine sits behind it."*

  Weigh it; it is not an obligation to run that experiment here.

  container* rather than on the host and found `opencode` absent. Measuring one layer deeper — **what
  would happen if it were added** — found that it cannot run there at all. **Each layer down has cost
  less than the one before and found something real.**

  chosen, the isolation trade-off must be stated plainly — but choosing it is not a failure of nerve.**

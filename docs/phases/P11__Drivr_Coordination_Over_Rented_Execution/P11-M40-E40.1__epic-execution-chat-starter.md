### Summary

Build the **serialized-lane scheduler** — one reasoning job at any instant, enrollment and concurrency
as **separate axes in the implementation** — and **decide the completion-signal question on
measurement**, recording what it costs and what the scheduler consequently does not know. Capture

### The one thing to read before designing: spec §F5

The milestone spec presents the ordered-ledger projection as *"the unblocker… already identified"*.
**Measured by execution on 2026-08-16, it unblocks half the problem.**

A **perfectly projected, perfectly classified** ledger on a **read-only run** still returns
`NO_EFFECTS_OBSERVED`, because `_decide` reads `is_effect`, `is_verification` and `UNCLASSIFIED` and
**never reads `Role.INSPECTION`**. Two inversions follow: **classifying a read correctly is worse than
admitting incomprehension**, and **taking a filesystem snapshot is worse than not taking one.**

**So the spec lists four admissible directions, not three.** The fourth — treating it as a vocabulary
/ consumer-contract problem — **is not in the milestone spec** and exists because of that
measurement. **See spec §D2 for all four with their costs, and §Escalation Triggers before touching
`_decide`.**

### And the method warning that goes with it: spec §F2

`parse_events` is **non-lossy** — it keeps every parsed JSON object. So *"can an ordered ledger be
projected?"* is a question about **what OpenCode's `--format json` stream actually contains**, not
about what Drivr's parser keeps. **Answering it by reading Drivr's code is verification at the wrong
layer — `P11-GH-2`'s recorded defect, by name.** Run the engine and look at the stream.

# Epic E36.2 — Renumber the misnumbered Layer-8/CFO note (+ B3.1 test obligation)

## Context

E36.1 is **merged** (PR #174, merge `f1a5e75`, 2026-08-04). Its two rules are on `milestone/M36`:
the **allocation rule** (next ID = highest in the directory + 1, regardless of issuing entity) and
the **separating rule** (*a bookkeeping defect never rewrites a citation in a normative document*).
Constraint 2 is therefore satisfied and this Epic is unblocked: **it applies a recorded rule rather
than inventing one.** That ordering was the whole point, and it is why this Epic could not run first.

The Layer-8/CFO Steering Note
(`.ai-project/artifacts/steering-notes/2026-07-31__layer-8-cfo__steering-note__system-hq-routing-model.md`)
claims `id: SN-1`, restarting a sequence that had already reached SN-27 — numbered as though System
HQ keeps its own sequence, while filed as though it belongs to `ai-project-system`'s. **HQ Ruling
2026-08-01, Decision 3 answers that: it is misnumbered.** Its citations are all non-normative, so
E36.1's separating rule sends it to **renumber** rather than **date-qualify**.

This Epic also carries M36's **one bounded mechanism exception**: discharging the obligation bugfix
B3.1 left behind (merged `65f83fe`, 2026-08-02). That is not new mechanism — it is the *completion*
of one already delivered, bounded to a single file.

---

## Problem Statement

**1. A duplicate ID with a live, ruled remedy.** Two Steering Notes claim `SN-1`: the original
2026-06-12 Creation Chat note and the 2026-07-31 Layer-8/CFO note. Unlike the `SN-23` collision —
which is permanent by decision — **this one is ordered cleared.**

**2. B3.1's guard breaks the moment it is cleared, and breaks in a way the P11 starter mis-predicted.**
`tests/test_steering_note_id_uniqueness.py` currently passes only because both collisions exist.
Renumbering `SN-1` makes `test_both_known_collisions_are_reported` **fail**, because it asserts
`set(duplicates) == {"SN-23", "SN-1"}`. This is not a hypothetical; it is arithmetic.

**3. The remedy cannot be "remove the xfail."** HQ Ruling 2026-08-01 **Decision 4** never renumbers
SN-23, so that collision is permanent, `test_steering_note_ids_are_unique` can **never** XPASS, and
deleting its marker leaves a plain failing test. The corrected obligation is constraint 2a below.

If this Epic is not completed: the ruled renumbering does not happen, and B3.1's guard remains a
test that passes for the wrong reason — green because the corpus is still broken.

---

## Goals

By the end of this Epic:

1. **The Layer-8/CFO note carries a non-colliding ID**, allocated by E36.1's now-recorded rule.
2. **Every prior citation of the old ID is traceable** — a reader following `SN-1` from any prior
   artifact reaches the renumbered note without guesswork.
3. **B3.1's guard is a plain passing test with one ruling-cited exception**, so a *third*,
   unratified collision still fails the suite — demonstrated, not asserted.
4. **The record no longer predicts an XPASS that cannot occur**, in any of the three places that
   currently do.

## Non-Goals

This Epic explicitly does **not** aim to:

- **Renumber SN-23.** Ruled 2026-08-01, Decision 4 — permanent by decision. E36.1 recorded why.
- **Re-derive the namespace question or the separating rule.** Both are recorded by E36.1. This Epic
  **applies** them.
- **Re-scope B3.1.** It is delivered and merged. The only obligation toward it is constraint 2a.
- **Build any new mechanism.** No registry, no validator, no linter. The single bounded exception is
  `tests/test_steering_note_id_uniqueness.py`, and the change there is *completion*, not creation.
- **Rewrite history.** Prior artifacts are amended with dated footnotes that leave the original claim
  legible — never silently edited.
- **Amend any `governance/` document.** This Epic touches `.ai-project/artifacts/` and `tests/` only.
- **Audit other artifact families.** E36.5's, and it reports rather than fixes.

### Constraint 2a — the B3.1 obligation, in its corrected form. Binding.

The P11 starter states that *"the moment E36.1/E36.2 clear those collisions the check XPASSes."*
**That is wrong and an Epic acting on it literally would deliver a red suite.** Decision 4 keeps
`SN-23` colliding permanently, so the check can never XPASS.

**What actually happens when you renumber:** the `SN-1` collision clears and
`test_both_known_collisions_are_reported` **fails** on its `== {"SN-23", "SN-1"}` assertion.

**Required end state — all four items binding:**

1. **`test_both_known_collisions_are_reported`** updated to the post-M36 corpus — **exactly one
   remaining collision, `SN-23`** — cited to HQ Ruling 2026-08-01 Decision 4 as ratified. Its name
   and docstring (*"Not just the first — SN-28 names two"*) no longer describe reality and must be
   brought into line.
2. **`test_steering_note_ids_are_unique`** converted from a blanket `xfail(strict=True)` into a
   **plain passing test carrying an explicit, ruling-cited allowlist of `SN-23`.** **No `xfail`
   marker remains.** A blanket xfail would make the guard blind to a *third*, unratified collision —
   the exact class B3.1 exists to catch. **The mechanism (module constant, parametrization, fixture)
   is this Epic's design decision; the property is not.**
3. **A synthetic third collision is shown to fail the suite** — demonstrated in a test, not asserted
   in prose. This is the acceptance criterion that proves the allowlist did not become a blanket.
4. **The stale "will XPASS" narrative corrected in place — in all three locations.**

> **Three, not one — verified on `milestone/M36`.** The milestone spec names the module docstring.
> There are **three** places carrying the wrong prediction, and a fix that corrects only the
> docstring leaves the other two contradicting the delivered code:
>
> | Location | Text |
> |---|---|

> | **`KNOWN_COLLISIONS_REASON`, lines ~64–68** | *"Cleared by P11-M36 …; strict=True so this fails as an XPASS once they are, forcing this marker's removal."* |

> constant either goes with it or is repurposed as the allowlist's justification — **either is
> acceptable; leaving it in place describing a removed marker is not.**

## Scope of Work

### 1. Renumber the note

Change the Layer-8/CFO note's `concerns[].id` from `SN-1` to the next free ID in the directory,
**determined at execution time by E36.1's recorded allocation rule.**

> **Verified on `milestone/M36`, 2026-08-04: IDs `SN-1`…`SN-28` are claimed with no gaps, so the
> next free ID is `SN-29`.** **Re-verify rather than trusting this** — a note filed between planning
> and execution would claim it, and B3.1's guard now catches that immediately. **Re-verification is
> a DoD item, not a courtesy.**

Update the note's own body wherever it refers to its concern by number, and record the rename in the
note itself so the artifact is self-explaining.

### 2. Footnote every prior citation

**The milestone spec says "both" citations. The verified count is three artifacts, ten
occurrences.** This is a divergence from the spec's planning-time inventory, re-measured on
`milestone/M36` at 2026-08-04:

| Artifact | Occurrences | Lines | Named in the milestone spec? |
|---|---|---|---|
| `rulings/2026-07-31__…__system-hq-routing-codification.md` | 3 | 4 (`concern_id:`), 13 (H1 title), 132 | ✅ yes |
| `progress-digests/2026-07-31__hq__progress-digest.md` | 3 | 65, 92, 106 | ✅ yes |
| **`rulings/2026-08-01__…__p11-opening-and-sn-26-27-28-triage.md`** | **4** | **63, 124, 219, 238** | ❌ **no — newly found** |

> **Why the spec said two, and why the finding is structurally interesting.** The milestone spec
> inherited the count from the 2026-08-01 ruling's own line 124:
>
> > *"**SN-1** is cited in two non-normative artifacts (a digest, a ruling). Renumber — cheap,
> > contained."*
>
> **The ruling that ordered the renumbering undercounted by not counting itself.** This is the same
> defect shape E36.1 was reworked for — a count stated in a record that omits the record's own
> contribution. Worth stating plainly in the delivery, because it is the second instance in this
> milestone and the pattern is now evidenced rather than anecdotal.

**Requirement:** every one of the three artifacts carries a dated footnote recording the old number
and the new one, sufficient that **following `SN-1` from any of them reaches the renumbered note
without guesswork.** Do not silently rewrite the ID in place — the rename must be **traceable**.

**One line needs more than a footnote — a judgment call this Epic owns.** Line 124 above is a
**factual claim that becomes doubly wrong**: the count was already three including itself, and after
this Epic the citations point at `SN-29`. A pointer-footnote does not repair a false count. **Decide
how to handle a stale factual claim versus a stale pointer, apply it consistently, and record the
distinction** — the *"amend, do not rewrite history"* discipline applies: leave the original claim
legible and add a dated correction. **Decide it; do not escalate it.**

### 3. Discharge the B3.1 obligation

Per constraint 2a above, all four items. `tests/test_steering_note_id_uniqueness.py` is the **only**
file in `tests/` this Epic may touch.

### 4. Confirm the frozen items

State explicitly in the Delivery Notice: SN-23's two notes still both carry `id: SN-23`; no
`governance/` document was amended; no second note was renumbered.

# Delivery Notice: P11-M38-E38.5 — Milestone-Context Evidence for `qwen3-coder:30b`

## Summary

**`qwen3-coder:30b`, measured through Ollama 0.30.0 at its loaded context window of 32,768 tokens, cannot hold a milestone's context.** The Milestone Chat's session-start document set alone — measured on M38's own material — occupies **~115.5% of the loaded window** before any conversation, evidence, or model output. This was confirmed by a marker-method probe that demonstrated **silent truncation**: a 63K-token prompt lost its position-0 marker, the model returned content from the end of the prompt, and neither the API nor the model reported the loss.

**This is a finding about the deployment, not about the model.** The model is fine; the 32,768-token window inherited through the `/v1` transport is too small for Milestone-scale context under this deployment's constraints. Row P4 is not decided by this evidence — a further HQ call decides it.

**The E35.5 model mismatch is recorded:** its 4-of-5 PASS belongs to `qwen3.6:27b`, chosen over `qwen3-coder:30b` because milestone work is general reasoning — and that model is absent from `opencode.json`.

## 1. Definition of "a milestone's context"

**Definition:** "A milestone's context" is the document set prescribed by the M38 Milestone Execution Chat Starter's "load at session start" context scoping (P9-M30-E30.3 standard) — the minimum viable set a model must hold to perform as a Milestone Chat conducting Stage-2 review of an Epic delivery.

**Justification:** The framework defines context scoping per level. The Milestone Execution Chat Starter's "load at session start" set is the authoritative boundary: it is the governance system's own answer to "what does a Milestone Chat need at session start." Using M38's own material avoids hypothetical scope — the milestone asking the question provides the answer. The definition was written and committed **before** any measurement result was computed (Constraint 10 — prevent fitting the definition to the result).

**Scope (load at session start):**

- M38 Milestone Execution Chat Starter (full)
- M38 Milestone Spec (full)
- Phase spec §P11.3 + §Milestones M38 entry + §Acceptance Criteria
- PSG: preamble, §1, §1A, §2, §5, §6, §7, §8, §9, §10, §11, §11.5, §11.6 (incl. §11.6.1), §12, §13C, §15
- AOG: preamble, §1, §1A, §2, §3.7, §3.9, §3.10, §4, §5, §6, §7, §9, §10, §12, §13, §14

Not included (load-on-trigger sections) — the measurement is of the session-start floor only. Adding them would increase the total.

## 4. Marker method probe and failure mode

**Method:** The phase spec §P11.3 marker method — plant a unique marker at position 0 of a prompt exceeding the suspected limit, ask for it back, and read `/api/ps` for `context_length`.

**Prompt:** 252,583 bytes (~63,145 estimated tokens at 4 bytes/token) — composed of the M38 milestone spec, phase spec, PSG, and AOG in full, with `MARKER_20260812_E38_5_PROBE_QWEN3_CODER_30B` at position 0.

**Command:**
```
curl -s http://localhost:11434/api/generate \
  -d '{"model":"qwen3-coder:30b","prompt":"<252KB prompt>","stream":false,"options":{"num_predict":30}}'
```

**Result:**

| Field | Value |
|---|---|
| `prompt_eval_count` | 32,764 |
| `done_reason` | `length` |
| `response` | `"END"` (from `END_OF_CONTENT_MARKER` at end of prompt, NOT the position-0 marker) |
| Marker at position 0 returned? | **NO** |
| `/api/ps` after probe | `context_length: 32768` unchanged |

**Failure mode: SILENT TRUNCATION.** The model processed only the last ~32,764 tokens of the ~63K prompt. The position-0 marker was lost without any error, warning, or signal. The model generated output ("END") as though nothing was wrong — the exact risk the phase spec names as the live danger.

**The usable window is equal to the loaded window (32,768 tokens) minus what the model has already consumed.** Content beyond that is silently dropped. A Milestone Chat session that loads its session-start context (~37,853 estimated tokens) will truncate before emitting a single token — and nothing will report it.

## 5. The honest finding: the model is fine, and the window is too small

**This measurement says nothing about the model's quality.** The variable that moved is the deployment: the `/v1` OpenAI-compatible endpoint used by the OpenCode adapter cannot set `num_ctx` (phase spec §P11.3 measured note), so 32,768 tokens is a fixed denominator through this path. At that window, Milestone-scale context does not fit — session-start alone is ~115.5% of capacity.

`local-agent-runner`'s native `/api/chat` honours `options` (including `num_ctx`), which would permit a wider window. That transport is not available through the adapter path today, and assessing it is E38.4's scope, not this Epic's.

**"The model is fine and the window is too small"** is the correct sentence. The finding is about the deployment, and a different deployment would produce a different result.

## 7. E35.5 model mismatch

**Recorded finding:** E35.5's 4-of-5 PASS with zero false alarms belongs to `qwen3.6:27b`, NOT `qwen3-coder:30b`. The model choice was deliberate — `qwen3.6:27b` was selected as a general reasoning model appropriate for Stage-2 review, while `qwen3-coder:30b` was listed only as an "optional comparator, if running it is cheap."

`qwen3.6:27b` is present in Ollama (`/api/tags` confirms) and declared nowhere in `opencode.json`. The model that passed the judgment back-test **is not currently routable through the OpenCode adapter** without a config addition — out of scope here, recorded for HQ.

**A fourth axis is only useful if the axes compose.** These two — judgment (E35.5) and capacity (E38.5) — were measured on different models. HQ should weigh this when ruling on row P4.

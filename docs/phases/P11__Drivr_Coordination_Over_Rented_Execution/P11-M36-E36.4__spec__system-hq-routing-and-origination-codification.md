# Epic E36.4 — System HQ Routing & Origination codification (SN-29 ruling, D1–D4)

## Context

**This Epic executes a ruling. It does not re-open one.** D1–D4 are **CFO decisions already made**,
recorded in the Layer-8/CFO Steering Note of 2026-07-31 (scribed by System HQ) and accepted by
`.ai-project/artifacts/rulings/2026-07-31__ai-project-system-hq__ruling__system-hq-routing-codification.md`,
Decisions 1–6. M36 executes it.

> **The source note is now `SN-29`, not `SN-1`.** E36.2 renumbered it (merged `65a512e`) by the rule
> E36.1 recorded. **Cite `SN-29`.** The milestone spec anticipated both orderings; E36.2 has landed,
> so the ambiguity is resolved — **an unqualified `SN-1` is what must not happen.**

The gap is real and verified on `milestone/M36` at planning time: `governance/systems/system-hq.md`
(v1.0.2) records only the `system_request` → `system_response` pair written back into the
**requesting** project, and `system-hq-seed.md` Rule 7 sanctions a Steering Note into a project only
in the re-instantiation context. **Neither A→B routing nor CFO-originated requests appear anywhere
normative, and both are standing practice.**

**This is the epic most likely to be misread as an authority expansion.** It is not one. Every
deliverable records practice already in use, and the SN-21/SN-22 pin against a "mighty governing
System Chat" stands unamended. The spec is written to make that legible in the diff.

---

## Problem Statement

**1. A→B routing is unrecorded.** When governed project A needs something from governed project B,
System HQ routes it via B's own artifact channels. That happens; nothing normative says so.

**2. CFO-originated requests are unrecorded.** The CFO (Layer-8) originates `system_request`s through
System HQ, which scribes them. That happens; nothing normative says so.

**3. The issuer-vs-scribe distinction has no normative statement, and losing it costs auditability.**
When System HQ scribes a CFO-originated request, the artifact must record the **true issuer**
(Layer-8/CFO), not the scribe. If the scribe becomes the apparent issuer, **the record loses the
ability to distinguish CFO-originated work from project-originated work** — and that distinction is
what makes the request chain auditable after the fact.

**4. A verbatim block reproduced across three documents is exactly what drifts under an adjacent
edit.** The Authority Boundary appears in `system-hq.md`, `system-hq-seed.md`, and
`chat-hierarchy.md`'s out-of-hierarchy annex. **This Epic edits one of those three.** Decision 4
therefore makes the agreement check a DoD item — *shown* identical after the edit, not assumed.

## Scope of Work

### 1. The *Routing & Origination* section in `governance/systems/system-hq.md`

Short. Recording, not expanding.

**Must include:**
- **D1** — route to project B via **B's own artifact channels**; **routing never commands** (B's
  chain triages under its own governance).
- **D2** — CFO-originated requests, **scribed**.
- **D3** — operating scope: **config and setup primarily**; planned work only in specific cases, and
  then **execution-only against artifact authorization**.

### 2. `steering_note` reused for the routed-to-B leg — with the reason recorded

**Record the reason, not merely the choice.** From Decision 3, and it is the load-bearing part:

> A `steering_note` **already encodes exactly the semantics D1 requires — direction, not
> authorization.** Inventing a `routing_request` would create an artifact whose authority semantics
> are **undefined on arrival**, and the first thing a receiving chain would have to decide is whether
> it must comply. **That question is precisely what D1 answers *no* to, and the existing type answers
> it by construction.** A new type would not merely be a larger decision — it would be a **worse**
> one.

Issuer: System HQ. Target: project B's HQ Chat. B's chain triages it like any other steering note.

### 3. The issuer-vs-scribe rule — verbatim DoD item (b)

**Must include:**
- When System HQ scribes a CFO-originated request, the artifact records the **true issuer
  (Layer-8/CFO), not the scribe.**
- **The scribing artifact must name both.**
- The reason: *if the scribe ever becomes the apparent issuer, the record loses the ability to
  distinguish CFO-originated from project-originated work — and that distinction is what makes the
  request chain auditable after the fact.*

> **The source note is itself a clean instance** — an instruction landing in a project asking it to
> work, filed as a `steering_note`, scribed by System HQ, with `issuer_chat` recording
> `Layer-8/CFO (scribed by System HQ at CFO instruction)`. **Verified on `milestone/M36`.** Worth
> citing: the rule is coherent in practice before it is coherent on paper, which is the SN-21
> pattern.

### 4. The byte-level Authority Boundary agreement check — verbatim DoD item (a)

**Verified baseline, measured on `milestone/M36` at planning time:**

| Document | Block location | Extent |
|---|---|---|
| `governance/systems/system-hq.md` | §Authority Boundary (normative) at line 54; block at **61–71** | 11 lines |
| `governance/systems/system-hq-seed.md` | §Authority Boundary at line 71; block at **77–87** | 11 lines |
| `governance/systems/chat-hierarchy.md` | out-of-hierarchy annex; block at **1077–1087** | 11 lines |

**They are identical today** — `sha256` prefix `baecaad4dbc2146c` for all three. **The Epic's job is
to keep them identical and to show it.**

> **Use a content-anchored check, not line numbers.** This Epic **adds a section to `system-hq.md`**,
> which shifts every line below it. A line-number-based check would break or, worse, silently compare
> the wrong range. The following was **written and run against `milestone/M36` at planning time** and
> is offered as a working starting point — **verify it yourself rather than trusting it**:
>
> ```bash
> extract() { awk '/^> \*\*System HQ Authority Boundary\.\*\*/{f=1} f{if(/^$/)exit; print}' "$1"; }
> for f in governance/systems/system-hq.md \
>          governance/systems/system-hq-seed.md \
>          governance/systems/chat-hierarchy.md; do
>   printf '%s  %s  (%s lines)\n' "$(extract "$f" | sha256sum | cut -c1-16)" "$f" "$(extract "$f" | wc -l)"
> done
> ```
>
> Expected on `milestone/M36` **before** the edit, and required **after** it:
> `baecaad4dbc2146c` × 3, 11 lines each.

**The evidence is the command and its output, committed with the delivery** — not a claim. Run it
**before** and **after** the edit and commit both.

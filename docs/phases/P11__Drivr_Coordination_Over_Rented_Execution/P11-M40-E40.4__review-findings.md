### B1 — `bin/ai-project-validate` (8 findings)

Quoted verbatim; the full text is in `local-model-findings.json`. Locations are the model's own and
are wrong as tabled above.

**Performance**

> **Concern**: Inefficient repeated YAML serialization/deserialization in `Node.value` property.
> […] The `value` property uses `yaml.serialize(self.node)` followed by `yaml.safe_load()` to get the
> resolved value. This is inefficient because it serializes the node to YAML string and then parses
> it back, when the original parsed value should be available directly from `self.node.value`.
> **Why it matters**: This pattern is repeated throughout the codebase for accessing node values,
> creating unnecessary overhead during validation of multiple configs or large files.

> **Concern**: Inefficient regex compilation in global scope. […] This means the regex objects are
> created once per process, which is fine, but the repeated use of these in validation loops could be
> optimized.

> **Concern**: Inefficient string conversion in `Node.keys()` method. […] uses `yaml.serialize(k)`
> followed by `yaml.safe_load()` to convert keys to strings, which is unnecessarily complex and
> costly for simple key access.

*Note, kept separate from the quote:* the serialize→parse round-trip is **real** and does recur at
four sites. The regex finding **argues itself down to "which is fine"** in its own text — a finding
that concludes there is no problem, reported as a concern.

**Security**

> **Concern**: No input sanitization or validation of file paths. […] The `resolve_targets` function
> directly uses user-provided paths without any path traversal checks or sanitization. […] While this
> tool is designed for validation and not modification, a maliciously crafted path could potentially
> cause unexpected behavior […]

> **Concern**: Potential command injection via file content. […] If a malicious YAML file were to
> contain specially crafted content, it could potentially exploit edge cases in the
> serialization/deserialization process.

*Note:* the second is titled **"command injection"** and describes no command execution; the file
runs none on parsed content, and `yaml.safe_load` is used throughout — the model says so itself, then
reports the concern anyway. **A severe-sounding title attached to a speculative body is exactly what
an unfiltered pipeline would escalate.**

**Scalability**

> **Concern**: Memory usage grows linearly with number of validation runs. […] `reports =
> [validate_file(t) for t in targets]` […] For large fleets, this could consume significant memory.

> **Concern**: No parallelization support for validation. […] As fleet size increases, performance
> degradation becomes exponential.

> **Concern**: Inefficient handling of large YAML documents. […] the repeated
> serialization/deserialization overhead will impact scalability and performance as document size
> increases.

*Note:* *"degradation becomes exponential"* is false as written — sequential validation of *n* files
is linear in *n*. The fleet is **eight** projects with configs of tens of lines.

### B2 — `bin/run-qa-agent` (9 findings)

**Performance:** reading the whole config to extract `models.epic_qa`; repeated `Path(...).exists()`
checks in `main`; string concatenation in `build_qa_context`.

**Security**, quoted:

> **Potential command injection via `runner` discovery**: The script uses `dev.discover_runner()`
> which likely returns an executable path. If this function does not properly validate or sanitize
> the discovered runner path, it could allow an attacker to inject a malicious binary if they control
> part of the PATH or have write access to directories in the search path.

> **No input sanitization for `epic_id` before directory creation**: Although `safe_epic_id` is
> generated using regex substitution, there's no explicit check that this sanitized version doesn't
> result in a path traversal vulnerability when used with `artifact_dir = ARTIFACT_ROOT /
> safe_epic_id`.

> **Tool set validation relies on JSON parsing without schema validation**: The script parses
> `qa-tools.json` but doesn't validate its structure against a known schema. If an attacker can
> modify this file, they might introduce malformed JSON or unexpected fields […]

**Scalability:** the hardcoded `FORBIDDEN_EPIC_IDS` set; sequential section processing in
`extract_standard`; no concurrency control when multiple QA agents write artifacts.

*Note:* the first security item is hedged on its own premise (*"which likely returns"*, *"if this
function does not properly validate"*) — it is a question about `discover_runner()`, reported as a
finding about `run-qa-agent`. The third is conditioned on an attacker already having write access to
the repository's committed tool policy.

### B3 — `bin/local-agent-runner-shim` (3 findings)

> **PERFORMANCE** […] The script uses `exec` with a variable `$@`, which may cause performance
> overhead in some shells due to argument handling. […] However, this is a minor concern and likely
> negligible in practice.

> **SECURITY** […] The script does not validate or sanitize the `LOCAL_AGENT_RUNNER_HOME` path before
> using it. […] If an attacker controls the `LOCAL_AGENT_RUNNER_HOME` environment variable, they
> could potentially manipulate the script to execute arbitrary code by pointing it to a malicious
> directory.

> **SCALABILITY** […] The script hardcodes `python3` as the interpreter without checking if it's
> available or appropriate.

*Note:* the performance item is **wrong** — `exec` replaces the process image and removes a fork; it
does not add argument-handling overhead — and the finding retracts itself in its final sentence. The
scalability item is wrong on its face: line 40 is `exec "${PYTHON:-python3}" -m local_agent_runner
"$@"`, which is **not** a hardcoded interpreter; `PYTHON` overrides it. The security item describes
the normal contract of an env-var-configurable shim, where an attacker who controls the environment
of your shell has already won.

## Nothing here was escalated, and why

The Epic spec requires escalation if *"a finding looks serious enough to demand action."* **No
finding met that bar**, assessed as follows:

- **Copilot's three** are a diagnostic-message improvement, a stale PR description, and a formatting
  nit. A2 is genuinely worth someone's attention and is surfaced to the Milestone Chat in this file;
  none is a defect in shipped behaviour.
- **The local model's twenty** name real constructs but arrive with **uniformly wrong locations**,
  several are self-retracting, the two "command injection" items describe no command execution, and
  the remainder are ordinary engineering observations about a validator that runs over eight small
  YAML files.

**The performance observation with the most substance** — `Node.value`'s serialize→parse round-trip
recurring at four sites — is a real characteristic of that file and is left standing as a finding.
Acting on it is out of scope by construction.

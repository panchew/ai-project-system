# E38.4 — `local-agent-runner` Retention Assessment

## Judgment

**Retain `local-agent-runner` for now.** OpenCode 1.18.10 does not cover the runner's C3 contract:
OpenCode's structured `serve` output distinguishes an ordinary finish from a crash and an abort, but a
configured `maxSteps` ceiling is returned as ordinary `finish: "stop"`. It therefore does **not**
distinguish **ran out of iterations** from **finished**, where `local-agent-runner` returns
`status: "max_iterations_exceeded"` and exit 2.

OpenCode also does not cover C1 for Drivr's chosen language, Python, and its plugin boundary does not
cover C2: mistyped primitive arguments reached a `z.number()` tool handler as strings, neither coerced
nor rejected. C3 is the load-bearing retention reason because P11/M39 specifically needs trustworthy
completion evidence.

**Nothing was retired.** This assessment does not decide whether a run completed; it only records the
signals each engine exposes. M39 owns the completion judgment. G11 is not claimed.

## Bar applied

The spec's **three-candidate fallback** applied: C1, C2 and C3.

The Creation Chat proposed the bar *"names a capability P11 actually needs that OpenCode does not
provide"* in SN-27 A1.2. HQ Decision 10 explicitly returned that proposal to the CFO **unacted**. A
repository-wide search on 2026-08-12 found no later CFO acceptance or replacement. The assessment did
not invent a fourth bar.

## Method and layers

| Layer | What was measured |
|---|---|
| host, 2026-08-12 | OpenCode binary 1.18.10, its real `serve` HTTP API, local JS/TS SDK and plugin 1.15.13, and Ollama-backed live calls |
| host, `~/soft-dev/local-agent-runner` @ `4ec1e8f`, 2026-08-12 | runner exports, signature, coercion, exit codes and statuses; no file modified |
| this repo, `epic/P11-M38-E38.4`, 2026-08-12 | measurement harness, evidence record and suite |

The OpenCode tests used an isolated `XDG_CONFIG_HOME`, isolated empty git workspace, and a plugin tool
whose `execute` function recorded its received arguments and runtime types. The user's OpenCode config
was not modified. Live model calls used `qwen2.5-coder:7b` and `llama3.1:8b`; no 30B model was loaded.

All C3 conclusions below come from HTTP status, structured message parts, session status, or SSE event
payloads — never from model prose.

## Runner-side re-measurement

All three candidates remain present at `local-agent-runner` HEAD `4ec1e8f`:

| Candidate | Re-measured contract |
|---|---|
| C1 | `__all__` exports `run`, `Result`, `ToolPermissions`, `OllamaClient`; `run(model, task, permissions, *, endpoint, max_iterations, system, context, options, client) -> Result`; `client` is injectable |
| C2 | `coerce_arguments(arguments, json_schema)` coerces strings to integer, number or boolean for flat schemas; string properties are never coerced; unknown properties pass through; missing/unusable values raise |
| C3 | exit 0 `EXIT_COMPLETED`, exit 2 `EXIT_DID_NOT_CONVERGE`, exit 3 `EXIT_CONFIG_ERROR`, exit 4 `EXIT_RUNTIME_ERROR`; result statuses `completed`, `max_iterations_exceeded`, `error`; CLI uses `sys.exit(main())` |

One small export asymmetry was noticed: `STATUS_ERROR` exists in `loop.py` but is not in package
`__all__`. It does not change the returned `Result.status` contract and was deliberately left.

## C1 — Python in-process entry point

**Result: OpenCode does not provide C1 for Drivr's chosen language.**

E38.1 chose **Python 3**. There is no importable Python `opencode` module on the host. The installed
OpenCode library-shaped surfaces are JS/TS: `@opencode-ai/sdk` 1.15.13 and
`@opencode-ai/plugin` 1.15.13, while the running binary is 1.18.10.

Tested for real against binary 1.18.10:

```text
$ opencode serve --port 4179 --hostname 127.0.0.1 --print-logs
opencode server listening on http://127.0.0.1:4179

$ curl http://127.0.0.1:4179/doc
HTTP 200; OpenAPI 3.1.0; 162 paths

$ curl http://127.0.0.1:4180/experimental/tool/ids
[...,"probe_number"]
```

This proves a real headless HTTP API and real JS/TS in-process plugin tool registration. For Python,
both are out-of-process boundaries. They are useful equivalents to Drivr's adapter needs, but neither
is the runner's Python in-process `run(...) -> Result` entry point with injectable client and handlers.
If Drivr were JS/TS, this conclusion would need to be re-run against a version-matched SDK/plugin; with
Drivr as Python, the language boundary decides it.

## C2 — recovery from mistyped primitive tool arguments

**Result: OpenCode 1.18.10 provides neither C2 recovery nor validation at the tested plugin boundary.**

The test plugin declared `count` with `tool.schema.number()` and recorded what reached `execute`.
`llama3.1:8b` made real tool calls through `serve`:

| Model argument | Structured tool state | Handler received | Outcome |
|---|---|---|---|
| `8` | `status: "completed"`, `input.count: 8` | number `8` | normal baseline |
| string `"8"` | completed | string `"\"8\""` | passed through, not coerced |
| string `"banana"` | `status: "completed"`, `input.count: "banana"` | string `"banana"` | passed through, not rejected |

The `banana` case is decisive: a value unusable as a number reached `execute` and the structured tool
state still reported completed. Rejection would have been validation rather than C2 recovery; OpenCode
did neither. `local-agent-runner`'s narrower capability — flat-schema primitive recovery with explicit
limits — remains distinct.

`qwen2.5-coder:7b` also emitted a requested tool call as literal text with `finish: "stop"`, reproducing
E38.2's Run B observation. That is model/transport behaviour, not a fourth retention candidate.

## C3 — completion-adjacent structured outcomes

**Result: partial OpenCode coverage, not contract equivalence. OpenCode cannot distinguish configured
step-ceiling exhaustion from ordinary finish in the returned structured result.**

### Ordinary finish

A real `/session/{id}/message` request returned HTTP 200 and structured assistant
`finish: "stop"`. Session status was idle/absent after completion.

### Crash

A real request naming a nonexistent Ollama model returned:

```json
{
  "http_status": 500,
  "body": {
    "name": "UnknownError",
    "data": {"message": "Unexpected server error. Check server logs for details.", "ref": "err_44956b08"}
  }
}
```

OpenCode `serve` therefore distinguishes this crash from ordinary finish at the HTTP boundary.

### Abort

An asynchronous real request transitioned `session.status` to `busy`; POST `/abort` returned HTTP 200
and `true`. The SSE stream emitted:

```json
{"type":"session.error","properties":{"sessionID":"ses_...","error":{"name":"MessageAbortedError","data":{"message":"Aborted"}}}}
{"type":"session.status","properties":{"sessionID":"ses_...","status":{"type":"idle"}}}
{"type":"session.idle","properties":{"sessionID":"ses_..."}}
```

OpenCode distinguishes abort from ordinary finish, although `busy`/`idle` are transport activity
states, not completion judgments.

### Configured step ceiling

The OpenAPI schema exposes `AgentConfig.maxSteps`; the CLI exposes no corresponding iteration flag.
With isolated config `agent.build.maxSteps: 1`, a real prompt requesting two tool calls produced this
server log:

```text
message=loop session.id=ses_... step=0
message=process session.id=ses_... messageID=msg_...
message=loop session.id=ses_... step=1
message="exiting loop" session.id=ses_...
```

The returned structured message was:

```json
{
  "info": {"finish": "stop", "tokens": {"output": 1}},
  "parts": [
    {"type": "step-start"},
    {"type": "step-finish", "reason": "stop"}
  ]
}
```

No tool executed, no `session.error` was returned, and `/session/status` was `{}` afterward. The engine
internally knew it had reached `step=1` and exited the loop, but the caller received the same
`finish: "stop"` shape as ordinary finish. This is not equivalent to the runner's explicit
`max_iterations_exceeded` status and exit 2.

### Full-contract comparison

| Outcome | `local-agent-runner` | OpenCode `serve` 1.18.10 |
|---|---|---|
| finished | status `completed`, exit 0 | HTTP 200, assistant `finish: "stop"` |
| ran out of iterations/steps | status `max_iterations_exceeded`, exit 2 | configured ceiling exits internally; caller receives `finish: "stop"` |
| crashed | status `error`, exit 4 | non-2xx typed error body; tested case HTTP 500 `UnknownError` |
| configuration error | exit 3 before loop | HTTP 4xx schemas exist; not equivalent to the runner's process exit contract |
| aborted | no separate runner status in the measured three-value contract | SSE `session.error` / `MessageAbortedError` |

The additional abort signal is a useful OpenCode capability discovered during C3 testing. It is
recorded as a finding, not added as a fourth candidate.

## Input to M39

The B3.1 field evidence showed the runner emit exit 2 plus `max_iterations_exceeded` while OpenCode
`run` exited 0 after doing no work. This assessment shows that `serve` improves the picture — crashes
and aborts are structured — but **does not remove the load-bearing gap**: ceiling exhaustion is folded
into ordinary `finish: "stop"`.

M39 should therefore plan with two facts already established:

1. the current sole roster engine does not expose a distinct ceiling-exhausted result through the
   tested `serve` response; and
2. `local-agent-runner` already exposes a three-valued result status including
   `max_iterations_exceeded`.

That is input evidence only. No rule deciding whether a run truly completed was built here.

## Route B.2

**The trigger did not fire.** This assessment retains the runner, satisfying the first limb. E38.2
implemented sandboxed dispatch as Drivr's default Direction B and host dispatch as selectable
Direction A, so the adapter **does cover sandboxed dispatch**; the second limb is false. The conjunctive
trigger therefore remains false, and the runner was not installed into the sandbox image.

## Things noticed and deliberately left

1. SDK/plugin 1.15.13 versus binary 1.18.10 version skew; no packages were upgraded.
2. `STATUS_ERROR` is not in the runner package's `__all__`; the runner was not modified.
3. OpenCode's plugin boundary accepted values contrary to its Zod declaration; OpenCode was not fixed.
4. OpenCode exposes a structured abort event not present in the runner's measured three-status result;
   this is a finding, not a new candidate.
5. `qwen2.5-coder:7b` rendered a tool call as text; no model-quality judgment was made.
6. The B3.1 matched-constraint fair re-run remains unrun, as required; its confound was not adopted.
7. The large generated OpenAPI snapshot is reproducibility input, not a normative API guarantee; the
   tested binary version remains the authority for this measurement.

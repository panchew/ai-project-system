# E40.4 — The Review Configuration (D1) and its Evidence (D2)

**Two reviewers, one real PR, no authority.** This file records what was configured (D1) and the
GitHub-side evidence that the configuration cannot be read as granting review authority (D2).

Every measurement below states its **layer, time and scope**, per `P11-GH-2`. That obligation is not
decoration here: this epic found a live instance of the defect in its own prerequisite check, and
that instance is recorded in §The layer trap, below.

---

## D1 — What was configured

### Reviewer A — GitHub Copilot code review

**Invoked, not automated.** Copilot was requested as a reviewer on PR #173 by a single API call:

```
gh api --method POST repos/panchew/ai-project-system/pulls/173/requested_reviewers \
  -f 'reviewers[]=copilot-pull-request-reviewer[bot]'
```

`2026-08-17T19:44:17Z`. **No file was added to the repository to make this happen**, and none is
needed. `.github/` remains absent (§D2).

### Reviewer B — a local model, `qwen3-coder:30b`, via Ollama

**Delegated decision 1 — which competing model, and its cost.**

Chosen: **the local model**, driven through Ollama at `http://localhost:11434`, by the committed
script [`run_competing_review.py`](../../../.ai-project/artifacts/reviews/P11-M40-E40.4/run_competing_review.py).

*Reasoning.* It is coherent with the phase spine — P11 is about renting execution, and this lane is
the one the phase already built — and it **avoids a second external dependency** in an epic that
already carries one (R2). A second hosted reviewer would have added an account, a subscription and a
second thing that can be switched off outside this repository, in the phase's final milestone.

*The cost, stated.* `qwen3-coder:30b` at Q4_K_M is a much weaker reviewer than Copilot, and it
showed: **every line number it produced was wrong** (§Findings, and the findings file). The choice
bought independence from external configuration and paid for it in finding quality. That trade is
recorded rather than hidden, because a reader comparing the two reviewers must not conclude that
"local review is as good" — this run is evidence that, on this task, it was not.

*Engine reachability, measured `2026-08-17T19:45:14Z`, from this sandbox:*

| Endpoint | `/api/tags` |
|---|---|
| `http://localhost:11434` | **200** |
| `http://127.0.0.1:11434` | **200** |
| `http://host.docker.internal:11434` | **000** |

This is the **reverse** of the shape B2.1 established, where `host.docker.internal` was the reachable
route and loopback was the negative control. M40 has already recorded that an engine now resolves
here on the reversed shape; this epic re-measured it independently and observed the same reversal.

### Delegated decision 2 — which PR, and what was optimised for

**Chosen: PR #173** — the phase delivery PR, `phase/P11` → `master`, open since 2026-08-03.

**Optimised for relevance, not size.** #173 is precisely the PR that PSG §11.6.1's CFO diff review
applies to at phase closure (§5C step 6), so findings on it **feed the review they are meant to
feed**. The alternative — an M40 epic PR — would have been smaller and fresher, but every M40 epic PR
was already merged by the time this epic ran (E40.1 at `e4a1388`, E40.2 at `efa1338`, E40.5 at
`724c66a`), leaving #173 as the only open PR in any case. Measured `2026-08-17T19:43:39Z` at the
GitHub layer: `gh pr list --state open` → **one** PR, #173.

**Size, and what it did to scope.** #173 is **187 changed files, +87,562 / −84**. The two reviewers
did **not** see the same material, and no claim here depends on pretending they did:

| Reviewer | Scope actually reviewed | How that was determined |
|---|---|---|
| Copilot | **90 of 187 changed files** | Copilot's own review body states it |
| `qwen3-coder:30b` | **3 files, 1,078 lines** — `bin/ai-project-validate`, `bin/run-qa-agent`, `bin/local-agent-runner-shim` | Scoped by this epic; see below |

The local model was given the **shipped executable code** the PR adds, because that is where
performance, security and scalability findings can exist at all. The other ~45,000 added "code" lines
are captured evidence artifacts (probe responses, run metadata, registry snapshots) — data, not
running code. **This is a scoping decision, not a coverage claim.** Neither reviewer reviewed the
whole PR, and this is therefore **not a controlled comparison** between them.

### Delegated decision 3 — where findings are captured, and in what shape

- **Human-readable, verbatim:** `docs/phases/P11__.../P11-M40-E40.4__review-findings.md`
- **Machine-readable raw capture:** `.ai-project/artifacts/reviews/P11-M40-E40.4/`

### Delegated decision 4 — triggered automatically, or invoked per PR?

**Invoked per PR. Neither reviewer runs automatically, and nothing in this repository triggers
either one.**

The spec permits automatic *triggering* while prohibiting automatic *acting*. This epic declined the
permitted half as well, for a reason worth recording: **automatic triggering would have required
adding repository configuration** — a ruleset that requests Copilot review, or a workflow that runs
the local model. R1 records that `.github/` is absent and that *whatever this epic adds becomes the
repository's precedent*. The strongest available answer to acceptance criterion 2 is therefore that
**there is no configuration to read**: no ruleset, no workflow, no `CODEOWNERS`, no `.github/` at all.

*The cost, stated.* A human must invoke the reviewers. Nothing reviews a PR unless someone asks. That
is a real ergonomic cost and it is the conservative direction on the only axis this epic cares about.

## D2 — The configuration evidence

### The layer trap — a live `P11-GH-2` instance, found in this epic's own prerequisite

**Prerequisite 4 asked whether Copilot review is enabled. Three layers gave two different answers.**

Measured `2026-08-17T19:44:16Z`–`19:44:48Z`, GitHub API, PR #173:

| Layer | Query | Answer |
|---|---|---|
| REST, PR object | `pulls/173` → `requested_reviewers` | **`[]` — no reviewer requested** |
| REST, timeline | `issues/173/timeline` → `review_requested` | **`Copilot`, `2026-08-17T19:44:17Z`** |
| GraphQL | `pullRequest.reviewRequests` | **`Bot / copilot-pull-request-reviewer`** |

**The obvious field is the one that lies.** `requested_reviewers` is what `gh pr view` surfaces and
what a reasonable person checks. Had this epic trusted it, it would have escalated *"Copilot review
cannot be enabled"* to the Milestone Chat — **a false blocker raised against the final milestone of
the phase**, on the strength of a field that simply does not enumerate bot reviewers.

**And the HTTP status is worthless as evidence.** A negative control run at `19:44:28Z` requested
review from `this-user-does-not-exist-zzz9`; the API returned **HTTP 200** and the full PR object,
exactly as the real request had. The bogus request produced **no timeline event and no GraphQL node**.
So the 200 discriminates nothing; the timeline and GraphQL layers discriminate correctly.

**Resolution: Copilot was enabled and working.** `copilot_work_started` at `19:44:59Z`; review
submitted `19:50:34Z`. **No escalation was owed and none was raised.**

### `.github/` is absent — and an active workflow exists anyway

**This is the epic's sharpest confirmation that reading the tree answers the wrong question.**

| Layer | Measurement | Result |
|---|---|---|
| Tree, `epic/P11-M40-E40.4` | `git ls-files .github` | **empty — nothing** |
| Tree | `git ls-files CODEOWNERS .github/CODEOWNERS docs/CODEOWNERS` | **empty — nothing** |
| GitHub, `19:47:44Z` | `repos/.../actions/workflows` | **1 workflow: `Copilot`, path `dynamic/agents/copilot-pull-request-reviewer`, state `active`** |
| GitHub, `19:47:44Z` | `commits/refs/heads/phase/P11/check-runs` | **1 check run: `copilot-pull-request-reviewer`, app `github-actions`** |

The workflow was created at `2026-08-17T19:44:26Z` — **nine seconds after the review request**, by
the request. It is *dynamic*: it exists on GitHub, it is `active`, it produced a check run on the head
commit, and **it has no representation in the tree whatsoever**.

A reader who ran `ls -a .github/`, saw nothing, and concluded *"no workflows, no checks, nothing that
could gate a merge"* would be **wrong on all three counts**. That is `P11-GH-2`'s recorded defect,
reproduced live.

| Mechanism | Measurement | Result |
|---|---|---|

| Branch protection, `phase/P11` | `branches/phase%2FP11/protection` | **404 "Branch not protected"** |
| Branch protection, `milestone/M40` | `branches/milestone%2FM40/protection` | **404 "Branch not protected"** |
| Rulesets | `repos/.../rulesets` | **`[]`** |
| Required status checks | *no protection and no ruleset exists to require anything* | **none** |
| Webhooks | `repos/.../hooks` | **`[]`** |
| Auto-merge | `allow_auto_merge` | **`false`** |
| `CODEOWNERS` | tree, all three canonical locations | **absent** |
| Collaborators with write | `repos/.../collaborators` | **`panchew` only** (admin+push) |
| Deploy keys | `repos/.../keys` | **`[]`** |
| Copilot's review verdict | `pulls/173/reviews` | **`COMMENTED`** — not `APPROVED`, not `CHANGES_REQUESTED` |

**The check run exists and is not required.** `copilot-pull-request-reviewer` completed with
conclusion **`success`** at ~`19:50:37Z`. With no branch protection and no ruleset, **no check is
required**, so its conclusion gates nothing. It is the raw material a required check would be built
from — which is exactly why D5 names it.

`CODEOWNERS` is checked at the **tree** layer and that is the correct layer for it: `CODEOWNERS` is a
tracked file by definition. The claim is not "no `CODEOWNERS` was added" but "no `CODEOWNERS` exists
in any of the three locations GitHub reads." Independently, **no model holds write access**, and
`CODEOWNERS` approval requires it.

### Two signals that invite misreading

1. **The legacy commit-status API returns `state: "pending"` with `total_count: 0`.** "Pending" here
   means *no statuses exist*, not *a check is running*. A reader looking for "is anything gating
   this?" gets a word that suggests yes and a count that means no.
2. **`conclusion: "success"` on the Copilot check run does not mean Copilot approved.** It means the
   review job ran. Copilot's actual review state is `COMMENTED`. The two are independent, and only
   one of them is a verdict-shaped word.

### An inventory is a floor — including this one

The spec names **five** prohibited paths. Method obligation 6 says five is the floor. Beyond the five,
this epic checked, and records, these further ways configuration could convert findings into
authority:

6. **Auto-merge** (`allow_auto_merge`) — with a required check, a merge completes without a human
   act. **Verified `false`.**
7. **Repository rulesets** — a separate, newer mechanism from branch protection, able to require
   reviews and to auto-request Copilot review. Checking branch protection alone would miss it.
   **Verified `[]`.**
8. **Webhooks** — an external listener on `pull_request_review` could act on a finding outside
   GitHub's own controls entirely. **Verified `[]`.**
9. **Actions workflows** — a workflow with write permission could commit a suggestion or resolve a
   thread. **Verified: one workflow, and it is the dynamic Copilot agent itself, not a repository
   workflow.**
10. **Deploy keys and collaborators** — write access held by a non-human. **Verified: no deploy keys;
    `panchew` is the only account with write access.**
11. **A `success` check conclusion read as an approval** — not a technical grant of authority, but a
    human-facing one, and the failure mode this epic is guarding against is precisely a configuration
    that *reads* as authority.

**One item could not be verified, and is recorded as a gap rather than an assumption:**

12. **GitHub App installations with write access.** `repos/.../installations` → **404**;
    `user/installations` → **403 "You must authenticate with an access token authorized to a GitHub
    App"**. A user token cannot enumerate them. What *can* be stated: no protection or ruleset exists
    that could make any app's output required, no non-owner account holds write access, and the
    reviewed content did not move (§D4). **The enumeration itself remains unperformed.**

## The two reviewers did not agree, and there was nothing to convert

Copilot produced **3** findings; the local model produced **20** (8 + 9 + 3 across its three
targets). **They overlap on nothing** — not a
file, not a concern, not a line. Copilot commented on `tests/test_fleet_registry.py`,
`governance/systems/fleet-operator.md`, and the PR description; the local model reviewed three `bin/`
scripts Copilot left uncommented.

There was accordingly **no agreement available to convert into a verdict** — which is fortunate,
because per the ceiling there is no mechanism that would have converted it, and none was built. Two
models agreeing would still have been two opinions.

# Contributing to AI Project System

Thank you for your interest in contributing to the AI Project System! This document explains how to contribute effectively.

---

## Welcome

Contributions are valued and appreciated. This system is designed to help engineers build better AI-assisted projects, and your experience using it makes you uniquely qualified to improve it.

**We especially value:**
- **Real usage experience** — Feedback from actual projects using this system
- **Clarity improvements** — Better explanations, examples, or documentation
- **Bug reports** — Issues with governance, unclear instructions, or broken examples

---

## Types of Contributions

### ✅ We Welcome

**Documentation improvements:**
- Fixing typos, broken links, or formatting issues
- Clarifying confusing sections
- Adding examples or use cases
- Improving template guidance

**Bug reports:**
- Governance conflicts or ambiguities
- Unclear procedures or missing steps
- Broken examples or outdated references

**Real-world usage questions:**
- "How do I handle [specific scenario]?"
- "This governance rule doesn't fit my project because..."
- Questions that reveal gaps in documentation

**Governance clarifications:**
- Proposals to resolve ambiguities
- Suggestions to simplify complex rules
- Improvements based on real usage experience

### ❌ Not Accepted (Without Discussion)

**Speculative features:**
- "It would be cool if..." (without real usage motivation)
- Major redesigns or new concepts not proven in practice
- Tooling, automation, or CLI proposals (too early)

**Style preferences:**
- "I prefer X over Y" without functional justification
- Reformatting that doesn't improve clarity

**Out-of-scope additions:**
- Multi-language translations (premature)
- Marketing materials or promotional content
- Community infrastructure (Discord, forums, etc.)

**If you're unsure:** Open an issue first to discuss.

## How to Contribute

### 1. File an Issue First

Before submitting a pull request, **open an issue** to discuss:
- What problem you're solving
- Your proposed solution
- Why it's needed (real usage context preferred)

**This prevents wasted effort on changes that won't be accepted.**

**Exception:** Obvious fixes (typos, broken links) can skip the issue.

### 2. Reference Relevant Governance

When proposing changes:
- Reference specific sections of [PROJECT-SYSTEM-GUIDELINES.md](governance/PROJECT-SYSTEM-GUIDELINES.md) or [AI-OPERATING-GUIDELINES.md](governance/AI-OPERATING-GUIDELINES.md)
- Explain how your change aligns with or improves existing governance
- If your change conflicts with governance, explain why the rule should change

### 3. Follow Existing Documentation Style

**Markdown formatting:**
- Use ATX-style headers (`#`, `##`, `###`)
- Include front-matter for specs and templates
- Use fenced code blocks with language tags
- Follow existing file naming conventions (see [docs/README.md](docs/README.md))

**Tone:**
- Professional and clear
- Honest about trade-offs (not marketing-speak)
- Practical and usage-driven (not theoretical)

### 4. Provide Real Usage Context

**Strong contributions include:**
- "I tried to use [template/process] for [project] and encountered [problem]"
- "This governance rule didn't make sense because [real scenario]"
- "I had to do [workaround], which suggests [improvement]"

**Weak contributions:**
- "I think this would be better if..."
- Theoretical scenarios without actual usage

**We prioritize improvements based on real experience over speculation.**

## Contribution Process

### Step-by-Step

1. **Fork the repository**
   - Create your own fork of `panchew/ai-project-system`

2. **Create a feature branch**
   - Use descriptive branch names (e.g., `docs/clarify-epic-closure`, `fix/broken-example-link`)

3. **Make your changes**
   - Follow existing style and conventions
   - Update relevant documentation
   - Test examples if applicable

4. **Commit with clear messages**
   - Use descriptive commit messages
   - Reference the issue number (e.g., "Fix broken link in FAQ (#42)")

5. **Submit a pull request**
   - Target the `master` branch (or `develop` if specified in issue)
   - Include a clear description:
     - What changed and why
     - What problem it solves (reference issue)
     - Any testing or validation done
   - Link to the related issue

6. **Respond to feedback**
   - Maintainers may request changes or clarifications
   - Be responsive and collaborative

## Code of Conduct

**Be respectful, constructive, and collaborative.**

**Expected behavior:**
- Assume good faith in others' contributions
- Provide constructive feedback
- Focus on ideas, not people
- Respect different perspectives and experience levels

**Unacceptable behavior:**
- Personal attacks or harassment
- Dismissive or hostile comments
- Bad faith arguments or trolling

**Enforcement:** Maintainers will remove comments or ban contributors who violate these expectations.

# Epic E1.1 — Task Creation & Storage

## Context

The Personal Task Tracker CLI requires a foundational capability: creating tasks. Before users can list, complete, or organize tasks, they must first be able to create them.

**Current State:**
- ✅ Repository structure established (Phase 0)
- ✅ Phase 1 initiated
- ✅ Milestone M1 active
- ❌ No task management functionality exists

**Why Now:**
Task creation is the most fundamental operation. Without it, no other task management features are possible. This Epic establishes the data model and creation workflow that all future Epics will build upon.

---

## Problem Statement

**Current State:**
- No way to create tasks
- No task data model defined
- No storage mechanism exists

**Gap:**
Users cannot create tasks, which is the most basic requirement for any task management tool.

**Impact if not addressed:**
- Tool is completely non-functional
- Cannot proceed to E1.2 (Task Listing) or E1.3 (Task Completion)
- Cannot validate that the system architecture works

**Solution:**
Implement a task creation command (`task add "description"`) with proper data model, validation, and in-memory storage.

---

## Goals

By the end of this Epic:

1. **Task data model defined** — Clear structure for task objects (ID, description, status, timestamps)
2. **Task creation command works** — Users can create tasks via `task add "description"`
3. **In-memory storage implemented** — Tasks are stored and retrievable (file persistence in M3)
4. **Input validation works** — Invalid input rejected with clear error messages
5. **Basic tests exist** — Core functionality is tested

---

## Scope of Work

### 1. Task Data Model

**Define `Task` class:**

```python
@dataclass
class Task:
    id: str              # UUID generated on creation
    description: str     # User-provided text (max 500 chars)
    status: str          # "pending" | "completed"
    created_at: datetime # Auto-set on creation
    completed_at: Optional[datetime] = None  # Set when completed
```

**Validation Rules:**
- Description: Required, 1-500 characters, non-empty after stripping whitespace
- Status: Defaults to "pending", only valid values are "pending" | "completed"
- ID: Auto-generated UUID, not user-provided
- Timestamps: Auto-managed, not user-editable

---

### 2. Task Creation Command

**CLI Command:**

```bash
task add "Buy groceries"
task add "Finish project report"
```

**Expected Output:**

```
✓ Task created: "Buy groceries" (ID: a3f2c1d4)
```

**Error Cases:**

```bash
task add ""
# Error: Task description cannot be empty

task add "Very long description over 500 characters..."
# Error: Task description cannot exceed 500 characters
```

---

### 3. In-Memory Storage

**Implementation:**

- `InMemoryStorage` class maintains a dictionary of tasks (keyed by ID)
- Supports operations: `add(task)`, `get(id)`, `get_all()`
- No file I/O in this Epic (deferred to M3)

**Rationale:**
In-memory storage is simpler to implement and test. It unblocks E1.2 and E1.3. File persistence will be added in M3 without requiring changes to the Task model.

---

### 4. Input Validation

**Validation Rules:**

1. **Description required:**
   - Cannot be empty string
   - Cannot be only whitespace
   - Must be 1-500 characters (after stripping)

2. **Error messages:**
   - Clear and specific
   - Suggest corrective action when possible

**Examples:**

```python
validate_description("")
# ValidationError: "Task description cannot be empty"

validate_description("   ")
# ValidationError: "Task description cannot be empty"

validate_description("x" * 501)
# ValidationError: "Task description cannot exceed 500 characters (got 501)"
```

---

### 5. Testing

**Unit Tests Required:**

## Open Questions

**Q: Should task IDs be short (e.g., `a3f2c1d4`) or full UUIDs?**  
**A:** Use full UUIDs internally, display short prefix (first 8 chars) to users.

**Q: Should empty descriptions be trimmed before validation?**  
**A:** Yes, strip whitespace before validation.

**Q: What happens if user provides description with quotes?**  
**A:** Handle gracefully — quotes are part of description if inside the string.

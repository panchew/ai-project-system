# Epic E3.2 — CI/CD Pipeline

## Context

Taskflow has a working, performant application but no automated pipeline. Every deployment is currently manual: a developer SSH-es into the staging server and runs `git pull && docker-compose up`. This is error-prone and does not scale.

E3.2 implements a GitHub Actions CI/CD pipeline that runs on every pull request and automatically deploys to staging on every merge to `main`.

---

## Problem Statement

Without a CI/CD pipeline, broken code can reach staging undetected, deployments are manual and error-prone, and there is no repeatable process to confirm that a PR is production-safe. CFO (Morgan Chen) has indicated that production deployment authorization will not be granted until automated testing gates are in place.

---

## Goals

By the end of this Epic, the system must:

1. Run linting (flake8 + ESLint), unit tests (pytest + Jest), and integration tests on every PR
2. Block PR merge if any pipeline stage fails
3. Automatically build and deploy to staging on every merge to `main`
4. Produce a deployable Docker image tagged with the git SHA
5. Include a Lighthouse CI step that reports the score on every PR

---

## Non-Goals

This Epic explicitly does **not** aim to:

- Implement production deployment (requires CFO Deployment Authorization — separate step)
- Set up monitoring or alerting (infrastructure team)
- Implement blue/green or canary deployment strategies

---

## Scope of Work

### 1. CI Workflow (Pull Request)

Create `.github/workflows/ci.yml`:

**Must include:**
- Trigger: `on: [pull_request]`
- Jobs: `lint-backend`, `lint-frontend`, `test-backend`, `test-frontend`, `integration-tests`
- `integration-tests` job uses a PostgreSQL service container
- All jobs must pass before PR can merge (branch protection rule)

### 2. CD Workflow (Staging Deploy)

Create `.github/workflows/deploy-staging.yml`:

**Must include:**
- Trigger: `on: push: branches: [main]`
- Build Docker image, tag with `ghcr.io/taskflow-app/taskflow:${{ github.sha }}`
- Push image to GitHub Container Registry
- SSH into staging server and run `docker pull + docker-compose up -d`
- Post-deploy health check: `curl /health` must return 200

### 3. Docker Configuration

Create `Dockerfile` and `docker-compose.yml`:

**Must include:**
- Multi-stage Dockerfile (build stage + runtime stage, ≤ 200MB final image)
- `docker-compose.yml` for local development with PostgreSQL and Redis services
- `docker-compose.staging.yml` override for staging environment variables

### 4. Lighthouse CI Step

Extend CI workflow with Lighthouse:

**Must include:**
- Builds frontend in CI, serves it with `serve` package
- Runs `lhci autorun` against the served build
- Posts Lighthouse score to the PR as a comment

## Definition of Done

Epic E3.2 is complete when:

- [ ] CI workflow runs on every open PR and all jobs complete
- [ ] Branch protection rules block merge if CI fails
- [ ] Staging deploy workflow runs successfully on merge to `main`
- [ ] Docker image builds successfully and is pushed to GHCR
- [ ] Lighthouse CI posts score to PRs
- [ ] Deployment runbook documents the manual steps for production
- [ ] Epic Completion Notice produced and committed
- [ ] Pull request opened to `milestone/M3`

---

## Acceptance Criteria

- [ ] A PR with a failing test is blocked from merging by the CI pipeline
- [ ] A successful merge to `main` results in a staging deployment within 5 minutes
- [ ] The staging health check URL returns 200 after auto-deploy
- [ ] The Lighthouse score appears as a PR comment from the CI bot

# Epic E1.1 — User Authentication

## Context

Milestone M1 is building the complete backend foundation for Taskflow. Epic E1.3 (Database Schema) established the `users` table and the `refresh_tokens` table. E1.1 now implements the authentication layer on top of that schema.

Authentication is a prerequisite for E1.2 (Task CRUD API) since every task endpoint must verify the caller's identity. Both Epics were approved to run in parallel once E1.3 merged, with E1.1 using the completed schema from day one.

---

## Problem Statement

Without authentication, any caller can access any task data. The API has no way to associate tasks with specific users or enforce access control. Until JWT-based auth is implemented and tested, the Task CRUD API cannot enforce ownership, and the frontend cannot distinguish one user from another.

---

## Goals

By the end of this Epic, the system must:

1. Expose POST `/auth/register` — create a user account with hashed password
2. Expose POST `/auth/login` — validate credentials and return a signed JWT + refresh token
3. Expose POST `/auth/refresh` — exchange a valid refresh token for a new access token
4. Expose POST `/auth/logout` — revoke the current refresh token
5. Provide reusable `require_auth` middleware that validates JWTs for downstream endpoints
6. Achieve ≥ 80% test coverage on the auth module

---

## Non-Goals

This Epic explicitly does **not** aim to:

- Implement OAuth2 / social login (Google, GitHub) — deferred to Phase P2
- Build a password reset flow — deferred to Phase P2
- Implement role-based access control (RBAC) — out of scope for P1
- Build any frontend login screens (deferred to E2.1)

---

## Scope of Work

### 1. Auth API Endpoints

Implement four REST endpoints in `src/auth/routes.py`:

**Must include:**
- `POST /auth/register` — validates email format, hashes password with bcrypt, inserts user row, returns 201
- `POST /auth/login` — looks up user by email, verifies bcrypt hash, generates JWT (15min expiry) and refresh token (7d expiry), returns both
- `POST /auth/refresh` — validates refresh token against `refresh_tokens` table, issues new JWT, returns 200
- `POST /auth/logout` — deletes refresh token row, returns 204
- All endpoints return structured JSON errors on failure (400, 401, 409)

### 2. JWT Middleware

Implement `require_auth` decorator in `src/auth/middleware.py`:

**Must include:**
- Reads `Authorization: Bearer <token>` header
- Validates signature using `JWT_SECRET` from environment
- Validates expiry claim
- Attaches decoded `user_id` to request context
- Returns 401 with structured error on any validation failure

### 3. Tests

Write tests in `tests/auth/test_auth_endpoints.py`:

**Must include:**
- Happy-path tests for register, login, refresh, logout
- Error-path tests: duplicate email, wrong password, expired token, revoked refresh token
- Test coverage ≥ 80% on `src/auth/`

## Acceptance Criteria

- [ ] A new user can register with a unique email and retrieve a valid JWT in a single API call
- [ ] An invalid login attempt (wrong password) returns 401, not a 500 error
- [ ] A revoked refresh token cannot be used to obtain a new access token
- [ ] The `require_auth` middleware is reusable by E1.2 without modification

---

## Technical Constraints

**Format:** Python (FastAPI), JWT via `python-jose`, password hashing via `passlib[bcrypt]`
**Technology:** FastAPI 0.110+, PostgreSQL 15+, Python 3.12
**Performance:** Token generation must complete in < 100ms
**Compatibility:** JWT payload schema must remain stable — E1.2 reads `user_id` from it

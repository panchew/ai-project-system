# Epic E1.2 — Task CRUD API

## Context

With the database schema (E1.3) and user authentication (E1.1) in place, E1.2 delivers the core business logic of Taskflow: the ability to create, read, update, and delete tasks. This is the API layer that the M2 frontend will call.

E1.2 runs in parallel with E1.1 (both started after E1.3 merged) and uses the `require_auth` middleware exported from E1.1.

---

## Problem Statement

The Taskflow API has no task endpoints. Without them, users cannot perform the primary operation the application exists to support — managing tasks. No task API means the frontend cannot be built, and the system delivers no user value.

---

## Goals

By the end of this Epic, the system must:

1. Expose GET `/tasks` — list tasks for the authenticated user (pagination, sort by due date or priority)
2. Expose POST `/tasks` — create a task with title, description, priority, assignee, due date
3. Expose GET `/tasks/{id}` — retrieve a single task (must belong to requesting user)
4. Expose PUT `/tasks/{id}` — update any field of a task
5. Expose DELETE `/tasks/{id}` — soft-delete a task (archived, not hard-deleted)
6. Enforce ownership: users can only read/modify their own tasks

---

## Non-Goals

This Epic explicitly does **not** aim to:

- Implement task sharing or multi-user assignment (deferred to Phase P2)
- Build bulk import/export endpoints
- Implement task comments or activity history
- Build any search or filter endpoints (covered in E2.3 at the frontend layer)

---

## Scope of Work

### 1. Task API Endpoints

Implement five REST endpoints in `src/tasks/routes.py`:

**Must include:**
- `GET /tasks` — returns paginated list, query params: `page`, `per_page`, `sort_by`, `order`
- `POST /tasks` — validates input, inserts task row, returns 201 with created task
- `GET /tasks/{id}` — returns task or 404 if not found / not owned by caller
- `PUT /tasks/{id}` — partial update via Pydantic schema, returns updated task
- `DELETE /tasks/{id}` — sets `archived_at` timestamp, returns 204
- All endpoints protected by `require_auth` from E1.1

### 2. Task Schemas and Validation

Implement Pydantic schemas in `src/tasks/schemas.py`:

**Must include:**
- `TaskCreate` — required: title; optional: description, priority (enum: low/medium/high/urgent), assignee_id, due_date
- `TaskUpdate` — all fields optional (partial update)
- `TaskResponse` — full task representation including `id`, `created_at`, `updated_at`, `archived_at`
- Priority enum validation (reject invalid values with 422)

### 3. Tests

Write tests in `tests/tasks/test_task_endpoints.py`:

**Must include:**
- CRUD happy-path tests (authenticated user)
- Authorization tests: user A cannot read/modify user B's tasks
- Pagination and sort tests for GET `/tasks`
- Validation error tests (missing title, invalid priority)

## Acceptance Criteria

- [ ] An authenticated user can create a task and immediately retrieve it via GET /tasks
- [ ] Attempting to delete another user's task returns 404 (not exposing that the task exists)
- [ ] GET /tasks with `sort_by=due_date&order=asc` returns tasks in ascending due-date order
- [ ] A task with `priority: "critical"` is rejected with a 422 Unprocessable Entity response

---

## Technical Constraints

**Format:** Python (FastAPI), SQLAlchemy ORM
**Technology:** FastAPI 0.110+, PostgreSQL 15+, Python 3.12
**Performance:** GET /tasks (50 results) must return in ≤ 100ms (indexed on `owner_id`)
**Compatibility:** Task response schema must match the contract expected by E2.2 (Task Dashboard)
